## Original issue body

Child of delivery master #120 (bring the build onto the design of record).

## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"the comparator appears, but the info panel with the resolution is *NOT VISIBLE*"* --- *"bug: info panel not visible when comparison curtain is present"*

> *"comparison curtain should have a toggle button, this is missing"*

> *"it is very inconsistent about when it decides to show the comparator curtain. The first time i drop an image in and use a filter, comparator does not appear. When i click lock, then apply a new filter, the comparator appears. The comparator should appear the first time i do an operation on it, whether that be an upscale or a filter."*

> *"Whether the curtain appears should be depending on the status of the 'Compare' toggle button on the bar. If i switch it off, never show it, if i switch it on, always show it. Frequently the toggle curtain appears and i have no way to switch it off."*

> *"the button to switch off the comparison curtain is missing ... NOW the compare button is visible and allows me to turn off the curtain comparator."*

## Three faults, one of which is a specification change

1. **Defect: the information panel is hidden while the curtain is shown.** `MainView`'s canvas suppresses the panel on `viewModel.showComparison`. Nothing in guide 2.3 asks for that, and the resolution readout is exactly what a user comparing two pictures wants.
2. **Defect: the Compare control disappears.** It is rendered only when a derived image exists, so the control that dismisses the curtain vanishes in states where the curtain is still up. That is how the author became stuck in it.
3. **Change: the curtain should follow the Compare control's state and nothing else.** Guide 2.3 says comparison is *"available throughout"* but does not say what governs its appearance, and the build decides per state. The author's rule --- off means never, on means always, comparing the last operation --- is a specification addition.

## Violated criteria

- **AC94.3** and **AC90.6** in [docs/ACs.md](../blob/master/docs/ACs.md): what the curtain compares and when it is offered. Whether "the control that dismisses it always exists" is inside those criteria or needs a backfill is for `audit-acs` to rule on.
- Nothing found so far covers the information panel's visibility during comparison. Expect a backfill onto the #90 family rather than a stretch of an existing criterion.

## Debugging and fix procedure

1. **Reproduce the stuck state precisely**: which sequence leaves the curtain shown with no control to dismiss it. The author reached it twice by different routes, so record both.
2. **Separate the control's existence from the curtain's state.** A control that dismisses something must not be conditional on the thing it dismisses being dismissible; that is the shape of fault two.
3. **Land after #121** (current-image state has two owners). "The last operation" is a question about which asset is current, and until there is one owner of that, "always comparing the last operation" cannot be implemented without a third hand-reconciliation.
4. **The information panel and the curtain must be laid out as siblings**, not one suppressing the other. #119 (the progress indicator not centred) established that the canvas stacks chrome as centred and anchored children; the same applies here.
5. Guide 2.3's rule on what the two sides *are* is unchanged and must not be disturbed: the candidate against the base it descends from, never an image and its own rendering.

## Test plan

- RT-126.1: the information panel is readable while the curtain is shown

- RT-126.3: with the Compare control off, no operation causes the curtain to appear

### The mechanism, from source

**The vanishing control.** The Compare button is rendered under `if derivedImage != nil`. And `derivedImage` is:

```swift
if let upscaled = viewModel.result { return upscaled }
guard workspace.canCompare, !workspace.showsBase else { return nil }
return viewModel.originalImage
```

So with no upscale behind the filter — the state the raise to the filterable minimum puts every undersized picture into — **toggling "Showing Original" makes `derivedImage` nil and takes the Compare control with it.** That is the author's *"the button to switch off the comparison curtain is missing"*, and it explains why it reappeared later: toggling back restores `derivedImage`.

**The hidden panel.** `if !infoPanelDismissed && !viewModel.showComparison` — the info panel is suppressed outright while comparing. Nothing in guide 2.3 asks for that, and the resolution readout is exactly what someone comparing two pictures wants.

### F1 (blocker) — the control that dismisses a thing must not be conditioned on that thing's own state

`derivedImage` answers *"is there a derivation to show right now"*, which is the right question for the **curtain's content** and the wrong one for **whether a dismissal control exists**. Conditioning them on one value is what produced the trap.

**Remediation.** The control's presence follows `workspace.canCompare || viewModel.result != nil` — whether a derivation exists at all — and is independent of which side the filtered/original toggle is showing.

### F2 (blocker) — the info panel and the curtain must be siblings, not one suppressing the other

**Remediation.** Drop the `!viewModel.showComparison` condition. #119 established that the canvas stacks its chrome as centred and anchored children; the panel is one of them.

Guide 2.3 says comparison is *"available throughout"* and does not say what governs its appearance. The author's rule — off means never, on means always, comparing the last operation — is new.

### The mechanism

`showComparison` is written by the application in four places, not by the user:

- `UpscaleViewModel.swift:677` and `:894` set it **true** whenever a rendering is served or a run publishes.
- `:471` (`releaseUpscaledResult`) and `:612` (a new image) set it **false**.

So the curtain follows *work completing*, which is exactly the inconsistency reported: *"The first time i drop an image in and use a filter, comparator does not appear. When i click lock, then apply a new filter, the comparator appears."*

### The rule, in the author's words

> *"Whether the curtain appears should be depending on the status of the 'Compare' toggle button on the bar. If i switch it off, never show it, if i switch it on, always show it."*

and

> *"The comparator should appear the first time i do an operation on it."*

Those two together give: **`showComparison` is a user preference, defaulting to on, that the application never writes.** The curtain shows when the preference is on and there is something to compare; the existing `derivedImage`/`comparisonBase` guard already supplies the second half.

### F1 (finding) --- removing the `false` writes is the part that needs care

`releaseUpscaledResult` and the new-image path set it false. Removing those does **not** leave a curtain over nothing: `canvasContent` already requires `derivedImage` and `comparisonBase`, and both are nil in exactly those states. What removing them buys is that a user who turned the curtain off does not find it back on after their next import, and a user who left it on does not have to press Compare again.

**Remediation:** remove all four writes; keep the guard. RT-126.7 covers the survival of the preference across a release.

### F2 (finding) --- the default flips, and that is a specification addition

`showComparison` currently defaults to `false`. Defaulting to **on** is what *"should appear the first time"* requires, and guide 2.3 says only that comparison is *"available throughout"*.

**Remediation:** guide 2.3 gains the governance rule before the code, as every other design change in this delivery has.
