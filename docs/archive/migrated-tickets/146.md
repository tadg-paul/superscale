## Original issue body

Child of delivery master #139 (the 2026-08-31 user-test round).

## Problem statement

**Observed by the author:**

> *"settings panel: items jump about when you enter a long api key"*
> *"you will see the admin key has pushed to a new line and rearranged itself when i type in the long admin key. the same happens for generation key."*

Evidenced by two screenshots he supplied, which I have read.

## What the screenshots show

**Empty admin field:** the label *"Account/admin key"* sits **beside** its text field, on one line.

**Filled admin field:** the label has moved **onto its own line above** the field, and the field has
taken the full width. Every row beneath it shifts down.

The Generation key row is already in the second arrangement in both shots --- because it already
holds a long key. So the two rows are not inconsistent with each other; **each row is inconsistent
with itself**, depending on what is typed into it.

## The cause

`credentialRow` (`SettingsView.swift:189`) builds each row as a `LabeledContent`, and the field
inside it is:

```swift
TextField(title, text: text)
    .frame(minWidth: 260)
```

`LabeledContent` in a macOS `Form` puts the label in a leading column beside the content **until the
content's ideal width will not fit**, at which point it reflows the label above. A `TextField`'s
ideal width follows its text, so a long key pushes past the column and the layout switches
arrangement **mid-typing**.

This class of problem was already known in this file. `statusSlotWidth` carries the comment:

> *"if they differed, the form's label column would still renegotiate between them"*

--- so a previous ticket pinned the status slot for exactly this reason and left the field free to do
the same thing.

## The fix, and why this one

**Both credential rows take the label-above arrangement unconditionally.** That is what a populated
row already looks like, so nothing moves when the field fills, and it is the arrangement that suits
the content: a FAL key is long and deserves the full width.

The alternative --- pinning the field's width so the label stays beside it --- keeps a narrower field
for a credential nobody reads at a glance, and would still renegotiate if the window were resized.

## Violated criteria

- **AC73.5**, that users can see separate controls for each credential. Unchanged as a rule; they can
  see them, and they move.
- **UT-73.2**, the Settings layout following the wireframes, which the author passed on 2026-08-30 ---
  **before** he tried a long key in the admin field. Re-offer it.

### What this issue delivers, in plain language

Typing a FAL key into Settings stops moving the window about. The row keeps its shape from the first
character to the sixtieth, and the rows underneath stay where they are.

### Evidence

- The author's two screenshots, read directly. Same row, empty and filled: label **beside** the field
  when empty, label **above** it when filled, everything below shifted down.
- `SettingsView.swift:189` --- the row was a `LabeledContent`. On macOS that puts the label in a
  leading column beside the content until the content's ideal width will not fit, then reflows above.
- `SettingsView.swift:223` --- `TextField(...).frame(minWidth: 260)`. A `TextField`'s ideal width
  follows its text, so the content's width grew with the key.
- `SettingsView.swift:176` --- **`statusSlotWidth` exists because #110 hit this same renegotiation
  from the other side**, and its comment says so: swapping a spinner for a badge *"made
  `LabeledContent` renegotiate the form's label column --- and the whole form moved under the user's
  typing."* It pinned the slot and left the field free.

### Edge cases

- **Paste rather than type.** Same path; the width changes in one step instead of sixty. Covered by
  the same criteria.
- **A key longer than the window is wide.** The field is greedy up to the row's width and scrolls
  within itself, so the row cannot grow past the form.
- **Window resized while a key is in the field.** The field takes the available width either way, so
  the arrangement does not change --- only the shared width does, which is the window's doing.
- **One row filled, the other empty.** AC146.4 exists for exactly this: it is the state in the
  author's screenshots, and the two rows must look alike.

### Quality self-audit

Four criteria, each a system state, each phrased as *stays in the same place* rather than as an
action. No forbidden language.

**AC146.2 is deliberately separate from AC146.1** because the defect has two levels: the label
reflowing above the field, and the field widening within its row and pushing the controls beside it.
A fix for the first alone would leave the second, and the author would report it a second time
looking like a partial fix.
