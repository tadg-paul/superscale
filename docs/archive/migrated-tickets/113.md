## Original issue body

## Problem statement

**Reported by the author, 2026-08-26:** when the API returns an error it
should be surfaced to the user.

**Grounding (read, not yet reproduced):** the two failure routes out of a
filter apply do not land in the same place.

- The *upload* stage throws into `MainView.submitFilter`'s catch, which calls
  `viewModel.report(error)` (`MainView.swift:288`) --- the one alert surface
  AC98.5 established. This is how "the provider would not accept the image"
  reached the author as a real error presentation during round 2.
- The *generation request itself* fails differently:
  `GenerationCoordinator.phase = .failed(error.localizedDescription)`
  (`GenerationCoordinator.swift:216`), which `MainView.statusText`
  (`MainView.swift:582`) renders as a small grey caption in the status bar,
  plus a red dot. It never reaches `report()`. A user watching the canvas for
  their result sees the progress text quietly replaced by a sentence in
  caption type at the foot of the window --- an API error in the place
  reserved for ambient state, easy to miss entirely, and gone as soon as
  anything else updates the status line.

## Violated AC

- **AC98.5** in [docs/ACs.md](../blob/master/docs/ACs.md): *"A failure
  reaches the user through one surface, whatever raised it."* The provider
  declining a generation request is a failure; the status bar caption is not
  the surface. The criterion's structural half (`errorMessage` is
  `private(set)`, `report` the only way in) is intact --- this path simply
  never calls it.

## Debugging and fix procedure

1. **Reproduce first**: with the stubbed provider forced to fail
   (`SUPERSCALE_UI_TEST_FAIL=provider` already exists for exactly this),
   apply a filter and record where the failure text appears. Confirm the
   asymmetry between the upload-failure and generation-failure presentations
   before changing anything.
2. **Route the phase failure into the one surface.** The plain fix: where
   MainView observes the coordinator's phase becoming `.failed`, call
   `viewModel.report` with the message rather than (not in addition to)
   leaving it only in `statusText`. Decide deliberately what the status bar
   then shows --- "Filter failed" as ambient state is fine; the *diagnostic*
   belongs on the alert.
3. **Sweep for the same shape**: any other place a failure becomes a phase,
   a caption, or a colour without passing through `report`. The candidates
   are the coordinator's other terminal states and the face-model download
   sheet (whose in-flow presentation is AC98.5's one documented exception and
   stays).
4. Existing GUI coverage to respect: the `SUPERSCALE_UI_TEST_FAIL` tests
   assert where each subsystem's failure is presented; they will need their
   expectations moved with the fix, not weakened.
5. UT re-offer: the author judges that a failed apply is unmissable.

## Test plan

- RT-113.1: with the provider stubbed to fail, applying a filter presents the
  failure on the application's error surface, not only in the status bar
- RT-113.2: the upload-failure path and the generation-failure path present
  through the same surface (the asymmetry is the defect)
- RT-113.3: after dismissing the failure, the status bar's ambient state is
  coherent (no orphaned "Applying filter", no stale red dot)
