## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure).

## Problem statement

**Observed (author, UT round 3, 2026-08-25 — UT-89.1 FAIL):** *"Lock seems to
do something, i can see thumbnails appear at the bottom in a panel as expected.
But when i click on a previously locked image, it loads that image, and the
lock panel disappears, so i can not navigate to any other previously locked
images."*

**Expected:** the chain stays present while an iteration is open, so moving
between iterations is a way to work — which is UT-89.1's whole criterion. From
an open iteration, both the other iterations and the live working image are
reachable.

## Violated ACs

- **AC89.3** in [docs/ACs.md](../blob/master/docs/ACs.md): *"Every locked
  iteration remains reachable from the current base..."* Reachable once and
  then gone is not reachable. RT-89.8 asserts both iterations reachable *in
  order* at the model level; nothing asserted the strip survives the act of
  using it, which is how the model-level tests stay green while the user
  cannot navigate.
- **AC89.8** in [docs/ACs.md](../blob/master/docs/ACs.md): *"The lock chain
  belongs to the working image: importing another image starts a new chain,
  and the previous chain's files are released."* Cited because the mechanism
  below shows viewing an iteration is currently processed **as an import**.
  This criterion must remain true for a genuine import after the fix; it is
  the one a careless fix breaks silently.

## Root cause, traced 2026-08-26

~~Step 1 of the original procedure listed the suspects as the strip's
visibility condition or the workspace's displayed-asset state.~~ **Superseded:
neither is the cause, and the strip's visibility does not consult the displayed
asset at all.** The chain is *emptied*. The path, in order:

1. `MainView.swift:67` renders the strip on `!workspace.lockedIterations.isEmpty`.
2. `showIteration` calls `display(reference)` (`MainView.swift:394-400`), which
   reaches `viewModel.upscale(source)`.
3. `UpscaleViewModel.swift:597,625-626` assigns `inputURL = url` whenever the
   URL is new. An iteration's file is a new URL.
4. `MainView.swift:79` observes it:
   `.onChange(of: viewModel.inputURL) { _, url in adoptImportedImage(url) }`.
5. `adoptImportedImage` (`MainView.swift:224-229`) guards on
   `url != currentlyDisplayedFileURL`, and that property
   (`MainView.swift:422-426`) resolves the **workspace's** displayed asset —
   still the base or candidate, never the iteration being viewed. The guard
   passes.
6. `workspace.importImage(...)` runs. Per AC89.8 that starts a new chain, the
   chain empties, and the strip's own condition removes it.

## Solution

Viewing an iteration must not be an import. The distinction belongs where the
two are told apart — the guard in `adoptImportedImage`, which today asks a
question about the workspace's displayed asset and needs to ask one about what
the view was last asked to show.

The strip belongs to the *chain*, not to the currently displayed asset, so once
viewing stops emptying the chain the strip persists on its existing condition.
Viewing additionally marks the open entry as current, and offers a way back to
the live base or candidate.

**The fix must not be made by weakening AC89.8.** Stopping `importImage` from
clearing the chain, or widening the guard until nothing re-imports, satisfies
RT-111.1 and RT-111.2 and breaks AC89.8 with nothing to notice: RT-89.25
exercises the workspace directly, not the view path that would now bypass it.
RT-111.4 exists to hold that line.

## Test plan

- RT-111.1: with two locked iterations and one open, the chain strip remains
  present, holds as many entries as locks were performed, and every other
  iteration remains clickable. **The entry count is asserted** because a strip
  that survives while losing its contents satisfies presence and hittability
  alone
- RT-111.2: navigating from one open iteration directly to another shows the
  second (the author's actual attempted action)
- RT-111.3: with a single locked iteration, opening it leaves the strip present
- RT-111.4: a genuine import performed while an iteration is open still empties
  the chain and removes the strip, so AC89.8 continues to hold through the view
  path
- RT-111.5: selecting an entry whose file has gone leaves the strip present and
  the entry reporting itself unavailable, per AC81.6
- RT-111.6: from an open iteration, one action restores the live base or
  candidate, **and the picture restored is that asset** rather than merely some
  other picture. Asserting only that the viewing state ended would pass against
  a control that returns to the wrong image
- RT-111.7: the strip reports which entry is currently open as an accessibility
  value, not by tint alone, per guide section 3.9. **Asserted across two
  different open entries**, so a hard-coded value fails
- RT-111.8: the strip persists with the scale both selected and cleared, since
  viewing runs through the upscale path

**Coverage boundary.** AC89.3 has three clauses: reachable, carrying
provenance, and saveable at the current scale selection. The tests above cover
reachability. Provenance stays with RT-89.9 and saveability with RT-89.10; this
ticket does not re-cover them, and says so rather than leaving a reader to infer
that two clauses went unconsidered.

**Verification dependency.** Every test above needs a locked iteration, which
needs a candidate, which needs the filter path — `lock` is unavailable with no
candidate, per RT-89.7. The verification run under master #114 shows that path
failing suite-wide, RT-089.10 among them, at `waitForFilterResult`. These tests
cannot be verified until that regression is resolved.

UT-89.1 (working the lock chain) re-offers on master #79 once green; it judges
usability, while the regression tests keep the mechanism.

## Recorded, not in scope

Applying a filter while an earlier iteration is displayed reads the **base**,
per AC89.1 and invariant I2, rather than the picture on the canvas. That is
correct by the invariants and potentially surprising. It is a product question
about what filtering from a viewed iteration should mean, not a defect, and it
is carried on master #114 for the author.

### What was wrong

`showIteration` called `display`, which set `viewModel.inputURL`, which fired the observer calling `adoptImportedImage`. Its guard compared the incoming URL against the **workspace's** displayed asset, which is the base or the candidate and never the iteration being viewed, so the guard passed and `importImage` ran. AC89.8 then started a new chain, and the strip's own `!lockedIterations.isEmpty` condition removed it.

The ticket's original suspects were the strip's visibility condition and the workspace's displayed-asset state. Neither was the cause, and the superseded list is struck in the body rather than deleted.

### Two tests retired, identifiers not reused

**RT-111.4**, a genuine import from the viewing state still empties the chain. Unperformable: with a picture loaded the application offers no route to open another. This one matters beyond the ticket, because it was the anti-gaming test. Nothing now fails if a later change widens `adoptImportedImage`'s guard until no import registers at all, and the related product question, that guide 2.2 promises the open panel as one of three routes, is on master #114.

**RT-111.5**, an entry whose file has gone. Unperformable: the runner's sandbox cannot remove a file the application wrote. RT-81.20 and RT-81.32 hold the behaviour at package level.

### Worth keeping

Two of the eight tests failed on hard-coded entry counts. The chain holds the source and each raise to the filterable minimum as well as each locked candidate, so two apply-and-lock cycles legitimately make four entries. They now assert the count is unchanged by opening one, which is what they were about. The suite's own note that *"a number written into a test goes stale in silence"* earned itself again.
