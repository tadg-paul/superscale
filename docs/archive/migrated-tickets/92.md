## Original issue body

Child of delivery master #79 (slice 5). Design of record: [`docs/IMPLEMENTATION_GUIDE_v2.md`](../blob/master/docs/IMPLEMENTATION_GUIDE_v2.md) 3.6; wire detail in [`docs/FAL_REQUEST_REFERENCE.md`](../blob/master/docs/FAL_REQUEST_REFERENCE.md).

## Problem

**The reference image is inlined as a base64 data URI, and it is built in a view.**

`MainView.swift:273` holds `dataURL(for:)`, which reads the file, guesses a media type from the path extension, and returns `data:<type>;base64,<payload>`. Three things are wrong with that:

- **It balloons the request.** Base64 costs a third again on top of the file. A 4-megapixel JPEG at 3 MB becomes 4 MB of JSON body on every apply, and applying is the paid operation the user repeats while exploring.
- **It lives in the wrong module.** `SuperscaleApp` is meant to hold SwiftUI views and platform integration only, per guide 3.1. Request construction belongs in `FalGenerationKit`, which is where every other piece of the FAL contract already lives and where it can be tested without a window.
- **The media type is guessed from the extension.** The FAL reference is explicit that references are validated by content rather than by extension, and that `pix` validating by extension was the weaker of the two implementations it drew on.

The guide chose the other approach at 3.6: *"The base is uploaded to FAL storage and passed as a URL. This replaces the base64 data-URI encoding currently in a view. Upload belongs in `FalGenerationKit`. Uploaded URLs expire at the provider's discretion and are never cached."*

## The protocol, verified rather than assumed

`FAL_REQUEST_REFERENCE.md` records only that `storyboard-gen` used the SDK's `upload_file`, so the wire protocol was not written down anywhere in this repository. Read from FAL's own client rather than guessed:

1. **Initiate.** `POST https://rest.fal.ai/storage/upload/initiate?storage_type=gcs`, with `Authorization: Key <token>`, `Accept: application/json` and `Content-Type: application/json`, and a body of `{"file_name": "<name>", "content_type": "<type>"}`.
2. **Put the bytes.** `PUT` the file data to the `upload_url` from that response.
3. **Use the URL.** The same response carries `file_url`, which is what the generation request references.

Files above a multipart threshold take a different path — `POST {base_upload_url}/files/upload/multipart`, then parts to `{access_url}/multipart/{uploadId}/{part_number}`. **Out of scope here**: the MVP sends one reference at model resolution, roughly a megapixel, which is far below any multipart threshold. Recorded so that its absence is a decision rather than an oversight.

**A correction to `FAL_REQUEST_REFERENCE.md`.** Its host table gives `api.fal.ai` for reference upload. The upload REST host is `rest.fal.ai`; `api.fal.ai` is the platform host for pricing, account and the catalogue. The row is wrong and this issue fixes it.

### Condition enumeration

- **AC92.1** implies three conditions: no bytes in the body, the right URL referenced, and the body's size decoupled from the picture's. The third is the point of the change and would otherwise be untested — a body that carried both a URL and a payload would satisfy the first two readings.
- **AC92.2** implies three: the initiate request's shape, the bytes going where they were told, and the returned URL being the provider's rather than one composed locally. A composed URL is the plausible shortcut and RT-92.6 blocks it.

  **It no longer says "two exchanges".** That is true of FAL's small-file path and false of its multipart path — `POST .../files/upload/multipart`, then a part per chunk — so the criterion would have been false the day a larger reference needed it, with nothing user-visible having changed. Asking the provider where to put the bytes is the property that matters, and it holds either way. Raised by the first AC audit.

- **AC92.7 is the rule every earlier slice guarded and this one nearly omitted.** AC79.2 holds that a cloud filter never receives pixels from an upscale targeting the user's chosen output size. L21 records why it is the easy mistake: the canvas shows the upscaled rendering by default, so sending what is on screen is the obvious implementation and it breaches invariant I1. AC87.6 carried the rule until the asset graph could enforce it.

  Each of those guarded it at a point where nothing was actually being uploaded. **This is the issue that opens the file and sends the bytes**, and without AC92.7 it is one careless `viewModel.result` away from breaching a delivery-level criterion. Three conditions, because the base must win over both a rendering and a candidate. Raised by the first AC audit.
- **AC92.3** implies two: two calls upload twice, and nothing is retained. The FAL reference calls this a hard rule — CDN URLs expire at the provider's discretion, and `storyboard-gen` raised an issue about exactly this.
- **AC92.4** implies two: content beats naming, and unsupported content is refused before any request is made. Refusing *before* uploading matters because the alternative spends bandwidth to learn what the file already said.
- **AC92.5** implies three: each of the two exchanges can fail, and neither may leave something half-made that the generation request then sends.
- **AC92.6** implies three: the header carries it, the URL and body do not, and nothing written down does. The third is the standing project rule rather than a new one.

## Solution

**A `FalStorageClient` in `FalGenerationKit`**, alongside the existing clients and behind the same `FalHTTPTransport` protocol declared at `FalGenerationClient.swift:22`, so every test runs against a stubbed transport and no test touches a paid or public endpoint.

Its single entry point takes the file's bytes and its name and returns the provider's `file_url`. It does not cache, and it holds no state between calls — the hard rule from the FAL reference is expressed by there being nowhere to put a cached value rather than by remembering not to write one.

**That guarantee is structural, so the test for it is behavioural.** A test cannot look inside for an absent cache, and one that tried would either reach into private state or repeat RT-92.7. Instead the stub issues a different URL for each upload, and RT-92.8 asserts that two applies of the same base send two *different* URLs — proof from outside, and a cache would fail it in a way an internals check would not. Raised by the first test audit.

**Content type by content.** `ImageIO`'s `CGImageSourceGetType` reads the file's own identifier, which is what "validate by content" means here, and it is already a dependency of the kit. A file whose type is not among PNG, JPEG, TIFF and HEIC — the set guide 2.2 accepts on import — is refused before the initiate call.

**`dataURL(for:)` is deleted from `MainView`**, not left unreferenced. `PromptComposer` in #85 and `GenerateView` in #87 were removed on the same reasoning: a view that still composes a request body is a compile error rather than something to remember.

**Errors map into the existing stage failure path**, so an upload failure reads as a filter failure, which is what it is from the user's side. The taxonomy work is slice 8's; this issue uses what exists and does not anticipate it.

### Anti-patterns this avoids

- **No string-built requests.** `URLRequest` and `JSONEncoder`, per `CODING.md` §Cross-Language Escaping, which requires a marshalling library rather than string building for JSON.
- **No secret outside a header.** `FAL_REQUEST_REFERENCE.md` is explicit that the secret lives only in the header, never in a body or URL, and AC92.6 tests it.
- **No caching.** Recorded above as a rule with its provenance.

## Test type and location

**RT-92.9 writes one file, and it writes it nowhere near the project.** Bytes whose content and extension disagree have to exist somewhere: the test derives them from an existing fixture, writes them under a name ending `.jpg` into a directory unique to the run from `FileManager.default.temporaryDirectory`, and registers `addTeardownBlock` to remove it. It does **not** add a permanently mis-named fixture to `Tests/images/` — an artefact whose only purpose is to be wrong is a thing a later reader has to work out. Raised by the first test audit.

All nineteen are regression tests in `Tests/FalGenerationKitTests/`, against a stubbed `FalHTTPTransport`. AC92.7's three run against the asset graph and the filter stage rather than the storage client, because which picture is chosen is a decision above the transport; they use the same stub and reach nothing. None reaches the network, and none needs a key: the stub asserts what the client *would* send, which is the whole surface being specified. This follows the guide's testing table, which puts request construction and transport under stubs and calls request construction "the highest-value surface in both reference implementations".

No user test is allocated. Nothing here is user-visible when it works — the filter behaves as it did, faster and with a smaller request. When it fails the user sees a filter-stage failure, which AC92.5 covers and which is not new presentation.
