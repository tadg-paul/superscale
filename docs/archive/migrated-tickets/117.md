## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure). Raised by the AC audit on #112 (a filter result offers no comparison curtain), which cannot proceed until this lands.

## Problem statement

The GUI suite's signal that an upscale has finished is the existence of a control:

```swift
private func waitForUpscaleComplete(timeout: TimeInterval = 120) -> Bool {
    app.buttons["compareButton"].waitForExistence(timeout: timeout)
}
```

`SuperscaleAppUITests.swift:135-137`, used at **45 call sites**.

Compare exists when `viewModel.result != nil` (`MainView.swift:492`) — that is, when an *upscale* has produced a rendering. #112 requires Compare to appear whenever there is a derivation to compare, including a filter result with no upscale behind it. The moment it does, this helper returns true before any upscale has run, and every one of those 45 tests begins asserting against a pre-upscale state **while continuing to report green**.

## This is a rule the project has already written down

`IMPLEMENTATION_GUIDE_v2.md` section 7, *"Widening what a control means can blind the suite"*, records the same mechanism from the Save control at forty-one call sites, and records the resolution: the signal was moved to Compare, *"which exists exactly when a derivation does"*. #112 changes what "a derivation" means for Compare, which is precisely what invalidates that choice.

The guide's own conclusion applies unchanged: *"A test that passes vacuously is worse than no test, because it occupies the place where a real one would go and nothing about the result looks different."*

## Why this is separate from #112

Two reasons, and the second is the one that matters.

The blast radius is 45 call sites and the subject is the harness, where #112's subject is the curtain. Mixing them makes a defect fix indistinguishable from a suite-wide change in review.

More importantly, **the order is load-bearing**. If #112 lands first, there is a window in which the suite reports green while asserting nothing, and any other work verified in that window is unverified. This has to be in place before Compare's meaning widens, not alongside it.

## Solution

**The canvas reports what it is currently showing, as an accessibility value, and the helper waits on that.**

A signal that is a property of the *state* cannot be invalidated by a control's affordance changing meaning. It is also the third time this delivery has applied guide section 3.9's rule that a perceivable state is expressed as a value rather than inferred: what the canvas is showing — the base, a filter result, an upscaled rendering — is a state a user can see and the accessibility tree currently cannot report.

That makes this an accessibility improvement first and a test fix second, which is the same order of priority the guide records for the four earlier occurrences.

Rejected alternatives, with reasons:

- **Wait for the progress indicator to disappear.** Racy: an upscale fast enough to finish between polls never shows one, and the helper would return on a state that never existed.
- **Bind the helper to the Save button.** Save's meaning already widened once, in #96, for exactly this kind of reason. Moving the signal to a second affordance is repeating the mistake with a different control.
- **Leave the helper and exclude the filter case.** A conditional signal is a signal nobody can reason about at 45 call sites.

## Acceptance criteria

| ID | AC | Tests |
|---|---|---|
| AC117.1 | The canvas reports which kind of image it is **currently displaying** — nothing, the base, a filter result, or an upscaled rendering — as a value available to assistive technology alongside its label, and that report changes only when what is displayed changes. | ⏳ RT-117.1: with no image, the canvas reports that it is showing nothing<br>⏳ RT-117.2: with an image imported and no scale selected, it reports the base<br>⏳ RT-117.3: with an upscale rendered, it reports an upscaled rendering<br>⏳ RT-117.4: with a filter result on the canvas and no upscale, it reports a filter result<br>⏳ RT-117.5: the report changes when the filter toggle switches between base and candidate<br>⏳ RT-117.6: the label names the element and the value is present, and the value differs from the label, so a value that merely echoes the name reports no state<br>⏳ RT-117.7: while an upscale is in flight over a previously displayed picture, the canvas still reports the previous kind, and reports the upscaled rendering only once it is on screen<br>⏳ RT-117.8: while an earlier locked iteration is being viewed, the canvas reports the base<br>⏳ RT-117.9: the four kinds are four distinct values, collected in one test that reaches all four states |

**Key:** ✅ passing · ⏳ pending · ❌ failing · ~~🚫 removed~~

**RT-117.7 is the one that keeps this ticket from recreating the defect it exists to prevent.** AC90.2 requires the canvas to keep showing what it was showing while an operation runs, with progress over it. A value that flips to "an upscaled rendering" when the upscale *starts* rather than when its result reaches the canvas makes `waitForUpscaleComplete` return before the upscale has finished — the same vacuity at the same 45 call sites, arriving by a different route.

**RT-117.6** exists because this codebase has now hit that mechanism twice — the credential badge in #95 and the comparison's pan in #101 — where an element reported its label and silently dropped its value. Setting both is the rule; asserting both, *separately*, is how it stays true. A test that only requires neither to be empty passes against a value that repeats the label and carries no state at all.

**RT-117.9 is what the migration rests on.** `waitForUpscaleComplete` will discriminate on exactly one of the four values. An implementation reporting the same string for a filter result and an upscaled rendering — plausible, since both are a derived picture and a terse implementation might well say so — satisfies RT-117.3 and RT-117.4 individually and returns the helper on a filter result. That is the vacuity at 45 call sites, arrived at through the ticket written to prevent it.

It is **one test walking all four states**, not four tests each seeing one. That is the rule the guide records from AC89.6, where four separate tests would each have passed against an implementation that coupled the pair they were meant to hold apart.

**RT-117.8**: an earlier locked iteration reports as **the base**. It is the base of its own position in the chain, the user is looking at their own picture rather than at something derived from it, and a fifth kind would make every caller handle a case that means the same thing. AC94.16 already specifies the canvas showing a locked iteration, and #111's fix makes that state ordinarily reachable rather than a dead end.

**The four kinds are display states and deliberately do not mirror `AssetRole`.** The role enum has `source`, `raisedToMinimum`, `filtered` and `upscaled`. A base raised to the filterable minimum is a `raisedToMinimum` asset and is still *the base* to a viewer, so mapping one enum onto the other would have the canvas report "raised" at a moment no user would call it that.

## Migration of the helper

`waitForUpscaleComplete` waits for the canvas to report an upscaled rendering. Its 45 call sites are unchanged: the helper keeps its name, its signature, and its meaning, and only what it observes moves.

**The migration is verified by the suite's own count.** Before and after, the full run executes the same number of tests with the same result. A helper that had gone vacuous would not change the count, so the count alone is not sufficient — which is why AC117.1's tests assert the value directly rather than relying on the suite staying green.

## Test plan

The six tests above are GUI-level, because the value is a property of the rendered accessibility tree and cannot be observed below it. They must not be satisfied at the `CanvasContent` layer: that layer already decides what is drawn, and what is being asserted here is that the decision reaches the tree.

## Ordering correction found during implementation: RT-117.8 is vacuous until #111 lands

Implementing this ticket surfaced a dependency none of its audits caught, and it is the kind that produces a passing test against broken code.

**RT-117.8** asserts that while an earlier locked iteration is being viewed, the canvas reports the base. That requires "viewing an earlier locked iteration" to be a state the application can hold. Today it is not.

Per the traced mechanism on #111 (opening a locked iteration hides the lock chain): selecting an iteration calls `showIteration` → `display` → `viewModel.upscale`, which assigns `inputURL`, which fires `MainView`'s observer, which calls `adoptImportedImage`, whose guard compares against the *workspace's* displayed asset rather than the iteration being viewed and therefore passes — so `workspace.importImage` runs and the graph is reset to a fresh import of that iteration's file.

The state does not persist. It collapses into "a freshly imported base".

**So RT-117.8 would pass today, for the wrong reason.** The canvas would report the base because the iteration has stopped being an iteration, not because the value is correct about a state the application is holding. It is exactly the shape this delivery's audits have caught four times already, and the shape guide section 7 warns about: a test occupying the place where a real one would go, with nothing about the result looking different.

## Consequence

The delivery order changes from **#117 → #112** to **#111 → #117 → #112**.

- **#111** (opening a locked iteration hides the lock chain) makes the viewing state persist. It has no dependencies of its own and both its pre-code audits have passed.
- **#117** then has a real state for RT-117.8 to observe.
- **#112** (a filter result offers no comparison curtain) follows, as already recorded.

No criterion and no identifier changes. RT-117.8 stays as written; what changes is when it can be honestly verified.

Recorded here and on master #114 rather than resolved by reordering the tests inside this ticket, because the dependency is between the tickets and belongs where a reader will meet it.
