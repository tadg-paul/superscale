## Original issue body

Child of delivery master #79 (slice 9a). Closes D8.

## Problem

**The application presents four peer modes where there is one pipeline.** `MainView` is a `NavigationSplitView` whose sidebar lists Upscale, Generate, History and Settings as equals (`MainView.swift:63-110`). Filtering an image and upscaling it are stages of one piece of work, and the interface makes the user carry the image between them by hand.

Four consequences, all observable:

- **The image is not the focus.** In Generate mode the canvas is a form: two pickers, an aspect picker, three reference wells and a prompt box occupy the top of the window, and the image appears underneath. In Upscale mode the image is the window, as it should be.
- **Settings consumes a workspace.** It is a mode (`AppMode.settings`), so opening it replaces the image entirely. macOS has a Settings scene for this, reached by `Cmd+,`, and using a mode instead is the reason removing modes forces the correct destination.
- **History is a surface nobody wants mid-session.** What a user wants while working is the iteration they just liked, not a browsable archive. Reaching older work is what `File > Open Recent` is for.
- **Three reference wells contradict the MVP.** `GenerationReferenceSelection.maximumCount` is 3 and `GenerateView` renders three wells. `IMPLEMENTATION_GUIDE_v2.md` section 2.2 states one image at a time. There is one working image, and it is the reference.

**D8:** `defaultUpscaleModelID` is honoured when an image arrives through the handoff path (`MainView.swift:113-115`) and ignored when the same image is dropped on the window, so the same file upscales with a different model depending on how it arrived.

## Solution

### One workspace

`AppMode` and `AppNavigation` are deleted rather than reduced to a single case. A mode enumeration with one case is an invitation to add a second.

`MainView` becomes the workspace itself: toolbar, canvas, status bar, and a filter side panel. The canvas keeps the v1 behaviour that already works, including drag and drop, the comparison view, the magnifier loupe and the info panel.

### The filter panel

A side panel beside the canvas, not a workspace and not a sheet. It holds:

- the 86 filters **listed within their categories**, which `PromptPackCatalogue` already supplies as `category` and `displayName` since #85;
- the editable prompt area, bound to `FilterSelection.text`, which fills when a filter is chosen and sends nothing;
- an **Apply** button, enabled exactly when `FilterSelection.canApply` is true;
- the cost beside that button, as the documented flat rate.

**`GenerateView` is deleted in the same commit that adds the panel**, and the workspace stops constructing `GenerationPricingCoordinator` and `GenerationAccountCoordinator`. Not deprecated, deleted: every test in this issue would pass just as well against a panel wired to its own copy of the filter state rather than to the `FilterSelection` slice 4 built and tested, which is exactly what #82 shipped and its code audit caught. Tests cannot catch that cheaply; removing the second implementation makes wiring to it a compile error.

Its capability moves into the panel; its form does not. The model picker goes, because the MVP ships one model. The aspect picker goes, because the aspect is the working image's. The reference wells go, because the working image is the reference.

**Cost is a constant, not a request.** `IMPLEMENTATION_GUIDE_v2.md` section 2.3 fixes grok at 2c per image for the MVP and removes the pricing client from scope. The panel shows that constant. `GenerationPricingCoordinator` and `GenerationAccountCoordinator` are no longer constructed by the workspace; they remain in the module for the version that needs them, with the Settings controls that drive them retired alongside the surface by slice 10.

### Settings becomes a scene

`SuperscaleApp` gains a `Settings` scene holding the existing `SettingsView`. It opens with `Cmd+,` and in its own window, which is what a macOS user expects and what removing modes forces.

### Prior sessions reach the user through the File menu

`HistoryView` is deleted. A `CommandGroup` after `.newItem` lists recent sessions from `GenerationSessionStore`, most recent first, each opening its generated image as the working image. The store already records every session with its prompt, timestamp and assets, so nothing new is persisted.

This is a menu built from the session store rather than `NSDocumentController`, because Superscale is not a document based application and adopting `NSDocument` to obtain one menu would be an architecture change for a cosmetic gain.

### D8

The default upscale model is applied where the working image is set, not where the handoff happens, so both routes pass through the same code and cannot diverge again.

### Patterns and anti-patterns

- SwiftUI. `CODING.md` and `SWIFT.md` apply: no force unwrapping, no `try!`, no empty `catch`, views describe UI and hold no business logic.
- Prefer the cross platform SwiftUI API where it is equal or better. `.fileImporter` and `.fileExporter` rather than `NSOpenPanel` and `NSSavePanel` where the panel is being touched anyway; `CGImage` as the currency between the kit and the view. This is not iPad support, which is out of scope, but it avoids foreclosing it.
- No new dependency, no new test architecture.

### Condition enumeration

- **AC87.1** implies three conditions: no mode list, the two surfaces coexisting, and the three former modes being gone as navigable surfaces. RT-87.1 to RT-87.3. The third is separate because deleting the sidebar while leaving a Generate surface reachable another way would satisfy the first two and miss the point.
- **AC87.2** implies three conditions: the canvas dominates, the panel does not replace it, and the working image is drawn whether or not an upscale is selected. RT-87.4, RT-87.5, RT-87.35.

  The third was added on 2026-08-24 after a defect found in use: with the scale toggled off there is no upscaled output, by AC82.6, and the canvas drew only the upscaled result. An image imported in that state loaded, set the base, and drew nothing, which is indistinguishable from the import being ignored. Filtering without upscaling is a legitimate use on its own, and so is doing both. Dominance is asserted by comparing the canvas frame against the window frame rather than by a fixed pixel figure, which would encode one window size as the contract.
- **AC87.3** implies two conditions: the scene opens, and nothing in the workspace is a Settings surface. RT-87.6, RT-87.7.
- **AC87.4** implies five conditions: every category is offered, choosing one narrows, choosing it again widens, search reaches across all of them, and a corpus that will not load says so. RT-87.8, RT-87.9, RT-87.36, RT-87.37, RT-87.10, RT-87.31.

  **The criterion was reworded on 2026-08-24**, after the first implementation was rejected on sight. It read "every bundled filter is reachable within its category", which section headings satisfy: 86 filters in one long scroll with headings between them, which is grouping rather than choosing. The wording now says what the panel is for — a category narrows the list, and narrowing and clearing each cost one action. The identifiers are unchanged; RT-87.36 and RT-87.37 are added for the conditions the original wording had no way to express.

  A filter bar rather than a drill-down, because the requirement is flexibility with few clicks rather than a fixed number of steps: narrowing is one click, clearing is one click, and search cuts across categories so nothing is hidden behind navigation. The fourth extends **AC85.9**, which fixes what the application holds after a failed load, to what the panel shows: an empty list with no explanation reads as a broken application. The third is what catches a grouping that drops a category with one member or mislays a filter whose category is spelled differently.
- **AC87.5** implies three conditions: selection fills, selection is free, and applying sends what is there. RT-87.11 to RT-87.13. These restate AC85.4 and AC85.5 at the workspace boundary; the model level is already covered, and this is what proves the panel is wired to it rather than to a second implementation.
- **AC87.6** implies three conditions: exactly one reference, it is the image at its own resolution rather than the upscaled rendering, and no well exists to add another. RT-87.14, RT-87.15, RT-87.24. The second is the one that matters and the one an implementation gets wrong by accident: the canvas shows the upscaled rendering by default, so sending what is on screen is the obvious move and it violates **AC79.2** on the delivery master, *"a cloud filter never receives pixels produced by an upscale targeting the user's chosen output size"*, which is invariant I1. The asset graph enforces this from slice 9b; until then the criterion has to carry it.
- **AC87.10** implies two conditions: the canvas offers somewhere to put an image, and nothing can be applied to an image that is not there. RT-87.25, RT-87.26. This is the state the application opens in every time, and every other criterion here assumes past it.
- **AC87.11** implies two conditions: filters are unavailable with a way to fix it, and the local half is untouched. RT-87.27, RT-87.28. Section 2.8 of `IMPLEMENTATION_GUIDE_v2.md` rules on this case directly, and the surface that used to carry the message is the `GenerateView` this issue deletes.
- **AC87.12** implies two conditions: a cancel exists while in flight, and cancelling leaves nothing behind. RT-87.29, RT-87.30. Section 2.3 requires it, and a paid call is the one a user most wants to stop.
- **AC87.7** implies two conditions: the rate is shown, and nothing is requested to obtain it. RT-87.16, RT-87.17. The second is the point: a pricing client that still runs would make the flat rate a lie about what the application does.
- **AC87.8** implies four conditions: the drop path honours the default, the filter-result path honours it, an explicit choice still wins, and a stored default that no longer names a real model falls back rather than failing. RT-87.18 to RT-87.20, RT-87.34. This closes D8, whose shape is exactly two paths disagreeing, so both are tested rather than the fixed one. The fourth exists because the default is a string in `UserDefaults` that survives an upgrade which removes a model.
- **AC87.9** implies five conditions: the menu lists sessions in order, choosing one loads it, History is gone, the list is bounded, and a session whose image has been deleted is reported rather than silently doing nothing. RT-87.21 to RT-87.23, RT-87.32, RT-87.33. The last two are ordinary rather than exotic: session assets live in Application Support, which users clear out, and an unbounded menu grows for the life of the installation.

### What this does to earlier criteria

**AC75.1** (#75, pre-cutover) requires Generate mode to expose *"prompt-pack selection, prompt entry, model selection, aspect selection, up to three reference image wells, and generate/cancel controls"*. It is superseded by AC87.2, AC87.5 and AC87.6: there is no Generate mode, one model, no aspect selection, and one reference which is the working image. Filter selection, prompt entry and execution survive in the panel. Its tests are rewritten against the workspace, keeping their identifiers, or marked removed where they assert a control the MVP does not have.

**AC77.x** (#77, history and sessions) covers session storage, which is unchanged, and a History surface, which is removed. The storage criteria stand; the surface criterion is superseded by AC87.9.

**AC73.5** (#73) requires Settings mode to show its controls. It is superseded in part by AC87.3: the controls remain, the mode does not. The pricing and account controls it names retire with the paused surface, which slice 10 handles.

Both are legacy criteria and migrate to `docs/ACs.md` as part of this issue rather than being cited from closed issues.

### A workspace model, so the behaviour is testable below the window

The logic this issue introduces — which filter is chosen, what the apply action sends, which upscale model an arrival path resolves to, which recent sessions exist, and when applying is available — belongs in `SuperscaleUXCore` as a `WorkspaceModel`, with the view rendering it.

This is implementing within the documented architecture rather than changing it: section 3.1 already places GUI-facing orchestration in `SuperscaleUXCore`, and `GenerationCoordinator`, `FilterSelection` and `ScaleSelection` are the same shape. `SWIFT.md` asks for views that describe UI and view models extracted when behaviour needs testing outside the UI.

The reason is the test suite. `make test-gui` runs 50 tests in eight minutes because every one launches the application. Slice 10 was delivered first precisely so that suite could become a gate; adding 34 more GUI tests would take it past a quarter of an hour, and a gate that slow is one that gets skipped.

### Test type justification

RT-87.1 to RT-87.34 are regression tests: every condition is machine verifiable, none needs human judgement, and none invokes the build system.

They are split by what they actually assert, following `TESTING.md`'s preference for the narrowest test that exercises real behaviour through a real boundary.

**GUI tests, in `SuperscaleApp/SuperscaleAppUITests/SuperscaleAppUITests.swift`.** These concern the window and the accessibility tree, which exist only when the application runs: RT-87.1 to RT-87.11, RT-87.15, RT-87.22, RT-87.23, RT-87.25, and one end-to-end apply through the panel.

**Package tests, in `Tests/SuperscaleUXCoreTests/`.** These concern behaviour the window merely exposes:

| Tests | What they assert | Why not the GUI |
|---|---|---|
| RT-87.12, RT-87.17 | no request is issued | A UI test observes a window; it cannot observe the absence of a network call. Written against a fixture service's recorded calls, which is the only form in which absence is observable |
| RT-87.13 | the request carries the prompt area's text | The model level already holds this as RT-85.15 and RT-85.16; this asserts the workspace builds its request the same way |
| RT-87.14, RT-87.24 | the reference is the unupscaled image | Request construction |
| RT-87.16 | the rate is the documented constant | The constant |
| RT-87.18 to RT-87.20, RT-87.34 | which upscale model each arrival path resolves to | A resolver function, which is what closing D8 properly means: one place both paths pass through |
| RT-87.21, RT-87.32, RT-87.33 | ordering, the ten-item cap, a missing asset | The session store |
| RT-87.26 | applying is unavailable with no image | `canApply` |
| RT-87.27, RT-87.28 | availability without a key | The settings state |
| RT-87.29, RT-87.30 | cancelling leaves nothing behind | The coordinator |
| RT-87.31 | a failed catalogue is explained | The model half is AC85.9; this extends it to what the panel is given to render |

Both packs run. The GUI tests cover the surface; the package tests cover the behaviour behind it.

**UT-79.1**, already on the master, is the human judgement that the running application shows a single workspace. It is presented when this issue is verified.

### Verification

**All 50 existing GUI tests must still pass**, not merely the new ones. This issue rewrites the shell that every one of them navigates: the drop path, the comparison view, the magnifier, the zoom controls, the model picker and the scale picker all have tests that pass today, and the risk of a workspace rewrite is breaking one of them quietly. Tests whose navigation changes are rewritten, keeping their identifiers; none is deleted to make the suite green.

Zero failures across the whole of `make test-gui` is the gate, which slice 10 made possible by clearing the three standing failures.

### Temporary state in tests

The GUI tests run against the UI test fixtures already established in `SuperscaleApp.swift`, which allocate a root from `SUPERSCALE_UI_TEST_ROOT` and reset it on launch. No test writes outside that root.
