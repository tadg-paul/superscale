## Original issue body

Child of delivery master #79 (slice 10). Test hygiene, in two unrelated parts: a prohibited test pattern, and the three standing `make test-gui` failures.

This issue contains **no AC table**. It cites the criteria the affected tests were written to satisfy, per `ISSUES.md` §"Bug-fix issues reference existing ACs".

## Part 1 — a test that greps project files

`TESTING.md` is unambiguous: *"Source code must never be grepped, parsed, or otherwise introspected to make a behaviour test pass. Grep is a discovery tool, not a test oracle."*

**RT-042** (`Tests/SuperscaleTests/FaceEnhancerTests.swift:54-91`) does exactly that in two of its three parts:

1. it reads `.gitignore` as text and asserts it contains `*.mlpackage` and `*.pth`;
2. it reads `Formula/superscale.rb` as text and asserts it does not contain "gfpgan".

Neither proves anything. An ignore pattern is not evidence that a file is untracked, and a formula's text is not evidence about what a built artefact contains. Its third part runs `git ls-files --cached` and asserts no GFPGAN weights are tracked, which queries real repository state and is the only part that ever supported the claim.

**Violated criterion:** AC1.5 (legacy - see #1), *"The GFPGAN weights are excluded from git, Homebrew formula, and all distribution artefacts"*, whose covering test is RT-042.

**Solution.** Delete parts 1 and 2. Keep part 3. The criterion is unchanged and remains covered by the assertion that was doing the work.

The criterion names the formula, so dropping the formula grep leaves a real question: what stops a `resource "gfpgan"` block being added that bundles non-commercial weights into a Homebrew install? Not a grep of the formula, which proves only what the file says. The answer is an install from the formula, inspected for the weights, and that is release-time verification rather than a regression test: it needs the network, the published release assets, and a Homebrew prefix. It is added to `docs/RELEASE_CHECKLIST.md` as human release evidence instead of being simulated by reading Ruby source.

The weights cannot reach a build that the repository does not carry, which is what RT-88.5 continues to assert.

The whole corpus was swept for the same pattern. `ReleasePackagingTests`, `TestLayoutGuardTests` and the one-off migration tests *execute* the scripts they concern rather than reading them, and the files they read are test fixtures or product assets. RT-042 is the only offender.

## Part 2 — the three standing GUI failures

`make test-gui` has failed on the same three tests since before this delivery began, established by running the suite in a worktree at `390dcab`. They are diagnosed from the result bundle rather than hypothesized.

### RT-130 — a test-side defect

`SuperscaleAppUITests.swift:779: Unable to parse the format string "value CONTAINS 'Tadhg O'Brien'" (NSInvalidArgumentException)`

The predicate's apostrophe is unescaped, so the test never runs at all. The behaviour it covers is live: `AboutView.swift:52` renders `Text("By Tadhg O'Brien")`.

**Violated criterion:** AC58.1 (legacy - see #58), which requires the About panel to display *"app name, version, author, all installed models with their licences, and a link to the project repository"*. The criterion holds; only its test is broken.

**Solution.** Escape the apostrophe. This is not a superseded criterion and the test is not retired.

### RT-73.8 and RT-76.6 — one cause, and it is not the test

Both fail on the same element:

`SuperscaleAppUITests.swift:169: No matches found for Elements matching predicate '"refreshAccountButton" IN identifiers'`
`SuperscaleAppUITests.swift:1047: XCTAssertTrue failed` — the same button

The button is **absent from the accessibility tree**, not disabled. Eleven assertions before it pass, including `accountState` at line 158 — which is the identifier applied to the button's own parent `HStack` at `SettingsView.swift:223`, with the button at `:221` and `accountSummaryState` at `:213` inside it.

The working hypothesis is that an accessibility identifier on a container collapses its subtree, leaving the children unreachable. That is a live defect rather than a stale test: a control that is absent from the accessibility tree is absent for VoiceOver too, so the refresh button is not operable by assistive technology.

**The hypothesis is tested before it is acted on.** Removing the container identifier and running only the two affected tests with `-only-testing` either reproduces or refutes it in about a minute. If refuted, the diagnosis continues rather than a second plausible cause being assumed.

The experiment is diagnosis, not verification, and the distinction matters: a test that passes after a change shows the change worked, not that the diagnosis was right. The experiment's result is recorded on this issue as evidence, and RT-88.3 is the standing guard regardless of which cause the experiment establishes.

**Violated criterion: a backfill, not a stretch.** AC73.5 (legacy - see #73) reads *"Given Settings mode is visible, users can see separate controls for generation key, account/admin key, account state, defaults, and prompt packs."* A sighted user **can** see the refresh control: it is drawn, it is on screen, and it works with a mouse. What it is not is *addressable*. Reading "see" as "reachable by assistive technology" would be stretching a criterion to cover something it does not say.

`ISSUES.md` provides for this case: the underlying feature has an AC table and the bug exposes a gap, so the AC is backfilled on the original feature. AC73.5 is migrated into `docs/ACs.md`, being load-bearing and cited twice inside two days, and this criterion is backfilled beside it:

> **AC73.6** — Every interactive control in Settings is individually addressable by assistive technology, rather than being absorbed into the row that contains it.

AC73.5 continues to cover *which* controls exist. AC73.6 covers whether they can be reached. RT-88.1 to RT-88.3 are added under AC73.6.

**Solution.** Identify the account row's children individually and leave the container unidentified, or mark the container as an accessibility container that keeps its children addressable, whichever the experiment shows to work. `accountState` is retained as an identifier on the summary text rather than the row, so the criterion's "account state" control remains addressable.

### What is superseded, and what is not

The pricing and account surface is paused for the MVP: `IMPLEMENTATION_GUIDE_v2.md` section 6 removes the pricing client, the account client, the session cache and the cost-confirmation policy from scope, and slice 9a removes the Settings mode these tests navigate by.

- **RT-76.6** is superseded entire. Its journey is pricing estimates, account balance and billing events, and every one of those surfaces goes. It is marked removed against **AC76.3**, whose remaining test RT-76.5 and the coordinator-level pricing tests continue to cover the policy that still exists.

  The dependency is worth stating rather than assuming: a test is not superseded because a plan intends to remove a surface, but because the surface goes. `GenerationPricingCoordinator` and `GenerationAccountCoordinator` still exist today and their Settings controls still render. **#87 deletes the workspace RT-76.6 navigates and retires those controls.** If #87 were abandoned, this removal would have to be revisited.

  **AC76.3 itself needs superseding later.** It specifies a cost-confirmation policy that section 6 of the implementation guide removes from MVP scope along with the threshold, so the criterion is not merely losing a test; it describes behaviour that is going away. That is #87's business, not this issue's, and it is recorded in the master's ledger so the criterion and its remaining test retire together.
- **UT-76.1**, still pending on closed #76, retires with it, because the wording it asks a human to judge is the wording of a removed surface.
- **RT-73.8** is *not* superseded. Its failure is the accessibility defect above, and eleven of its assertions cover controls that remain. Its two pricing and account assertions are removed with the paused surface; its navigation by `modeSettings` is rewritten by slice 9a when Settings becomes a scene.
- **UT-73.2**, pending on closed #73, transfers to the master's roll-up and is presented after slice 9a rebuilds Settings, not before.

Marking a failing test as superseded without establishing what it was written to satisfy is how a real defect gets deleted. That is why each is traced to its criterion first.

## Regression tests

Allocated to this issue, added to the coverage of the criteria above rather than to any new criterion:

- ⏳ RT-88.1: the account refresh control is reachable in the accessibility tree, under AC73.6
- ⏳ RT-88.2: the account summary is reachable in the accessibility tree, under AC73.6
- ⏳ RT-88.3: each control AC73.5 names is reachable in the accessibility tree by its own identifier, none of them absorbed into a containing row, under AC73.6
- ⏳ RT-88.4: the About panel's author line reads exactly "By Tadhg O'Brien", under AC58.1
- ⏳ RT-88.5: no tracked file is a GFPGAN model weight, judged by extension rather than by path prefix, under AC1.5

**"Every control" is asserted against a finite list, not discovered.** A test cannot enumerate "every" from nothing: it either hard-codes a list, so a control added later is uncovered and the word is a lie, or it walks the tree and asserts something vacuous. RT-88.3 uses the set AC73.5 already enumerates — generation key, account key, account state, defaults, prompt packs — each of which has an identifier today. A control added to Settings later is covered when its own criterion is written, which is where that obligation belongs.

**RT-88.4 asserts the exact line rather than a fragment.** The narrowest way to make a predicate-parse failure go away is to loosen the predicate until it matches almost anything, and `label CONTAINS 'Tadhg'` would pass against the wrong credit entirely. `TESTING.md` permits a string assertion where the exact string is the contract and is observed through the real boundary; a rendered credit line read from the running application's accessibility tree is that case.

**RT-88.5 filters by extension, not by path.** The assertion inherited from RT-042 excluded `scripts/` before looking for the string "gfpgan", because the download script legitimately carries the name. Filtering by path means a weight committed under `scripts/` would pass, and the criterion is about weights rather than about a word in a filename. Judging by `.pth`, `.mlpackage` and `.mlmodelc` covers every directory and stops the filename being the thing under test.

RT-88.3 is the one that stops this recurring. RT-88.1 and RT-88.2 would both pass while a later change reintroduced a container identifier somewhere else in the panel; RT-88.3 states the rule the defect broke, across every control Settings offers, which is what AC73.6 says.

**Type justification.** All five are regression tests: each guards ongoing behaviour, none needs human judgement, and none invokes the build system. RT-88.1 to RT-88.4 run under `make test-gui` because an accessibility tree exists only when the application runs. RT-88.5 is the surviving assertion of RT-042 and runs under `make test`.

**Location.** `SuperscaleApp/SuperscaleAppUITests/SuperscaleAppUITests.swift` for RT-88.1 to RT-88.4; `Tests/SuperscaleTests/FaceEnhancerTests.swift` for RT-88.5.
