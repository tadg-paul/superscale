## Original issue body

Child of delivery master #79 (slice 9c). Reported from use.

## Problem

**The canvas goes blank while an upscale runs.** `MainView` shows `ProgressOverlay` *instead of* the image, so importing an image gives a spinner where the picture should be. There is an image; it should be on screen, with progress over it.

Four faults follow from the same cause, which is that the canvas renders one thing — the finished upscale — rather than a base and a derivation of it:

- **Nothing appears until the upscale finishes.** Dropping an image should show it at once, with the upscale arriving when it is ready.
- **Turning the upscale off leaves the old rendering on screen**, or nothing, rather than falling back to the image itself.
- **Toggling face enhancement swaps the display to a spinner** and rebuilds, when the previous rendering could stay until the new one exists. Both versions are already computed and cached in `UpscaleViewModel` (`cachedWithFaces`, `cachedWithoutFaces`); the display does not use them, so a comparison that could be instant costs a rebuild.
- **Comparison defaults to the magnifier loupe.** The loupe is a custom cursor tracking the mouse, and it is clunky and brittle in use. The curtain — a divider dragged across the image — is the appropriate instrument for before-and-after, and the loupe is not.

## The display model

One rule, from which the rest follows:

> **The canvas always shows the base image. When an operation has produced something from it, the canvas shows that instead, and the curtain compares the two.**

- **Base**: the image the user imported, or the last locked iteration. Always available, always displayed the moment it exists.
- **Derived**: the output of the *last* operation — an upscale, or an AI filter. At most one exists.
- **In flight**: an operation runs asynchronously. The canvas keeps showing what it was showing, with progress over it. It never blanks and never shows a stale image as though it were new.
- **Turning something off** — the upscale, or the filter — falls back to the base immediately. There is nothing to build, so there is nothing to wait for.
- **Face enhancement** is the exception to immediacy: toggling it does not change the display until the new image exists, because both versions are of the same operation rather than one being a fallback. Both are cached, so the second toggle is instant.
- **The curtain** compares base against derived, and appears only when they differ. Base against base shows no curtain.

## Solution

### The canvas takes a base and an optional derivation

`MainView`'s content becomes a function of two images rather than one: the base, always; and the current derivation, when one exists. `ProgressOverlay` becomes an overlay in fact as well as in name, drawn over whichever image is showing.

### The curtain becomes the comparison

`ComparisonMode.slider` becomes the default and the loupe is removed. This supersedes **AC68.4**, which made the magnifier the default, and retires **AC68.1**, **AC68.2**, **AC68.5** and **AC68.6**, which specify the loupe's behaviour. **AC68.3**, the toggle between the two modes, goes with it: with one mode there is nothing to toggle.

`MagnifierView.swift` is deleted rather than left unreferenced.

**AC67.2**, the divider opening at 35%, is unaffected and carries over.

### A rendering cache, so toggling costs nothing twice

`UpscaleViewModel` already holds `cachedWithFaces` and `cachedWithoutFaces`: a two-entry cache for one asset and one setting. Generalising it is what makes the whole display model cheap.

**The key is what produced the rendering**: the asset it derives from, the model, the sizing, and whether faces were enhanced. A rendering is reusable exactly when all four match, so toggling the upscale off and on again finds the rendering already there, and so does toggling face enhancement back.

**Invalidation falls out of the key rather than being managed.** Applying a filter produces a new asset with a new identity, so its renderings simply miss; nothing has to be cleared, and nothing that is still valid is thrown away. What bounds memory is the cache's size, not correctness: a small LRU, four entries, which is deep enough to hold the with-and-without-faces pair for both the base and the current candidate. `PipelineCache` holds two pipelines on the same reasoning.

**Undo is not in this slice.** A cache of prior renderings is most of what an undo of operations would need, and the user asked for it *if it comes cheaply*. It does not: undo needs a history of operations with their inputs, a way to move through it, and a decision about what undoing an *applied filter* means when the filter cost money. That is a feature, not a side effect of caching, and it is recorded on the master's backlog rather than smuggled in here.

### Added by the AC audit

Five states the first draft did not describe. Each is small in code and each is a defect if left
implicit.

- **A rendering carries what produced it.** The key that makes the cache work — asset, model,
  sizing, face setting — is also what makes lateness detectable, so it travels with the rendering
  rather than only with the cache entry. A rendering whose key no longer matches the current state
  is refused at admission. Without this, a slow upscale of one image can be drawn as a derivation
  of the next one, and `CanvasContent.decide` cannot see it because it draws the derivation it is
  handed.
- **Failure is a state, not an absence.** An operation that throws clears progress, leaves the
  display alone, and contributes nothing to the store. #91 adds a memory cap that refuses work by
  design, so this path is ordinary rather than exceptional.
- **The curtain fits both sides to one frame.** A 4x upscale is four times the width of its base;
  presenting both at their own sizes puts the divider on different parts of the picture. The
  geometry is a function over two sizes and a container, which keeps it testable without a window.
- **A filter result outlives the filter toggle.** Toggling the filter off shows the base, per
  AC90.3, and toggling it back on shows the result that already exists. The result is an asset on
  the graph, not a rendering, so the cache does not cover it and the candidate pointer is what
  holds it.
- **Eviction knows what is on screen.** The displayed key is an input to the store, exempt from
  the bound. Four entries is exactly the base and candidate faces pairs, so in ordinary use the
  store is full and the next admission would otherwise evict the picture the user is looking at.

### Added by use, 2026-08-25

Two defects reported by the author against the first cut of this slice, folded in here rather than
raised as separate children because both are display-model behaviours and this slice owns the
display model. Recorded on the master as ledger entries L34, L35 and L36.

- **The progress overlay blurs the picture, and must not.** `ProgressOverlay.swift:19` frames the
  overlay at `maxWidth: .infinity, maxHeight: .infinity`, and `MainView.swift:103` backs that
  full-canvas frame with `.thinMaterial`, which is a blur. The requirement was plainly stated and
  the implementation embellished it. The overlay becomes a compact indicator sized to its own
  content, and nothing is drawn across the image.
- **The curtain divider does not track the pointer.** `ComparisonView.swift:245` divides
  `value.location.x`, which is local to the 28-point drag handle the gesture is attached to, by
  `window.contentView.frame.width`, which is the whole window including the filter side panel, with
  a `?? 600` fallback when there is no key window. Three faults in four lines. The divider position
  becomes a pure function of the pointer's x within the canvas and the canvas width, both taken
  from the same `GeometryReader`, with the gesture attached to the full-size container in a named
  coordinate space. The window is not consulted at all.

  The arithmetic predates this delivery: `git log -L 245,254` places it in `1c6ec18`, 2026-03-28,
  and it was untouched while AC68.4 made the loupe the default comparison. Removing the loupe is
  what put it in front of a user. Recorded as L35, offered as attribution rather than as excuse.

  **The frame is the displayed image, not the canvas.** `audit-acs` caught the first wording
  specifying the fix against the canvas, which is the same coordinate-space error one level up:
  AC90.10 fits both sides into one displayed size, so a picture letterboxed in a wider canvas has
  bars on either side and canvas x is not image x. The gesture is attached to the container in a
  named coordinate space, the fraction is computed against the displayed image frame from the same
  `GeometryReader`, and the divider is drawn in view space so zoom and pan do not move it. The
  window is not consulted at all.

  **The 28-point handle stays the drag target.** Whether the whole image should be draggable is a
  separate interaction question and the report was about alignment, not reach. Left alone so this
  fix does not widen the interaction by accident.

### Condition enumeration

- **AC90.1** implies three conditions: an imported image is on the canvas before anything derives from it, no state leaves the canvas empty while an image is loaded, and the import's own loading is the single exception because there is nothing yet beneath it. RT-90.1, RT-90.2, RT-90.25, RT-90.40. The exception is stated rather than left to fall out of an implementation, since a canvas that is empty during import looks exactly like the defect this slice removes.
- **AC90.2** implies three conditions: the base stays during a first operation, progress is drawn over the image rather than in place of it, and a previous *rendering* stays during a second. RT-90.3 to RT-90.5. The third is separate because falling back to the base mid-operation would be a regression dressed as a fix.
- **AC90.3** implies three conditions: the scale off falls back at once, the filter off falls back at once, and neither leaves the old rendering behind. RT-90.6 to RT-90.8. Immediate, because the base already exists: there is nothing to build and so nothing to wait for.
- **AC90.4** implies three conditions: the display holds while the new rendering builds, the second toggle of a pair costs no work, and with no upscale selected the setting is inert. RT-90.9, RT-90.11, RT-90.41. Face enhancement is the deliberate exception to AC90.3's immediacy: both versions are renderings of the same operation, and neither is a fallback for the other. Reuse of an existing rendering belongs to AC90.7 and is not restated here.
- **AC90.5** implies three conditions: the curtain is what appears, the loupe and its mode toggle are gone, and the divider moves. RT-90.12 to RT-90.14.
- **AC90.6** implies three conditions: the curtain compares against an upscale, against a filter result, and is absent when base and derivation are the same image. RT-90.15 to RT-90.17.
- **AC90.7** implies six conditions: a rendering is reused across a scale toggle, across a face toggle, generally when the key matches, is not offered for a different asset, is not offered at a different scale, and the store is bounded. RT-90.18 to RT-90.22, RT-90.10. The fourth and fifth are what stop a cache showing the wrong picture, which is worse than rebuilding; the sixth is what stops it growing for the life of the session.
- **AC90.8** implies four conditions: the display survives a failure, progress stops, no partial output is shown as a result, and nothing failed enters the store. RT-90.26 to RT-90.29. Failure is a designed outcome here rather than an exception, because #91 adds a memory cap that refuses work by design.
- **AC90.9** implies four conditions: lateness against a replaced base, against a locked base, against a changed setting, and that the canvas moves to the new base without waiting for the superseded work. RT-90.30 to RT-90.33. This is the one fault `CanvasContent.decide` cannot catch on its own: it draws the derivation it is handed, so what a rendering was produced *from* has to be carried with it.
- **AC90.10** implies three conditions: one displayed frame for two pixel sizes, the divider mapping to the same relative position on both sides, and the whole holding for a real 4x upscale. RT-90.34 to RT-90.36. Without it the curtain compares different parts of the picture, which reads as a defect in the upscaler rather than in the comparison.
- **AC90.11** implies three conditions: the result survives the toggle, the second toggle is free, and a new filter replaces rather than accumulates. RT-90.37 to RT-90.39. A filter is a paid provider call, so re-issuing one to redisplay something already on disk spends the user's money to no effect.
- **AC90.13** implies three machine-checkable conditions and one that is not: the indicator covers a small part of the canvas rather than all of it, the image stays present beneath it, the indicator sits at the top rather than across the middle, and the picture *looks* untouched. ## Test type justification and location

All 52 are regression tests. They follow the split #87 established: the GUI covers the surface,
the package covers the behaviour behind it.

**The decision is a function, and that is where most of these live.** What the canvas should draw
is determined by the base, the current derivation, whether an operation is in flight, and which
the toggle has chosen — and `CanvasContent` in `SuperscaleUXCore` returns it. RT-90.1, RT-90.2,
RT-90.3 to RT-90.9, RT-90.11, RT-90.15 to RT-90.17, RT-90.24, RT-90.25, RT-90.26 to RT-90.28,
RT-90.30 to RT-90.33, RT-90.40 and RT-90.41 test that function in milliseconds, with no Core ML
and no waiting. RT-90.5 in particular needs a state with a prior rendering *and* an operation in
flight, which in a GUI test would mean waiting for real upscales twice.

RT-90.23 is **not** in that list. Cancellation is a stage behaviour, not a drawing decision, so it
runs through `GUIUpscaleProcessing` with a stub processor.

**Lateness is decided where the rendering is admitted, not where it is drawn.** AC90.9's tests
give `CanvasContent` a derivation stamped with the base and settings that produced it, and assert
that a stamp which no longer matches is refused. Testing it through the view would mean racing a
real upscale against a real import.

**The cache is a keyed store**, so RT-90.10, RT-90.18 to RT-90.22, RT-90.29, RT-90.42 and
RT-90.43 are package tests over it. RT-90.42 and RT-90.43 need a store that knows which entry is
displayed, so the displayed key is an input to eviction rather than a property of the view.

**The curtain's geometry is arithmetic**, so RT-90.34 and RT-90.35 are package tests over the
function that fits two differently-sized images into one frame. RT-90.36 is the GUI check that
the view actually uses it.

**RT-90.11 counts renderings, not pipeline loads.** A counting producer is injected into the
rendering store and asserts exactly one production across two toggles. `PipelineCache`'s loader
count is a different event and would silently measure the wrong thing.

**RT-90.38 counts provider requests** against the stub transport the filter tests already use, so
no paid call is made to prove that no paid call is made.

**The divider's arithmetic is a pure function**, so RT-90.46, RT-90.47, RT-90.50 and RT-90.51 are
package tests over it: a pointer x, a displayed image frame, and a clamp in, a fraction out. Window
width, panel width, canvas aspect, zoom and pan are inputs it never sees, which is the point. Only
RT-90.48 needs the assembled view, because the defect was the view feeding it the wrong numbers
rather than the arithmetic being wrong in itself.

**AC90.13's tests read frames, not styling.** RT-90.44, RT-90.45 and RT-90.49 compare the
indicator's frame against the canvas frame and assert the image element is still present and
hit-testable. Whether a blur is applied is not observable through the accessibility tree at all,
which is why UT-90.2 exists: the defect was visual and the judgement stays human.

**GUI, in `SuperscaleAppUITests`:** RT-90.12 to RT-90.14, RT-90.36, RT-90.37, RT-90.39, RT-90.44,
RT-90.45, RT-90.48, RT-90.49 and RT-90.52, plus GUI counterparts of RT-90.2 and RT-90.25 asserting
the canvas image element is present throughout an import and an upscale.

### What the test audit changed

**RT-90.2 and RT-90.25 exist in both harnesses, deliberately.** They are committed as package tests
at `CanvasContentTests.swift:23` and `:51`, and this section previously listed them as GUI tests
only. Keeping both is the correct resolution rather than choosing: the package version exercises
every state combination in microseconds, and the GUI version proves the window is wired to the
function at all.

**That wiring is a stated boundary, not an assumption.** Twenty-odd package tests exercise
`CanvasContent.decide`; a `MainView` that ignored it entirely would leave every one of them green.
The GUI counterparts above, with RT-90.48, are what close it. This is the same shape as the defect
this slice repairs — defensible arithmetic, a view feeding it the wrong numbers, five months
unnoticed — so it is written down rather than trusted.

**RT-90.3 tests a transition, not a state.** It previously repeated RT-90.1's exact call and
assertion. It now asserts that with a derivation present the image is the same before work starts
and while it runs, which is AC90.2's distinct claim and the thing a naive fall-back-to-base
implementation breaks.

**RT-90.23 moves to the stage.** Cancellation cannot be observed by a pure function over four
values, so it is tested through `GUIUpscaleProcessing` with a stub processor, matching the pattern
in the implementation guide's testing table: the stub records that its run was cancelled, and a
completion arriving afterwards is not admitted.

**RT-90.52 replaces half of a user test.** Whether the picture is altered is machine-checkable:
the canvas region outside the indicator's frame is either identical between the idle and working
states or it is not. `SWIFT.md` requires snapshot tests to be justified, and this is not one: no
image is stored, nothing is pinned, and the assertion is invariance between two states of a single
run. UT-90.2 keeps only the judgement no assertion reaches.

**Its ordering is part of its specification, not an implementation detail.** Capture idle *before*
work begins, start the upscale, capture while it runs, then compare. Taking the idle capture
afterwards would compare two different pictures — the base and its upscale — and fail for a reason
that has nothing to do with blur. A flaky test in a gate suite is worse than no test, because it
teaches the reader to rerun rather than to look.

**RT-90.44 and RT-90.49 carry numbers rather than adjectives.** "A small fraction" is whatever the
author decides it is, and the defect being fixed was an overlay at exactly 100% of the canvas: an
author choosing 90% as small would pass it. A quarter of the canvas area is four times smaller than
the defect and generous to any reasonable indicator; the upper third is where `.padding(.top, 24)`
already puts it.

**Two accessibility identifiers are added** so RT-90.48 can be written at all: `curtainDivider` on
the drag handle and `curtainDividerLine` on the rule. `ComparisonView` currently identifies
`zoomInButton`, `zoomOutButton` and `minimap` and nothing else. Both go on the controls themselves,
per the rule in implementation guide 3.9 that an identifier on a container absorbs its children.

**The rendering store holds identities, not pixels.** `RenderedImage` is an identifier already, and
the store is keyed by asset, model, sizing and face setting. So RT-90.10, RT-90.18 to RT-90.22,
RT-90.29, RT-90.42 and RT-90.43 need no files and no temporary directory. An 8-megapixel rendering
written per test would be unbounded output in a regression pack, and this records why none is
written rather than leaving it to chance.

**`MagnifierView.swift` is deleted in the same commit that makes the curtain the only mode.**
RT-90.13 asserts no loupe is present, which would pass equally against a loupe that was merely
hidden or no longer the default; deletion makes its return a compile error. `PromptComposer` in
#85 and `GenerateView` in #87 were removed on the same reasoning.

**Two user tests are allocated:**

> ❌ UT-90.1: the curtain is a usable way to compare before and after
>
> **Failed by the author, 2026-08-25**, in these words: *"whatever way you have implemented it, the mouse pointer does not align with the curtain."* AC90.14 is the criterion that failure exposed. Re-presented once the divider tracks.

> ⏳ UT-90.2: the indicator reads well over a photograph
>
> Narrowed by `audit-tests`. Whether the picture is *unaltered* is machine-checkable and became RT-90.52, comparing the canvas outside the indicator's frame between the idle and working states. What remains for human judgement is whether the indicator is legible and unobtrusive over a real photograph, which no assertion reaches.

Whether the curtain is a *good* instrument is the judgement that condemned the loupe, and it is
not machine-verifiable. It transfers to #79's roll-up when this child closes.

## A dependency this slice does not fix

**A 2000-pixel-wide image at 4× crashes the application**, reported from use. The stitching buffer
holds roughly 36 bytes per output pixel, all resident: 8000 × 8000 is about 2.3 GB before anything
else in the process.

The documented caps do not prevent it. `IMPLEMENTATION_GUIDE_v2.md` warns above 4096 on the long
edge and refuses above 8192, and 8000 sits between the two — so this input is permitted and fatal.
The cap was written against dimensions when the constraint is area.

A criterion promising the canvas is never empty, in an application that dies on a common input, is
promising the wrong thing. That is raised as its own issue rather than folded in here, because the
resolution is a product decision: bounding by output pixel count rather than long edge, and
**reducing the scale to the largest that fits rather than refusing**, so a 2× result with a note
replaces an error. AC90.1's "never empty" holds for every input the application accepts.

## Out of scope

- The minimap and zoom, which AC67.4 covers and this does not change.
- The lock chain, which is #89.
- **Undo.** The rendering cache holds most of what an undo of operations would need, and it is not the same feature: undo needs a history of operations with their inputs, a way to move through it, and a ruling on what undoing a *paid* filter means. Recorded on the master's backlog.

**The curtain took four diagnoses.** A nil base; a compare button that toggles rather than enters; a graph that never recorded the view model's upscales; and finally the tree. The first three were plausible, each was checked against the code, and each was wrong. What settled it was a run in which *only* the new tests failed while the rest of the suite passed — which said the application was fine and the tests were asking for something that did not exist.

## Error handling

`RenderingStore` is bounded at four with LRU eviction and the displayed key exempt, so the cache cannot grow without limit and cannot evict what is on screen. `CanvasContent.admissible(_:expecting:)` compares the stamp against the key currently expected, so a rendering from a superseded run is discarded rather than drawn — the race that previously left two runs' results competing with nothing deciding between them.

`CurtainGeometry` guards every degenerate input: a zero-sized container, a zero-sized image, a fraction outside 0.05…0.95. Each has a test, because a NaN reaching a view is a crash rather than a wrong number.

## Security

No credential handling, no network surface. `RenderingStore` holds decoded images in memory only.

## Complexity

`CurtainGeometry` is five static functions over rectangles, and moving them out of the view is what made AC90.14 and AC96.4 testable at all — the divider's arithmetic was a defect nobody could write a test for while it lived inside a `body`.
