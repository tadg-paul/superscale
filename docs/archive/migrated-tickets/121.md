## Original issue body

Child of delivery master #120 (bring the build onto the design of record).

## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"CONFIRMED: This is the biggest defect! When i select a previous lock image and apply a filter, it is applying the filter to the WRONG IMAGE. I was working on a series of filters to try out different ones, i locked a few that were candidates to keep and reuse later. Clicked back to my original image and changed the prompt to 'Remove background' which is a very straightforward instruction. The image returned was the right-most lock image, not the selected image, with the background removed."*

And, from the same round:

> *"toggling 'showing filtered' and 'showing original' shows a different image but it is not showing the correct original image. It is showing a third image i do not know where it came from, seems to be identical but slightly brighter. No idea where it got this image. Then compare is showing it against the wrong image too."*

> *"when i click on a previous lock image, apply a filter, the 'Show original'/show filtered button is missing now."*

## Two distinct causes, and the order matters

**Cause one --- the specification was incomplete, and the build was conforming.** Until guide 3.31 the base moved only forwards, on lock. A filter reads the base (2.1 step 4, invariants I2 and I3), so applying one after scrolling back sent the most recent lock. That is what the author saw, and it was what the design said to do. Guide 2.4 and invariant I4 now carry the rule the author supplied: **selecting an earlier locked iteration moves the base back to that iteration's own parent and makes the iteration the candidate.** Amended in commit `a17f445`.

**Cause two --- two owners of the same state.** Guide section 3.4's flow has the asset graph publishing to the view. In the build, `UpscaleViewModel` independently owns `originalImage`, `result`, `resultSource`, `inputURL` and `showComparison`, and contains **zero** references to the workspace or the graph. `MainView` reconciles the two by hand at each call site. The code already records the consequence at `MainView.swift:219`:

> *"Taken from the asset graph rather than from `viewModel.originalImage`, which `processImage` replaces with whatever it was last asked to upscale --- so after a filter it holds the filter's own output, and the curtain compared that against its own upscale."*

The unexplained third image and the vanishing comparison control are that seam, reported twice more.

Fixing cause one without cause two would add a third hand-reconciliation rather than removing the need for one.

## Violated criteria

- **I4** in [docs/IMPLEMENTATION_GUIDE_v2.md](../blob/master/docs/IMPLEMENTATION_GUIDE_v2.md) section 3.2, as amended: selecting an earlier iteration moves the base and the candidate together.
- **AC89.3** in [docs/ACs.md](../blob/master/docs/ACs.md): the lock chain remains reachable and workable. Reachability was restored by #111 (the hidden lock chain); this is the other half --- an iteration a user can reach but cannot work from.
- **AC94.3** and **AC90.6**: what the curtain compares. The pair must be the candidate and the base it descends from, which after selection is the selected iteration and its parent.

Whether these are violations or require backfill is for `audit-acs` to rule on; the audit must not assume.

## Debugging and fix procedure

1. **Reproduce both symptoms before changing anything.** Import a picture, apply and lock two filters, select the first iteration, then (a) apply a filter and record which asset was sent, and (b) toggle filtered/original and record which two images are shown. Capture the asset identifiers, not the appearance --- "slightly brighter" is a symptom of comparing the wrong pair, and guessing which pair wastes the reproduction.
2. **Establish where the third image comes from.** The hypothesis is `viewModel.originalImage` holding a previous `processImage` input. Confirm it by identifier before accepting it.
3. **Move ownership.** The graph owns base, candidate and what is displayed. `UpscaleViewModel` keeps rendering concerns --- progress, cancellation, the produced `NSImage` --- and stops holding an opinion about which asset is current. The view reads one source.
4. **Implement selection** as the graph operation guide 3.2 now describes: candidate becomes the selected asset, base becomes its `parentID`. No stored snapshot; the lineage under I7 already holds it.
5. **Do not weaken I2 or I3.** A filter still reads the base and still replaces the candidate. Only which asset the base points at has changed.
6. The existing GUI tests that encode the old timing are expected to need superseding rather than weakening. Any test whose expectation moves must have the reason recorded on its criterion.

## Test plan

- RT-121.1: after selecting an earlier locked iteration, the asset submitted by a filter is that iteration's parent, not the most recent lock
- RT-121.2: after selecting an earlier locked iteration, the comparison pair is that iteration and its parent
- RT-121.3: the filtered/original control is present after a filter is applied to a selected iteration
- RT-121.4: selecting an iteration and then locking the result extends the chain from the selected point
- RT-121.5: no view-held image is displayed that is absent from the graph
- UT-121.1: select an earlier iteration, apply a filter, and judge that the result is a transformation of the picture on screen

### What this delivers, in plain language

A user applies a few filters, locking the ones worth keeping, then scrolls back to an earlier iteration to try a different direction from that point. Today the filter they apply next transforms the most recent lock instead, and the filtered/original toggle shows a picture from neither side of the pair. ### F1 (blocker) --- the design amendment I wrote conflicts with AC89.3, and the obvious implementation reinstates the defect #111 was raised to fix

`AssetGraph.lockedIterations` derives the chain by walking **backwards from the current base's parent**:

```swift
guard let baseID, let baseAsset = assets[baseID] else { return [] }
var cursor = baseAsset.parentID
while let id = cursor, let asset = assets[id] { chain.append(asset); cursor = asset.parentID }
```

The strip therefore shows the ancestors of the base and nothing forward of it. Guide 3.31 now says selecting an earlier iteration moves the base **backwards**. Against that derivation:

| Chain | Base | Strip shows |
|---|---|---|
| S, L1, L2, L3 | L3 | S, L1, L2 |
| after selecting L1 | S | **nothing** |

**AC89.3** requires that *"every locked iteration remains reachable from the current base"*. L2 and L3 vanish the moment a user scrolls back — **the exact defect #111 (the hidden lock chain) was raised to fix**, arriving again by a new route. And it would pass RT-111.1 to RT-111.6, because not one of those tests moves the base.

**Remediation.** The chain shown must be the lineage of the furthest-forward lock, not of the current base. The graph needs a **tip** pointer that lock advances and selection does not move; `lockedIterations` derives from the tip, and base and candidate say where in that chain the user is standing. One source of truth, no stored snapshot, and AC89.3 and the amended I4 hold together.

**The guide amendment is also incomplete.** Guide 2.4 says what selection does to the base and candidate and nothing about what the strip then shows. That is my omission from commit `a17f445` and it must be corrected before any code, or the next reader implements the version that breaks AC89.3.

**Remediation.** State it as what a user can check: the canvas shows an asset the graph holds, and the comparison's two sides are the candidate and the base it descends from. ### Coverage

AC89.9 (selection restores the working context) has RT-121.3, RT-121.5, RT-121.8 and UT-121.1. AC89.10 (no parent) has RT-121.6 — a single test, which step 1 flags. ### F1 (finding) --- RT-121.1 is gameable, and the shortcut is the current behaviour

*"The result is a transformation of that iteration's parent"* can be satisfied by an implementation that sends the right asset and displays the wrong one, or vice versa. Worse, on a two-lock chain the parent of the selected iteration may coincidentally equal the current base, so the test passes without the fix.

**Remediation.** RT-121.1 builds a chain of **three** locks and selects the **first**, so the correct asset and the unfixed behaviour's asset are provably different. The assertion is on the asset actually submitted, read through the request the stub receives, not on the returned picture's appearance.

### F2 (finding) --- no test fails against the author's reported symptom

The author's clearest evidence was *"a third image i do not know where it came from, seems to be identical but slightly brighter"*. RT-121.5 as written asserts the canvas shows an asset the graph holds — which is right, but a third image loaded from a real asset would satisfy it.

**Remediation.** RT-121.5 asserts the displayed asset **identity** matches the expected reference, not merely that it exists in the graph. Identity is the thing that was wrong; existence never was.

### F3 (finding) --- RT-121.8 races the fixture

The suite's fixture is small enough that an upscale routinely finishes before a poll can catch it. #119 lost four remediation cycles to exactly this, and the retired RT-119.4 records that a cached rendering can make the run instantaneous.

**Remediation.** Assert the observable consequence rather than the cancellation: after selecting during a run, the picture presented is the selected iteration and no rendering of the previously-working asset arrives afterwards. If the run finished first, the assertion still holds. Where the timing genuinely cannot be arranged, retire the identifier with its reason rather than leaving a test that passes by not running — the lesson recorded on AC90.13 from RT-90.49.

### F4 (finding) --- the tip is not directly observable, so RT-121.9 needs care

The tip is internal. A GUI test can only see the strip and what is selected.

**Remediation.** RT-121.9 asserts through the strip: after selecting the first of three iterations, all three remain listed, and selecting the last makes it the base again — demonstrated by a subsequent filter reading it. That tests the tip's *effect*, which is what AC89.3 is about, and needs no access to the pointer.

### F5 (finding) --- the package tests carry more of this than the GUI tests should

RT-121.1, RT-121.2, RT-121.4, RT-121.6, RT-121.7 and RT-121.9 are all statements about graph state that `WorkspaceState` and `AssetGraph` can be driven to directly, deterministically, with no window.

**Remediation.** Place them as package tests in `Tests/SuperscaleUXCoreTests/`, and keep **RT-121.3** (the control is present) and **RT-121.5** (what the canvas shows) as GUI tests, because both are claims about what reaches the user. All remain **RT** under the `TESTING.md` decision tree: automated, deterministic, no build system invoked. This is the split #109 used and it is the right one here — the graph rules are pure logic over the graph, exactly as guide 3.2 says.

### Integration, architecture, temporary state, typing

- **Integration gap.** The one that could pass component-by-component and fail together is selection versus the strip: the graph could move both pointers correctly while the strip still derives from the base. RT-121.7 and RT-121.9 exercise them in one sequence rather than separately.
- **Test architecture creep.** None. Existing XCTest and XCUITest only.
- **Temporary state.** Package tests use the existing per-run temporary root and `InMemoryCredentialStorage` pattern; GUI tests write only through the app under test.
- **Typing.** Nine RT, one UT. UT-121.1 is correctly a user test: whether a result reads as a transformation of the picture on screen is human judgement, and it is the judgement the author exercised when they found the defect.

- **Remediation summary:** RT-121.1 rebuilt on a three-lock chain asserting the submitted asset; RT-121.5 asserts identity not existence; RT-121.8 asserts the observable consequence rather than the cancellation; RT-121.9 tests the tip through the strip; six tests relocated to the package suite.
