## Original issue body

## Problem

Superscale's CoreML `.mlpackage` model files are large binary artefacts (~65–100 MB each, ~400 MB total for six models). They are:

- **Too large for git** — `.gitignore` already excludes `*.mlpackage` and `*.pth`
- **Produced rarely** — only when models are converted (Phase 1) or reconverted (coremltools upgrade, new model added)
- **Needed at multiple stages** — local development, Homebrew install, on-demand user download

There is currently no documented or implemented strategy for:
1. Where these files live locally during development
2. How they are uploaded to a hosting location
3. How `make sync` avoids clobbering or losing them
4. How `make release` publishes them
5. How the Homebrew formula and on-demand download code fetch them

## Context

- Issue #2 decides **user-side** model storage (`~/Library/Application Support/superscale/models/`)
- This issue covers the **developer/build-side** artefact pipeline: conversion → local storage → hosting → distribution

## Solution

### Hosting: GitHub Releases with a dedicated models tag

Model files are attached as release assets to a dedicated GitHub Release tag (e.g. `models-v1`), separate from version releases. This tag is updated only when models change.

```
Release: models-v1
  ├── RealESRGAN_x4plus.mlpackage.zip
  ├── RealESRGAN_x2plus.mlpackage.zip
  ├── RealESRNet_x4plus.mlpackage.zip
  ├── RealESRGAN_x4plus_anime_6B.mlpackage.zip
  ├── realesr-animevideov3.mlpackage.zip
  └── realesr-general-x4v3.mlpackage.zip

Release: v0.1.0
  └── source tarball + compiled binary (no models)
```

**Why separate tags:**
- Models change rarely; code changes often. Re-uploading ~400 MB with every point release is wasteful.
- Homebrew formula fetches the default model as a `resource` block from the models release.
- On-demand download manifest (Phase 6, issue #13) points to the same models release assets.
- When models are reconverted, bump to `models-v2` and update manifest + formula.

### Local storage during development

Converted `.mlpackage` files live in a local directory that is gitignored:

```
models/                          ← gitignored, local only
  ├── RealESRGAN_x4plus.mlpackage
  ├── RealESRGAN_x2plus.mlpackage
  └── ...
```

A **manifest file** (`models/manifest.json`) IS tracked by git. It records:
- Model name, filename, scale factor
- SHA256 hash of each `.mlpackage` (or its tarball)
- The GitHub Release tag where it's hosted
- Download URL template

This manifest is the source of truth for the on-demand download code (Phase 6) and the Homebrew formula's `resource` blocks.

### `make sync` behaviour

`make sync` must be model-artefact-aware:

1. The manifest file (`models/manifest.json`) is tracked and synced normally
2. The `.mlpackage` files themselves are gitignored — `git add --all` won't touch them
3. After push, if any `.mlpackage` files have changed (SHA256 differs from manifest), warn the developer:
   ```
   WARNING: Local model files differ from manifest. Run 'make release-models' to upload.
   ```
4. No automatic upload on sync — model releases are deliberate

### `make release-models` (new target)

A dedicated target for publishing model artefacts:

1. Verify all `.mlpackage` files listed in manifest exist locally in `models/`
2. Compute SHA256 for each, compare against manifest
3. If any have changed: compress each to `.tar.gz`, create (or update) the `models-vN` GitHub Release, upload as assets
4. Update `models/manifest.json` with new hashes and URLs
5. Commit the updated manifest
6. Print summary: which models were uploaded, the release tag, total size

### `make release` behaviour

Version releases (`make release VERSION=x.y.z`) do NOT include model files. They:

1. Run tests (unless `SKIP_TESTS=1`)
2. Tag the version
3. Build the release binary
4. Create the GitHub Release with source tarball
5. Update the Homebrew formula (source URL + SHA256 of tarball, plus `resource` block pointing to the current models release tag for the default model)
6. Push tag and formula

### `make convert-models` integration

After conversion (Phase 1), the output `.mlpackage` files land in `models/`. The developer then:
1. Runs `make convert-models` — produces `.mlpackage` files in `models/`
2. Inspects output quality (UT-001, UT-002)
3. Runs `make release-models` — uploads to GitHub Release, updates manifest
4. Commits manifest change

## Dependencies

- Phase 6 (issue #13) — on-demand download consumes the manifest

## Phases affected

This is cross-cutting infrastructure. It should be implemented alongside Phase 1 (model conversion), since that's when the artefacts first exist. The manifest becomes the input for Phases 5 and 6.

## Decisions

1. **Model directory**: `./models/` at repo root
2. **Archive format**: `.zip` with store-only (`zip -0`) — `.mlpackage` is a directory so needs a container for upload, but compression gains are negligible on neural network weights. Zero CPU cost.
3. **Manifest version**: Explicit `release_tag` field in `models/manifest.json`
