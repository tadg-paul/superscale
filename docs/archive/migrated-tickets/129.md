## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"when i click on a previous lock image, there is a check mark next to the last applied filter which implies a filter that is not appropriate to the currently displayed image"*

> *"perhaps when i start editing any prompt text, the check mark should be removed from the filter name too, to indicate that we are no longer applying one of the canned filter prompts"*

> *"'Showing filtered' - which btw should just be 'Filter' and never 'Original'. The change of wording on the toggle is confusing, the user will understand 'Filter' and that the button is a toggle. It should only be shown on an image that has had a filter applied to it."*

## Three related claims about what the interface says is selected

1. **Defect: the filter mark is not tied to the displayed picture.** Selecting an earlier iteration leaves the mark on whatever was last applied, which is a statement about a different picture.
2. **Change: an edited prompt clears the mark.** Guide 2.3 permits ad hoc editing and says edits are not saved and apply to that execution only. Once the text differs from the built-in filter, the mark asserts something untrue. The author offers this as *"perhaps"*, so it is a proposal to accept or decline rather than a settled requirement --- but it follows directly from what the mark means.
3. **Change: the comparison control reads "Filter" in both states, and appears only on a filtered picture.** This is UI copy and it is the author's own wording. The current control alternates between "Compare" and "Full View"; the author's objection is to wording that changes under the pointer.

## Interaction with the wider round

Claim three overlaps **#126** (the curtain cannot be dismissed and appears inconsistently), which governs when the control exists and what it does. This child owns **what it says**; #126 owns **when it is there and what it controls**. Neither may silently take the other's half; the audits must hold that line or the two will contradict each other.

Claim one is downstream of **#121** (current-image state has two owners): "the currently displayed image" is the question #121 gives a single answer to.

## Violated criteria

## Debugging and fix procedure

1. **Establish what the mark currently reads from.** The hypothesis is the selection state alone, with no reference to the displayed asset's provenance. `Provenance` already records `filterID` and `prompt` on a filtered asset, so the honest source is the asset, not the picker.
2. **Land after #121.** Until one component owns which asset is displayed, "the filter that produced this picture" has two possible answers.
3. **Decide claim two explicitly.** The author phrased it as a suggestion. Record the decision on this ticket rather than implementing a "perhaps" silently.
4. **Coordinate claim three with #126** before either is implemented. Agree which ticket changes the control's label and which changes its lifecycle, and write the split into both.
5. Guide 2.3's rule that selecting a filter is free and changes nothing else is unchanged; this is about reporting, not about behaviour.
