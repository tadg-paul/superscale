## Problem statement

Six of the 101 GUI tests fail because a raise to the filterable minimum cannot write its output. The picture is never raised, no candidate reaches the canvas, and the failure the user is shown names a `.png` as a missing *folder*.

`make test-gui`, 2026-08-26T03:31:05Z to 04:02:56Z, exclusive machine, display awake throughout: **Executed 101 tests, with 6 failures**, against a recorded baseline of 101 executed and 0 failures.

## Root cause

**The asset graph allocates output locations in a directory that nothing creates, and it has only ever worked because a different component created that directory as a side effect.**

1. `AssetGraph` holds `outputDirectory` (`Sources/SuperscaleUXCore/AssetGraph.swift:188,198-199`) and mints paths beneath it — `raised-<uuid>.<ext>` at line 271-272 for a raise, and the equivalent at line 393 for an upscale. **It never creates that directory.** `GenerationCoordinator` (`GenerationCoordinator.swift:109`) and `GenerationSessionStore` (`GenerationSessionStore.swift:90`) both call `createDirectory(at:withIntermediateDirectories:)` for theirs; the graph does not.
2. `MainView.swift:22` builds `WorkspaceState(outputDirectory: V2AppPaths.generated)`, which resolves to `~/Library/Application Support/Superscale/Generated` (`SuperscaleApp.swift:13-22`).
3. In an ordinary launch, `SuperscaleApp.swift:35` also builds `GenerationCoordinator(outputDirectory: V2AppPaths.generated)`, and *that* call creates the directory. The graph then finds it there. The dependency is invisible and unstated.
4. Under UI test, `SuperscaleApp.swift:55-71` replaces the coordinator with one whose store points at `<SUPERSCALE_UI_TEST_ROOT>/Generated`. **The side effect that created `V2AppPaths.generated` is gone**, and nothing else creates it.
5. Observed on this machine: `~/Library/Application Support/Superscale/` contains `compiled` and `models` and **no `Generated`**. So every raise allocates a path into a directory that does not exist, the write fails, and the subsequent read of `raised-<uuid>.png` throws `NSFileReadNoSuchFileError`, which Foundation renders as *"The folder … doesn't exist."* — the exact sentence RT-098.14 captured.

This also explains the baseline. A machine on which the app had ever launched normally would have the directory, and the suite would pass. The 0-failure baseline was not wrong; it was contingent on residue.

## Violated AC and the gap

No existing criterion covers this, and the underlying feature has an AC table, so this is path 2a of `ISSUES.md` §"Bug-fix issues reference existing ACs": **backfill onto the stage family introduced by #82.**

AC82.5 states *"A stage writes its output only to the location the graph allocated for it."* It constrains where a stage writes and says nothing about whether the graph's allocation is usable. The missing states are the complement, and they are proposed as backfills rather than restatements:

> **AC82.9** — The directory beneath which the graph allocates an output location exists at the moment of allocation, independently of any other component having been constructed.

> **AC82.10** — Where the output directory cannot be brought into existence, allocation fails at the point of allocation, naming the directory and the reason, rather than yielding a location that fails when a stage writes to it.

AC82.10 exists because AC82.9 alone admits the defect one layer along: an implementation that guarantees existence on the happy path and stays silent when creation fails still hands back a location that will fail at write time, which is what this ticket is about.

Consequential failures are already covered and need no new criteria — AC96.1 (the raise is performed and reported) and AC98.5 (a failure reaches the user through one surface) both fail downstream of this and are the criteria the six tests above hold.

## Fix procedure

1. **Reproduce deliberately.** Move `~/Library/Application Support/Superscale/Generated` aside with `trash`, launch the app normally, import a picture under 1024 pixels on its long edge, and apply a filter. Expect the missing-folder sentence. This confirms the defect is not confined to the test harness before anything is changed.
2. **Create the directory in the allocation methods, not in the initialiser.** The graph owns the allocation contract, so the graph ensures the directory — but `AssetGraph.init` is the wrong site despite being the obvious one. `AssetGraph` is `public` in `SuperscaleUXCore` and its initialiser is non-throwing (`AssetGraph.swift:198`), so creating a directory there means either making a public initialiser `throws` — a public API change, which `MAIN.md` §3 lists as a **mandatory architecture stop** — or swallowing the failure where it cannot be reported. `recordRaiseToMinimum` and the upscale allocation both already `throw`, so AC82.10's failure has somewhere to go and no public signature changes. Do it there.
3. **Do not fix this by making `MainView` create the directory.** That reproduces the invisible side-effect dependency in a new place, which is the actual defect.
4. **Do not fix it by pointing the graph at the coordinator's directory.** They are separate concerns that currently share a path by coincidence.
5. Re-run the six failing tests, then the full suite.

## Test plan

Package-level, over the allocation contract:

- RT-115.1: allocating a raise yields a location whose directory exists, **asserting the directory is absent immediately before the allocation and present immediately after**
- RT-115.2: the same for an upscale allocation, with the same before-and-after assertion
- RT-115.3: a stage writing to a freshly allocated location succeeds with no directory prepared by any other component
- RT-115.4: an existing output directory with assets already in it is not disturbed by allocation
- RT-115.6: where the output directory cannot be brought into existence, allocation throws rather than returning a location
- RT-115.7: that failure names the directory and carries the underlying reason, so a read-only location and a path already occupied by a file are distinguishable. Observed through the failure a caller actually receives, not through a string built for the assertion
- RT-115.8: allocation succeeds when the directory already exists and is writable, so the ordinary path is unchanged and the guarantee is not satisfied by throwing unconditionally

GUI-level, over the consequence:

- RT-115.5: with the real output directory absent beforehand, importing an undersized picture and applying a filter raises it, reports the raise, and puts a result on the canvas — **exercised through the application, not through the package**

**Why RT-115.5's layer is part of the specification and not an implementation detail.** This delivery's own verification ran `make test` to 533 executed, 6 skipped, **0 failures** while the application was comprehensively broken, because the package tests construct `AssetGraph` with directories they create themselves. A package-level RT-115.5 would prove the fix at precisely the layer that was already green. Guide section 7 has the sentence: *a package that is complete and a feature that is delivered are not the same claim.*

**Temporary state.** Every test above allocates its own per-run directory beneath the operating-system temporary directory and removes that exact directory in teardown, on success and on failure. None touches `~/Library/Application Support/Superscale`, and none uses the project-local `.agent/tmp` path the GUI suite currently uses.

**Ordering.** RT-115.5 runs in the GUI suite, which until #116 lands writes the workspace's assets into the user's real Application Support. **#116 is implemented before RT-115.5 is written**, so the test that proves this fix does not pollute real storage every time it runs.
