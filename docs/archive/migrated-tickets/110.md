## Original issue body

## Problem statement

**Observed (author, UT round of 2026-08-25, part of the UT-95.1 FAIL):** *"when
i add the api keys, the text box sizes change when i enter input and the layout
of the whole form jumps about."*

**Expected:** typing into a field changes the text in the field. Nothing else
moves.

## Violated AC

- **AC95.1** in [docs/ACs.md](../blob/master/docs/ACs.md): *"the whole scene
  reads cleanly"* — a form that reflows underneath the user's typing does not.

## Likely mechanism (unverified — verify before fixing)

Not yet diagnosed; logged before investigation per the SDLC. The usual SwiftUI
suspects, in the order worth checking:

1. **Conditional content appearing beside the field as state changes** — the
   checking spinner, the green check, or the status badge being inserted and
   removed rather than reserving space. Insertion resizes the `HStack`, which
   resizes the field, which reflows the `Form`. The classic fix is to reserve
   the space: fixed-size status slot (`.frame(width:)` on the badge container)
   or `.opacity(0)` placeholders, so state changes repaint but never re-lay.
2. **The field style itself** — a `TextField` in a `Form` with no
   `.textFieldStyle`/frame can negotiate width from its content; a
   `SecureField`/`TextField` swap (show/hide secret) can also differ in
   intrinsic size.
3. **Label column renegotiation** — macOS `Form` aligns label columns; a row
   whose label or trailing content changes width forces the whole column to
   renegotiate, which reads as the form "jumping about".

## Debugging and fix procedure

1. Reproduce with slow deliberate typing and watch *which* element moves
   first — that names the mechanism above. A screen recording frame-stepped
   beats reasoning here.
2. Apply the narrowest fix from the diagnosis (reserved status slot is the
   most likely), touching layout only — no behaviour changes ride along.
3. Regression: GUI test typing into each credential field and asserting the
   field's frame is identical before, during and after (the frame-stability
   assertion pattern RT-90.52 already established for the canvas — reuse its
   shape).
4. UT-95.1 re-offer with the author judges the result; the RT keeps it.

## Test plan

- RT-110.1: the credential field's frame is unchanged while text is entered
  and while the checking/verified state changes
- RT-110.2: no sibling row's frame changes when one row's status changes


## Mechanism, identified 2026-08-27

The first suspect was right and the other two are set aside, inspected rather than deleted.

`SettingsView.swift:189-205` ends each credential row's `HStack` with either a `ProgressView` or the status badge, chosen by `isChecking`:

```swift
if isChecking {
    ProgressView().controlSize(.small)
} else {
    credentialStatusBadge(for: status)
}
```

The two have different intrinsic widths. Every state change therefore resizes the `HStack`, which resizes the `TextField` carrying `minWidth: 260`, which makes `LabeledContent` renegotiate the form's label column. That is the whole of *"the layout of the whole form jumps about"*.

**Set aside:** the field style is explicit (`.roundedBorder`) with a stated `minWidth`, and there is no `SecureField`/`TextField` swap since #95 made the key legible. Label-column renegotiation is a *consequence* here rather than an independent cause.

## Criterion

Nothing in the #95 family covers layout stability, so this is a backfill under path 2 of `ISSUES.md` §"Bug-fix issues reference existing ACs".

| ID | AC | Tests |
|---|---|---|
| AC95.6 | A credential row's controls occupy the same space whatever the row's state, so entering text, saving, checking and the result of a check change what the row says and never what it measures. | ⏳ RT-110.1: the row's frame is unchanged between empty and filled<br>⏳ RT-110.2: the row's frame is unchanged between the checking state and each settled state<br>⏳ RT-110.3: the form's other rows do not move while one row changes state |

**Key:** ✅ passing · ⏳ pending · ❌ failing · ~~🚫 removed~~

The criterion covers the checking state as well as typing. The author's words are about typing, but the widest movement is the spinner appearing and disappearing around a provider check, and a criterion written only about keystrokes would leave the larger one unspecified.

## Solution

Give the status area a fixed-width slot so the row's width cannot depend on its state. The spinner and the badge occupy the same reserved space; only what is drawn inside it changes.
