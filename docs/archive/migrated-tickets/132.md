## Problem statement

**Observed by the author, 2026-08-27:**

> *"when i go back to a previous lock image, generate something new, click lock, all locks to the right disappear: this should not happen. it makes it completely unreliable now. This is a regression."*

## This is a regression introduced by #121, and it was a decision I made without asking

`AssetGraph.lock()` was changed to advance the tip:

```swift
baseID = candidateID
// Lock is the only thing that advances the tip. Locking after a selection therefore
// abandons whatever was forward of it, which is the honest outcome: the user has chosen to
// build from an earlier point, and the chain now records what they built.
tipID = candidateID
```

The chain is read from the tip's lineage, so locking after a selection leaves every later iteration outside it. They are still in the graph; they are unreachable from the strip.

**The comment calls it "the honest outcome". It is not.** It destroys work the author has paid the provider for, and it was recorded in a commit message rather than put to the author as a decision — which `MAIN.md` §1 requires for anything that changes user-visible behaviour of this consequence. The author's judgement is the one that counts and it is unambiguous.

## The model change, accepted by the author

**The strip holds every locked iteration, in the order it was made, rather than one lineage.**

Branching from an earlier point therefore **adds** to the chain instead of replacing its tail. Nothing a user has locked is ever removed except by importing a different picture, which AC89.8 already governs.

The lineage in the graph is unchanged and still records what descends from what. What changes is that the strip is no longer derived by walking it.

## Violated criteria

- **AC89.3** in [docs/ACs.md](../blob/master/docs/ACs.md): *"Every locked iteration remains reachable."* Locking after a selection makes later iterations unreachable, which is the same failure #111 fixed and #121's own audit caught in a different form — arriving a third time, by the route the audit did not check.
- **AC89.9**, introduced by #121: selecting an iteration restores the working context it was made in. That criterion is unaffected; only what happens on the *next* lock is wrong.

## Debugging and fix procedure

1. **Reproduce and record which assets leave the strip**, by identifier rather than by count, so the test that follows asserts the right thing.
2. **Hold the chain explicitly** rather than deriving it: an ordered list of locked assets, appended by `lock()`, seeded by the import, and extended by a promoted raise so the strip keeps showing what it shows today.
3. **The tip becomes the last entry of that list**, so returning to the newest iteration is unchanged.
4. **Do not touch the lineage.** `parentID` still records what descends from what, and I2, I3 and I7 are unaffected. Only the strip's derivation changes.
5. **AC89.3's note must be corrected**: it now says reachability is from the tip, which this supersedes.

## Test plan

- RT-132.1: locking after selecting an earlier iteration leaves every previously locked iteration in the chain
- RT-132.2: the newly locked result joins the chain and is the one shown
- RT-132.3: the new iteration's lineage still records the selected point as its parent
- RT-132.4: importing a different picture still empties the chain (AC89.8)
- RT-132.5: returning to the newest iteration still reaches the most recently locked one
- UT-132.1: work back and forth across a chain and judge that nothing is ever lost
