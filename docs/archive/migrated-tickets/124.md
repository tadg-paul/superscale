## Original issue body

## Problem statement

**Requested by the author, user-test round of 2026-08-27:**

> *"When I reapply a FAL filter it costs real money. We should be caching all generated photos within a session at least. The selected model and prompt text (even if edited) along with original photo should generate a hash, that would give us a definitive key for cases where we select a previous lock image and apply the same filter."*

## This is a new requirement

Guide section 2.3 establishes that selecting a filter is free and applying one is paid, and that the two-step interaction exists precisely so exploration does not cost money. It does not say a repeated identical application should be free. Nothing in the specification covers it.

The case the author names is real and reachable in ordinary use: select an earlier locked iteration, apply the same filter you applied before, and the provider is paid again for a result already held. Once #121 (current-image state has two owners) makes selecting an iteration a normal working state, that path becomes common rather than incidental.

## The key

The author's specification: **source asset, model, and prompt text as sent** --- including any ad hoc edit, since guide 2.3 allows the text area to be edited per execution.

Points the audits must settle rather than assume:

- Whether the key covers only the current session or persists. The author said *"within a session at least"*, which is a floor, not a ceiling. Persisting it raises questions about disk growth and about a stale result outliving a provider-side model change; recommend session-scoped for this delivery and record the reasoning.
- Whether a cache hit is visible to the user. A paid action completing instantly, with no charge, is a good surprise only if the interface says why. The status bar already carries the reduction and raise notices on an unobtrusive channel.
- What the hash covers exactly. Prompt text must be compared as sent, after any trimming the request builder performs, or an invisible whitespace difference produces a miss and a charge.

## Acceptance criteria

To be drafted and audited. In outline:

- Applying a filter whose source asset, model and prompt text match a result already held in the session presents that result without a provider request.
- Any difference in source asset, model or prompt text produces a request.
- A held result is attributed to the same source asset it was produced from, so it can never be presented against a different picture.

## Debugging and fix procedure

1. This is new behaviour, so there is nothing to reproduce. Begin with the failing tests.
2. **Land after #121** (current-image state has two owners). The cache is keyed on the source asset, and until there is one owner of what "the source asset" is, the key is computed from a value two components disagree about.
3. Keep the key's construction in one named function with the prompt normalisation visible. A hash assembled at the call site is a hash nobody can reason about when it misses.
4. `Provenance` already records `filterID`, `modelID` and `prompt` against a filtered asset. Establish whether the cache can be a read of the graph rather than a second store; a second store is a second place the truth about a result lives.
5. Secrets never enter the key. `Provenance.prompt` is documented as redacted of any supplied secret, and the same must hold here.

## Test plan

- RT-124.1: applying an identical filter to the same source asset issues no provider request and presents the held result
- RT-124.2: an edited prompt against the same source asset issues a request
- RT-124.3: the same prompt against a different source asset issues a request
- RT-124.4: a held result is never presented against a source asset it was not produced from
- RT-124.5: a whitespace-only difference in prompt text is treated as identical, matching what is actually sent
- UT-124.1: re-apply a filter already applied in the session and judge that the result is immediate and no charge is implied

A parallel store keyed on a hash would be a second place the truth about a result lives, and the two would drift — which is the shape #100 and #103 each found and removed from this codebase.
