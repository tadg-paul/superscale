## Original issue body

Child of delivery master #139 (the 2026-08-31 user-test round).

## Problem statement

**Observed by the author, second raising:**

> *"before we clear any images with cmd+o (or cmd+n) we should warn the user any images not saved will be lost. it is up to the user to go and save them, but let them go back and cancel and save manually. (2nd time raising)"*

And, on Cmd+N specifically:

> *"*if* and only if there are any unsaved lock images then warn first and allow to cancel."*

## This reverses a criterion I wrote

**AC135.8 currently says the opposite**, and I wrote it:

> *"A clear takes effect immediately and asks for no confirmation, on the same terms as the import in AC89.8, and an unsaved result goes with it."*

I recorded that as **DECISION D-5**'s neighbour, reasoning that AC89.8 already discarded on import
without prompting so there was precedent. **The author had already raised this once at that point.**
I wrote the criterion that made his request wrong instead of the code that made it right, which is
the more expensive kind of mistake because it then reads as intentional.

The author has confirmed the reversal and granted authority to amend. **AC135.8 is being amended,
not worked around.**

## What "unsaved" means, and it is a real question

The warning must fire *"if and only if there are any unsaved lock images"*. So the condition has to
distinguish a locked iteration that has been written to disk from one that has not.

**Chosen definition:** a locked iteration counts as unsaved when no `Save As` has written it during
this session. The graph holds every locked asset and the application knows what it wrote. A false
positive nags; a false negative loses work --- so where the two cannot be told apart, warn.

**This is recorded as a decision for validation at the exit gate**, per the author's standing
authority, rather than blocking the round on a question.

## Where it applies

Three routes clear the picture, and the author named two of them:

| Route | Warn? |
|---|---|
| **Cmd+N** (#144) | Yes --- he said so explicitly |
| **Cmd+O** / File ▸ Open Image | Yes --- he said so explicitly |
| **The Clear Image control** (#135) | **Yes.** He did not name it, and it is the same act by a third door. A warning that fires on two of three routes is worse than none, because it teaches a habit that then fails |

Drag and drop is deliberately **excluded**: it is a deliberate act on a specific file and interposing
a dialogue there would make the primary import route hostile. Recorded as a decision.

## Violated criteria

- **AC135.8**, which says no confirmation. **Being amended.**
- **AC89.8**, that an import starts a new chain and discards the previous one. Unchanged as a rule;
  what changes is that the user is asked first.

## Test plan

- RT-WARN.1: with unsaved locked iterations, clearing raises a warning naming what will be lost
- RT-WARN.2: cancelling the warning leaves the picture, the chain and the candidate untouched
- RT-WARN.3: confirming the warning clears, exactly as before
- RT-WARN.4: with **no** locked iterations, no warning is raised and the clear is immediate
- RT-WARN.5: with every locked iteration saved this session, no warning is raised
- RT-WARN.6: the warning appears on Cmd+O and on Cmd+N, not only on the Clear control
- RT-WARN.7: dragging a new picture in raises no warning
- UT-WARN.1: build a lock chain, press Cmd+N, cancel, save, press Cmd+N again; judge that nothing was lost and the warning did not nag

*Identifiers are placeholders until this issue has its number.*


## Acceptance criteria

- **AC143.1** Where any locked iteration has not been saved this session, an action that would discard it asks first and names how many are at stake.
- **AC143.2** Cancelling that question leaves the picture, the lock chain, the candidate and the filter selection exactly as they were.
- **AC143.3** Confirming it proceeds with the action that was asked for, whether that was clearing or opening another picture.
- **AC143.4** Where every locked iteration has been saved, or there are none, no question is asked and the action happens immediately.
- **AC143.5** The question is asked by every route that would discard the chain --- the Clear Image control, Cmd+N and Cmd+O --- and by none that would not.
- **AC143.6** A locked iteration counts as saved once it has been written to disk during this session while it was the picture on display.

## Amendment to AC135.8

**AC135.8 said the opposite and is superseded by AC143.1 and AC143.4.** Its original wording:

> *"A clear takes effect immediately and asks for no confirmation, on the same terms as the import in AC89.8, and an unsaved result goes with it."*

I wrote that, citing AC89.8's precedent for discarding without a prompt --- **after the author had
already raised this request once.** The criterion made his ask read as contrary to the specification
rather than as a correction to it, which is the more expensive kind of mistake because it then looks
intentional.

What survives from AC135.8 is the immediacy where nothing is at stake, which is now AC143.4.

- **AC143.7** Dragging a picture onto the canvas raises no question, because it is a deliberate act on a chosen file and the primary import route must not be made hostile.

### What this issue delivers, in plain language

Work the user has paid a provider for stops disappearing without being mentioned. Clearing the
canvas, pressing Cmd+N or opening another picture now asks first --- but only when there is actually
something unsaved to lose, so a user who has saved everything, or made nothing, is never nagged.

### Evidence

- The author's words, twice: *"before we clear any images with cmd+o (or cmd+n) we should warn the
  user any images not saved will be lost... let them go back and cancel and save manually"*, and
  *"if and only if there are any unsaved lock images"*.
- **AC135.8**, which I wrote, says the opposite. Amended above.
- `UpscaleViewModel.saveAs` --- the one save path, reached by both the toolbar and the File menu.
- `MainView.swift:44` --- `WorkspaceState` is owned by the view, not the scene, which is why the
  menu commands send requests.

### Edge cases

- **No locked iterations at all.** The commonest case, and it must be silent. AC143.4.
- **Locked iterations, all saved.** Also silent, and it is the case that makes the feature bearable
  rather than irritating. AC143.4.
- **Cancel then save then clear.** The second clear must be silent, which follows from AC143.6.
- **Cancel** must be genuinely inert --- not "clear anyway after a delay", not partially reset.
  AC143.2 states it as a system state.
- **The same warning for two different actions.** Cancelling an open must not clear, and confirming
  a clear must not open a panel. AC143.3 covers it.

### Quality self-audit

Six criteria. Each describes a system state. **AC143.6 is a definition rather than a behaviour** and
I considered removing it --- but "unsaved" is the load-bearing word in every other criterion here, and
leaving it undefined is how the first implementation and the first test disagree.

Totals: **1 missing AC, 1 edge-case gap, 0 quality violations.**

### Findings

- **F1 blocker.** Nothing covers **drag and drop**, which also replaces the working picture and
  therefore also discards the chain. AC143.5 lists three routes and drag is a fourth. It must either
  be in the list or explicitly excluded, because silence there is how the fourth report arrives.
- **F2 edge case.** Nothing says what happens if the user **quits** with unsaved iterations. Out of
  scope --- the master's exclusions have carried save-on-quit prompting since #79 --- but it should be
  named as excluded rather than left as an oversight.

### Remediation

- **F1:** add **AC143.7** --- dragging a picture in raises no question. It is a deliberate act on a
  chosen file, and interposing a dialogue would make the primary import route hostile. Recorded as a
  decision rather than an omission.
- **F2:** no criterion. Recorded on the master as still excluded, unchanged from #79.
