## Original issue body

Child of delivery master #79. Reported from use, 2026-08-25.

## Problem

**The toolbar says one thing and the application does another.**

Two reports, one theme: a control that reports a setting the user chose rather than the state the application is actually in.

- **After a reduction the scale control still reads 4x.** The author: *"when i drop in a large image, i get the warning telling me it will only show original size. But the UX buttons are not changed, it indicates to the user a 4x upscale is active when it is not."* The message in the status bar and the highlighted button contradict each other, and the button is the more prominent of the two.
- **The face-enhancement control is live with no upscale selected.** The author: *"face button should disable as soon as an upscale is toggled off actually, as it is meaningless without the upscale: that is a new requirement."*

## This corrects a criterion of mine, and the reasoning that produced it

**AC83.7**, migrated 2026-08-25 by #91, says the reduction is reported *"while the scale selection continues to show what was asked for."* I wrote that clause and defended it at the second AC audit on #91, reasoning from **AC82.8** — a scale selection persists until the user chooses a scale, and importing an image, changing the model and editing the custom dimensions all leave it alone — that a reduction rewriting the control would have the application change the user's choice on their behalf.

That reasoning was wrong, and the audit that accepted it was wrong with it. AC82.8 protects the user's *choice* from being silently replaced. It does not license the control to misreport what is happening. A button lit at 4x while 1x is running is not a preserved choice; it is a false statement about the current state, and the status-bar message that contradicts it is the quieter of the two.

The distinction the criterion needs is between what was asked for and what is in effect. Both are worth showing. Only one may be shown as though it were the other.

### Condition enumeration

- **AC93.1** implies seven conditions, the last raised by the second AC audit: **a scale shown as not in effect is still choosable.** The natural way to render "not in effect" is to dim it, and dimmed reads as disabled — so an implementation could satisfy every other condition while trapping the user at the reduced scale until they imported something else. Six others: the effective scale is what reads as active, the requested scale is still legible so the user can see what they asked for, the ordinary case shows one scale only, the custom dimension fields obey the same rule, the truth is shown before any upscale completes, and a picture that fits at no scale lights nothing. The third matters because a design that always showed two states would be noise on every upscale that needed no reduction.

  **The fourth and fifth were found by the AC audit and are the substance of it.** The custom fields carry the identical defect: a user who typed 10000 by 5000 and got 5657 by 2828 has two fields reading something that is not happening, in the place they are most likely to be checking. And `UpscaleDecision` is returned by `GUIUpscaleCoordinator.process`, so an implementation reading the reduction from the *result* would show 4x, run, then correct itself to 2x — still wrong while the user was looking at it. `UpscaleCeiling.decide` is a pure function of the source size and the request, so the truth is available the moment the picture's dimensions are known and the control never has to correct itself.
- **AC93.2** implies two: the choice survives, and it survives *usefully* — a smaller picture later runs at the scale originally asked for, without the user having to notice and reselect. This is what AC82.8 was actually protecting, separated from the display question it was wrongly used to settle.
- **AC93.3** implies five: **every** face control disabled with no scale, enabled with one, the reason available, and the face model still obtainable. **There are two controls**, which the third AC audit found: the toolbar button at `MainView.swift:420` and `faceEnhanceRow` at `ModelPicker.swift:86`, both toggling the same `faceEnhance` binding. Disabling one would leave a user with the scale off looking at a dimmed button in the toolbar and a working toggle one sheet away, setting a value that does nothing — worse than the reported defect, because it looks deliberate. The third is the difference between a control that looks broken and one that explains itself. The fourth is a consequence the AC audit caught arriving as a side effect: this button currently opens the model-download sheet when GFPGAN is absent, so disabling it removes that route. It stays closed here and the upscale-model sheet keeps it open — decided rather than inherited, because a download flow disappearing silently is how a feature goes missing.

  **The first remediation of this named the wrong surface.** It said Settings, which has no download flow at all: `FaceModelDownloadView` is presented from `MainView.swift:448`, the button being disabled, and from `ModelPicker.swift:118`, the upscale-model sheet. Caught at the second AC audit. Had it gone through, it would have produced either a Settings route nobody asked for or a test asserting something false.

### What this does to AC83.7

**AC83.7's clause "while the scale selection continues to show what was asked for" is superseded by AC93.1.** The rest of AC83.7 — the area ceiling, the reduction to the largest that fits, the proportional reduction of a custom target, the refusal when nothing fits, and the minimum long edge being unaffected — stands unchanged and its tests continue to hold. RT-91.2's second assertion, that the selection still holds what was asked for, is superseded by RT-93.2 and RT-93.5, which separate the stored selection from the displayed state.

## Solution

**The toolbar reads an effective scale, not a selection.** `UpscaleDecision` carries `requested`, `sizing` and `wasReduced`. What is missing is that nothing shows it. The scale buttons take their active state from the decision when one exists and from the selection otherwise, and the requested scale is drawn in a distinguishable weight when the two differ. The custom dimension fields follow the same rule.

**`ScaleReadout` is where it is computed.** A function in `SuperscaleUXCore` taking the source size, the scale selection and the custom dimensions, returning what reads as active, what is marked as requested but not in effect, and what the dimension fields show. The toolbar renders it and decides nothing itself. Introduced by the test audit, which found that seven of the first plan's tests would each have run a ceiling-sized upscale in the GUI suite to assert a fact about two integers.

**The decision is computed, not awaited.** `GUIUpscaleCoordinator.process` returns it, which invites reading it from the result — and that would show 4x, run, then correct itself to 2x, which is the reported defect in miniature. `UpscaleCeiling.decide` is a pure function of the source size and the request, so the view model computes it whenever either changes and the control is never wrong to begin with. The coordinator's returned decision remains what the notice message renders, because that describes a run that happened.

**The stored selection is untouched**, which is what makes AC93.2 hold for free: `ScaleSelection` continues to hold what the user chose, and only the presentation consults the decision.

**The face control is disabled when `scaleSelection.isOff`,** with a help string explaining why. Face enhancement is a stage of the upscale pipeline; with no upscale there is no stage.

**AC93.3's implementation is already committed**, at `2ac025e`, alongside two regression fixes reported in the same message. That is the child lifecycle out of order — the code preceded the issue and its audits — and it is recorded here rather than tidied away. The audits below cover it as landed work, as they did for #90.

## Test type and location

All fifteen are regression tests.

**What the toolbar shows is a function, and that is where these live.** `ScaleReadout` in
`SuperscaleUXCore` takes the source size, the scale selection and the custom dimensions, and returns
which scale reads as active, which is marked as requested-but-not-in-effect, and what the dimension
fields display. Every state this issue describes is then two integers rather than a photograph:
RT-93.1, RT-93.2, RT-93.3, RT-93.9, RT-93.10, RT-93.11 and RT-93.14 are package tests in
`Tests/SuperscaleUXCoreTests/UpscaleCeilingTests.swift`'s neighbouring file, alongside RT-93.4 and
RT-93.5 over `ScaleSelection`.

**This is the same move `CurtainGeometry` made** for the divider earlier in this delivery, and for
the same reason: the arithmetic was never the risk, the view feeding it the wrong inputs was.

**Why not the window.** The first plan put seven of these in `SuperscaleAppUITests`, which the test
audit rejected. Their states only arise when the ceiling bites, needing a source of at least eight
megapixels and, for the refusal case, over thirty-two — each a larger upscale than the one already
rejected as too slow, in a suite that is a gate and already runs about eight minutes, with a
multi-megabyte fixture committed for one assertion about a button. `toby-small.jpg`'s own header
records that judgement being made once already.

**GUI, in `SuperscaleAppUITests`:** RT-93.6, RT-93.7, RT-93.8, RT-93.12 and RT-93.13, which concern
control enablement at the existing small fixture and cost nothing; plus **one** wiring test,
RT-93.15, asserting that the toolbar's active scale comes from `ScaleReadout` rather than from the
selection, and that it is correct while an upscale is still in flight. That single test is what
stops the rule being right and unused, which is the fault this delivery has now found three times.

**No large fixture is added.**

**The scale controls gain an accessibility value**, carrying active, requested-but-not-in-effect, or
inactive, set from `ScaleReadout`. Without it RT-93.15 cannot be written at all: `ScalePicker.swift:34`
expresses the active scale as `.tint(...)` and `:35` as a `.help(...)` string, and neither reaches
the accessibility tree, so a test could find `scale4x` and click it while being unable to tell
whether it was the active one. It would have asserted the button exists — which it always does — and
passed against the broken implementation.

This is the third time in this delivery that a criterion has pointed at a state expressed only as
colour: `refreshAccountButton` in #88, the curtain divider in #90, and now this. The value goes on
the control itself, per implementation guide 3.9's rule that an identifier on a container absorbs
its children.

**One user test is allocated:**

> ⏳ UT-93.1: with a reduction in force, the toolbar reads unambiguously

Whether two states shown at once are *clear* rather than merely both present is a judgement. The author has now failed two user tests on presentation, and this issue exists because a criterion I wrote read well and misled in use.
