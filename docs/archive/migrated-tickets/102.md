## Original issue body

Child of delivery master #99. Closes finding 3, recorded on #92 during the v2 MVP delivery.

## Problem

`MainView.submitFilter` is `@MainActor`. Before handing a picture to the provider it calls `Data(contentsOf: asset.fileURL)`, which is **synchronous disk I/O on the thread drawing the window**, every time Apply is pressed. For a 32-megapixel PNG that is tens of milliseconds during which the interface cannot redraw.

That is the whole of the cost, and it is worth saying so. An earlier draft of this issue claimed the picture was also resident twice in memory. **It is not:** Swift's `Data` is copy-on-write, so passing it as a parameter and assigning it to `httpBody` duplicate nothing while neither is mutated, and neither is. The picture is resident once today and will be resident once afterwards. An issue claiming two benefits and delivering one justifies more risk than it should.

**This is pre-existing rather than introduced.** The function it replaced, `dataURL(for:)`, performed the same read in the same place *and* base64-encoded the result, so the current path is strictly less work on that thread than the one before it. What changed is that the encoding went, not that the read arrived.

It was recorded rather than fixed during #92 because the correction is not local: `GenerationServing` is `@MainActor`, so moving the read behind it means either changing that annotation or changing what the method takes.

## Solution

**`uploadReference` takes the file's URL rather than its bytes.**

The read then happens inside `FalStorageClient`, which is `Sendable` and not main-actor-bound, on the cooperative pool rather than on the thread drawing the window. The whole picture is held once rather than twice, because the bytes go straight from the read into the request body without a main-actor round trip.

This is the correction recorded on #92 and it is the smaller of the two options. Changing `GenerationServing` off `@MainActor` would touch every conformance, including the coordinator's published state, and buys nothing this does not.

**The stub conformances change with it.** Four test doubles and the UI-test service implement `uploadReference`; each takes a URL instead of `Data`. The UI-test service already ignores the payload entirely, so it is unaffected in substance.

**What does not change:** the reference is still uploaded afresh on every apply, the credential still travels only in a header, and an upload that fails still leaves no partial reference behind. Those are AC92.3, AC92.6 and AC92.5, all already covered, and this issue must not disturb them.

## Acceptance criteria

This is a bug-fix issue against existing criteria and introduces no new AC table. It cites:

- **AC92.1** in `docs/ACs.md`: *"A filter's reference reaches the provider as a URL that the provider itself issued, and no request body carries image bytes."*
- **AC92.5** in `docs/ACs.md`: *"An upload that fails is reported against the filter stage, and the base and any candidate survive it."*

- **AC92.6** in `docs/ACs.md`: *"The credential used for upload is the generation key, and it appears only in a request header."*

This issue carries no AC table, and the reason has two halves. It mirrors AC98.5 in the previous delivery.

**The purpose is structural.** "The read does not occur on the main actor" is a fact about where code runs. A test asserting it would have to measure main-thread occupancy, which is timing-dependent and flaky, and establishing it by reading source is what `TESTING.md` forbids outright. It is confirmed by `audit-code`, which is where facts about the code's shape are properly checked.

**The safety is regression coverage.** The three criteria above describe behaviour that must continue to hold across a signature change, and RT-102.1 to RT-102.5 prove that it does. That is path 1 of `ISSUES.md` §"Bug-fix issues reference existing ACs": existing criteria, existing coverage, extended.

### Why four

**RT-102.1** is the substitution itself: passing a URL must send the same bytes that passing `Data` did. Without it the change could silently send something else.

**RT-102.2 is the new failure mode this introduces.** Reading `Data(contentsOf:)` at the call site meant an unreadable file threw before the upload began. Moving the read inside means the upload must now handle it, and the wrong implementation sends a zero-byte body and lets the provider reject it — which costs a round trip and produces a provider error for a local problem.

**RT-102.3** carries AC92.5's guarantee across the change. The dangerous shape is unchanged: the initiate exchange returns a `file_url` before the bytes are sent, so an implementation returning it after a failed read would hand the provider a URL with nothing behind it.

**RT-102.4** pins AC92.6 across the signature change, because a refactor that rebuilds the request is exactly where a credential leaks into a URL by accident.

**RT-102.2 asserts that no transfer was attempted**, not merely that an error was thrown. An implementation that initiates the upload, fails to read the file, and still sends a zero-byte PUT before throwing would satisfy the weaker assertion — while having handed the provider an empty file at a URL it issued. The stubbed transport already records every request, so the stronger form costs nothing.

### Read once: a structural claim, not a test

The first AC audit found the gap and the first test audit found that it cannot be closed by a test. `upload` needs the bytes twice — once for `contentType(of:)` to sniff the format, once for the request body — and taking a URL, the obvious implementation reads for each use, **doubling the disk I/O this issue exists to reduce** while every assertion above still passes.

It cannot be observed from outside. Counting reads needs the file system instrumented; the file cannot be altered mid-call from a test's side; and a named pipe, the one construct that would make a second read deterministically fail, would **hang** the test rather than fail it.

So the design carries it instead: **`upload` reads the URL once into a local, and passes those bytes to both `contentType(of:)` and `put`.** A double read cannot then occur by construction. `audit-code` confirms it, which is where a fact about the shape of the code belongs — the third such claim in this delivery, after AC98.5's single failure surface and this issue's own main-actor property.

### The integration guarantee is the compiler

No integration test is proposed, and that is deliberate rather than an oversight. `uploadReference` is a protocol requirement and `upload` is public API: **after the signature change no caller can keep passing `Data` and still compile.** Four test doubles and the UI-test service must change with it. That is a stronger guarantee than a test, and it is the same argument AC98.5 used for making `errorMessage` `private(set)`.

## Test type and location

Four regression tests in `Tests/FalGenerationKitTests/FalStorageClientTests.swift`, beside the existing upload coverage, against the stubbed transport already used there. No test reaches the network and none reaches a paid endpoint. RT-102.5's identifier is retired and not reused.

All four are RT: machine-verifiable, guarding ongoing behaviour, invoking no build system.

**These tests newly require files on disk.** The existing coverage builds its PNG in memory through `pngData()`; a URL-taking API has nothing to give it but a path.

Fixtures are written into a per-run directory obtained from `FileManager.default.temporaryDirectory`, and that exact directory is removed in `addTeardownBlock` on success and failure alike, never a shared parent. Each is a few kilobytes against the 100 MiB limit in `TESTING.md`.

No user test. Nothing a user sees changes; the interface is expected to stop stuttering on a large picture, which is not a judgement worth asking for.

# Code audit: #102

**Verdict: FINDINGS** — 0 blockers, 2 smells, both introduced and both with concrete fixes.

## Files reviewed

- `Sources/FalGenerationKit/FalStorageClient.swift`
- `Sources/SuperscaleUXCore/GenerationCoordinator.swift`
- `SuperscaleApp/SuperscaleApp/MainView.swift`
- `SuperscaleApp/SuperscaleApp/SuperscaleApp.swift`

## The structural claim this audit exists to confirm

**Read once, used twice: confirmed.** `FalStorageClient.swift:96-109`. `data` is read at line 98 and used at 103 for the content-type sniff and at 109 for the transfer. A second read cannot occur without adding one.

**The read is off the main actor: confirmed, with a caveat below.** `FalStorageClient` is a `Sendable` struct carrying no global actor, so `upload` is a non-isolated `async` function. A non-isolated async function called from a `@MainActor` context runs on the generic executor rather than the caller's actor, so the read leaves the main thread even though `GenerationServing.uploadReference` is `@MainActor`.

**Nothing is sent before the read succeeds: confirmed.** The read is the first statement; `initiate` is not reached on failure, so the provider cannot be left holding a URL with nothing behind it. RT-102.2 asserts it from outside.

## Standards

**The original defect was already prohibited.** `SWIFT.md` §"SwiftUI and Apple UI Code" says *"Do not hide networking, persistence, or process execution inside views."* Reading a file in `MainView` is persistence in a view. The standard existed, the code predated nobody noticing, and it took a code audit on a different issue to surface it.

`ABOUTME:` headers intact. Doc comments explain why rather than what. No function over 50 lines; `upload` is 16 with one level of nesting.

## Findings

### Smell: the underlying read failure is discarded

`FalStorageClient.swift:97-101`

```swift
do {
    data = try Data(contentsOf: fileURL)
} catch {
    throw FalStorageError.unreadableFile(fileURL.lastPathComponent)
}
```

The caught `error` is thrown away. `SWIFT.md` §"Error Handling" requires: *"Preserve context when mapping errors."*

A user whose file was deleted and a user whose file they lack permission to read receive the identical sentence, *"That file could not be read: photo.png"*. The second needs to know it is a permissions problem; the first needs to know the file is gone. Both are told the same unhelpful thing, and the information to tell them apart was in hand and dropped.

**Recommended fix:** carry the reason. `case unreadableFile(name: String, reason: String)`, populated from `error.localizedDescription`, rendered as *"That file could not be read: photo.png — <reason>"*. The path is already reduced to `lastPathComponent`, so nothing about the user's directory structure leaks either way.

### Smell: the off-main-actor guarantee is undefended

The whole point of this issue holds because `FalStorageClient` carries no global actor. **Nothing says so, and nothing would notice if it changed.** Someone marking the type `@MainActor` — for a plausible reason, such as touching published state — silently reverts the fix, every test still passes, and the window starts freezing again.

This is the same shape as the delivery's recurring finding: a property that is real, load-bearing, and invisible to everything automated.

**Recommended fix:** state the requirement at the type's declaration, not only at the method's — that `FalStorageClient` must remain non-isolated, and why. A comment is weak defence, but it is the defence available: Swift offers no way to assert "this type has no global actor" from a test.

## Error handling

Every other path is sound. `initiate` and `put` propagate typed failures with the provider's diagnostic preserved and redacted. No suppression patterns: no `try!`, no empty `catch`, no `|| true` equivalent. The one `catch` that discards is the finding above.

## Security

**The credential's handling is unchanged and still correct.** RT-102.4 asserts it across both exchanges: header only, absent from every URL and body. The signature change rebuilds no request, so there was little exposure, but a refactor touching request construction is exactly where a credential leaks and the test is right to exist.

The error message uses `lastPathComponent` rather than the full path, so a diagnostic surfaced to a user or a log does not disclose their directory structure. Deliberate and worth keeping through the recommended fix.

## Complexity

Reduced at the call site: `MainView.submitFilter` loses a `Data(contentsOf:)` and a local. `upload` gains four lines.

## Documentation impact validation

Reviewed `docs/FAL_REQUEST_REFERENCE.md`, `IMPLEMENTATION_GUIDE_v2.md` sections 3.6 and 6, and `docs/ACs.md`.

- **`FAL_REQUEST_REFERENCE.md` needs nothing.** It documents the wire protocol — initiate, then PUT to the returned address — which is unchanged. Nothing in it describes the Swift signature.
- **The guide needs nothing.** Section 3.6 describes what a request carries, not how the bytes reach it. `SWIFT.md` §"SwiftUI and Apple UI Code" already prohibits the original defect, so no new project rule is warranted; adding one would restate a standard that is already binding.
- **`docs/ACs.md` needs no edit.** AC92.1, AC92.5 and AC92.6 describe behaviour that is unchanged; this issue extends their coverage rather than altering them.

## Remediation

1. Carry the underlying reason in `FalStorageError.unreadableFile`.
2. State at `FalStorageClient`'s declaration that it must remain non-isolated, and why.
