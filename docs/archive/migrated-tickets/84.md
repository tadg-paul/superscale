## Original issue body

Child of delivery master #79 (slice 3, second of two). Follows #83 against the same quality gate.

## Problem

**Every upscale loads the model from scratch.**

`SuperscaleGUIUpscaleProcessor.process` constructs a fresh `Pipeline` on each call (`GUIUpscaleCoordinator.swift:150`), and `Pipeline.init` constructs a `CoreMLInference`, which loads and compiles the model. Nothing is kept.

That cost is not incidental. `IMPLEMENTATION_GUIDE_v2.md` section 2.5 puts it at "roughly three seconds of model load plus processing", and it is paid on every run — and upscaling is reactive, so a run happens whenever the scale changes, the model changes, face enhancement is toggled, or a custom dimension settles after its debounce. Nudging a slider from 4x to 8x reloads the same model that was loaded a second earlier.

**And a shared pipeline would not be safe today.** `Pipeline` is a class with mutable `onProgress` and a `CoreMLInference` holding Vision request state. Two runs sharing one instance would race on both: progress from one run delivered to the other's observer, and concurrent use of a request object that does not expect it. Reuse and confinement are the same change — the reason nothing is kept is that keeping it would be unsafe.

## Solution

A `PipelineCache` actor owns the loaded pipelines and lends one out for the duration of a run.

```swift
public struct PipelineSettings: Hashable, Sendable {
    public let modelName: String
    /// Resolved, never the caller's optional: `Pipeline.init` substitutes the model's default for
    /// nil, so `nil` and an explicit value equal to that default build the same pipeline. Keyed
    /// on the argument rather than the result, they would be two entries for one thing, and the
    /// next distinct settings would evict a live entry to make room for a duplicate.
    public let tileSize: Int
    public let overlap: Int
    public let faceEnhance: Bool

    public init(modelName: String, tileSize: Int? = nil, overlap: Int = 16, faceEnhance: Bool) throws
}

public actor PipelineCache {
    public static let shared = PipelineCache()

    public func withPipeline<T: Sendable>(
        _ settings: PipelineSettings,
        _ body: @Sendable (Pipeline) throws -> T
    ) throws -> T
}
```

The instance never escapes the actor: `body` receives it, uses it, and returns. Actor isolation means one run at a time, which is what makes reuse safe without changing `Pipeline` at all.

**`body` and the loader are both synchronous, and that is load-bearing twice over.** Swift actors are reentrant: with an `async` `body`, a second call could interleave at any `await` inside the first, and AC84.4 would be false while every test still passed — a test would have to contrive a suspension inside `body` to see it.

The same property covers the classic cache bug. With an `async` loader, two concurrent runs for settings nothing is held for would both find nothing, both suspend, and both load. Loading a Core ML model is genuinely I/O, so an `async` loader is the natural thing to reach for later; it would introduce a double load without failing anything else specified here, which is why RT-84.18 states the guarantee rather than leaving it resting on a signature.

Non-overlap and single-loading are therefore properties of these two signatures rather than of discipline. Making either `async` needs a different mechanism, not a different signature.

**The observer is detached when the run returns.** `Pipeline.onProgress` is a mutable property on an instance the cache now keeps for the life of the process. Left set, it holds the previous run's closure and everything that closure captured — in the application, a continuation feeding a view model. Before this slice the pipeline was discarded with the run and the closure went with it; now it has to be cleared deliberately.

**The processor takes its cache rather than reaching for the shared one.** `SuperscaleGUIUpscaleProcessor` is given a `PipelineCache`, defaulting to the shared instance. A singleton reached for internally cannot be observed by a test, and AC84.6 exists precisely because an unobserved seam is the one that breaks.

### Why not make `Pipeline` itself an actor

That is the phrasing the delivery plan uses, and it is the more invasive reading. Making `Pipeline` an actor turns `process` into an `async` call and `onProgress` into an isolated property, changing the command-line tool and the GUI coordinator with it — and it would put an `await` in the middle of a synchronous pipeline whose behaviour is guarded by a quality gate.

Confining it to an actor achieves what the plan is for — one instance, reused, never touched by two runs at once — while `Pipeline` stays a synchronous, directly testable type. `SuperscaleKit`'s public API is unchanged.

### Serialising every run, not just runs against one model

One run at a time across the whole cache, rather than one per model. Two reasons: the Neural Engine is a single shared resource, so concurrent inference buys little and costs memory in an operation already bounded by it; and the application runs one upscale at a time by design, since a new run supersedes the one in flight (#82).

### What is held, and how much

Held pipelines are keyed by every setting `Pipeline.init` reads, so a pipeline is reused only when it would have been constructed identically.

**At most two are held, and the least recently used is released first.** Each Real-ESRGAN model is roughly 64 MB once loaded, so an unbounded cache trades a three-second load for tens of megabytes per model the user tries.

The alternation the second slot exists for is **the face-enhancement toggle**, not model comparison. `faceEnhance` is part of the key — it changes what `process` does, so a pipeline built with it off must not serve a run that wants it on — and toggling it is one of the five triggers that starts a run (#82). Toggling faces therefore alternates between exactly two keys holding the same underlying model, and one slot would reload on every press.

A third slot would be held at the cost of a third model's memory, for a pattern nobody has been observed to have.

### Cancellation

A run cancelled mid-flight (#83) throws out of `body`, and the pipeline returns to the cache rather than being discarded — the model is loaded and uncorrupted, and the next run should have it. A failure while *loading* holds nothing, so a transient failure does not poison the entry.

### Patterns and anti-patterns

- Swift, existing project structure. No new dependency, no new test architecture.
- `SWIFT.md` §Concurrency: structured concurrency, actor isolation for shared mutable state, no `Task.detached`.
- `CODING.md` §Prohibited Anti-Patterns: no error suppression. A load failure propagates rather than yielding a cache miss that looks like a hit.
- The loader is injectable so tests can count loads. Nothing else about the cache is exposed for testing.

### Condition enumeration

- **AC84.1** implies three conditions: the load happens once, the same instance is handed back, and reuse survives an intervening run against different settings. RT-84.1 to RT-84.3. The second is separate from the first because a cache could load once and hand back a copy; the third because a cache holding only the most recent entry would satisfy the first two.
- **AC84.2** implies four conditions: three elements of the key that must not be collapsed, and one pair that must not be *distinguished*. RT-84.4 to RT-84.6, RT-84.19. Each of the first three is separate because a key that omitted one would reuse a pipeline built for different settings, which is worse than reloading: the user would get an upscale at the wrong tile size and no error. RT-84.19 is the other direction — the key is the settings a pipeline was *built with* rather than the arguments it was asked for, so an unresolved tile size and an explicit one equal to the model's default are one entry rather than two, and a duplicate does not occupy a slot and release something live to make room.
- **AC84.3** implies three conditions: the bound is enforced, it holds under any usage, and the release order is by recency rather than by insertion. RT-84.7 to RT-84.9. The last is what distinguishes a cache from a queue, and it is the one that decides whether the face toggle thrashes.

  Each is observed through the loader rather than through a published count. A cache that exposed how many it holds would be production API with one caller, which the last two slices each shipped and each had to remove. A pipeline that is no longer held reloads, and the loader already counts — so RT-84.8 returns to four settings in turn and asserts which of them reload, which measures the bound through its consequence and says how many were actually held when it fails.
- **AC84.4** implies five conditions: runs do not overlap, progress is not crossed between them, a failure does not leave the actor unusable, an observer does not outlive its run, and concurrent first-use of the same settings loads once. RT-84.10 to RT-84.12, RT-84.17, RT-84.18. The last is the classic cache bug, and it cannot happen as designed for the same reason the others cannot — but that reason lives in a signature, and RT-84.18 is what makes it fail loudly if the signature changes. Progress crossing is separate because it is the specific way a shared `Pipeline` would misbehave — `onProgress` is a mutable property on a shared instance. The observer's lifetime is separate because it is a new problem this slice creates: before it, the pipeline was discarded with the run, so a retained closure went with it. Kept for the life of the process, it holds whatever the caller captured — in the application, a continuation feeding a view model — until the next run replaces it.
- **AC84.5** implies two conditions: a load failure is not swallowed, and it is not sticky. RT-84.13, RT-84.14. The first is stated as propagation rather than as "nothing is held", because "nothing is held" can only be observed by a later run reloading — which is the second test, and two tests with one observation between them cover one condition, not two. The second is what stops a transient failure poisoning the entry for the life of the process.
- **AC84.6** implies two conditions: the application's upscale goes through the cache, and going through it does not change the result. RT-84.15, RT-84.16. This criterion exists because every other one here is about `PipelineCache`, and #82 shipped a runner that was built, tested fifteen ways, and wired to nothing while the application kept its old path. Fourteen passing tests would show the cache is correct and nothing about whether the three seconds ever stop being paid. RT-84.16 is what stops "reuse" being achieved by handing back a stale result.

  **RT-84.15 counts exactly one load, and zero is the failure that matters.** The count comes from the loader injected into the cache the processor was given, so a processor that ignores that cache and constructs a `Pipeline` directly — which is what it does today — calls it zero times. An assertion phrased as "at most once", or as "the second run added nothing", passes at zero and would be satisfied by the code the criterion was written against.

### Test type justification

All nineteen are regression tests. Every condition is machine-verifiable, each guards behaviour that must hold for the life of the project, and none invokes the build system.

Seventeen need no Core ML: the cache's loader is injectable, so they supply a counting stub rather than loading a model — which is what makes "loaded once" observable at all. Timing would not be a test.

RT-84.15 and RT-84.16 are the exception, deliberately. `Pipeline` is a concrete class with no protocol behind it, so a counting loader must still return a real one, and a criterion about the application's path cannot be met below that path. They need the x4plus model and skip without it, which is reported in the closing evidence rather than passed over as a pass. A small input keeps each run at roughly a second.

Introducing a protocol behind `Pipeline` to make them model-free was considered and rejected: that is a public API change to a shipped module for the sake of a test, in the slice that has just argued against making `Pipeline` an actor for a larger reason. Two model-dependent tests are the cheaper answer.

No user test is allocated. The user-visible consequence is that adjusting a scale stops costing three seconds, which is measurable rather than a matter of judgement, and is felt in the workspace slice 9 builds.

### Temporary state in tests

The cache holds no files, so most tests need none. Any that write allocate a unique per-run directory beneath the operating-system temporary directory and remove it in teardown on success, on failure, and on handled interruption.

### Test location

`Tests/SuperscaleUXCoreTests/PipelineCacheTests.swift`, XCTest, in the existing `SuperscaleUXCoreTests` target. No new target, no new dependency, nothing in the `OneOff` package.

Every test constructs its own `PipelineCache` with an injected loader. None touches `PipelineCache.shared`, which is process-wide state and would make one test's history another test's starting point.

RT-84.15 and RT-84.16 upscale a small synthetic image, for the reason recorded above: they run real inference, so the input is kept small enough that each run costs about a second.

`RT-84.13` uses a loader that fails for *valid* settings rather than an unknown model name. Resolving the tile size consults `ModelRegistry`, so an unknown model now fails when the settings are constructed, ahead of the cache — nothing is held, the user sees `SuperscaleError.modelNotFound`, which #83 made readable, and the loader failure AC84.5 is about is a different one.

## Verification constraint

**The SSIM quality gate must not regress.** `make test-ssim` runs `RT-064`, which asserts a score of at least `0.90` per image. This slice does not change how an image is produced — the same `Pipeline` runs the same way — so the gate should be unmoved. It is part of the evidence because "should be unmoved" is a claim about a change to shared, quality-critical state, and #83 established the baseline it is measured against.

## Out of scope

- Making `Pipeline` itself an actor, for the reasons recorded above. What the delivery plan asks for — one instance, reused, never touched by two runs at once — is delivered by confining it.
- Releasing held pipelines when the application goes idle. Two models is roughly 128 MB held for the life of the process, which is proportionate against what the workspace already holds — a 4096-pixel result is roughly 50 MB, and the face-enhancement toggle keeps two of them cached — but nothing releases them. Worth revisiting when there is a workspace to decide what idle means, which is slice 9. Recorded on the master's backlog so the number is a decision rather than an oversight.
- Preloading a model before the first run. That trades a wait the user notices for one they do not, and is worth doing only once there is a workspace to decide when it is idle. Slice 9.
- FAL request construction, which is slices 5 and 6.

## On confining rather than converting

The delivery plan says "actor-confined reusable `Pipeline`". Making `Pipeline` an actor would turn `process` into an `async` call and `onProgress` into an isolated property, changing the command-line tool with it, and would put a suspension point inside a synchronous pipeline whose behaviour is guarded by a quality gate.

Confining it gives what the plan is for — one instance, reused, never touched by two runs at once — while `Pipeline` stays synchronous and directly testable, and `SuperscaleKit`'s public API is unchanged. Recorded in `IMPLEMENTATION_GUIDE_v2.md` beneath the delivery table.

**Two guarantees rest on signatures rather than on discipline**, and both are written down. `withPipeline`'s body is synchronous, so there is no suspension point and actor reentrancy cannot interleave two runs. The loader is synchronous for the same reason: were it `async`, two concurrent first uses of the same settings would both find nothing held and both load. Loading a Core ML model is genuinely I/O, so an `async` loader is the natural thing to reach for later — RT-84.10 and RT-84.18 exist to make that loud rather than silent.
