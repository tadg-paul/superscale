## Original issue body

## Problem

Generated images need to enter the same local upscaling path as dropped or selected files. The current GUI upscaling flow is centred on `UpscaleViewModel`, so v2 needs a GUI-safe processing coordinator that can accept both existing user-selected files and future generated files without duplicating pipeline logic.

## Solution Design

### Scope

- Extract a small GUI-facing upscaling coordinator from the current `UpscaleViewModel` flow.
- Keep `SuperscaleKit` as the local processing implementation.
- Allow both selected/dropped files and generated files to use the same coordinator entry point.
- Preserve current Upscale labels, options, errors, and save behaviour unless a change is required by the v2 shell.

### Patterns to follow

- Keep processing side effects out of SwiftUI views.
- Keep option resolution and error mapping in a view model or coordinator.
- Use fixture images for automated tests rather than paid or network-dependent inputs.

### Anti-patterns to avoid

- Do not copy the local pipeline into a second generated-image-specific code path.
- Do not change CLI behaviour.
- Do not change GFPGAN licence acceptance behaviour.
- Avoid CODING.md violations: duplicated logic, hidden errors, and implementation-detail tests that would miss user-facing regressions.
- Avoid CODE/SWIFT.md violations: force unwraps, unstructured UI updates, and empty `catch` blocks.

### Test locations

- Existing GUI/unit test target for `UpscaleViewModel` or the new coordinator.
- Fixture images under the existing test resources location, or a new test resource directory if the project has no current convention.
