## GUI verification blocked by an authentication prompt holding the screen

Three consecutive GUI runs failed identically at 15:02, 15:04 and 15:06 with:

```
Failed to initialize for UI testing: Timed out while enabling automation mode.
** TEST EXECUTE FAILED **
```

No `Executed N tests` line, so all three are **inconclusive, never green**, per this master's own rule.

### The cause, named rather than guessed

`lsappinfo front` reports the frontmost application as **`coreautha`** — macOS's Core Authentication agent. A system authentication dialogue holds first responder, so the runner's synthesized events land nowhere and automation mode never enables.

This is the pattern guide 3.26 records from #118 (the GUI suite intermittently failing to give the prompt field keyboard focus), where the culprit was an external managed installer. The signature is identical and the diagnosis is now specific rather than inferred.

### What was ruled out along the way

- **Screen locked or asleep.** `ioreg` reports no lock, `loginwindow` is normal, the console user is the author's. A persistent `caffeinate -dims` hold is running.
- **My own keepalive.** The second attempt ran with a persistent `caffeinate -dimsu`; suspecting the continuous `-u` user-activity assertion, it was replaced with the known-good `caffeinate -dims` wrapper plus a periodic `caffeinate -u -t 1` poke — the exact configuration under which this suite ran **141 tests, 0 failures**, earlier today. It failed the same way, so the keepalive is not the cause.
- **Stale runners.** No leftover `SuperscaleAppUITests-Runner` or app processes between attempts.

### Effect on this delivery

- **#121** (two owners of current-image state) has its package verification: **40 tests, 0 failures**, including the seven new ones. Its two GUI tests, RT-121.3 and RT-121.5, are unverified.

### Comment by tigger-developer at 2026-08-28T19:10:48Z

DECISION D-1

- **Question:** the curtain's shared-width rule leaves unused canvas width on a picture proportionally taller than the canvas. Change it, or keep it?
- **Classification:** routine implementation ambiguity
- **Chosen interpretation:** **keep guide 2.3's rule unchanged.** No code change on #127.
- **Evidence:** measured in `CurtainProportionTests`. A 3423x2698 pair (1.27:1) against a 900x600 canvas (1.5:1) yields a shared width of **761 of 900 points**, filling the height exactly. Filling the width instead would make the pair a third taller than the canvas and clip it --- which guide 2.3 states as the reason for the rule: *"using the full width unconditionally clips the more portrait of the two off the bottom."* The alternative, fitting each side independently, gives a 1:1 return a different width from a 3:4 original so one divider line means two positions --- the defect UT-90.1 failed on.
- **Reversibility:** fully reversible. RT-127.5 pins the current behaviour, so a later change supersedes a test rather than silently breaking one.
- **Affected issues, ACs, and tests:** #127; AC96.3 and the criterion superseding AC90.10; RT-127.1 to RT-127.5.

DECISION D-2

- **Question:** how should a scale that was requested but reduced by the area ceiling be drawn, so it does not read as pressed?
- **Classification:** routine implementation ambiguity
- **Chosen interpretation:** **an outline rather than a fill.** The scale in effect keeps the accent fill; the requested-but-reduced one gets a bordered outline and no fill.
- **Evidence:** three options were put on #131. The outline is the only one that keeps AC82.8's requirement --- the control goes on showing what was asked for --- while removing the fill that reads as selection. A badge adds an element for a state that already has a value and a help string; untinting entirely discards the information AC82.8 exists to preserve. It changes no behaviour and no state, only how one existing state is drawn.
- **Reversibility:** fully reversible, a single `tint(for:)` branch.
- **Affected issues, ACs, and tests:** #131, #125; AC82.8, AC93.1; RT-131.4 to RT-131.6.

DECISION D-3

- **Question:** should every upscale control be disabled for a picture that fits at no scale, as requested in the user-test round?
- **Classification:** material --- it reverses a documented decision --- **and therefore resolved by keeping the documented behaviour rather than by changing it**
- **Chosen interpretation:** **no controls are disabled.** `ScaleReadout.isChoosable` continues to return true for every choice.
- **Evidence:** the existing rule is deliberate and its reason is recorded at `ScaleReadout.swift:88` --- *"the natural way to render it is to dim the control, and dimmed reads as disabled --- which would trap the user at the reduced scale until they imported a different picture."* The author's report identified the **appearance** as the problem (*"it looks depressed because it is in fact disabled"*), and the measurement showed nothing is disabled at all: the appearance is the `.secondary` tint, which D-2 fixes. Disabling the controls would deliver the letter of the request while creating the trap the rule exists to prevent.
- **Reversibility:** reversible, but choosing the status quo means nothing to reverse. Recorded so the request is visibly answered rather than dropped, and so the author can overrule it knowing the trade-off.
- **Affected issues, ACs, and tests:** #125; AC82.8; RT-125.1 to RT-125.7.
