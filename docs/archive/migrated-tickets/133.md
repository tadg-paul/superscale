## Raised from #135's code audit: AC89.8 promises something nothing delivers

Found while auditing the clear, and it is **not** a defect introduced by this round --- it is a
criterion that has been wrong since it was written, and I would rather you saw it than have it
inherited quietly by every future ticket that reads it.

**AC89.8 says:** *"importing another image starts a new chain, and the previous chain's files are
released."*

**The first clause is true and tested.** `importSource` resets `chainIDs`, `baseID`, `candidateID`
and `currentUpscaleID`, and RT-89.25 stands over it.

**The second clause is not.** Nothing deletes the previous chain's files. `importSource` leaves
`assets` populated and every file on disk. The test cited for that clause, **RT-89.26**, asserts
something narrower that *is* true: a **superseded upscale** is released when a second upscale of the
same input replaces it. `AssetGraph.release` refuses any role but `.upscaled`, so it could not
release a chain even if something called it that way, and only `UpscaleRunner` calls it.

`WorkspaceState.clear()`, added by #135, inherits exactly this. It rebuilds the graph and touches no
files, so **clearing leaks on precisely the same terms importing already does** --- no better, no
worse.

### My recommendation: correct the criterion, do not implement it

**Deleting a cleared chain's files would destroy locked iterations permanently.** Those are the
results you have paid the provider for, and losing them is the exact harm #132 was raised about. A
clear that quietly deleted them would be a far worse defect than an output directory that grows.

So I would narrow AC89.8's second clause to what is both true and wanted --- superseded upscales are
released; locked iterations and their files are not --- and let the directory grow.

**This is a change to a closed criterion and outside #135's scope, so I have not made it.** It needs
your call on one thing I cannot decide: whether an ever-growing output directory is acceptable for
the MVP, or whether cleanup belongs somewhere else entirely, such as a size cap or a prune on launch.
It is not blocking anything --- #135 is closed on its own terms and the behaviour is unchanged from
what has shipped all along.
