## Original issue body

Child of delivery master #79 (slice 4). Closes D4.

## Problem

**Filter metadata is derived from filenames.** `PromptPackCatalogue.descriptor(resourceName:)` splits the resource name on hyphens: `image-design-soviet-poster` becomes category "Design" and display name "Soviet Poster" (`PromptPacks.swift:154-166`).

That makes the filename a schema. A filter cannot be named "Chiaroscuro" without the file being called `image-lighting-chiaroscuro`; a two-word category is impossible; and `image-lighting-chiaoscurod.md` — a real file, with a real typo — presents to the user as "Chiaoscurod". The corpus is content, and its presentation should be authored rather than inferred from a path.

**D4: three of the 86 send their own filename to the provider.** `image-lighting-film-noir.md` begins:

```markdown
# image-lighting-film-noir.md

Transform the input image using film noir lighting.
```

The body is the whole file, so that heading is prompt text. The provider is told to make an image about `# image-lighting-film-noir.md`. The same applies to `image-lighting-vermeer-window.md` and `image-lighting-chiaoscurod.md`.

**Selecting a filter and applying it are one step.** The application offers a picker of pack names alongside a separate prompt field, and composes the two at send time (`PromptComposer.compose(pack:userPrompt:)`). A user cannot read what a filter will send before paying for it, and cannot adjust it.

## Solution

### Metadata moves into the file

Each filter carries a frontmatter block delimited by `---`, holding its own metadata:

```markdown
---
{
  "id": "image-lighting-film-noir",
  "name": "Film Noir",
  "category": "Lighting",
  "requiresInput": true
}
---

Transform the input image using film noir lighting.
...
```

**All four fields are required.** `id`, `name`, `category` and `requiresInput` must each be present and, for the three strings, non-empty. `requiresInput` is stated as required despite nothing in this slice reading it, because a field that is optional today is absent from most of the corpus tomorrow, and the version that starts reading it then finds 60 files that never declared it.

**The block is JSON, not YAML.** `CODING.md` requires structured data to be read by a format-aware parser rather than by line splitting, and `JSONDecoder` is one in the standard library. YAML would mean either a new dependency for four scalar fields, or a hand-rolled key-value reader that is a line-oriented parser wearing a schema — and one that quietly breaks the first time somebody writes a list in it.

**`compatibleModelIDs` stays out of the frontmatter.** `PromptPackDescriptor` carries it and `PromptPackLoader.validate` checks it against the supported set (`PromptPacks.swift:112-118`), but it was never file metadata: `PromptPacks.swift:164` hardcodes it to `FalGenerationRequest.defaultModelID` for every pack. Nothing observable changes by leaving it out, provided the descriptor keeps supplying the default — so **AC74.1**'s model-compatibility clause remains true and **AC74.2**'s unsupported-model condition, covered by RT-74.3, keeps its subject. Stated because otherwise this is where an implementer either adds a fifth required field to 86 files or deletes a validation that is still covered.

**The identifiers do not change.** They stay exactly what the previous version derived from the resource name — `image-lighting-film-noir` — because `GenerationPreferences` stores the user's default filter under that value in `UserDefaults` (`GenerationPreferences.swift:20`, `:69`) and restores it on appearance. A prettier identifier would make every existing default resolve to nothing, with no error and no message: a preference that disappears is the kind of fault nobody reports and everybody notices. Nothing is gained by the change, and the identifier is now *declared* rather than derived, which is the point — a later rename of the file cannot move it.

**Identifiers must be unique.** Today that is guaranteed by construction, because the identifier is the filename and a directory holds one of each. Moving it into frontmatter removes the guarantee at exactly the moment 86 files are hand-edited, and `PromptPackCatalogue.pack(id:)` uses `first(where:)` — so a duplicate would make one filter permanently unreachable, with no error and no way to notice but by counting the list. Loading rejects a corpus containing one.

`requiresInput` is carried because the corpus is built for transformation — 60 of the 86 have preserve clauses — and the next version adds generation from a bare prompt, where a filter that needs an input image is not applicable. It is recorded now so that change is an addition rather than a migration.

### The body is what is sent

`PromptPack.body` is the text after the frontmatter, trimmed. Nothing else reaches the provider. The three files carrying a heading of their own filename lose it, because the heading was never anything but an editing artefact and the frontmatter now holds the metadata it was standing in for.

### Loading validates rather than guesses

`PromptPackLoader` reports a file it cannot read as an error naming the file and the reason, rather than yielding a filter with metadata inferred from somewhere else. A corpus that fails to load is a build-time problem; a corpus that loads with wrong metadata is a user-facing one.

### Selecting is free; applying costs

Choosing a filter loads its body into an editable text field and sends nothing. The user reads exactly what will be sent, adjusts it if they want, and a separate action applies it. `PromptComposer`'s compose-at-send-time goes: what is sent is the field's contents.

**`PromptComposer` is removed, not deprecated.** `GenerateView` composes at four sites — the preview row (`GenerateView.swift:230`), the enablement guard (`:344`), and the two request constructions (`:404`, `:454`). A selection model that behaves perfectly while the view goes on concatenating a pack body with a user prompt passes every test this issue lists and ships the old behaviour, which is the fault #82 shipped and its code audit caught. Removing the type makes the four call sites a compile error rather than a thing to remember. A test that grepped the source for callers would be the wrong instrument; the compiler is the right one.

**Edits are not saved.** They apply to that execution only, do not modify the built-in filter, and do not persist across selections or sessions, as `IMPLEMENTATION_GUIDE_v2.md` section 2.3 states.

**The text area works with no filter chosen.** A user who writes their own instruction and picks nothing applies what they wrote. That is what happens today — `PromptComposer.compose(pack: nil, userPrompt:)` sends the user's text alone — and a two-step flow that required a selection would remove the capability silently. Section 2.2 rules out *generating* from a bare prompt in the MVP, which is a different thing: creating an image from nothing, rather than transforming one with wording the user chose. Applying with neither text nor a filter is refused, because an empty prompt to an edit endpoint costs money and returns something arbitrary.

**This slice delivers the selection model, not its final presentation.** The workspace that renders the catalogue as a sidebar is slice 9. The existing Generate view is rewired to the new model so the behaviour is real rather than pending, and slice 9 replaces the rendering.

### Patterns and anti-patterns

- Swift, existing project structure. No new dependency, no new test architecture.
- `CODING.md` §Data Handling: a format-aware parser for the frontmatter, never line splitting.
- `CODING.md` §Prohibited Anti-Patterns: a malformed filter is reported, not skipped silently.
- `SWIFT.md`: no force unwrapping, no `try!`, no empty `catch`.
- Tests assert against what the loader produces, never against file contents read directly.

### Condition enumeration

- **AC85.1** implies three conditions: metadata is read from frontmatter, it wins over anything the filename would suggest, and the whole shipped corpus satisfies it. RT-85.1 to RT-85.3. The second is separate because a loader that read frontmatter *and* fell back to the filename would pass the first; the third because 86 files hand-edited in one pass is exactly where one gets missed.
- **AC85.2** implies five conditions, one per way a file can fail to describe itself: absent, malformed, incomplete, blank, or describing nothing. RT-85.4 to RT-85.7 and RT-85.26. Each is separate because they fail at different points in the parse, and the failure that matters is the one that names the file — a corpus that fails to load is a build problem, one that loads wrongly is the user's. RT-85.26 is the one a decoder cannot catch: `"name": ""` decodes into a `String` perfectly well and yields a filter with a blank row in the list, which is exactly what hand-editing 86 files in one pass produces. The failure is of the corpus rather than of the file: a bad file yields no filters at all, rather than 85 and a message, because a catalogue quietly short by one is not something anybody counts.
- **AC85.3** implies five conditions: no delimiter survives, no bundled filter opens with a heading, no resource name appears anywhere in the corpus, the three known offenders are clean, and the body is carried verbatim. RT-85.8 to RT-85.11, RT-85.32. The corpus-wide test is what closes D4 rather than the three files, because the defect is a class and the three are its known instances. RT-85.10 tests for the *resource name* as a contiguous string and for a leading `#`, not for words the filename contains: a filter whose file is `image-print-risograph` has every reason to say "risograph" in its body, and `image-lighting-film-noir` should certainly say "film noir". RT-85.24 covers the other direction — `---` is also a markdown horizontal rule, and a parser splitting on every occurrence rather than on the first two would truncate such a body silently, which is invisible because a shortened prompt still produces an image. The contract is that the first two delimiters bound the frontmatter and everything after the second is body, carried verbatim. RT-85.32 exists because RT-85.9 to RT-85.11 are all satisfied by a loader that discards a leading `#` line: the three files would stay as they are, D4 would be closed on paper, and the first filter that legitimately opens with a heading would be silently truncated. Asserting that the loader does not edit bodies leaves the corpus as the only place the fix can live.
- **AC85.4** implies five conditions: the text arrives, nothing is sent, a second choice replaces rather than accumulates, choosing the same filter again yields it afresh, and a choice replaces hand-written text too. RT-85.12 to RT-85.14, RT-85.25, RT-85.29. The fifth becomes reachable only because AC85.8 makes writing without a filter a first-class thing to do, and that text is then destroyed without warning. It is the right behaviour — selection is how the field gets filled, and a confirmation is slice 9's presentation problem — but right by design and right by accident read the same in the code and differently in six months. The second is the point of the two-step flow: selecting must be free, so a user can read eighty-six filters at no cost. The fourth is how a user reverts — edit the text, dislike it, click the filter again — and without it the only way back to the built-in wording is to choose something else and return, which works by accident rather than by design. Selection is idempotent in what it produces, not in whether it acts.
- **AC85.5** implies three conditions: unedited text is sent, edited text is sent, and an edit does not outlive its selection. RT-85.15 to RT-85.17. The third is what keeps a built-in filter built-in.
- **AC85.6** implies two conditions: a stored identifier resolves, and the whole corpus uses the form that was stored. RT-85.18, RT-85.19. It exists because of **AC73.2**, which requires the GUI to persist *"generation model, upscale model, output folder, prompt-pack selection, and cost threshold outside secret storage"* — the persisted selection is the identifier, and a criterion is a more durable citation than a line number. AC73.2 is unchanged and unchallenged by this slice. The second is what catches one file among 86 getting a prettier identifier during a hand-edit, which would lose that filter's saved default silently.
- **AC85.9** implies two conditions: a failed load leaves nothing to choose from and something to read, and it leaves the local half of the application alone. RT-85.30, RT-85.31. It exists because making AC85.2 a whole-corpus failure creates a state that nothing else describes — the application running with no filters at all. Section 2.8 of `IMPLEMENTATION_GUIDE_v2.md` already rules on the shape of that state for the case where filters are unavailable for want of a key: *"Local upscaling works fully."* A corpus that will not load is the same condition reached by a different route, and the route should not change what the user gets. The rendering of the reason is slice 9; what the application holds after the failure is this slice.
- **AC85.8** implies four conditions: hand-written text alone is applied, nothing at all is refused, a chosen filter whose text has been cleared is refused, and whitespace alone is refused. RT-85.22, RT-85.23, RT-85.27, RT-85.28. The refusal belongs to the text rather than to the pair of (text, filter): AC85.5 already says what is sent is the field's contents, so a filter sitting highlighted beside an empty field is still nothing to send. Framing it on the pair leaves the reachable case — choose a filter, clear the box, apply — sending an empty prompt to a paid edit endpoint, which is the outcome the condition exists to prevent.

### What this does to #74's acceptance criteria

The filter corpus is not new, and neither are its criteria. **#74** established four, pre-cutover, so they live in that issue and are citeable as legacy. Three are load-bearing here and change, which `ISSUES.md` makes the forcing function for migrating them into `docs/ACs.md` first.

**AC74.2** — *"the prompt-pack loader rejects [invalid resources] with actionable diagnostics and no secret leakage"*, whose RT-74.3 already covers *"missing prompt body, duplicate identifier, malformed metadata, and unsupported model references"*. Duplicate rejection is existing, passing coverage, not something this slice invents. What changes is why duplicates are possible at all: they were prevented by the filesystem, and frontmatter removes that. Two tests are added to this criterion's coverage rather than to a new one:

> ⏳ RT-85.20: a corpus with two filters declaring the same identifier is reported, naming it
> ⏳ RT-85.21: the bundled corpus contains no duplicate identifier

**AC74.1** — *"the GUI can load prompt packs with stable identifiers, display names, categories, prompt bodies, and model compatibility metadata"* — remains true and migrates unchanged. Its RT-74.2 names *"category derivation, display name derivation"* as the mechanism, and is rewritten against frontmatter keeping its identifier. Identifier *stability* becomes AC85.6's subject, and is the one part of the old derivation this slice deliberately preserves.

**AC74.3** — *"selected prompt-pack text combines with user prompt text without mutating the bundled resource"* — is superseded by AC85.5. The composition it specifies is what the two-step flow removes, and `RT-74.5` and `RT-74.6` call `PromptComposer.compose` directly (`PromptPackTests.swift:76-83`), so leaving them alone would stop the test target compiling. They are rewritten against the new model, keeping their identifiers. The half that survives — *without mutating the bundled resource* — is AC85.5's third condition.

**AC74.4** — *"user-authored prompt-pack editing is deferred"*, with RT-74.7 asserting *"bundled prompt-pack selection without in-app editing controls"* — is superseded by AC85.4 and AC85.5. It is not stale; it says the opposite of what this slice delivers, and its test asserts the absence of the thing being built.

The distinction it drew survives and is worth keeping explicit: **editing the text of a run is not authoring a filter.** Section 2.3 keeps the latter deferred — edits apply to one execution, do not modify the built-in filter, and do not persist across selections or sessions. RT-74.7 is marked removed rather than deleted, and its identifier stays.

**UT-74.1** — *"Human review confirms placeholder/internal prompt-pack names are acceptable for MVP discovery refinement"* — is an unresolved user test, still pending, on an issue that closed. It is about exactly what this slice changes, and it transfers to #79's user-test roll-up when AC74.1 migrates, restated against what the frontmatter now declares:

> ⏳ UT-74.1: the filter names shown to the user read as intended names rather than as filenames

Whether "Film Noir" and "Vermeer Window" read well is a judgement no test can make, and this is the first slice that gives a human something to judge.

### Test type justification

All thirty of this issue's own are regression tests, plus RT-85.20 and RT-85.21 added to AC74.2's coverage. Every condition is machine-verifiable, none needs Core ML or the network, and none invokes the build system. The loader is a pure function over text; the selection model is a value type.

One user test is carried rather than allocated: **UT-74.1**, transferred from #74 to the delivery master, because whether the filter names read as names is a judgement and this slice is what makes them judgeable.

Tests assert against what the loader produces — `PromptPack.body`, `.displayName`, `.category` — and never against file contents read directly. The corpus-wide tests load the bundled catalogue through the real loader, which is the boundary the application uses.

Whether a filter's *wording* produces a good image is also a judgement, but it is not changed here: the bodies are unchanged except for three headings that were never meant to be sent.

### Temporary state in tests

The loader and selection tests write nothing at all. `PromptPackLoader.load(descriptors:bodyProvider:)` already takes its bodies from a closure (`PromptPacks.swift:59-62`), and frontmatter parsing is a pure function over text: every validation case — absent, malformed, incomplete, blank, duplicate — is a string in and an error out. The frontmatter parser is therefore reachable with `(resourceName, text)` pairs rather than with file locations, which is what keeps this true.

The corpus-wide tests read the bundled resources, which are project content rather than test state, and write nothing. Temporary state that does not exist cannot leak, and teardown that is not needed cannot be got wrong.

Two exceptions, both covering AC85.9: a settings state needs a preferences store, which needs a `UserDefaults` suite, and a suite persists a plist. Those two allocate a suite named for a fresh `UUID` and remove its domain in a teardown block, which runs on success and on failure alike — the pattern already used in `GenerationSettingsTests.swift`.

### Test location

`Tests/SuperscaleUXCoreTests/PromptPackTests.swift` for loading and validation, and `Tests/SuperscaleUXCoreTests/FilterSelectionTests.swift` for the two-step flow, including AC85.9's pair, which describe the state a failed load leaves the selection model in. XCTest, in the existing `SuperscaleUXCoreTests` target. No new target, no new dependency, nothing in the `OneOff` package.

## Verification constraint

**The GUI test suite must pass.** `make test-gui` runs `SuperscaleAppUITests`, which `make test` does not. `RT-75.1` (`SuperscaleAppUITests.swift:963-981`) asserts the Generate workspace's controls, and `RT-75.5` to `RT-75.7` drive a fixture generation through that view — which is the view this slice rewires. It is part of this issue's verification evidence, not optional: without it, the slice that rewrites the Generate view would be checked by a command that never loads it.

**The accessibility identifiers survive.** `generationPromptPackPicker` and `generationPromptField` are the names those tests address the view by. The two-step flow keeps both capabilities — a filter list and an editable text area — so the identifiers carry over rather than being renamed to match new wording.

That also settles **AC75.1**, which requires the Generate mode to expose *"prompt-pack selection, prompt entry, model selection, aspect selection, up to three reference image wells, and generate/cancel controls"*. It is not contradicted: filter selection and text entry both remain, unified rather than removed.
