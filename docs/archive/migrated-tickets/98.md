## Original issue body

Child of delivery master #79 (slice 8). Design of record: `IMPLEMENTATION_GUIDE_v2.md` 3.6 and 6.

## Problem

Guide 6 describes slice 8 as *"Multi-envelope parser, mapped taxonomy, redaction, one presentation surface replacing four."* Three of those four are partly present and none is finished.

### The parser exists and only one client can use it

`FalDiagnosticRedactor` at `FalGenerationClient.swift:148` reads a provider error from `message`, then `detail`, then a nested `error.message`, attaches a request identifier when there is one, and redacts known secrets. That is the multi-envelope parser, and it is `private` to that file.

`FalPricingClient.swift:175` does its own smaller version: `object["message"] as? String ?? object["detail"] as? String`. No nesting, no request identifier, **no redaction**. `FalAccountClient` has a third error type again. So a pricing failure carrying a key in its echoed payload would surface it, while the identical failure from a generation call would not.

### `detail` is handled as a string and FAL sends a list

`stringValue(dictionary["detail"])` returns a string or nothing. FastAPI — which the platform host runs — reports validation failures as `detail: [{...}, {...}]`. Against a list, the parser falls through to the next envelope and then to "The provider rejected the request.", discarding the only part that says what was actually wrong. `FAL_REQUEST_REFERENCE.md` names both shapes: *"FastAPI `detail` as string or list"*.

### There is no taxonomy

Each client raises its own enum — `FalGenerationError`, `FalPricingError`, `FalAccountError` — and a caller wanting to know whether a failure is worth retrying, or is the user's fault, or is a missing credential, has to match on three unrelated types.

### Four presentation surfaces

`errorMessage` is set in `MainView`, `UpscaleViewModel`, `SuperscaleApp` and `FaceModelDownloadView`, nine times in `MainView` alone. Guide 6 asks for one.

### Condition enumeration

- **AC98.1** implies three: one parser, the nested envelope everywhere, and the request identifier everywhere. Identical bodies producing identical diagnostics is the strongest form of "the same parser" that can be asserted from outside.
- **AC98.2** implies three: one entry, several, and the string form still working. The third guards the regression a list-handling fix invites.
- **AC98.3** implies six: each envelope shape, the unparseable body, every client, every credential, and the truncation boundary. Redaction being on one client of three is the live defect; the last two were raised by the first AC audit.

  **Every credential, not the one the call used.** `redact(_:secrets:)` removes only what it is handed, so a caller passing the generation key alone would leave an account key echoed in a body untouched — and this delivery keeps both keys.

  **Redact, then truncate.** The unparseable-body path currently takes `data.prefix(500)` and redacts afterwards. A key straddling that boundary leaves a fragment, because `redact` replaces whole occurrences and half a key is not one. The path is taken when the provider returns something the parser cannot read, which is exactly when bodies are unusual — and a test asserting the key is absent would pass, because the whole key genuinely is.
- **AC98.4** implies three: credentials, actionability, and that classifying a failure does not throw away what the provider said. The third is what stops a taxonomy replacing a useful message with a category.
- **AC98.5** implies one testable condition: a failure from either subsystem is presented the same way. RT-98.14 covers it.

  **There is nowhere else to write, and that is a design property rather than a test.** It was first phrased as "no failure path bypasses that surface", which asks a test to prove a negative across paths that do not exist yet; the AC audit rejected that, and the replacement — "exactly one type exposes a user-visible failure" — was rejected in turn by the test audit for the same reason in a different sentence. A fact about the code's shape can only be checked by inspecting source, which `TESTING.md` prohibits outright.

  So it is recorded here as what the implementation must do, and `audit-code` confirms it: **one owner holds the failure state and the other three assignment sites are removed**, so a later path finds nowhere else and fails to compile. A compile error is a stronger guarantee than a test nobody re-runs, and the audit is where structural claims are properly checked.

## Solution

**The parser moves out of `FalGenerationClient` and becomes shared.** It is already the most complete of the three; the other two adopt it rather than a fourth being written. Redaction comes with it, which closes the defect where a pricing failure could surface a key.

**`detail` accepts both shapes.** A string as now; a list by taking each entry's `msg` — FastAPI's field — and joining them. Neither shape falls through.

**The taxonomy is a small enum on the failure, not a replacement for it.** A `FalFailure` carrying a `kind` — `credential`, `request`, `provider`, `transport` — alongside the parsed diagnostic. Callers switch on the kind; the diagnostic still says what happened. `LocalizedError` conformance is unchanged, so what a user reads is unaffected except that it is now the same wherever it came from.

**One presentation surface.** The four assignment sites become one path, which is where slice 9's error criteria already expect it. This is the smallest part in code and the largest in discipline: the test that no path bypasses it is what keeps it true.

## Test type and location

Sixteen regression tests. AC98.1 to AC98.4's are package tests in `Tests/FalGenerationKitTests/`, against constructed response bodies — no network, no key, no paid endpoint. The keys they redact are strings invented by the test, so no real credential is involved in proving that real credentials are removed.

AC98.5's RT-98.14 is a GUI test in `SuperscaleAppUITests`, because presenting a failure the same way is a claim about the window. It is the only test that criterion carries: the "nowhere else to write" half is a design property confirmed by `audit-code`, not an assertion, for the reason recorded in the enumeration.

No user test. The wording a user reads is the provider's, and this issue changes where it appears rather than what it says.

## Security

**This is the security-relevant part of the delivery and it now holds on every client.**

- Redaction was on the generation client alone. `FalPricingClient` and `FalAccountClient` both
  route through `FalDiagnosticRedactor.providerDiagnostic`, asserted from outside by RT-98.10 giving

## Error handling

No suppression. Every `catch` either rethrows a typed failure or converts to one with the
provider's own words preserved. `FalFailure` adds the classification *to* the diagnostic rather
than replacing it, so a taxonomy cannot turn "the model rejected that aspect ratio" into "request
error".

`report(_:)` reads a `FalFailure`'s diagnostic in preference to `localizedDescription`. The two say
the same thing today; going through the diagnostic makes the redaction guarantee explicit rather
than incidental.

## Complexity

`FalDiagnosticRedactor` is four small functions, none over 25 lines. Threading `secrets: [String]`
through the pricing and account clients replaced a single-key parameter at each hop rather than
adding a hop.
