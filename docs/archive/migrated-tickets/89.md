## Original issue body

Child of delivery master #79 (slice 9b). Depends on #87.

## Problem

**The asset graph has no consumer.** `AssetGraph`, `FilterStage`, `UpscaleStage` and `UpscaleRunner` were built by slices 1 and 2 with 30-odd regression tests over their invariants. Nothing in `SuperscaleApp/` references any of them. The application runs on `UpscaleViewModel` and, since #87, a base and a candidate held as two `@State` properties in `MainView`.

That arrangement is right as far as it goes: applying a filter reads the base, so a second filter replaces the first rather than compounding on it. What it cannot do is the rest of the model the graph exists for:

- **Lock.** There is no way to promote a candidate, so filters cannot be stacked deliberately: noir *then* woodblock. Section 2.4 makes lock the only action that moves the base, and it does not exist.
- **The lock chain.** Locked iterations are not retained, so a user cannot scroll back to an earlier one or save it. Invariant I7 requires the lineage of a locked asset to remain reachable.
- **Provenance.** Nothing records how an asset was produced, so a saved file cannot say which filter made it.
- **Enforcement.** I1, that an upscaled asset is never input to a stage, is enforced by the graph in tests and by a comment in `MainView` in the application. A comment is not an invariant.

**The filter toggle does not exist.** Section 2.3 offers comparison between base and candidate; the workspace has no way to see the base while a candidate exists other than applying nothing.

**Settings still offers pricing and account controls.** `checkPricingButton` and `refreshAccountButton` call clients the MVP excludes. #88 removed the assertions that covered them and recorded that the controls themselves retire here.

## Solution

### The graph becomes the state

`MainView`'s `baseImageURL` and the coordinator's output give way to an `AssetGraph` held by a workspace object. Importing calls `importSource`; applying calls `recordFilterOutput`; upscaling calls `recordUpscale`; Lock calls `lock()`.

The graph already enforces what the criteria require, including refusing an upscaled asset as a stage input and allocating a distinct location per upscale. Wiring it replaces a comment with a type.

### Lock, and the chain

A **Lock** control beside Apply promotes the candidate to base. Locked iterations appear in a chain the user can scroll back through, each one saveable, which is what I7 keeps reachable.

### The filter toggle

A control that shows the base while a candidate exists, honouring the scale toggle independently: base, base upscaled, candidate, candidate upscaled. It changes what is displayed and never what is stored, so toggling is free and reversible.

### Pricing and account controls retire

`checkPricingButton`, `refreshAccountButton`, the account summary and the billing list go from Settings, with `GenerationPricingCoordinator` and `GenerationAccountCoordinator` no longer constructed. The clients remain in `FalGenerationKit` for the version that needs them.

This supersedes the part of **AC73.5** naming "account state" as a visible Settings control. The credential fields, defaults and filter selection it also names are unaffected.

### Condition enumeration

- **AC89.1** implies three conditions: a second filter without a lock reads the base, a second filter after a lock reads the locked result, and only one candidate exists at a time. RT-89.1 to RT-89.3.
- **AC89.2** implies five conditions: locking moves the base, applying does not, upscaling does not, locking with nothing to promote reports why, and locking promotes the candidate rather than what is on screen. RT-89.4 to RT-89.7, RT-89.23. The fifth is the one an implementation gets wrong by accident: with the scale on, what the user is looking at *is* the upscaled rendering of the candidate, so "lock what I see" is the natural code and it stores a derivation as the base. The same shape as AC87.6's reference, which this delivery has already got wrong once.
- **AC89.3** implies three conditions: iterations remain reachable in order, each says how it was made, and each can be saved as displayed. RT-89.8 to RT-89.10. Section 2.6 rules that saving an earlier iteration re-derives its upscale on demand, which is why saving is *at the current scale selection* rather than at whatever resolution the iteration happens to be.
- **AC89.4** implies two conditions: a filter applied over an upscale reads the base, and an upscaled reference submitted directly is refused with the rule it breaks. RT-89.11, RT-89.12. The second is what makes this the graph's job rather than the view's: the view can only avoid the mistake, the graph can refuse it.
- **AC89.5** implies five conditions: the toggle shows the base, it shows the candidate again, it stores nothing, it is unavailable with nothing to compare, and a new candidate displaces the choice. RT-89.13 to RT-89.15, RT-89.27, RT-89.28. The last exists because applying while showing the base would otherwise look as though nothing had happened.
- **AC89.6** implies four conditions: the four combinations of toggle and scale. RT-89.16 to RT-89.19. Showing the base upscaled means running Core ML on the base, which is seconds of work started by flicking a toggle; showing an unupscaled base while the scale is on would be the cheaper answer and the worse one, because the user could not tell whether they were looking at a rendering or a raw image.

  **The cost of that is #90's, not this issue's.** RT-89.24 required the base to be upscaled once and reused thereafter, which is a rendering cache — and #90 was raised afterwards with exactly that as AC90.7, keyed by the asset, the model, the sizing and the face setting. Two issues implementing one cache would produce two caches. RT-89.24 is therefore marked removed and transferred to #90 as RT-90.18, with its identifier retired. This issue makes all four combinations *reachable*; #90 makes reaching them cheap.
- **AC89.7** implies three conditions: no pricing control, no account control, and no client constructed. RT-89.20 to RT-89.22. The third is the point: controls removed while the clients still run would leave the application contacting a provider the MVP excludes.
- **AC89.8** implies two conditions: a new image starts a new chain, and the old chain's files go. RT-89.25, RT-89.26. The chain belongs to the image it was built from; carrying it across would offer iterations of a picture no longer on screen, and keeping the files would grow the output directory for the life of the session.

## Test type justification and location

All 28 are regression tests: machine-verifiable, needing no human judgement and no build-system
invocation. They are split by what they assert, following the division #87 established — the GUI
covers the surface, the package covers the behaviour behind it. That split is why `make test-gui`
is 66 tests and ten minutes rather than 86 and fifteen.

**Package, in `Tests/SuperscaleUXCoreTests/`:**

| Tests | What they assert |
|---|---|
| RT-89.1 to RT-89.12, RT-89.15 | Graph state: what applying reads, what locking promotes, what the toggle leaves alone |
| RT-89.16 to RT-89.19, RT-89.28 | The display decision: which asset the canvas should show for a given toggle and scale, which is a function rather than a view |
| RT-89.22 | That no pricing or account client is constructed, which a window cannot observe |
| RT-89.23 | Locking with a rendering present |
| RT-89.25, RT-89.26 | The chain's lifecycle and the release of its files |

**GUI, in `SuperscaleApp/SuperscaleAppUITests/`:** RT-89.13, RT-89.14, RT-89.27 for the toggle
existing, working, and being unavailable with nothing to compare; RT-89.20 and RT-89.21 for
Settings offering no pricing or account control; and one assertion that the canvas draws what the
display decision chose, so the function and the view cannot drift apart.

**RT-89.24 counts loads rather than timing them.** "Upscales once and reuses" is about work not
happening, and the suite already has the instrument: RT-84.15 counts calls on a loader through
`PipelineCache`. One load for the first toggle to the base, none for the second and third.

**RT-89.23 asserts its own precondition.** With no rendering on screen, locking the candidate is
the only thing the code could do, so the test would pass without exercising the case it exists
for. It asserts that the rendering was displayed before the lock, and that the new base's pixel
size is the candidate's rather than the rendering's.

**One user test is allocated:**

> ⏳ UT-89.1: the lock chain is a usable way to move between iterations of an image

The lock chain is the first thing in this delivery a human can judge as a *way of working*
rather than as a behaviour. It transfers to #79's roll-up when this child closes.

## Temporary state in tests

RT-89.26 asserts that a released chain's files no longer occupy the output directory. It uses a
unique per-run directory beneath the operating system's temporary directory, removed in teardown
on success and on failure, as `AssetGraphTests` and `SessionStoreTests` already do. Run against
the real output directory it would delete a user's work; run against a shared path it would
collide with other tests.

No other test in this issue writes to disk.

## Guarding against a second copy of the state

`MainView.baseImageURL` is deleted in the same commit that introduces the graph-backed state.
Every test here would pass if the view kept its own base beside the graph and the two disagreed,
which is the pattern #82 shipped and its code audit caught. Deleting the property makes the
compiler find every reader, and the comment currently standing in for invariant I1 goes with it —
which is the stated point of this slice.

## Out of scope

- Search within the lock chain.
- Saving user-authored filters.
- Anything the graph does not already enforce: this slice wires what slices 1 and 2 built rather than extending it.
