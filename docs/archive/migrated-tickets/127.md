## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"the generated image in the example image is a different proportion (1024x1024) to the one that I have used as my original image (1471x1661). That means the curtain is kind of useless, since the people and items in the image are moved about."*

> *"This was an earlier defect/requirement that the returned image be *rendered* in the same proportion as the original image. Whether we actually physically resize it is a decision we need to make on it, since the realESRGAN models only upscale in 2x and 4x and the fact that the app upscales is in itself a complicating factor. I would not upscale to 2x then reduce to the right proportion, as that would be destructive on image quality. I would simply ensure that the image is *RENDERED* at the same proportion as the original. the FAL model has in fact stretched the image wide in this case, and it would be destructive to reduce the 1024x1024 image especially at such a low res then to upscale it."*

And, separately, on a 3423x2698 source:

> *"Only now I can see the returned image is actually the correct aspect ratio, but it is not being rendered to cover the whole display area, resulting in a very odd comparison that makes no sense."*

## The design already specifies this, and the build does not do it

Guide section 2.3:

> *"**The two sides share a width and may differ in height.** Each keeps its own proportions, so nothing is stretched to match the other's shape, and the single vertical divider therefore falls at the same fraction of width on both. Fitting each side into the canvas independently gave a 1:1 return a different width from a 3:4 original, so one line meant two different things --- which is what grok produces whenever the picture it is given has a short edge under 1024. The shared width is bounded by the canvas: the canvas's own width where both sides fit, and otherwise whatever width makes the taller of the two exactly fill the canvas's height, because using the full width unconditionally clips the more portrait of the two off the bottom."*

That is precisely the author's case --- a 1471x1661 source whose short edge is under 1024, returning 1024x1024 --- and it is precisely the rule that is not in effect. This is a defect against a written specification, not a new requirement.

The author's instruction that nothing be **physically** resized matches the design: the rule is about rendering, and guide 3.2 keeps physical derivations to the upscale stage.

## Violated AC

- **AC96.3** and the criterion superseding AC90.10 in [docs/ACs.md](../blob/master/docs/ACs.md), which carry the shared-width rule. `audit-acs` must confirm the exact IDs and whether the second observation --- a correctly-proportioned return not filling the display area --- is inside the same criterion or a second one.
- **UT-96.1** (the differently-shaped comparison) failed on this in the round and is re-offered on closure.

## Debugging and fix procedure

1. **Reproduce with the author's numbers**: a 1471x1661 source returning 1024x1024, and separately a 3423x2698 source returning a correctly-proportioned result. Record the rendered frame of each side. Two symptoms were reported and they may not share a cause.
2. **`CurtainGeometry` already owns this arithmetic.** #90 moved it there after UT-90.1 failed on pointer alignment. Establish whether the shared-width rule is absent from it or is present and not being called with the right sizes --- those are different fixes and the second is the more likely, given the second observation is about a *correctly* proportioned image.
3. **Physically resize nothing.** The author's reasoning is sound and matches guide 3.2: reducing a 1024x1024 return and then upscaling it is destructive twice.
4. **Do not disturb the divider mapping.** UT-90.1 failed once on pointer alignment and passed on re-offer; the shared-width rule is what makes one divider line mean the same thing on both sides, so a change here can break it. RT-96.13 asserts the mapping as inverses and must stay green.
5. Guide 2.3's notice requirement is separate and already delivered: a return whose shape differs from what was sent is reported to the status bar. Confirm it still fires; do not re-implement it.

## Test plan

- RT-127.1: a square return against a portrait source renders both sides at a shared width, each keeping its own proportions
- RT-127.2: where both sides fit, the shared width is the canvas width
- RT-127.3: where they do not, the shared width makes the taller side exactly fill the canvas height
- RT-127.4: a return matching the source's proportions fills the display area
- RT-127.5: neither side is stretched to match the other's shape
- RT-127.6: the divider falls at the same fraction of width on both sides, at any window width
- UT-96.1 re-offered: filter a picture whose short edge is under 1024 and judge the comparison

### F1 (blocker) — the ticket's premise is wrong: the shared-width rule is implemented and is called

I expected to find the rule absent. It is not. `CurtainGeometry.pairedFrames` implements guide 2.3 exactly:

```swift
let tallestInverseAspect = max(first.height / first.width, second.height / second.width)
let widthLimitedByHeight = container.height / tallestInverseAspect
let sharedWidth = min(container.width, widthLimitedByHeight)
```

That is *"the canvas's own width where both sides fit, and otherwise whatever width makes the taller of the two exactly fill the canvas's height"*, verbatim. Each side then keeps its own proportions. And `ComparisonView.swift:61` calls it.

So this is **not** a specified rule going unimplemented. The ticket says *"This is a defect against a written specification, not a new requirement"*, and that framing must be corrected before anything is changed.

### What the two symptoms are, given that

**Symptom one** — *"the generated image is a different proportion (1024x1024) to the one I used (1471x1661) ... the people and items in the image are moved about."* The curtain already renders both at a shared width, each keeping its proportions. What is being objected to is that **grok recomposed the picture**: a 1471×1661 portrait returned as a 1024×1024 square is not the same framing, and no rendering rule realigns subjects the provider has moved. Guide 2.3 anticipated the shape change and required the user be told; it never promised the comparison would stay useful across a recomposition.

**Symptom two** — *"the returned image is actually the correct aspect ratio, but it is not being rendered to cover the whole display area."* On a 3423×2698 source, roughly 1.27:1, with a canvas taller than that, `sharedWidth` is limited by height and the pair does not fill the width. **That is the rule behaving as specified.**

### F2 (blocker) — reproduction must come before any change

Both symptoms are claims about rendered geometry that cannot be settled from a description. Guessing at frame arithmetic is what cost #119 four remediation cycles, and the lesson recorded on AC119.1 applies directly: **when a measurement disagrees with the code, measure what is being measured.**

**Remediation.** No code changes until `pairedFrames` has been called with the author's two size pairs — 1471×1661 against 1024×1024, and 3423×2698 against its return — and its output compared against the canvas. Those are package-level calls and need no window, so this is cheap and should be the first thing done.

### F3 (finding) — one symptom is likely a specification change, and it is the author's to make

If symptom two is the rule working as written, closing it means **changing guide 2.3's shared-width rule**, not fixing an implementation. The guide records the trade-off already: fitting each side independently is what made a 1:1 return a different width from a 3:4 original, *"so one line meant two different things"*. Any change must keep the divider meaning one thing on both sides — which is what UT-90.1 failed on once.

**Remediation.** Once measured, put the options to the author with the trade-off stated. Do not decide it silently.

### F4 (finding) — RT-127.4 as drafted asserts the opposite of the rule

*"A return matching the source's proportions fills the display area"* holds only when the canvas is wider than the pair's shared aspect. Written unconditionally it contradicts `pairedFrames` and would fail on a tall window for the right reason.

**Remediation.** Split it: fills the canvas **width** where both sides fit within the canvas height, and fills the **height** otherwise.

### F5 (smell, kept as a guard) — the divider mapping must not move

RT-96.13 asserts `dividerFraction` and `dividerX` are inverses, and UT-90.1 failed on pointer alignment before that arithmetic moved into `CurtainGeometry`. Any change to the shared width changes what the divider maps onto. Run it before and after, unweakened.

## Measured. The second symptom is the specification, not a defect.

Commit above adds `CurtainProportionTests` and runs `pairedFrames` against your numbers. **5 tests, 0 failures.**

### What the measurement says

Your 3423×2698 source is **1.27:1**. A typical canvas is nearer **1.5:1**. So the picture is proportionally *taller* than the canvas, height is the binding constraint, and the shared width comes out at **761 points of 900** — filling the height exactly and leaving 139 points of canvas unused on either side.

Filling the width instead would make the pair a third taller than the canvas and clip it. Guide 2.3 chose this deliberately, and says so: *"using the full width unconditionally clips the more portrait of the two off the bottom."*

So *"it is not being rendered to cover the whole display area"* is the rule doing what it was written to do.

### Your first symptom is a different thing again

The 1471×1661 source returning 1024×1024 renders correctly — both sides share a width, neither is stretched, each keeps its shape. What makes that comparison useless is that **grok recomposed the picture**. A portrait returned as a square is not the same framing, and no rendering rule can realign subjects the provider has moved. Guide 2.3 anticipated the shape change and required you be told about it; it never promised the comparison would survive a recomposition.

### One correction to my own work, worth recording

My first version of RT-127.2 asserted that a 3423×2698 pair fills a 900-point canvas width. It does not, and the measurement caught it in the first run. Had I written that assertion into the fix instead of into a test, I would have "corrected" working geometry — which is exactly what #119 did for four cycles.

### What I need from you

Nothing here is broken, so there is nothing for me to fix without a decision from you. Three options:

1. **Leave it.** The rule protects against clipping, and the unused width is the cost.
2. **Let the pair fill the width and accept vertical clipping** on pictures taller in proportion than the canvas. Cheap, and it is what you asked for literally — but it hides part of the picture you are comparing.
3. **Fit each side independently.** This is what the rule replaced. It gives a 1:1 return a different width from a 3:4 original, so the one divider line means a different position on each side — the defect UT-90.1 failed on.

I recommend **1**, and if the unused width is the real objection, the better answer is probably a canvas that uses the window's shape rather than a change to the pairing rule.
