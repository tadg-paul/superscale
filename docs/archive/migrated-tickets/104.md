## Original issue body

## Problem statement

**Observed:** import a picture, and within a few seconds — while the import's own
upscale is still running — click a different scale. Nothing happens. The
application returns to idle with no run, no error and no notice, while the scale
control reads "8x requested, 4x in effect": a claim about a run that was never
started. The user waits for a picture nobody asked for.

**Expected:** choosing a scale causes an upscale at that scale, superseding the
run in flight.

Found by #101's RT-101.1 and RT-101.3, which timed out waiting for the reduction
notice; diagnosed by instrumenting the tests to report the application's own
state rather than by reasoning about it (two prior reasoned diagnoses were both
wrong).

## Reproduction

1. Import a picture large enough that its native upscale takes several seconds
2. Before that run completes, click a scale not currently in effect (e.g. 8x)
3. Observe: the readout updates, and the application goes idle without running

## Violated AC

- **AC93.1** in [docs/ACs.md](../blob/master/docs/ACs.md): *"A scale shown as
  not in effect remains choosable."* Choosable means choosing it does
  something. The control accepted the click and nothing acted on it.
- **AC83.7**'s reporting clause is the visible casualty: the reduction is never
  reported because the run that would report it never starts.

## Cause

`UpscaleViewModel.reupscaleIfNeeded` guarded on `!isProcessing`. A choice made
during a run was dropped without a word. The readout is deliberately a pure
function of the source and the request (`ScaleReadout`), so it is correct
before any run exists — which also means it cannot notice that nothing acted on
the request.

## Solution outline

The guard's real job was re-entrancy defence, not busyness defence, and it was
doing it by proxy — see #105 for what happened when it was removed outright.
The fix is the narrow flag: `isConfiguringRun`, set while `processImage`
configures a run, so a mutation the configuration itself causes cannot start
another. A run merely *in flight* no longer refuses the choice: superseding is
handled where it belongs, in `start`'s cancellation and in `publish`/`abandon`
guarding on `activeRun`, with cancellation treated as not a failure.

## Test plan

No new test IDs. The defect is covered end to end by existing regression tests
under AC83.7 and AC101.1 — RT-101.1 (the reduction is reported where the user
reads it) and RT-101.3 (the bar's contents are addressable) — which fail
against the defect by timeout and pass against the fix in 36s and 41s
respectively. A dedicated re-test would duplicate their coverage.
