## Original issue body

Child of delivery master #120 (bring the build onto the design of record).

## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"When applying a filter, there is an inexplicable delay in clicking it, and the spinner appearing and the 'Apply' button becoming disabled. This means I could double click the button and it would fire twice which is a problem esp since it costs money to fire that twice."*

## Why this is the first defect after the state model

Every other item in the round costs time. This one costs money, at 2c per firing, and it costs it silently --- a user who double-clicks gets one visible result and two charges.

## Violated AC

- **AC94.1** in [docs/ACs.md](../blob/master/docs/ACs.md): work on the working image reports immediately. The gap the author describes is the criterion's own subject seen from the other side: if the interface said something the instant the click landed, there would be no window in which a second click looked reasonable.

The second-firing half may not be covered by AC94.1, which is about reporting rather than about idempotence. If `audit-acs` finds no criterion covering *a paid action being issued once per intent*, backfill on the #94 family per `ISSUES.md` §"Bug-fix issues reference existing ACs" rather than stretching AC94.1.

## Debugging and fix procedure

1. **Measure the gap before closing it.** Record the interval between the click landing and (a) the control disabling, (b) the indicator appearing. Both matter and they may not be the same number. A fix aimed at the wrong one will look right and change nothing.
2. **Establish what occupies the gap.** `applyFilter` starts a `Task` which awaits `raiseBaseToMinimumIfNeeded` before `submitFilter`. On a picture below the filterable minimum that raise is a real Neural Engine run of several seconds. The hypothesis is that the disabling is bound to a state the coordinator sets only once the request is submitted, so the whole raise sits inside the window. Confirm before accepting.
3. **Close the window at the source rather than debouncing.** A time-based guard would make the second click land silently and leave the interface still saying nothing for the same interval. The control's enabled state should follow the intent, set synchronously when the click is handled.
4. **The indicator is a separate obligation.** AC94.1 requires the interface to report immediately, and a disabled button that says nothing else is not a report.
5. Re-run the `SUPERSCALE_UI_TEST_FAIL` tests: a request that never issues and a request that fails must both leave the control usable again.

## Test plan

- RT-122.1: the Apply control is disabled synchronously with the click, before any asynchronous work begins
- RT-122.2: two clicks in rapid succession issue exactly one provider request
- RT-122.3: the interface reports that work has begun within the same interaction as the click
- RT-122.4: after a failed apply, the control is enabled again
- RT-122.5: after a cancelled apply, the control is enabled again

### What this delivers, in plain language

A user presses Apply. Today nothing visible changes for as long as it takes to raise the picture to the filterable minimum and upload it to the provider — several seconds on a small photograph — and the control stays live throughout. A second, impatient click sends a second paid request. After this issue, the press is acknowledged the instant it lands and cannot be repeated.

### The mechanism, established from code before any change

`FilterPanel.canApply` ends in `!isApplying`, and `MainView` supplies `isApplying` as `generationCoordinator.phase == .generating`. That phase is set inside `GenerationCoordinator.generate`, which is reached only after:

1. `applyFilter` starts a `Task`;
2. `raiseBaseToMinimumIfNeeded` runs — on a picture below the filterable minimum this is a **real Neural Engine upscale of several seconds**;
3. `submitFilter` uploads the base to provider storage — a network round trip;
4. and only then does `generationCoordinator.start` reach `generate`.

So the entire raise and the entire upload sit inside the window during which the control is live. The ticket's hypothesis is confirmed, and the window is far wider than "a moment": on the author's own fixture it is the slowest path in the application.

### F1 (blocker) — the ticket names one gap; there are two, and they need different fixes

The ticket says *"the delay in clicking it, and the spinner appearing and the 'Apply' button becoming disabled"*. Those are two obligations:

- **Idempotence**: one press issues one paid request.
- **Acknowledgement**: the interface says something immediately.

A fix that only disables the control satisfies the first and leaves the user watching an unchanged window, which is the defect AC94.1 already exists to prevent. A fix that only shows an indicator satisfies the second and still charges twice.

**Remediation.** Both, with separate tests. RT-122.1 and RT-122.2 cover idempotence; RT-122.3 covers acknowledgement.

### F2 (blocker) — no criterion covers a paid action being issued once per intent

**AC94.1** covers the reporting half: work on the working image reports immediately. It says nothing about how many requests an intent produces, and stretching it to mean that would be manufacturing coverage.

**Remediation.** Backfill onto the #94 family:

> **AC94.4** — A single intent to apply a filter issues at most one provider request, whatever the interface does between the intent and the request being sent.

Self-audit: system state, not an action. No forbidden verb. Falsifiable without specifying observation.

### F3 (finding) — a time-based guard would be the wrong fix and is the obvious one

Debouncing the control for N milliseconds satisfies RT-122.2 and leaves the interface saying nothing for the same interval, so the second click still looks reasonable to the user and merely lands silently. It also converts a correctness property into a tuning constant.

**Remediation.** The control's enabled state must follow a flag set **synchronously in the click handler**, before any `await`. Recorded so the cheaper fix is not reached for later.

### F4 (finding) — the flag must clear on every terminal path, and there are four

Success, provider failure, upload failure, and cancellation. A flag that leaks on any of them leaves Apply permanently dead — a worse defect than the one being fixed, and one a happy-path test will not catch.

**Remediation.** RT-122.4 and RT-122.5 cover failure and cancellation. The upload-failure path is distinct from the provider-failure path — #113 established they are different routes — so both are exercised, through `SUPERSCALE_UI_TEST_FAIL=provider` and `=generation` respectively.

### F5 (smell, recorded) — the same shape exists on Lock and on the scale controls

`lockButton` and the scale buttons also start asynchronous work. Neither was reported and neither is in this ticket's scope.

**Left alone, recorded.** Lock is local and effectively instantaneous, and the scale controls are a toggle group where a second press means something different rather than repeating the first. Noted so a later reader does not assume they were overlooked.

### F1 (finding) — RT-122.2 cannot count provider requests through the interface

*"Exactly one provider request"* is the criterion, and a GUI test observes results, not requests. Counting arrivals is not the same claim: a second request that returns an identical picture produces one visible change and two charges, which is precisely the defect.

**Remediation.** The UI-test generation stub already exists and is the only thing that sees the requests. Give it a **request counter** readable through the app's own accessibility tree — a status element the suite can read — rather than inventing a side channel. The stub is `#if DEBUG` and UI-test-only, so this adds nothing to a shipping build. **This is a change to the test harness and is recorded as such**, though not test-architecture creep: no new runner, framework or dependency, and it is the only way to observe the property the criterion is about.

### F2 (finding) — RT-122.1's "immediately" is a race as written

Asserting the control is disabled *after* clicking is a poll, and a poll that runs after the disabling has already happened cannot distinguish "disabled synchronously" from "disabled a second later". The bug is precisely that it happens late.

**Remediation.** Assert the negative that the defect produces: after a single click, a **second click within the window changes nothing** — no second request by F1's counter. That is decidable and it fails against the unfixed code, where the second click lands during the raise. Recorded because the intuitive assertion is the useless one here.

### F3 (finding) — RT-122.7 is the only test that reproduces the reported conditions, and the suite fixture is already undersized

The suite's fixture is 240×320, below the filterable minimum, so every existing filter test already goes through a raise. That is convenient but accidental.

**Remediation.** RT-122.7 asserts the fixture is undersized as a precondition rather than relying on it, so the test fails loudly if the fixture is ever changed instead of silently exercising a millisecond window.

### F4 (finding) — RT-122.5's cancellation may not be reachable

The generation stub returns immediately, so there may be no window in which to press Cancel — the wall that retired RT-113.6 and RT-119.4. The raise, however, is real work of several seconds and Cancel is offered during it.

**Remediation.** Target the cancellation at the **raise**, which is genuinely slow and genuinely cancellable, rather than at the stubbed provider call. If it still proves unreachable, retire the identifier with its reason rather than leaving a test that passes by not running.

### Coverage, gaming, integration, architecture, temporary state, typing

- **Coverage.** AC94.4 has six tests across four terminal paths. AC94.1 gains RT-122.3. No single-test criterion.
- **Gaming.** The narrowest shortcut is a time-based debounce, which passes RT-122.2 and leaves the interface silent. **RT-122.3 blocks it** by requiring acknowledgement in the same interaction. The next narrowest is disabling on the coordinator's phase as today and merely making the phase arrive sooner, which RT-122.7 blocks by covering the raise.
- **Integration.** The failure paths and the enablement flag could each pass alone and disagree together. RT-122.4 and RT-122.6 exercise the flag's clearing through two different subsystems' failures.
- **Test architecture.** One addition to the existing UI-test stub, recorded in F1. No new harness.
- **Temporary state.** GUI tests write only through the app under test, into the suite's existing per-run root.
- **Typing.** Seven RT. No UT: every condition here is machine-decidable, and *"Apply responds immediately"* is already **UT-94.1**, re-offered on closure rather than duplicated.

- **Remediation summary:** add a request counter to the UI-test stub, readable through the accessibility tree; rewrite RT-122.1 as the second-click-changes-nothing assertion; make RT-122.7 assert its precondition; retarget RT-122.5 at the raise. Re-audit follows.
