## Discovered during #100, recorded and not implemented: EXIF orientation

The AC audit on #100 found a second way image metadata can alter the dimensions the application measures. **It was not among the risks recorded at the v2 delivery gate, so it is outside this delivery's confirmed scope** and is recorded here rather than implemented.

A photograph from a phone commonly stores its pixels in one orientation and records an EXIF tag describing how to rotate them for display.

**The hypothesis, stated as a hypothesis:** `CGImageSourceCreateImageAtIndex` with `nil` options returns the **stored** dimensions and does not apply that tag. It has not been verified, and verifying it needs a fixture carrying an orientation tag, which the suite does not have.

If it holds, a portrait photograph is measured as landscape, and that reaches three places:

- **The 1024 floor**, which is a *long-edge* rule and therefore orientation-sensitive. A 768 x 1024 photograph stored as 1024 x 768 with a rotate tag would be judged to clear the floor when its displayed long edge is the same 1024 either way — so this particular case is benign, but a 600 x 1200 stored as 1200 x 600 is not.
- **`Provenance.providerChangedTheShape`**, which compares aspect ratios. A provider that preserved the framing exactly could be reported as having reshaped the picture, and the user told so.
- **`CurtainGeometry.pairedFrames`**, which lays the two sides out by aspect, so the curtain would present a correctly-oriented picture at the wrong shape.

The area ceiling is unaffected: area is orientation-invariant.

**Recommended follow-up**, for a ticket outside this delivery: first establish empirically whether the hypothesis holds, using a fixture written with `kCGImagePropertyOrientation`. Only if it does, decide whether the floor and the aspect comparison should read oriented dimensions. Deciding that before establishing the fact would be the guess-first pattern this delivery's predecessor kept having to correct.
