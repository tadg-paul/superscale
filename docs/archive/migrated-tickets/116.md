## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure). Surfaced by the diagnosis on #115 (the graph allocates into a directory nothing creates).

## Problem statement

The GUI suite redirects the app's generated-image store and its session history to a test root, but **not the workspace's asset graph**. Every raise and every upscale a UI test performs is allocated into the author's real `~/Library/Application Support/Superscale/Generated`.

Nothing detected this because the writes have been failing for the separate reason recorded on #115. Once #115 is fixed, they will start succeeding — into the user's real application-support directory, from a test suite, 101 tests at a time.

## Evidence

- `SuperscaleAppUITests.setUpWithError` (`SuperscaleAppUITests.swift:70-75`) sets `SUPERSCALE_UI_TEST_ROOT`.
- `SuperscaleApp.swift:55-71` consumes it for `credentialStorage`, the `GenerationCoordinator`'s `GeneratedImageStore` (`root/Generated`), and the session store. The redirection is deliberate and documented in the surrounding comments.
- `MainView.swift:22` is not part of that: `@StateObject private var workspace = WorkspaceState(outputDirectory: V2AppPaths.generated)`. It is a property initialiser with no environment check, so it resolves to `~/Library/Application Support/Superscale/Generated` (`SuperscaleApp.swift:13-22`) in every launch, test or not.

So the app under test has two output directories: the coordinator's, correctly under the test root, and the graph's, in the user's real storage.

## Acceptance criteria

The behaviour was never specified: `docs/ACs.md` has no storage family, and no existing criterion says where the application resolves its asset storage. Under path 2 of `ISSUES.md` §"Bug-fix issues reference existing ACs", second sub-case, it is defined here rather than backfilled onto a family that does not exist.

**Key:** ✅ passing · ⏳ pending · ❌ failing · ~~🚫 removed~~

**The workspace shares the coordinator's `Generated` directory** rather than taking a sibling. Both resolve to the same path in production today, so sharing preserves current behaviour and a sibling would silently change where assets land on an ordinary launch. Recorded here rather than left to be inferred from the diff.

This is not only a harness concern. Underneath the test failure, the application resolves its storage root in two independent places — `SuperscaleApp.swift:55-71` for the coordinator and session store, `MainView.swift:22` for the workspace — with nothing holding them together. That is the same class of defect as AC100.2's "through one function": two ways of deciding the same thing, and no way to tell them apart.

## One deliberate widening, recorded

Before this fix, the debug block redirected storage only when **both** `SUPERSCALE_UI_TEST_ROOT` and `SUPERSCALE_UI_TEST_GENERATED_IMAGE` were set. A launch supplying only the root redirected nothing.

The root is now honoured on its own; the stubbed generation service still requires both, because it genuinely needs the image. The two variables answer unrelated questions — where the application keeps its files, and what picture a stubbed provider returns — and requiring the second before honouring the first is a smaller version of the same coupling this ticket exists to remove. The GUI suite sets both, so no existing run behaves differently.

Recorded as decision D-2 on master #114 rather than left in the diff.

## The second violation, recorded and not fixed here

`TESTING.md` §"Temporary test state" requires a unique per-run directory beneath the operating system temporary directory, with teardown on success, failure, and handled interruption. `setUpWithError` points the test root at `<projectRoot>/.agent/tmp/ui-test-runtime`, which is project-local and fixed, and the test class defines no `tearDown`. That is a suite-wide correction touching every test in the file, recorded on master #114 as its own concern. Folding it in here would mix a one-line redirection with a harness change.

## Fix procedure

1. Give the workspace the same environment-derived root the coordinator already uses, resolved in one place rather than read twice. `SuperscaleApp` already computes the root at line 57; the workspace should take its directory from the same value rather than from `V2AppPaths` directly.
2. `MainView.swift:22` is a `@StateObject` property initialiser, so the value has to arrive through the environment or an initialiser parameter rather than being read at the point of declaration. Prefer whichever the app already uses for the coordinator, so there is one mechanism and not two.
3. Verify by running one GUI test with the real `~/Library/Application Support/Superscale/Generated` absent and confirming it is still absent afterwards, with the assets under the test root instead.

## Test plan

The six tests are listed against AC116.1 above. What matters is where each is written, not only what it asserts.

**The wrong value is produced in a SwiftUI property initialiser.** `MainView.swift:22` is a `@StateObject` declaration, which no package test can reach. A test that constructs its own `WorkspaceState` with a root and checks where allocation lands proves the type behaves — which it already does — and says nothing about what the application passes it. So the coverage is deliberately split:

- **RT-116.1, RT-116.2, RT-116.3, RT-116.5 and RT-116.6** are unit tests over the **one resolution function** the fix introduces, across three storage kinds and both root configurations.
- **RT-116.4** is a GUI test proving the application routes through that function rather than around it. Without it, the unit tests describe a function nothing is obliged to call, which is how this defect came to exist.

Making the resolution a single function is not incidental. AC116.1 says "a single configured root", and one function is what makes that testable at all — the same correction AC100.2 made for measurement, for the same reason: two ways of deciding one thing, with no way to tell them apart.

Notes on two individual tests:

- **RT-116.4 asserts positively**, that the assets are present beneath the configured root, before it asserts negatively that the user's directory is untouched. The negative alone cannot discriminate: against the unfixed code the application tries to write to the user's directory, fails because it does not exist (#115), and leaves it absent — so a negative-only test passes without the fix, and would only start discriminating once #115 landed. Asserting the positive removes that dependency, and removes a circular ordering between the two tickets.
- **RT-116.3** is the one a careless redirection breaks: reading the configured root unconditionally, with no fallback, would move every ordinary launch's storage.

**Temporary state.** The unit tests allocate their own per-run directory beneath the operating-system temporary directory and remove that exact directory in teardown, on success and on failure. RT-116.4 inherits the GUI suite's project-local root, which remains recorded on master #114 as its own concern.

## Why this matters beyond tidiness

`TESTING.md` requires the isolation, but the operational reason is sharper: a suite that writes into the user's real storage cannot be run safely on a machine that has real work in it, and a suite whose assets accumulate outside any teardown grows without bound. Both are true here the moment #115 lands.
