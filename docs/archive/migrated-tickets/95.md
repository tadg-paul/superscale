## Original issue body

Child of delivery master #79. Five reports from use, 2026-08-25, four of them read from a screenshot of the Settings scene and each traced to its cause in the source.

## Problem

### Every credential row says its name twice

`SettingsView.swift:156` draws the row with `LabeledContent(title)`, and `:158` passes the same `title` into `SecureField(title, text:)` as the field's own label, which macOS renders beside the field. So the row reads *"Generation key ●●●●●●●● Generation key ✓ 🗑"*, and the same for the account key.

### The key is masked, and it is not a password

`SettingsView.swift:158` is a `SecureField`. The author: *"in config panel API key should not be a password field it is not a password."* A FAL key is a credential, not a secret the user recites from memory, and masking it prevents the one check anybody performs on a pasted key: looking at it.

### The green tick means "saved", not "works"

`SettingsView.swift:181` renders `Label(configured ? "Configured" : "Not configured", ...)`, and `configured` reports whether a key is *stored*. Paste a typo, press save, and the tick goes green. The author: *"green checkmark should only appear after validating that key against the live api."*

### There is no default output folder

`GenerationPreferences.swift:9` initialises `outputFolder: nil`. Nothing supplies a fallback, so a user who has never opened Settings has no output folder. The author asks for `~/Downloads`.

### A control the MVP excludes is still there

Visible in the same screenshot, and not reported: **"Confirm generation above / $ Threshold 0.05"**, at `SettingsView.swift:77`. `IMPLEMENTATION_GUIDE_v2.md` section 6 removes the pricing client, the account client, the session cache **and the cost-confirmation policy** from MVP scope. This is the third paused control still present in Settings after the two ledger entry L24 recorded. Its label is also mis-wrapping to "Thres hold".

### Condition enumeration

- **AC95.1** implies two conditions, one per row. Both are the same defect and both are asserted, because fixing one field's label and not the other is exactly the kind of half-fix a single test permits.
- **AC95.2** implies two: legible while typing and legible afterwards. The second is the one that matters — a key is checked when the user returns to Settings wondering whether the right one is in there.
- **AC95.3** implies four: stored-but-unchecked, accepted, rejected with a reason, and unreachable. The fourth is what stops a network failure being reported as a bad key, which would have the user delete a perfectly good credential.
- **AC95.4** implies three: the default, persistence of a choice, and recovery when a stored folder has gone. The third is real — an external disk, or a folder the user deleted — and without it the application has no output folder and no way to say so.
- **AC95.5** implies three: the cost-confirmation control goes, the pricing and account controls go, and the account key row stays. L24 recorded that #88 removed the *tests* for the pricing and account controls while leaving the controls themselves; this removes them.

  **The third condition is the distinction the first AC audit forced.** The criterion first read "no control for a feature the MVP excludes", which would have required deleting the account key row — a credential guide 2.7 explicitly retains while noting no MVP feature uses it — and which contradicted AC95.1's test of that same row's label. The line is between *storing* a credential for later and *operating* a paused feature. A Check Pricing button performs an operation the MVP has removed; a key field holds a value for a version that will.

- **AC95.3's asymmetry between the two keys is deliberate.** The generation key can be verified with a cheap live call. Verifying the account key would mean calling an account or billing endpoint, which is the surface this MVP has paused and whose client this delivery removes — so an implementation covering both keys would either resurrect that client or write a check that cannot work. The account key therefore shows stored or absent and nothing more. Raised by the first AC audit.

## Solution

**The field labels are hidden, not renamed.** `.labelsHidden()` on each field, with the accessibility identifiers unchanged so the existing GUI tests still find them. The row's `LabeledContent` keeps the visible name.

**That name gets an identifier of its own** — `generationKeyLabel`, `accountKeyLabel` — so RT-95.1 and RT-95.2 can assert that exactly one element carries it. Without that the tests count matches in the accessibility tree, and `.labelsHidden()` hides a label *visually* while the element may keep it as its accessibility label: the count could be identical before and after the fix, and the two tests for the reported defect would pass against the unfixed view. Raised by the first test audit.

**The persistence tests use their own preferences.** `GenerationPreferencesStore.init(defaults:)` takes an injectable `UserDefaults` and falls back to `.standard`; a test taking that default would rewrite the author's own output folder. RT-95.10 and RT-95.11 construct the store with a run-unique `UserDefaults(suiteName:)` and remove that suite in teardown.

**`SecureField` becomes `TextField`.** A FAL key is a bearer credential and the standing rule is that it lives only in a request header and never in a body, a URL, a log or a persisted record — that rule is about where it *travels*, not about whether the person who owns it may look at it in their own settings window. It remains in the Keychain.

**Validation is a request, and its outcome is a third state.** The tick becomes one of: absent, stored, verified, rejected. A network failure leaves the key *stored*, not *rejected*: the difference between "we could not ask" and "the answer was no" is the difference between a user waiting and a user deleting a working key. Editing a key returns it to unverified, because a tick beside changed text is the same lie in a new place.

**The check is the model catalogue, and it is free.** `GET /v1/models?category=<c>&status=active` on `api.fal.ai`, which `FAL_REQUEST_REFERENCE.md` lists and which the generation key authorizes. A 401 from it is the unambiguous answer.

Named in the criterion rather than left to the implementer, because the client most obviously to hand is `FalGenerationClient`, whose calls **generate images at 2c each**. An implementation that verified by generating would make pressing save cost money, and a user checking a mistyped key twice would pay twice for the privilege. Raised by the second AC audit; RT-95.16 asserts that verification issues no generation request.

It goes through `FalGenerationKit`'s existing `FalHTTPTransport`, the same seam every other client uses, so it is stubbed in tests and no test reaches the network.

**The output folder gains a default in one place.** `GenerationPreferences` supplies the user's Downloads directory when nothing is stored, resolved through `FileManager.urls(for:in:)` rather than by building a path from the home directory, so it is correct on a machine where Downloads has been relocated.

**The cost-confirmation control is deleted**, with `costThreshold` and its persistence going with it. `GenerationSettingsState.costThreshold` and the `Key.costThreshold` preference are removed rather than left unread: a stored value nothing consults is a thing a later reader has to prove is dead.

## Test type and location

Seventeen regression tests.

**AC95.4's are package tests** in `Tests/SuperscaleUXCoreTests/`, over `GenerationPreferences`: what the default is, that a choice round-trips, and what happens when a stored folder has gone. None needs a window.

**AC95.3's are package tests** over the verification call, against a stubbed `FalHTTPTransport` as `FalGenerationKit`'s other clients already are. The four outcomes are four stubbed responses. **No test calls a paid or live endpoint.**

**AC95.1, AC95.2 and AC95.5's are GUI tests** in `SuperscaleAppUITests`, because each is a question about what the Settings window contains: a name appearing once, a field's contents being readable, a control being absent. None involves an upscale, so they cost the suite almost nothing.

**One user test:**

> ⏳ UT-95.1: the Settings scene reads cleanly, with each row saying what it is once

The author read this window and found four separate faults in it. That the remedy *looks* right is a judgement no assertion reaches, and it is the judgement that found the faults in the first place.

## Standards

Naming, `ABOUTME:` headers, doc comments explaining *why* rather than *what*, and one
responsibility per type all hold. No function exceeds 50 lines; the deepest nesting is two levels.

## Error handling

Every path is either a hard fail or handled explicitly. No `try!`, no empty `catch`, no `|| true`
equivalent. `saveAndVerifyGenerationKey` throws on the store and does not verify what was never
stored, which is right: there is nothing to ask about. The `defer` clearing
`isVerifyingGenerationKey` runs on both paths.

`FalCredentialVerdict.unreachable` is deliberately distinct from `.rejected` and both the verifier
and the state preserve the distinction. Collapsing them would have a user delete a working key.

## Security

**The credential never leaves the header.** `FalCredentialVerifier` sets `Authorization` and builds
no body; `test_theKeyTravelsInTheHeaderOnly` asserts the key is absent from the URL, where it would
otherwise reach every proxy log between here and the provider.

**The check is free.** `GET /v1/models`, not a generation. `RT-98.16` asserts no body, one call, no
model name and no queue path in the URL — so an implementation that verified by generating would
fail rather than silently charge the user 2c per keystroke-check.

**`TextField` rather than `SecureField` is not a security regression.** Storage is unchanged (the
Keychain) and transport is unchanged (the header). What changed is whether the person who owns the
credential may look at it in their own settings window.

**No credential reaches a log or a persisted record.** `GenerationPreferences` holds no secret;
`storeCredential` routes to the Keychain service.

## Complexity

`SettingsView.credentialRow` takes seven parameters, which is at the edge of comfortable. It is a
view builder with one caller shape and two call sites, and collapsing them into a struct would add
a type that exists only to be destructured immediately. Left as it is.
