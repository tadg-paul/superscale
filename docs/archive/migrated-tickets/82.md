## Original issue body

Child of delivery master #79 (slice 2). Builds directly on the asset graph delivered in #81.

## Problem

Local and cloud work are the same shape of job — take an image, do something slow to it, produce another image — and the application models them twice, differently.

**Two run-state models.** The cloud path has `GenerationPhase` with `idle`, `generating`, `succeeded`, `cancelled` and `failed` (`GenerationCoordinator.swift:61-77`), a retained `Task`, and a `cancel()` that both cancels the work and records that it was cancelled. The local path has `isProcessing: Bool` and `progressMessage: String` (`UpscaleViewModel.swift:37-38`). A caller cannot ask the two the same question.

**Structure is discarded and then recovered by parsing prose.** The kit reports progress as a sentence. The view model matches on the wording to get the structure back:

```swift
if message.hasPrefix("Enhancing") && message.contains("face") {
    if let num = Int(message.components(separatedBy: " ")[1]) {
        self.lastUpscaleFaceCount = num
    }
}
if message.hasPrefix("Stitching output"), case .custom = self.scaleMode {
```

(`UpscaleViewModel.swift:428-438`)

The kit knows the phase and the face count. It flattens both into English, and the view model splits the English on spaces to get the number back. Rewording a progress message silently breaks the face count.

**The local path cannot be cancelled at all.** `UpscaleViewModel.swift:421` starts the work with `Task.detached` and discards the handle. There is nothing to cancel, and nothing to await.

That matters beyond the missing button. `reupscaleIfNeeded` guards on `isProcessing`, but `processImage` is also reached from `handleDrop` and `upscale(_:)`, which do not. Dropping a second image while the first is still upscaling starts a second detached task, and both write `result`, `resultData` and `resultSource` when they finish. Which one lands last is not determined by anything. The user can be left looking at the upscale of the image they replaced.

`Task.detached` is also what `SWIFT.md` asks to avoid unless isolation from the current task is required and documented; here it is neither.

**Automatic upscaling cannot be turned off.** `ScaleMode` is `.preset(Int)` or `.custom` (`UpscaleViewModel.swift:17-20`) with no off state, and every button in `ScalePicker.swift:26-57` selects and none clears. Dropping an image always spends roughly three seconds of model load and processing, which in a filter-first session is spent on an output the user is about to set aside.

## Solution

One `Stage` shape, in `SuperscaleUXCore`, that both kinds of work take.

```swift
public enum StagePhase: Equatable, Sendable {
    case loading
    case detecting
    case tiling(completed: Int, total: Int)
    case stitching
    case enhancingFaces(count: Int)
    case uploading
    case awaitingModel
    case downloading
    /// A report the mapping does not recognize. It still reaches the caller, so an unmapped
    /// message degrades to plain text rather than leaving progress frozen.
    case unclassified
}

public struct StageProgress: Equatable, Sendable {
    public let phase: StagePhase
    public let detail: String?   // for display only; never parsed
}

public enum StageRunState: Equatable, Sendable {
    case idle
    case running(StageProgress)
    case succeeded(AssetReference)
    case cancelled
    case failed(StageFailure)
}
```

`detail` exists so a phase can carry wording for the user without that wording becoming the interface. Nothing reads it to decide anything.

### The stage signature, and why it differs from the guide

`IMPLEMENTATION_GUIDE_v2.md` section 3.3 publishes:

```swift
func run(input: Asset, options: Options,
         progress: @Sendable (StageProgress) -> Void) async throws -> Asset
```

That cannot be implemented against the graph as built in #81. `AssetGraph.recordUpscale` allocates the asset and the location it must be written to, precisely so no two upscales can collide — a stage returning an `Asset` it minted itself would put that guarantee back in the caller's hands.

The signature is therefore:

```swift
/// What a stage reads: the graph's reference to the asset, paired with where it lives.
/// The reference travels with it so a completion can be recorded against the right asset.
public struct StageInput: Equatable, Sendable {
    public let reference: AssetReference
    public let fileURL: URL
    public let pixelSize: CGSize
}

/// Where a stage writes. Allocated by the graph, never chosen by the stage.
public struct StageOutputLocation: Equatable, Sendable {
    public let reference: AssetReference
    public let fileURL: URL
}

public struct StageOutput: Equatable, Sendable {
    public let pixelSize: CGSize
    public let resolvedModelName: String?
    public let wasAutoDetect: Bool
}

/// One failure type for both stages, which is what AC82.2 asks for. Slice 8 maps the FAL
/// error taxonomy into it; this slice establishes that there is one shape to map into.
public enum StageFailure: LocalizedError, Equatable, Sendable {
    case inputUnavailable(URL)
    case processingFailed(stage: String, reason: String)
    case outputNotWritten(URL)
}

public protocol Stage {
    associatedtype Options
    func run(
        input: StageInput,
        output: StageOutputLocation,
        options: Options,
        progress: @Sendable (StageProgress) -> Void
    ) async throws -> StageOutput
}
```

The graph allocates, the stage writes the bytes to the location it was given, and reports what it made. The caller records the completion against the reference the graph already holds.

**The stage writes; it does not hand bytes back.** `GUIUpscaleProcessing` already holds the whole image in memory, and a 4096-pixel output is roughly 50 MB. Returning that through the caller as well would move the buffer one more time for nothing, and it would make AC82.5 false — a stage that returns bytes never writes anything, and there would be no partial output for AC82.4 to be about.

The change is recorded in the guide as part of this slice.

### Two stages

- `UpscaleStage` wraps `SuperscaleKit` through the existing `GUIUpscaleProcessing` seam, so its behaviour is testable with a stub processor and no Core ML. It serves both upscale targets; the target is an option, not a separate stage.
- `FilterStage` wraps `FalGenerationKit` through `GenerationCoordinator`. Its request construction is slices 5 and 6; this slice gives it the shared shape.

They are observed independently rather than chained, which is what lets the view show a candidate while its upscale is still running.

### Cancellation

A `StageRunner` holds the `Task` for the run in flight and cancels it when a new run starts for the same stage. This replaces `Task.detached` with a structured child task, so a superseded run's completion cannot overwrite the newer one's: the runner ignores a result from a task it no longer holds.

**It disconnects progress as well as results.** A run has two output channels, and dropping only the result would leave the superseded run's progress on screen — alternating with the new run's, for as long as the old one keeps working. That is not hypothetical while the kit does not check for cancellation, which it does not until slice 3.

**What this slice does not promise.** `SuperscaleKit`'s tile loop does not yet check for cancellation, so a cancelled upscale stops being *observed* immediately but keeps *running* until the current pipeline call returns. Making it stop is D6, in slice 3. No acceptance criterion here claims otherwise, and the distinction is why AC82.3 is written about the result never being published rather than about the work stopping.

### Scale selection

`ScaleMode` becomes:

```swift
public enum ScaleSelection: Equatable, Sendable {
    case off
    case preset(Int)
    case custom
}
```

with `choose(_:)` returning `.off` when the choice is already active, which is what makes the buttons a toggle group.

**The transition is the only way to a new selection.** `ScaleSelection` exposes no way to construct a value directly, and `UpscaleViewModel.scaleSelection` is `private(set)` with mutation only through a method that delegates to `choose(_:)`. This matters because every test in this issue runs against the package, and `make test` does not build the application target — so without it, all thirty-six could pass while `ScalePicker.swift:27` still assigns `viewModel.scaleMode = .preset(scale)` directly and the toggle never works for the user. That is the same shape as D1 in #81: a correct accessor sitting unused beside the wrong one. Making the wrong call stop compiling is the instrument that worked there, and the application build is part of this issue's verification evidence for the same reason.

### The runner owns the trigger

`UpscaleRunner` owns not only the run in flight but the decision to start one. "The working image changed, so the run in flight is stale" and "the model changed, so a run is due" are the same question asked at different moments, and splitting them is why `scaleMode` has four writers today.

It holds the graph, allocates each run against it, and decides from the selection whether a run is due at all. This is also what makes the decision testable: left in the view model, RT-82.33 and RT-82.34 would describe behaviour in the application target, where the regression command cannot reach it.

**How far the application goes with it, and why it stops there.** The upscale workspace does not yet hold an `AssetGraph` — the graph reaches it in slice 9, which is where the workspace is rebuilt around it. Until then the workspace drives the same stage types through `GUIUpscaleCoordinator` rather than through the runner: `UpscaleProgressReader` for structured phases, one retained cancellable task per run, and a run token that decides which run may publish.

That boundary is a deliberate trade, not an omission. Routing the workspace through the runner now would mean taking the result as a file the graph allocated, and `StageOutput` carries no bytes by design — a 4096-pixel output is roughly 50 MB and moving it twice buys nothing. But the face-enhancement toggle is instant because the *pre*-face variant is cached in memory from `preFaceImageData`, and that cannot survive a bytes-free return. Full wiring would either lose that v1 behaviour or reintroduce the buffer the design rejected.

What the workspace does take is everything the problem statement is about: the progress parsing is gone, the discarded-handle detached task is gone, a superseded run is cancelled, and its result and progress reach nothing.

**Four places currently overwrite the selection, and each has to stop.** An off state is worthless if anything else can turn it back on:

| Location | Today | After |
|---|---|---|
| `UpscaleViewModel.swift:416` | Every import sets `.preset(nativeScale)` | The native scale is adopted **only when a scale is already selected**. A cleared selection stays cleared, and an image dropped with the scale off simply becomes the base |
| `UpscaleViewModel.swift:211` | Changing the model sets `.preset(scale)` | The same: the model's native scale replaces the *selected* scale, and does not create a selection |
| `UpscaleViewModel.swift:118`, `:154` | Emptying a custom field reverts to `.preset(nativeScale)` | Reverts to the previously selected preset, or to cleared if there was none |

RT-82.25 is what stops the obvious over-correction. Deleting the import-time assignment altogether would satisfy AC82.8 while losing the v1 behaviour where a new image adopts its model's native scale, which is a regression the user would feel immediately.

**The selection is the single source of the active choice.** Today it is two states that have to agree: `showCustomFields` says whether the fields are open, and `scaleMode` becomes `.custom` only once a valid dimension has been typed. Between those two moments custom is shown but not selected, and choosing it again neither clears it nor re-opens it — a dead control. After this slice, `showCustomFields` is derived from the selection rather than assigned alongside it, so choosing custom makes it the active choice immediately and choosing it again clears it.

**Clearing the selection does not discard typed dimensions.** The typed width and height are the user's work, and a toggle press is not a request to throw it away. Re-selecting custom returns them to what they had.

**Clearing the selection releases the upscaled output that exists.** AC82.6 is a claim in both directions. An upscale is a deterministic derivation reproducible in seconds, so releasing one costs the user nothing, and leaving one on screen with no scale selected would contradict what the control says. Re-selecting the scale re-derives it.

### Cancelling something that is not running

`GenerationCoordinator.cancel()` sets `phase = .cancelled` unconditionally, so cancelling an idle coordinator reports a cancellation that never happened. AC82.2 promises one run-state model, so this is settled in the model's favour: cancelling a stage that is not running leaves it idle. That is a change to existing cloud behaviour, made here because the alternative is two stages that disagree in exactly the case the AC is about.

**It moves into `SuperscaleUXCore`.** It is in the app target today, where `make test` cannot reach it — the app target is built by `make test-gui`, not by the regression command. Scale selection is orchestration rather than presentation, which `ARCHITECTURE.md:29-33` places in `SuperscaleUXCore`, and `SWIFT.md` asks for behaviour needing tests outside the UI to be extracted from the view. `ScalePicker` becomes a renderer of the selection and a sender of choices.

### Patterns and anti-patterns

- Swift, existing project structure. No new dependency, no new test architecture.
- `async`/`await` with structured child tasks. No `Task.detached` (`SWIFT.md` §Concurrency).
- `CODING.md` §Prohibited Anti-Patterns: no error suppression. A stage failure is a typed `StageFailure`, not a discarded error or a bool.
- `SWIFT.md`: no force unwrapping, no `try!`, no empty `catch`.
- Progress phases are values. Nothing matches on prose to recover structure — that is the defect being removed, not a pattern to preserve.
- UI state stays on the main actor; stage work does not.

### Condition enumeration

- **AC82.1** implies four conditions: phases are distinguishable as values, the face count is numeric at the boundary, tile progress carries its counts as numbers, and a report the mapping cannot classify is not lost. RT-82.1 to RT-82.3, RT-82.26. The face count and the tile counts are separate tests because they are recovered from different messages by different rules, and either can be got wrong alone. The fourth exists because `StagePhase` is a closed enum mapped from what `SuperscaleKit` emits, and this slice does not change the kit: an unmapped message would otherwise vanish and leave progress frozen while work continued.
- **AC82.2** implies four conditions: the same run-state sequence, a failure arriving with its reason from either stage, cancellation distinguishable from failure, and cancelling something not running leaving it alone. RT-82.4 to RT-82.6, RT-82.27. RT-82.5 is written about the reason surviving rather than about the failure sharing a type, because sharing a type is a compile-time fact a test could only restate; what is observable is that a failure arrives as a run state carrying why it failed. Today the local path has no failure state at all — `UpscaleViewModel.swift:454-459` sets a message string and discards the error. The last condition is where the two paths disagree: `GenerationCoordinator.cancel()` reports a cancellation unconditionally, even when nothing was in flight.
- **AC82.3** implies five conditions: the superseded run is cancelled, its output is not published when it finishes last, the newer one's is, the newer one failing does not resurrect the older, and the superseded run's progress stops being observed. RT-82.7 to RT-82.9, RT-82.28, RT-82.36. The middle two are separate because they fail through different doors: publishing the wrong result by ordering is one fault, and holding it as a fallback for a failure is another. RT-82.36 covers the other output channel, and it matters because of the slice boundary: the kit does not check for cancellation until slice 3, so a superseded run keeps reporting progress for seconds. A runner that drops its results but leaves its progress connected would put the two runs' phases on screen alternately.
- **AC82.4** implies four conditions: cancelled leaves no asset, failed leaves no asset, neither disturbs the current output, and neither leaves bytes at the allocated location. RT-82.10 to RT-82.12, RT-82.29. Cancelled and failed are separate tests because cleaning up on one path only is a common fault. The location is covered separately from the graph because a file no asset references is exactly the orphan #81 bounded against.
- **AC82.5** implies three conditions: the bytes land at the allocated location, the reference is the graph's rather than a fresh one, and nothing else is left behind. RT-82.13, RT-82.14, RT-82.35. The third is what makes "only" mean something: `SuperscaleGUIUpscaleProcessor` already writes an intermediate during processing, and an implementation that put it beside the output rather than in the system temporary directory would leave a file in the asset store that nothing references — which the graph's release path would never reach, because it only touches assets the graph holds.
- **AC82.6** implies six conditions, one per path that can start or leave an upscale. No selection at import means no output, a selection at import means one, and selecting later means one then: RT-82.15 to RT-82.17. Clearing the selection afterwards releases the output that exists, because "only while" is a claim about both directions: RT-82.31. The two remaining triggers are separate functions that can each violate the rule on their own — the face-enhancement toggle goes through `reupscaleForFaceToggle` rather than `reupscaleIfNeeded`, and a model change goes through the `$selectedModelName` sink: RT-82.33, RT-82.34.
- **AC82.7** implies six conditions: the active preset clears, a different preset selects, the active custom option clears, nothing reports itself active when the selection is empty, typed dimensions survive a clear, and choosing custom makes it active before anything is typed. RT-82.18 to RT-82.21, RT-82.30, RT-82.32. Custom is separate from preset because they are different controls today: the preset buttons assign `scaleMode` while the custom button assigns `showCustomFields`, and `scaleMode` only becomes `.custom` once a valid dimension has been typed. RT-82.32 is what gives RT-82.20 a state to start from — without it there is no way for custom to be the active choice, so nothing to clear. RT-82.30 exists because the typed dimensions are the user's work and clearing a selection is not a request to discard them.
- **AC82.8** implies four conditions: three paths that must leave a cleared selection alone, and one that must still adopt the native scale. RT-82.22 to RT-82.25. RT-82.25 is the blocking test of the four: without it, deleting the import-time assignment satisfies the other three while losing the v1 behaviour where a new image adopts its model's native scale. RT-82.24 is stated as the invariant rather than as an interaction, because once the custom fields are derived from the selection there is no way for the user to edit one while the selection is cleared — but the guarantee underneath, that editing dimensions never creates a selection, is exactly what `UpscaleViewModel.swift:115-118` violates today.

### Test type justification

All thirty-six are regression tests. Every condition is machine-verifiable, and each exercises real behaviour through the type's own API: stages through a stub `GUIUpscaleProcessing` and a stub generation service, so no Core ML and no network; scale selection and run triggering through the runner that owns them. None invokes the build system. All guard behaviour that must hold for the life of the project.

Every one of them runs against the package, which `make test` builds. The seam they cannot reach — whether the views use the transitions rather than assigning around them — is enforced by the compiler instead, and demonstrated by the application build rather than by a test.

No user test is allocated. The visible consequences — a candidate appearing before its upscale, and the scale buttons behaving as a toggle group — are judged in slice 9, where the workspace presents them.

### Temporary state in tests

Tests needing files on disk allocate a unique per-run directory beneath the operating-system temporary directory and remove it in teardown on success, on failure, and on handled interruption. Stage outputs written by the stub processor are small placeholders rather than real images, so the data written stays bounded by construction.

### Test location

`Tests/SuperscaleUXCoreTests/StageTests.swift`, `Tests/SuperscaleUXCoreTests/StageRunnerTests.swift` and `Tests/SuperscaleUXCoreTests/ScaleSelectionTests.swift`, XCTest, in the existing `SuperscaleUXCoreTests` target. No new target, no new dependency, nothing in the `OneOff` package.

The runner has a file of its own because it holds the tests for both halves of the slice that meet there: supersession and cancellation on one side, the triggers that start a run on the other.

## Out of scope

- Cooperative cancellation inside `SuperscaleKit`'s tile loop, which is slice 3 (D6). This slice cancels the observation and the structured task around the kit as it stands.
- Structured progress **inside** `SuperscaleKit`, also slice 3. The kit still emits sentences, so the phase is recovered by matching its wording — in one adapter, which is the improvement here. Rewording a kit message still breaks that mapping until slice 3 replaces it, and `StagePhase.unclassified` is what stops such a message being lost in the meantime. No acceptance criterion claims wording-independence.
- FAL request construction, which is slices 5 and 6. `FilterStage` takes the shared shape here; what it sends is settled there.
- The workspace that presents a candidate while its upscale runs, which is slice 9. This slice provides the independent observation that makes it possible.
- Putting `UpscaleRunner` on the application's path, which waits for the graph to reach the upscale workspace in slice 9. Its fifteen tests are evidence about the runner and about the model behind slice 9's workspace; they are not evidence about the workspace as it stands today, which drives the same stage types through the coordinator for the reason recorded in the solution.
- The wiring from the view model's events into the runner is not covered by a package test, because the view model is in the application target. The compiler enforces that a view cannot assign around a transition; it cannot enforce that an event is forwarded at all. ## What was delivered

**One shape for local and cloud work.** A `Stage` takes what the graph resolved, writes to the location the graph allocated, and reports what it made. `StageRunState` gives both a single run-state model — `idle`, `running`, `succeeded`, `cancelled`, `failed` — replacing a phase enum on the cloud side and a boolean on the local one.

**Progress is a value again.** The pipeline reports sentences, and the application was recovering structure by parsing them: `message.hasPrefix("Enhancing")`, then splitting on spaces to get the face count out. Rewording a progress message silently broke the count. `StagePhase` now carries the face count and the tile position as numbers, and the coupling to the pipeline's wording lives in one adapter rather than in the view model. A message the adapter cannot place arrives as `unclassified` with its text intact, so it degrades to plain wording rather than freezing the progress line while work continues.

**Runs no longer race.** The upscale was started with `Task.detached` and its handle discarded, so there was nothing to cancel and nothing to await. Dropping a second image while the first was still upscaling started a second task, and both wrote the result when they finished — which one landed last was not determined by anything, and the user could be left looking at the upscale of the image they had replaced. The run is now retained and cancellable, and a run token decides which run may publish. Neither the result nor the progress of a superseded run reaches anything.

**The scale control turns off.** `ScaleSelection` has a genuine off state, and `choose(_:)` clears the active choice rather than re-selecting it. Drop an image with the scale off and it simply becomes the image to work on, ready to filter — which is what a filter-first session wants, rather than spending three seconds of model load on an output about to be set aside.

Four places used to overwrite the selection: every import, every model change, and both custom dimension fields when emptied. Each now replaces a *selected* scale without creating one, so a cleared selection stays cleared. The custom control also had a dead state — the fields opened before the selection became custom, so pressing it again neither cleared nor reopened it — which is gone now that the selection is the single source of the active choice.

## Findings worth recording

**The implementation reproduced the fault it was closing, twice.**

1. **The application used none of it.** The first code audit found `UpscaleRunner` built, tested by fifteen tests, and wired to nothing: `Task.detached`, the string parsing, and the racing runs were all still in `UpscaleViewModel`. Thirty-six passing tests demonstrated the package was correct and demonstrated nothing about the running application. This is the same shape as D1 in #81, where the correct accessor sat three lines from the wrong one, and it is the second time in this delivery.

2. **A superseded run orphaned its output.** The runner released a superseded run's allocation immediately, but the run itself keeps working — the pipeline does not check for cancellation until slice 3 — and then wrote to that location afterwards. The file was left behind with nothing referencing it, in the directory the graph owns: exactly the leak #81 went to some trouble to bound, arriving through a new door.

Two more, both found by audit before any code was written: a test that specified something no test can assert, and one AC (AC82.6) that was unimplementable as written because `UpscaleViewModel` reset the scale on every import — a line the solution had not accounted for.

A third code-audit finding was about the record rather than the behaviour: the solution described a design that was not built, and was corrected in place rather than left describing fiction.

## A boundary worth being explicit about

`UpscaleRunner` is not on the application's path. The upscale workspace drives the same stage types through `GUIUpscaleCoordinator` until the asset graph reaches it in slice 9.

That is a trade, not an omission. Routing the workspace through the runner means taking the result as a file, and `StageOutput` carries no bytes by design — a 4096-pixel output is roughly 50 MB and moving it twice buys nothing. But the face-enhancement toggle is instant because the pre-face variant is cached in memory, and that cannot survive a bytes-free return. Full wiring would either lose that v1 behaviour or reintroduce the buffer the design rejected.

The workspace takes everything the problem statement is about. The runner's fifteen tests are evidence about the runner and about the model behind slice 9's workspace; they are not evidence about the workspace as it stands today, and the issue now says so.
