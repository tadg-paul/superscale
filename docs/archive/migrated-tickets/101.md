## Original issue body

Child of delivery master #99. Closes finding 2, recorded on #91 during the v2 MVP delivery.

## Problem

The application tells the user things that are not failures: an upscale reduced to fit the memory ceiling, a picture raised to the filterable minimum, a provider that returned a different shape from the one it was sent. All three arrive in the status bar, through `noticeMessage`.

**Until `f76f8c0`, every one of them was rendered on screen and absent from the accessibility tree.** `appStatusBar` carried an `accessibilityIdentifier` with no `accessibilityElement(children: .contain)`, so SwiftUI treated the whole bar as a single element and absorbed everything inside it. That is the D-2 rule recorded in `IMPLEMENTATION_GUIDE_v2.md` 3.9, and it was its sixth occurrence in the delivery, in code that predates the rule.

Absorption removes an element from the accessibility tree; it does not hide it. **A sighted user always saw these messages.** The defect is an accessibility one and nothing else, and saying otherwise would send a later reader hunting for a rendering bug that never existed.

The consequence is not a testing one, and the testing gap is the lesser half: **the status bar was unreachable to VoiceOver.** A user relying on it was told nothing when their picture was reduced, raised, or reshaped — which is the whole of the application's channel for "something happened that you should know about, and it is not a failure".

`f76f8c0` added the missing modifier and #96 added a GUI test reading the raise notice, so the *mechanism* is now covered.

**#91's own notice is still not.** Its tests are all package-level over `UpscaleCeiling` and assert the decision: which scale was chosen, what size resulted, that a reduction occurred. None crosses into the window. AC83.7 requires that "the reduction is reported", and the half of that criterion which says *reported* has never been verified where a user reads it.

## Solution

Add GUI coverage for the reduction notice and for the status bar remaining addressable.

**The reduction is driven by a real picture rather than simulated.** The ceiling is 32 megapixels; a 2048 x 1536 picture at 4x would produce 8192 x 6144, which is 50 megapixels, so the reduction genuinely fires. The fixture is generated at runtime into a per-run directory beneath the operating system temporary directory, and that exact directory is removed in teardown, on success and failure alike.

**Addressability gets its own test, separate from content.** The two fail for different reasons and one test could not say which: an absorbing container reports nothing at all, while an addressable bar carrying the wrong sentence reports the wrong thing. The delivery that produced this finding spent four diagnoses on a defect of exactly the first kind.

## Acceptance criteria

This issue has two halves and they take different paths through `ISSUES.md` §"Bug-fix issues reference existing ACs". The first AC audit established which is which.

### The reduction report cites an existing criterion

- **AC83.7** in `docs/ACs.md`: *"An upscale's output never exceeds the supported area, whatever asked for it: a scale is reduced to the largest that fits, a custom target is reduced proportionally, and the reduction is reported while the scale selection continues to show what was asked for."*

The clause at issue is *reported*. No behaviour changes; regression tests are added under the criterion's existing coverage. That is path 1 exactly.

### The addressability half needs its own criterion

**AC73.6 was cited here and the citation was wrong.** It reads *"Every interactive control **in Settings** is individually addressable..."*. The status bar is not Settings and `noticeMessage` is static text, not an interactive control; neither the scope nor the subject matches. It cannot be broadened to fit either, because `ISSUES.md` §"Immutability and supersession" makes a migrated AC's text read-only history — and AC73.6's own note in `docs/ACs.md` records that it was *"backfilled rather than stretched from AC73.5"*, which is the precedent to follow rather than the exception to take.

So the behaviour was never specified outside Settings, and path 2 applies: backfill.

| Test | Asserts |

| ⏳ RT-101.1 | With a reduction in force, the status bar reports it where a user reads it |

**RT-101.2 asserts scales, not dimensions.** `UpscaleViewModel.reductionNotice` was read rather than assumed: for a preset it returns *"Upscaled \(actual)× rather than \(asked)×, to stay within available memory."* Only its custom-target branch names pixel dimensions. A test asserting on dimensions would fail against correct behaviour, and the message would then have been "fixed" when it was right.

**The fixture is 800 x 640 with 8x selected.** The ceiling is 32 megapixels, so a reduction needs a large *request*, not a large source: 6400 x 5120 is 32.8 megapixels and reduces to 4x, whose output is about 8 megapixels. A 2048 x 1536 source at 4x was proposed first and is the exact shape that failed on RT-100.10 in this delivery, by leaving the application unresponsive long enough that the accessibility hierarchy returned no snapshot at all.

### Condition enumeration

**AC83.7's coverage gains three conditions.**

RT-101.1 and RT-101.2 are separate because a notice that appears saying the wrong number passes the first and fails the second. "The reduction is reported" is worth nothing if what it reports is the request rather than the result, and AC83.7 explicitly requires the selection to keep showing what was asked for *while* the message reconciles it with what ran.

RT-101.4 blocks the cheapest wrong implementation, a notice that is always present, and pins the common case: an ordinary upscale within the ceiling says nothing at all.

**AC101.1 implies three conditions**, the last two added by the first AC audit.

- **The notice is reachable.** The recorded finding.
- **The status text beside it is reachable.** The bar holds more than `noticeMessage`, and the same absorption silenced all of it. A test covering only the notice proves the fix for one label and leaves the rule unproven of the bar — which is the distinction RT-88.3 was written to make in Settings.
- **A notice replaced while displayed carries the new text.** An element recreated rather than updated may not be announced.

  **Driven through the sequence the application already performs**, which costs nothing extra: with the stubbed provider pointed at `remy2.jpg` at 1024 x 1024 and the suite's 240 x 320 fixture, applying one filter sets the raise notice and then replaces it with the reshape notice when the square result is adopted. #96's RT-96.14 already establishes that setup. The alternative, raise then reduce, needs an upscale of about 23 megapixels and would reintroduce the unresponsiveness that RT-101.1's fixture was corrected to avoid.

### The status text needs an identifier

`MainView.statusBar` holds a decorative `Circle`, a `Text(statusText)`, a `Spacer`, and the notice. **The status text carries no accessibility identifier**, so RT-101.5 has nothing to address. Adding one is part of this issue's work rather than a precondition of it: the finding is that the bar's contents were unreachable, and discovering that one of them is still unreachable for a second reason is the same defect one layer down.

## Test type and location

Six regression tests in `SuperscaleAppUITests`. Each is machine-verifiable, guards ongoing behaviour, and invokes no build system, so all six are RT rather than OT or UT.

They are GUI tests rather than package tests **because that is the whole of the finding**: the behaviour was correct at package level throughout and unreachable in the window, and package tests are precisely what failed to notice for the length of the previous delivery.

No new user test. UT-91.1 already covers the human judgement of whether the message reads clearly and unobtrusively, and it remains pending on master #79.

Without it an identifier on an `HStack` makes SwiftUI treat the stack as a single element and absorb its children, so the notice and the status text were rendered on screen and absent from the accessibility tree — unreachable by VoiceOver, not merely by a test.

**Sixth occurrence of guide 3.9's D-2 rule in this codebase**, and the first in code that predates the rule. That is worth more than the fix: a rule found six times is not being read at the point where it applies.

The `Circle` at `MainView.swift:540` stays decorative and correctly so. Shapes never enter the accessibility tree (guide 3.11), and the state it shows is carried in the adjacent text — a colour reaches nobody on its own. Marking it hidden would add ceremony without changing the tree.

## A claim I checked rather than accepted

RT-101.4 asserts a **negative** — that no notice is shown — immediately after the upscale completes. That is the classic vacuous-pass shape: the assertion can succeed merely because the thing has not appeared *yet*, and this issue's own first run failed because the notice appears later than the test expected.

It is sound here, and the reason is specific rather than reassuring. `UpscaleViewModel.publish` (lines 803-828) is one synchronous body on the main actor: `result` at 809, `noticeMessage` at 814, `isProcessing = false` at 827. Completion becomes observable and the notice becomes present in the same run-loop turn, so by the time `waitForUpscaleComplete()` returns, a notice would exist if there were one to show.

Also confirmed while reading it: line 814 assigns **unconditionally**, so a run with no reduction clears any notice left by a previous run rather than leaving a stale sentence in the bar.

## Smell: RT-101.4 reasons about a scale it never selects

`SuperscaleAppUITests.swift:812-823`. The comment does the arithmetic — *"1200 x 900 at 8x is 69 megapixels, so 4x is used here instead, giving 17 megapixels, under the ceiling"* — and then the test loads the fixture and calls `waitForUpscaleComplete()` without selecting anything. The scale it reasons about is the default, and the default is neither asserted nor named.

The failure direction is the safe one: if the default were 8x, the picture would be reduced, a notice would appear, and the test would fail loudly rather than pass hollowly. So this is a legibility defect rather than a correctness one — but a reader checking why RT-101.4 passes finds arithmetic about a scale that appears nowhere in the test body.

This issue added `selectScale(_:)` precisely because *which scale is active follows the model's native scale rather than a constant, so it cannot be assumed*. RT-101.4 assumes it.

**Recommended fix:** assert the premise instead of narrating it. Read `scale4x`'s value before waiting and assert it is the one in effect, so the test states the condition its arithmetic depends on:

```swift
let inEffect = app.buttons["scale4x"]
XCTAssertTrue(inEffect.waitForExistence(timeout: 10))
XCTAssertTrue(
    (inEffect.value as? String ?? "").lowercased().contains("in effect"),
    "the arithmetic above is about 4x, so 4x is what must be running")
```

## The helpers

`statusBarText(of:timeout:)` reads **both** label and value and concatenates them. That is the right shape: a container reports its label where it does not reliably report its value, and this delivery has been caught by that twice in two different element types. It returns `""` on timeout rather than failing, which would be dangerous under a negative assertion — every one of its four call sites asserts non-emptiness or `contains`, so a timeout fails loudly at all four. Checked individually.

`selectScale(_:)` asserts the scale is not already in effect before clicking. The buttons are a toggle group, so clicking the active choice **clears** it: a test naming a scale without checking silently turns upscaling off and then waits for a result that will never come. That is exactly how this issue's first run failed, and the helper turns a silent hang into a named assertion failure.

`writeFixture(width:height:named:)` allocates a per-run directory beneath the OS temporary directory, removes that exact directory in teardown on success and failure alike, and writes a bounded fixture.

## Error handling, security, complexity

No error path is suppressed. `statusText` is a total function over the coordinator's five phases with no default arm, so a new phase is a compile error rather than a silently blank bar. `statusBar` is 37 lines with two levels of nesting. Nothing user-supplied reaches a format string, a path, or a network call.
