## Original issue body

Child of delivery master #79 (slice 7). Two reports from use, 2026-08-25, and they are the same fault seen twice.

## Problem

The author:

> *"in the case of grok if any edge is below 1024x it seems to return a 1024x1024 image. I thought we agreed minimum edge 1024x."*
>
> *"if the resolution of the return image is different we need some way of ensuring the display of the images being compared is displayed in a proportionally equal way. In the case of grok which has upscaled one edge resulting in a different aspect ratio it has now stretched the original and so superscale needs to adjust the display of the returned image to restore the original proportions."*

### The floor is documented and not enforced

`IMPLEMENTATION_GUIDE_v2.md` 2.5 states the minimum plainly: *"The minimum is 1024 pixels on the long edge"*, held in one named constant, with the application performing the sequence the user could have performed by hand — import, upscale to the minimum, lock, turn the scale off, and say so.

**None of that is built.** Slice 7 is unstarted, so an undersized picture is sent as it is. The provider then does its own thing with it, and what it does is the second report.

### The provider changes the shape, and the comparison shows it stretched

Given a picture whose short edge is under 1024, grok appears to return **1024 × 1024** — it raises the short edge to the model's working size and squares the result. The returned picture is therefore a different *shape* from the one sent, not merely a different size.

The curtain then presents both sides at one displayed size, per **AC90.10**, which was written on the assumption that the two sides share an aspect ratio. They do not. Fitting a 1:1 return and a 3:4 original into one frame stretches one of them, and what the author sees is their own photograph distorted next to the filter's output.

**AC90.10 is wrong as written**, in the same way AC90.6 was: it describes a rule that produces the reported defect. One displayed size is right when the shapes match and is exactly what breaks when they do not.

### Condition enumeration

- **AC96.1** implies five: undersized pictures are raised, sized ones are not touched, the user is told, the result becomes the base with the scale off, and a picture that cannot reach the floor at any scale is raised as far as it goes and reported as possibly altered. The fourth is guide 2.5's own reasoning — without it the application keeps re-upscaling a picture that is already the size the provider wants.

  **The fifth was found by the first AC audit.** The scale control offers 2x, 4x and 8x, so a 50 by 50 picture reaches 400 and no further, far below 1024. The criterion previously said such a picture "is raised to it", which is impossible, and the plausible implementation would raise to 400, send it anyway, and let the provider do what it does — which is exactly the situation this issue exists to end. Raising as far as possible and saying so matches the reduce-and-tell posture the author chose for the memory ceiling.
- **AC96.2** implies three: a setting change that would drop below the floor raises again, it says so again, and a change that stays above does nothing. Guide 2.5: *"The floor is enforced continuously, not only on import."*
- **AC96.3** implies four: differing aspects each keep their own, the reported case specifically, the equal-aspect case is unchanged, and the two sides share a width. The third matters because most comparisons have matching shapes and must not regress to accommodate the ones that do not.

  **The shared width is what makes AC96.3 and AC96.4 compatible, and the first AC audit caught that they were not.** The curtain is one vertical line. Each side drawn at its own aspect in a frame of its own width would put that line at a different fraction of each picture, so "each keeps its proportions" and "the divider means the same thing on both" described a geometry that does not exist. Matching the **width** resolves it: the line falls at the same fraction of width on each side, nothing is stretched, and a 1:1 return simply appears shorter than a 3:4 original — which is honest, because it is a different shape. That is the second curtain rule in this delivery to specify an impossible geometry; AC90.10 was the first, and this issue supersedes it.

- **AC96.4** implies three: the divider means the same fraction of width on both sides, that holds across differing aspects, and AC90.14's rule that the divider follows the pointer is unaffected.
- **AC96.5** implies two: marked when the shape changed, unmarked when it did not. A user who sees a square result from a portrait photograph should not have to work out whether the application or the provider did it.

### What this does to AC90.10

**AC96.3 supersedes AC90.10.** That criterion reads: *"The curtain presents both sides at one displayed size, so the divider falls on the same part of the picture on each side regardless of the two images' pixel dimensions."* It was written for a picture and its own upscale, which differ in pixel count and not in shape, and one displayed size is right for that. It is wrong the moment the shapes differ, because one displayed size then means one displayed *rectangle*, and something has to be stretched to fill it.

What AC90.10 was reaching for survives as **AC96.4**: the divider addressing the same relative position in both. That was always the point; "one displayed size" was a means that happens to fail on the case this issue is about.

RT-90.34 and RT-90.35 are superseded by RT-96.8 to RT-96.12. RT-90.36 is superseded by RT-96.9.

## Solution

**The floor is one constant and one function.** `MinimumResolution.raise(_:)` in `SuperscaleUXCore` takes a pixel size and returns the size to raise it to, or nothing when it already suffices. Guide 2.5 puts the figure in a single named place and calls it an assumption open to revision; that is where it stays.

**Raising uses the machinery that exists.** Guide 2.5 is explicit that this needs no special path: it is `UpscaleStage` with a different target, producing a `raisedToMinimum` asset — a role `AssetRole` already declares and slice 1 already built. Lock promotes it, the scale is cleared, and the session continues ordinarily.

**The curtain gives both sides one width and lets their heights differ.** `CurtainGeometry` gains a function taking two image sizes and a container, returning a shared width and a frame per side, each at its own aspect within that width. The divider's fraction is then a fraction of that one width, so it means the same thing on both sides while nothing is stretched.

Matching the width rather than fitting each side independently is the resolution the first AC audit forced: with a single vertical divider and two frames of different widths, "each keeps its proportions" and "the divider means the same on both" cannot both be true. Matching height instead would work equally as geometry and worse in use, since a wide return beside a portrait original would then overflow the container's width.

**That width is bounded by the canvas, not equal to it.** The largest width at which *both* sides
fit: the canvas's width where that works, and otherwise whatever width makes the taller side exactly
fill the canvas's height. Stated because the obvious reading — use the full width — clips the more
portrait of the two off the bottom, which reads as a new defect rather than an incomplete fix.
Raised by the second AC audit.

**Fifteen tests become eighteen**, with RT-96.16 asserting the shared width, RT-96.17 the picture too
small to reach the floor, and RT-96.18 that a portrait side is not clipped in a wide canvas.

**Differing aspect is a fact about the candidate**, so it belongs on the asset rather than being recomputed by the view: `Provenance` records what was sent and what came back.

## Test type and location

Eighteen regression tests.

**AC96.1 and AC96.2's are package tests** in `Tests/SuperscaleUXCoreTests/`, and they span two subsystems deliberately.

The **raising decision and the upscale stage** are tested with a stub processor: what target was chosen, and what the stage was asked to produce. Sizes are integers and nothing runs Core ML or writes a file.

**RT-96.1 goes through `FilterStage` against the stubbed transport**, asserting that the reference actually submitted is at or above the minimum. Raising and sending are different subsystems and the criterion is about the second: proving the picture was raised is not proving the raised picture is what went out, and the whole defect is that the provider received something too small. Raised by the first test audit, which found the test's wording and its location describing different code. No test reaches a paid endpoint.

**AC96.3 and AC96.4's are package tests** over the curtain's geometry, extending `CurtainGeometryTests`. Two frames from two sizes, and a fraction mapped into each: arithmetic, and the same reasoning that moved the divider's mapping out of the view in #90 after five months of a defect nobody could test.

**AC96.5's are package tests** over the recorded provenance, with one GUI test that the mark appears.

**One user test:**

> ⏳ UT-96.1: a filtered result of a different shape reads correctly beside the original

Whether two differently-shaped pictures side by side look right, rather than merely undistorted, is a judgement. It is also the report that produced this issue.

## Standards

`MinimumResolution` holds the figure in one named constant, as guide 2.5 requires, with the
supporting evidence and its status as an assumption in the doc comment. `CurtainGeometry` remains
pure arithmetic with no view types, which is what makes AC96.3 and AC96.4 testable at all.

## Error handling

**Every degenerate input is guarded rather than allowed to produce a NaN the view would then try to
draw.** `pairedFrames` returns `.zero` for a zero-sized container or a zero-sized image;
`MinimumResolution.decide` returns "not raisable" for a zero long edge rather than dividing;
`raiseToMinimumNeeded` returns nil with no base. Each has a test.

**Allocate-then-promote is the right shape and matches `recordUpscale`.** The raise is allocated
with `promote: false`, the work runs, the data is written, and only then does `adoptRaise` move the
base. A failed raise cannot leave the base pointing at a file nothing ever wrote.

`raiseBaseToMinimumIfNeeded` returns `false` only where a raise was attempted and failed, so the
caller does not submit a picture whose size it has just told the user was corrected.

## Security

No new network surface, no credential handling, no file path taken from user input. The raise
writes to a location the graph derives from a fresh UUID inside its own output directory, so a
released location is never reused.

## Complexity

`raiseBaseToMinimumIfNeeded` is 38 lines with two levels of nesting, within limits. The three
`guard` clauses at its head each return `true` — "nothing to raise, carry on" — which reads
correctly but would repay a comment if a fourth is ever added.

## Closing

Slice 7 lands, and it reached further than the criterion describes.

**The floor is enforced.** A picture whose long edge falls below 1024 is raised to the least scale that clears it, becomes the base as a `raisedToMinimum` asset, the scale is turned off, and the user is told. Where no offered scale reaches the floor, it is raised as far as it goes and the user is warned the provider may reshape it.

The check sits at **Apply**, not at import: every submission passes through one place, and the base can change after import, so a check made only on the way in satisfies AC96.1 and leaves the defect in place on every subsequent apply.

**The curtain gives both sides one width and lets their heights differ.** Each side was fitted into the canvas independently, so a 1:1 return occupied a different width from a 3:4 original, and the single vertical divider fell at a different fraction of each picture. One line meant two things.

### Four consequences of the raise, none of them in the criterion

1. **It ran silently.** A raise is the same Neural Engine work as any other upscale and takes the same seconds. AC94.1 covers work of any kind on the working image.
2. **It measured points, not pixels.** `NSImage.size` is DPI-adjusted, so a 2048 x 1536 photograph at 300 dpi reported about 492 x 369 — undersized by the floor's reckoning, raised 4x it did not need, on a photograph twice the minimum. The view model already used `ImageLoader`; the view did not, and the two disagreed about the same picture.
3. **It made the result unsaveable.** Save was bound to a completed upscale, and the raise turns the scale off, so a filtered result just paid for could not be written to disk.
4. **Fixing (3) would have blinded the suite.** `waitForUpscaleComplete` used Save's appearance as its signal that an upscale had finished, at forty-one call sites. Written into the guide at 3.17.

**And AC96.5 was recorded without being shown.** The provenance held whether the provider reshaped the picture, the package tests asserted that it held it, and nothing displayed it — so a user seeing a square result from their portrait photograph still could not tell whether this application or the provider had done it, which is the question the criterion exists to answer.
