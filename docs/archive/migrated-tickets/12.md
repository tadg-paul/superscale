## Original issue body

## Problem

Superscale needs to be installable by non-developers via Homebrew. This requires a formula, release automation, and model bundling.

## Solution

1. **Homebrew formula** (`Formula/superscale.rb`): build from source, bundle **all six models** as resources
2. **Release automation** (`make release`): tag, build release binary, create GitHub release, update formula SHA256 and version, push tap
3. **Model bundling**: bundle all models (~111MB total) — not just the default. Every install method (Homebrew, `make build`, `make install`) provisions all models
4. **Model updates on upgrade**: when a release includes new or updated models, `brew upgrade` and `make install` pull them in automatically. The `release.sh` script regenerates the formula with current model resource blocks and SHA256s on each release, so upgrades always reflect the latest model set
5. **Source builds**: `make build` / `make install` download missing models from the GitHub release if not present locally
6. **README quickstart**: verify end-to-end that the documented install steps work
7. **Set repo to public**: once licensing (issue #5) is resolved

### Prerequisite

Issue #5 (licensing review) must be complete before making the repo public.

## AC status update — 2026-03-20

- **AC12.1 → ❌ failing**: Homebrew install fails with `Errno::ENOENT: No such file or directory - RealESRGAN_x4plus.mlpackage`. This is a formula resource staging bug — the model zips are downloaded but the `.mlpackage` directories aren't being extracted/staged correctly before `swift build` runs. Needs a separate fix issue.
- **AC12.6 → ✅ passing**: RT-046 passes — all six `.mlpackage` directories present after `make build`.

### Responses to questions from earlier comment

1. **Dev machine clash with `make install`?** — Possible. `make install` puts models in `~/.local/share/superscale/models/` while Homebrew puts them in `$(brew --prefix)/opt/superscale/models/`. The `ModelRegistry` search paths should keep them separate, but if there's a stale compiled model cache (`.mlmodelc`) from a previous `make install`, it could interfere. Recommend `brew uninstall superscale` then `make uninstall` (or vice versa) to start clean.

2. **CLT warning / `rm -rf` text** — That text is from Homebrew itself, not from us. It's Homebrew's standard message when it detects an outdated Xcode Command Line Tools version. We have no control over it. The `rm -rf` suggestion is Apple's official way to force-reinstall CLT (there's no `trash` alternative for system directories). This is cosmetic — it doesn't affect the build.

3. **`swift build -c release --disable-sandbox`** — This is Homebrew's standard Swift build command. The `--disable-sandbox` flag is needed because Homebrew's build sandbox conflicts with Swift Package Manager's own sandbox. This compiles our Swift executable — it does not touch models. The models are already downloaded as Homebrew resources; the formula's `install` method stages them after the build completes.

### Comment by m13v at 2026-03-22T02:48:57Z

For the Homebrew formula + release automation, one thing worth considering: if you are building a universal binary (arm64 + x86_64), make sure your Makefile builds with `--arch arm64 --arch x86_64` or uses `lipo` to combine, and that the formula's SHA256 matches the universal archive rather than an architecture-specific one.

We use Codemagic for our macOS release pipeline and it handles the universal binary creation, code signing, notarization, and then publishes to GitHub Releases. The Sparkle framework then picks up the release for auto-update. For a CLI tool distributed via Homebrew you obviously do not need Sparkle, but the model bundling challenge is similar to what we deal with for ML model assets in our app bundle.

One tip for the model resource blocks in the formula: rather than hardcoding all six model URLs, you could generate the formula from a template during `make release` so it always picks up the latest model set. That way adding a 7th model later just means adding it to a manifest file and the release script handles the rest.
