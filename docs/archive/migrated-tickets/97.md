## Original issue body

Child of delivery master #79 (slice 6). Design of record: `IMPLEMENTATION_GUIDE_v2.md` 3.6; wire detail in `FAL_REQUEST_REFERENCE.md`.

## Problem

**Every request carries a sizing parameter, including the edit requests that reject it.**

`FalRequestBuilder.swift:51-55` builds the payload with `handler.sizingField: request.aspectRatio` unconditionally, and `:62` then chooses the edit endpoint whenever a reference image is present. So an edit request goes out carrying `aspect_ratio`.

`IMPLEMENTATION_GUIDE_v2.md` 3.6 says plainly that this is wrong: *"Its edit endpoint is the plain `/edit` suffix, which is correct for this family, and its edit endpoint **rejects sizing parameters**."*

### This may be the cause of a reported defect

The author, 2026-08-25:

> *"in the case of grok if any edge is below 1024x it seems to return a 1024x1024 image."*

A sizing parameter the endpoint rejects does not produce the sizing that was asked for. What it produces instead is whatever the model does by default, and a square return is exactly what a defaulted aspect looks like. **This is a hypothesis, not an established cause** — it is consistent with the report and with the documented contract, and it has not been observed directly, because doing so costs a paid call against a real key. Issue #96 addresses the *consequences* of a differently-shaped return regardless of why it arrives; this addresses one candidate cause.

### Condition enumeration

- **AC97.1** implies three: edit carries none, text-to-image still does, and the endpoint choice is unaffected. The second matters because the obvious fix — stop sending the field — would break the path that needs it, and the MVP's own journeys do not exercise that path, so nothing else would notice.
- **AC97.2** implies two: one model today, and the shape admits more. Guide 3.6: *"The handler is declarative so a second model is a data change, but the family matrix in the FAL reference is knowledge held for later, not work to do now."*
- **AC97.3** implies four: the plural form, the singular form, the over-limit warning, and the no-reference case. `FAL_REQUEST_REFERENCE.md` records that single-reference families accept one and drop extras with a warning.

  **The first draft got this backwards, and the AC audit caught it.** It said a single reference is sent "as the field's own type rather than wrapped", which describes `fal-ai/flux-pro/kontext` — `image_url`, limit 1. Grok's handler declares `image_urls` with a limit of **3**, so one reference is correctly wrapped in a list, and following the original wording would have unwrapped it into a bare string against a plural field. A criterion meant to prevent a request-shape defect would have introduced one.

- **AC97.2's "selectable" is load-bearing.** The handler table also knows `fal-ai/flux-pro/kontext`, and guide 3.6 keeps that deliberately: *"the family matrix in the FAL reference is knowledge held for later, not work to do now."* What the MVP restricts is what a user can choose, not what the code knows how to build.
- **AC97.4** implies three: snapping, passing through, and reporting. The third is what stops the caller believing it got what it asked for. `FAL_REQUEST_REFERENCE.md` gives the supported set as `{9:16, 1:1, 4:3, 16:9}`.

## Solution

**Sizing becomes a property of the endpoint, not of the request.** `FalModelHandler` gains a statement of whether its edit endpoint accepts sizing; the builder consults it rather than including the field unconditionally. That keeps the knowledge in the registry, where the rest of each model's contract already lives, and makes a second model with different behaviour a data change.

**Nothing is removed from the text-to-image path.** It is not exercised by the MVP's journeys — every filter carries a reference — which is precisely why a change that broke it would go unnoticed until the next version.

**The handler `switch` becomes a table.** `FalModelHandler.handler(for:)` at `FalRequestBuilder.swift:85` is a hardcoded `switch`, so "adding a model is a data change" was not true: it is a branch, and a test cannot add one at runtime. A dictionary of `FalModelHandler` values keyed by model ID makes the claim true and RT-97.5 writable, and it is what guide 3.6 means by calling the handler declarative. Raised by the first test audit, which found the criterion asserting a property the code did not have and the test that would have caught it unwritable.

**A snapped ratio is reported the way dropped references already are.** `FalGenerationWarning` gains a case naming the requested ratio and the one actually sent, beside `extraReferencesIgnored`. A snap is a silent adjustment to what the user asked for, and the mechanism for saying so exists.

## Test type and location

Twelve regression tests, all in `Tests/FalGenerationKitTests/`, against constructed requests rather than a network. Request construction is a pure function of its inputs, and `IMPLEMENTATION_GUIDE_v2.md` 7 calls it *"the highest-value surface in both reference implementations"*. **No test calls a paid endpoint**; RT-97.5 constructs a second registry entry in the test rather than adding one to the shipped registry.

No user test is allocated. Nothing here is visible when it works: the request is correct or it is not, and the consequences of an incorrect one are #96's business.
