## Original issue body

Child of delivery master #99. Closes finding 1, recorded on #96 during the v2 MVP delivery.

## Problem

Every sizing decision the application makes is arithmetic on **pixels**: the 1024-pixel minimum long edge for filtering, the 32-megapixel output ceiling, the effective-scale readout, and the record of what was sent to the provider against what came back.

`NSImage.size` does not report pixels. It reports **points**, adjusted by the file's stored resolution. A 2048 x 1536 photograph saved at 300 dpi reports approximately 492 x 369.

`MainView.importedPixelSize` returned exactly that until commit `efef02d`, so a photograph twice the filterable minimum was measured as a quarter of its size, judged undersized, upscaled 4x it did not need, and its owner's scale selection turned off. It now reads through `ImageLoader`, which decodes the file and reports the decoded dimensions.

**Nothing tests this.** Every fixture in `Tests/images/` is 72 dpi, where points and pixels are numerically identical, so the two functions cannot disagree on any picture the suite owns. The correction is unverified and can regress silently.

## Solution

Add regression coverage over `ImageLoader.load(from:)` proving that the dimensions it reports are the file's decoded pixel dimensions and are unaffected by the resolution recorded in the file's metadata.

**The fixture is generated at runtime, not committed.** A picture whose only purpose is to carry an unusual resolution is a thing a later reader has to work out; `Tests/FalGenerationKitTests/FalStorageClientTests.swift` already establishes this precedent for the mis-named PNG in RT-92.9. The test writes the image into a per-run directory beneath the operating system temporary directory, obtained through `FileManager.default.temporaryDirectory`, and removes that exact directory in `addTeardownBlock`.

**The stored resolution is asserted separately from the dimensions.** Asserting only that `ImageLoader` returns 2048 would pass against a fixture that silently failed to record 300 dpi, because points and pixels would then be equal and the test would prove nothing. Reading the resolution back from the file through `CGImageSourceCopyPropertiesAtIndex` establishes that the condition under test genuinely exists.

`NSImage` is not used for the comparison. It lives in AppKit, which `SuperscaleKit` does not import, and adding that dependency to a kit with a pinned dependency-free public API to make a test read better is not a trade worth making. The stored DPI is the same fact `NSImage` derives its answer from, and `ImageIO` already exposes it.

### Condition enumeration

**AC100.1 implies six conditions.** Three were in the first draft; the first AC audit found the other three.

- **A non-default resolution gives pixels.** The defect's own case. Without it the criterion is untested.
- **The default resolution gives the same number.** Without this, an implementation that hard-coded a divisor, or read the wrong field, could pass the first condition and be wrong everywhere else. It also pins that the correction did not introduce a resolution-dependent path in the other direction.
- **The fixture actually carries the resolution it claims to.** A fixture that silently failed to record 300 dpi would leave points and pixels equal again, and the test would pass while proving nothing. This is what stops the whole thing being vacuous.
- **No resolution recorded at all.** A PNG frequently carries no `pHYs` chunk, `ImageIO` takes a different path, and `NSImage` assumes 72. This is the commonest real file and it is a distinct code path from "72 recorded".
- **Horizontal and vertical resolutions differ.** An implementation dividing by a single resolution value passes every square case and is wrong here. Both TIFF and JPEG permit it.
- **A format other than PNG.** Resolution is stored by an entirely different mechanism in each format: `pHYs` in PNG, JFIF density and EXIF in JPEG, `XResolution` and `YResolution` tags in TIFF. **The defect arrives on camera and scanner files, which are JPEG and TIFF**, so testing PNG alone would test the format it is least likely to arrive in.

**AC100.2 implies four conditions**, added by the first test audit after it found that the six tests above would all have passed against the broken application.

- **A non-default resolution measures at pixels**, through the function the *application* uses rather than the one the kit exposes.
- **No resolution recorded measures the same way**, which is the commonest real file.
- **An undecodable file measures as zero rather than crashing.** The function is called on a path where a failed raise may have written nothing, so this is reachable rather than theoretical.
- **The user-observable consequence.** A picture comfortably above the floor that records 300 dpi is not raised. Under the broken implementation the user's large photograph was judged small, upscaled 4x it did not need, and their scale selection turned off.

### Why AC100.2 exists at all

`ImageLoader` was never broken. The defect was `MainView.importedPixelSize`, private to the app target and exercised by nothing, and `UpscaleViewModel.swift:591` measures pictures through a second path of its own. **Two measurement paths disagreed for months and no test could tell them apart.**

So the six tests under AC100.1 pin a contract that was already sound. They are worth having, because `ImageLoader` is `SuperscaleKit`'s public API and the command-line tool's real entry point, but they do not protect what this issue exists to protect.

The measurement moves into `SuperscaleUXCore` as one public function that both call sites use. This is not tidying: the defect existed *because* there were two, and the correction is unverifiable while the wrong one is private to a view. It is not an architecture change under `MAIN.md` §3 either — no new module, no new abstraction, no boundary moved; a private helper becomes a public function in a module the app already depends on.

### Recorded, not implemented: EXIF orientation

The first AC audit found a second way metadata can alter reported dimensions, and it is **outside this delivery's confirmed scope** because it was not among the risks recorded at the v2 delivery gate.

A photograph from a phone commonly stores its pixels in one orientation and records an EXIF tag describing how to rotate them for display. The hypothesis, stated as a hypothesis, is that `CGImageSourceCreateImageAtIndex` with `nil` options returns the **stored** dimensions and does not apply that tag. If that holds, a portrait photograph is measured as landscape, which reaches the 1024 floor (a long-edge rule, so orientation-sensitive), `Provenance.providerChangedTheShape` (which compares aspect ratios), and `CurtainGeometry.pairedFrames` (which lays out by aspect). The area ceiling is unaffected, area being orientation-invariant.

Recorded on master #99 with a recommended follow-up. Not implemented here.

## Test type and location

Ten regression tests. Each is machine-verifiable, guards ongoing behaviour, and invokes no build system, so all ten are RT rather than OT or UT.

**AC100.1's six** are in `Tests/SuperscaleTests/ImageIOTests.swift`, beside the existing `ImageLoader` coverage. They pin `SuperscaleKit`'s public contract, which the command-line tool depends on directly.

**AC100.2's RT-100.7 to RT-100.9** are in `Tests/SuperscaleUXCoreTests/`, over the relocated public measurement function. That is where the defect was.

**RT-100.10 is a GUI test** in `SuperscaleAppUITests`, because "the picture is not needlessly raised" is a claim about what the application does with a file a user brought in, and it is the only one of the ten that would have failed against the broken code end to end.

**Every fixture is generated at runtime with distinct dimensions**, so an implementation returning a hard-coded pair fails rather than passing all of them. Fixtures are written into a per-run directory obtained from `FileManager.default.temporaryDirectory` and **that exact directory** is removed in `addTeardownBlock`, never a shared parent, on success and on failure alike. Each is a few kilobytes against the 100 MiB limit in `TESTING.md`.

No user test. The property is a number, and a human reading a number is a worse oracle than an assertion.

## The structural claim this audit exists to confirm

**One measurement, and only one: confirmed.** No `NSImage.size` read survives anywhere in the application. `grep` across `Sources/` and `SuperscaleApp/` returns exactly one mention, and it is the 🚫 comment at `MainView.swift:427` recording the removal.

The three surviving `NSImage(contentsOf:)` uses are all *rendering*, not measuring, and each was read to confirm it: `LockChainStrip.swift:59` draws a thumbnail into a fixed 56×44 frame, `MainView.swift:166` and `UpscaleViewModel.swift:589` hand a picture to `Image(nsImage:)`. None reads `.size`, `.width` or `.height`.

That is the correctness claim of this issue and it holds.

## Blocker: measuring a picture decodes it in full, and sometimes twice

`ImageDimensions.swift:26-29` calls `ImageLoader.load(from:)`. `ImageLoader.swift:30-46` does this:

- `CGImageSourceCreateImageAtIndex` — decompresses the **entire** picture into a `CGImage`
- if the picture has an alpha channel, `extractAlpha(from:)` — builds a **second** full-size greyscale image

All of it is discarded. Two integers are kept.

For a 32-megapixel RGBA PNG — which is precisely the size this application exists to produce, and #91 set that ceiling deliberately — measuring costs roughly 128 MB for the decode and another 32 MB for the alpha plane. `MainView.swift:228` calls it synchronously on the main actor while importing.

This is the same defect #102 has just finished removing from the neighbouring line: expensive synchronous file work on the thread drawing the window. `SWIFT.md` §"SwiftUI and Apple UI Code" prohibits it. The measurement fix is correct and the cost is new, so it is in scope for this issue rather than inherited.

**Recommended fix:** read the properties instead of the pixels. `CGImageSourceCopyPropertiesAtIndex` returns `kCGImagePropertyPixelWidth` and `kCGImagePropertyPixelHeight` without decompressing anything.

```swift
public static func pixelSize(of url: URL) -> CGSize {
    guard let source = CGImageSourceCreateWithURL(url as CFURL, nil),
          let properties = CGImageSourceCopyPropertiesAtIndex(source, 0, nil)
              as? [CFString: Any],
          let width = properties[kCGImagePropertyPixelWidth] as? Int,
          let height = properties[kCGImagePropertyPixelHeight] as? Int
    else { return .zero }
    return CGSize(width: width, height: height)
}
```

Two properties of that replacement matter and must be verified rather than assumed:

- **It is still pixels.** `kCGImagePropertyPixelWidth` is the stored pixel count and is unaffected by the DPI that caused this issue. That is the whole point of choosing it.
- **It agrees with the pipeline on orientation.** Neither `kCGImagePropertyPixelWidth` nor `CGImageSourceCreateImageAtIndex` applies EXIF orientation, so a rotated photograph measures the same either way — and the same as what `SuperscaleKit` will actually upscale. Swapping to an orientation-corrected source would silently disagree with the pipeline.

RT-100.7, RT-100.8 and the anisotropic case pin the first. RT-100.9 must be re-run rather than reasoned about: `CGImageSourceCreateWithURL` succeeds lazily on a file that is not a picture, so whether properties come back nil for garbage is an empirical question, and the test asserts `.zero`.

## Smell: three call sites lose the space after the argument label

`MainView.swift:228`, `:279`, `:356` read `ImageDimensions.pixelSize(of:url)`. The codebase writes `of: url` everywhere else, including this file's own neighbouring calls, and `pixelSize(of:url)` reads at a glance like the *selector* `pixelSize(of:)` rather than a call passing `url`.

No formatter enforces it: the `Makefile` has no format target and `.git/hooks` contains nothing but samples, both checked. So this survives only if a reader fixes it.

**Recommended fix:** `ImageDimensions.pixelSize(of: url)` at all three sites.

## Error handling

`pixelSize` returns `.zero` rather than throwing, and the doc comment justifies it: every caller sits on a path where an unreadable file is a state to carry rather than a failure to report. `try?` here discards an error deliberately and the reasoning is recorded at the point of the discard, which is the distinction `SWIFT.md` draws. RT-100.9 pins both the undecodable and the absent file.

The recommended replacement keeps that contract exactly — `guard ... else { return .zero }`.

## Security

Nothing reachable. No credential, no network, no user-supplied path escaping its own read. A malformed picture reaches `ImageIO`, which is the platform decoder and the same one the rest of the pipeline uses; the recommended fix reduces exposure by not decompressing attacker-supplied pixel data merely to count them.

## Complexity

`ImageDimensions` is one function of three lines behind twenty of explanation, which is the right ratio for a thing whose entire purpose is that nobody writes a second one. The recommended fix takes it to eight.

## Test quality

`ImageDimensionsTests` is sound. Each fixture carries **distinct dimensions**, so an implementation returning a hard-coded pair fails rather than passing the group — the gaming shortcut is closed deliberately. The anisotropic case (300 × 150 on a 640 × 960 picture) blocks an implementation that divides by a single resolution value and passes every square case. Scratch directories are per-run beneath the OS temporary directory and torn down on success and failure alike.

RT-100.7 was written against the defect and reported `491.52 × 368.64` against an expected `2048 × 1536` before the fix, so it is known to catch the thing it exists for.
