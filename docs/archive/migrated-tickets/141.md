## Problem statement

**Observed by the author, and this is the third raising:**

> *"clicking in the search box should clear the selected category so that all filters are searched - 3rd time i am raising this one"*

## Restating the ask in his words before any code

**Three raisings means the previous readings were wrong, not that the code was hard.** So, plainly:

- The trigger is **clicking into the search box**, not typing in it.
- The effect is that **the selected category is cleared**.
- The purpose he gives is that **all filters are searched** --- so search reaches the whole corpus.

He is not asking for search to *ignore* the chip while leaving it lit. He is asking for the chip to
**clear**, which is a visible change and the thing that tells him the search is now over all 108.

## The cause

`FilterPanel.visibleFilters` (`FilterPanel.swift:157`) applies both narrowings with an `and`:

```swift
.filter { activeCategory == nil || $0.category == activeCategory }
.filter { query.isEmpty || name-or-category matches }
```

So with a chip active, a search only ever reaches that chip's filters. With **Lighting** chosen ---
4 of 108 --- searching for anything outside those four returns nothing, and the interface gives no
sign why.

## Violated criteria

- **AC87.x**, the filter catalogue's search reaching across categories. **RT-87.37** already asserts
  *"search reaches across categories, so nothing is behind a chip"* --- and it passes, because it
  runs with **no chip active**. The criterion is right, the test never enters the failing state.
- That is the whole reason this survived two fixes with a green suite.

## Debugging and fix procedure

1. **Clear `activeCategory` when the search field takes focus**, not when text changes. The author
   said *clicking in*, and clearing on first keystroke would leave one keystroke's worth of results
   filtered by a chip that is about to vanish.
2. **Do not simply make search ignore the chip.** The chip would stay lit while not applying, which
   is a worse interface than the defect: the user would be looking at a control that lies.
3. **Widen RT-87.37 to start with a chip active**, rather than adding a test beside it. The narrow
   fixture is what let this through twice.

## Test plan

- RT-142.1: with a category chosen, clicking into the search field clears the chip
- RT-142.2: with a category chosen, a search then finds a filter from a different category
- RT-142.3: the count returns to 108 when the chip clears and the query is empty
- RT-142.4: clicking into the search field with no category chosen changes nothing
- RT-142.5: RT-87.37 widened --- search reaches across categories *from a chipped starting state*
- UT-142.1: choose a category, click the search box, and judge that searching now reaches everything


## Acceptance criteria

- **AC141.1** When the search field takes the keyboard, no category is active, so a search covers the whole corpus.
- **AC141.2** A search entered after a category was chosen finds filters from every category, not only the one that had been chosen.
- **AC141.3** The category chip's appearance always matches whether it is narrowing the list, so no chip is lit while not applying.
