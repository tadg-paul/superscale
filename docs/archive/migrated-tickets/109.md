## Original issue body

## Problem statement

**Observed (author, UT round of 2026-08-25, part of the UT-95.1 FAIL):**
*"enter fal key and account key. fal key validates with a green checkmark.
account key does nothing"* — and, in the additional observations, *"the fal
account key validation button does nothing."*

**Expected:** a control that accepts a click communicates its outcome.

## Context that the fixer must not steamroll

The absence of *verification* is deliberate and documented at
`SettingsView.swift:44-46`: verifying the account key would call an account or
billing endpoint, which is exactly the surface the MVP paused (#89, #95;
AC89.7). "Stored or absent is all that can honestly be said about it." That
reasoning is sound and stays.

The defect is narrower: the row is drawn by the same `credentialRow` component
as the FAL key, so it *presents the same affordance* — and where the FAL key
answers a press with a green check, the account key answers with nothing the
author could see. A deliberate no-verification policy expressed through a
control that looks like its verifying sibling reads as a broken button, and
the author read it exactly that way. Same family as #104: a control that
accepts input must cause something or say it did not.

## Violated AC

- **AC95.1** in [docs/ACs.md](../blob/master/docs/ACs.md): *"each row says
  what it is once, and the whole scene reads cleanly"* — a button that appears
  broken fails the reading. If review concludes AC95.1 does not strictly cover
  control feedback, backfill on the #95 family per ISSUES.md rather than
  minting a parallel criterion.

## Debugging and fix procedure

1. First establish precisely what the author pressed and what happened:
   `credentialRow`'s save path for the account key (`saveAccountKey`) versus
   the FAL key's check path. Read, then reproduce in the running app — the
   status badge may flip `absent → stored` too subtly to notice, or may not
   flip at all until focus changes; those are different fixes.
2. Then pick the honest presentation, in order of preference:
   a. **Say what it does:** the row's action is *Save*, not *Validate* — label
      it so, and answer a save with the same visual state-change vocabulary
      the app already uses (the badge flipping to "Stored", immediately).
   b. If the row genuinely cannot say anything useful, remove the button and
      save on commit/blur, with the badge as the feedback.
   Either way the row should say *why* it does not validate — one short help
   string ("stored for future account features; not verified") replaces a
   mystery with a sentence.
3. The comment at `SettingsView.swift:44` stays and gains the ticket number.
4. UT-95.1 re-offer covers the human judgement; add a GUI RT that presses the
   control and asserts the observable state change, whichever form it takes.

## Test plan

- RT-109.1: pressing the account row's control produces an observable state
  change (badge, label, or the control's own state) within the same
  interaction
- RT-109.2: the row explains its non-verifying nature where the user can read
  it

### The mechanism, established from code before any change

`SettingsView.swift:47` passes the account row's status as `state.isAccountAdministrationConfigured ? .stored : .absent`, and `GenerationSettingsState.swift:152` defines that as a non-empty *text field*:

```swift
public var isAccountAdministrationConfigured: Bool {
    !accountAdministrationKey.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty
}
```

So the badge flips `absent -> stored` on the **first keystroke**. By the time the author pressed save, the badge already read "stored, not checked" and there was no state change left for the press to make. The press stored the key and repainted an identical row.

This is sharper than the ticket's two hypotheses. Step 1 proposed the badge "may flip `absent -> stored` too subtly to notice, or may not flip at all until focus changes". Neither: the flip had already happened, caused by typing. The `notice` at `SettingsView.swift:103-107` does set to "Account key saved", but it renders at the foot of the whole Form, several rows from the control pressed, and never clears.

The correct citation exists, and it is stronger than the backfill the ticket offered as a fallback: **AC95.3** -- *"The account key reads as stored or absent and carries no verification state."* A key typed and never saved reads as **stored**. The row states something untrue about the Keychain. AC95.3 is violated on its own terms.

**F4 (blocker) - "one short help string" would put the explanation behind a hover.** `.help()` in this file renders as a tooltip: invisible until hovered, invisible to anyone who never hovers, and unreadable by XCUITest, so RT-109.8 could not assert it.

**F5 (smell, pre-existing, out of scope) - the FAL row's badge reads its field too.** `generationKeyStatus` returns `.stored` for any non-empty text, so the FAL badge also says "stored, not checked" for a key only typed.
**Left alone, with reason:** for the FAL row this is *specified*. RT-95.17 requires that editing a verified key returns it to unverified immediately, and AC95.3 contrasts "stored" with "verified" rather than with "typed". So "stored" means slightly different things in the two rows, and the difference is principled: **the FAL row's press has its own answer to deliver (the provider's verdict), so its badge need not report the store; the account row's press has no other answer, so its badge must report the only thing the press changes.** Recorded so nobody later "tidies" the two into agreement and breaks RT-95.17.

If the trash control keeps reading `status.isPresent`, then making the badge honest silently **disables "remove" the moment a user edits a stored key** -- so someone correcting a typo in a saved key can no longer delete it. The badge answers *"does the field match the Keychain"*; the trash answers *"is anything in the Keychain"*. Different questions, different inputs. RT-109.9 guards it.
