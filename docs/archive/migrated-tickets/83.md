## Original issue body

Child of delivery master #79 (slice 3, first of two). Closes D3, D5 and D6.

## Problem

**D3: every image the application has ever produced carries a one-pixel black border.**

`Tiler.blendWeight` (`Tiler.swift:182-197`) returns the minimum distance to each of the tile's four edges, normalized within the overlap zone:

```swift
let left = min(Float(x) / o, 1.0)
...
return min(left, right, top, bottom)
```

At `x == 0` that is `0/o`, which is zero, and so is the returned minimum. Feathering a tile's edge is correct where a neighbouring tile overlaps it — the two ramps sum to one and the seam disappears. On the image boundary there is no neighbour. The pixel is covered by exactly one tile, that tile's weight there is zero, `weightAccum` stays zero, and `Tiler.swift:156` leaves the initialized zero in place:

```swift
if weightAccum[i] > 0 {
    outputPixels[i] = UInt8(...)
}
```

Zero in every channel including alpha. A black, transparent border, on every output, at every scale, since v1.

Measured on `Tests/visual_output/remy1_4x.png`: the outermost row and column are 100% black, the rows immediately inside are 0% black, and the source image is 0% black.

`RT-087` does not catch it. It samples at `x: 380` in a 400-pixel-wide output (`PipelineTests.swift:139`) — twenty pixels inside the edge, which is where the defect is not.

**D6: the upscale cannot be stopped.** It is the long local operation, and nothing in `Pipeline.process` checks for cancellation. Slice 2 deliberately did not promise this: it made a superseded run stop being *observed*, and recorded that the work itself keeps going until the pipeline learns to stop. This is where it learns.

**D5: kit failures are unreadable.** `ImageIOError`, `SuperscaleError` and `FaceEnhancerError` conform to `Error` and `CustomStringConvertible` but not `LocalizedError`, so `error.localizedDescription` falls back to the type name and a code. The user sees:

> The operation couldn't be completed. (SuperscaleKit.ImageIOError error 0.)

**Progress is prose.** The kit reports sentences, and slice 2 recovers structure from them by matching prefixes in `UpscaleProgressReader`. That mapping works and is confined to one place, but it is coupled to the kit's wording: rewording "Enhancing 3 faces..." breaks the face count. The kit knows the phase and the counts; it should say so.

## Solution

### D3: a boundary is not a seam

`Tiler.stitch` already knows each tile's origin and size and the output dimensions, so it can tell an interior seam from the image boundary:

```swift
let feathering = TileFeathering(
    left: originX > 0,
    right: originX + tileW < outputWidth,
    top: originY > 0,
    bottom: originY + tileH < outputHeight
)
```

`blendWeight` takes it and returns `1.0` for any edge that is not feathered, so a tile edge lying on the image boundary contributes at full weight. Interior seams are unchanged, which is what keeps the existing quality result.

This also removes the `weightAccum[i] > 0` guard's ability to hide a fault: with boundaries at full weight, every pixel of the output is covered by at least one tile at non-zero weight. The guard stays as a division-by-zero precondition, not as a silent fallback.

**Normalization rounds rather than truncates.** `Tiler.swift:157` currently converts with `UInt8(...)`, which truncates. In an overlap region two tiles carry identical values with weights summing to one, so the quotient should be that value exactly — but in floating point it can be `127.99999`, and truncation makes it `127`. That is an off-by-one along every seam, and it is also a downward bias on every blended pixel of a real upscale, not only of a round trip.

**The stitcher sees no alpha.** `Pipeline.swift:135-165` upscales the alpha channel separately and recombines it after stitching, so a partially transparent pixel never reaches the accumulation buffers. That is why AC83.1 speaks of an opaque image: a round trip through a premultiplied context would be lossy for one, and the code never asks it to be.

**The round trip is the test.** Splitting an image and stitching it back without processing must reproduce it exactly. That exercises the whole weighting scheme against a known answer, needs no Core ML, and would have caught D3 on the day it was written.

### D6: cancellation in the tile loop

The tile loop moves into a function that takes the per-tile work as a closure:

```swift
static func processTiles(
    _ tiles: [Tile],
    scale: Int,
    tileSize: Int,
    report: (PipelineProgress) -> Void,
    upscale: (CGImage) throws -> CGImage
) throws -> [Tile]
```

It calls `try Task.checkCancellation()` before each tile. `Pipeline.process` passes `inference.upscale`; a test passes a counting closure, so the loop's behaviour is verifiable without a model.

`Task.checkCancellation()` reads the current task, and `process` is called from inside one — slice 2's workspace runs it in a task whose cancellation was previously pointless. It stops being pointless here.

`Tiler.stitch` checks once per tile row as well. It is the second long loop, and at roughly 36 bytes per output pixel all resident, it is the expensive one to leave running.

`FaceEnhancer.enhance` checks before each face (`FaceEnhancer.swift:69`). It is the third, and the one that matters most for the user: it runs *after* the stitch, several seconds on a group photograph, each face costing a crop, a resize to 512×512, a GFPGAN inference and a feathered composite. It is also the phase the interface is displaying at the moment someone is most likely to press cancel. Cancelling during tiling and not during face enhancement would be a difference no one could explain.

Each of the three takes the per-unit work as a closure, so the loop's behaviour is verifiable with a counting stub and no Core ML.

### D5: errors that read as sentences

`ImageIOError`, `SuperscaleError` and `FaceEnhancerError` adopt `LocalizedError`, with `errorDescription` returning what `description` already returns where that reads well, and better wording where it does not. No case loses information.

**Errors from Vision and Core ML pass through unchanged.** `CoreMLInference` and the face path call into system frameworks that raise their own `NSError` values, and those are outside anything a conformance here can reach. They are propagated rather than wrapped, because wrapping would bury the platform's own diagnostic behind a generic sentence. AC83.5 is therefore about failures the kit raises. If one of the propagated errors proves unreadable in use, mapping that specific error is a separate change with its own evidence.

**Every `errorDescription` is a `switch` with no `default`.** RT-83.15 can only sample: the three enums carry associated values, so none is `CaseIterable`, and a test can check the cases someone remembered. A case added later without a description is exactly how D5 arose. With no `default` arm, that case does not compile — which is the guarantee wanted, held by the instrument that can hold it. The evidence is that the project builds, and RT-83.15 remains the check that the wording of the cases that exist is right.

### Structured progress

```swift
public enum PipelineProgress: Equatable, Sendable {
    case loading(fileName: String)
    case inspecting(width: Int, height: Int, scale: Int)
    case tiling(completed: Int, total: Int)
    case stitching(width: Int, height: Int)
    case upscalingAlpha
    case enhancingFaces(count: Int)
    case resizing(width: Int, height: Int)
    case writing(fileName: String)
    case finished(width: Int, height: Int, fileName: String)
    case warning(String)
}
```

`Pipeline.onProgress` becomes `((PipelineProgress) -> Void)?`. `UpscaleProgressReader`'s prefix matching is deleted: `UpscaleStage` maps `PipelineProgress` to `StagePhase` case by case, with no wording involved.

The CLI keeps printing exactly what it prints today, through a rendering function that takes a `PipelineProgress` and returns the sentence the pipeline used to emit. That text is the interface a scripted caller reads, and this slice rewrites every line that produces it, so AC83.6 holds it in place. The function is pure, so the tests need no process invocation and no model — the expected strings are the ones at `Pipeline.swift:63-199` as they stand.

**That rendering function is the tool's progress handler, not a helper beside it.** Nothing else in the executable formats a `PipelineProgress`, so there is nothing for the printed line to diverge into. This is worth stating because the tests reach the renderer rather than the printed line: running the built binary would be a build-system invocation, which `TESTING.md` keeps out of the regression pack, and typing these as one-off tests would be wrong for behaviour that must hold indefinitely. A test at the renderer plus a single call site is the honest reading of AC83.6's evidence.

`StagePhase.unclassified` stays. It stops being the fallback for an unmapped sentence and becomes the fallback for a `PipelineProgress` case a future kit version adds.

### Patterns and anti-patterns

- Swift, existing project structure. No new dependency, no new test architecture.
- `CODING.md` §Prohibited Anti-Patterns: no error suppression. The `weightAccum > 0` guard stays a precondition and does not become a way to tolerate uncovered pixels.
- `SWIFT.md`: no force unwrapping, no `try!`, no empty `catch`.
- `CODING.md` §Code Structure: the tile loop is extracted rather than grown.
- The accumulation buffers in `stitch` are already the memory ceiling. Nothing added to the loop may allocate per pixel.

### Condition enumeration

- **AC83.1** implies six conditions: the boundary is reproduced, a seam is reproduced, three geometries where `Tiler.split` behaves differently — one tile only, a final tile landing exactly on a stride step, and a final tile narrower than the overlap — and the same guarantee at a real scale. RT-83.1 to RT-83.4, RT-83.18, RT-83.23. The seam test is separate because a fix that special-cases boundaries and breaks seams would satisfy the first alone; it is also the row that rounding decides. The narrow final tile is the geometry where a tile's own left and right ramps overlap each other, so its interior weight is near zero before the boundary case is reached at all.

  **RT-83.1 requires a zero-valued source channel deliberately.** The defect makes pixels black, so the obvious wrong fix is to clamp every output channel to a minimum of one — which would satisfy RT-83.23 without touching the weighting at all. What blocks it is exact reproduction: a source channel of zero must come back as zero, and that only bites if the fixture contains one. Stating it in the test keeps the block from depending on an accident of the gradient.

  **RT-83.23 is the only test here that meets the user's actual output.** Every other one stitches at 1x, while the real path stitches already-upscaled tiles with `scaledOverlap = overlap * scale` and origins multiplied by `scale` (`Pipeline.swift:113-125`). Should those two ever disagree, the boundary weighting breaks again and every pure test still passes: they hold `Tiler`, and nothing else holds `Pipeline`'s arithmetic into it. D3 was found by looking at `remy1_4x.png`, not at a round trip, and RT-83.23 samples exactly what `RT-087` steps over. It needs the model and skips without one, which is why it complements the pure tests rather than replacing them; a skip is reported in the closing evidence rather than passed over as a pass.
- **AC83.2** implies two conditions: a boundary edge is not feathered, and an interior seam still is. RT-83.5, RT-83.6. Stated separately from AC83.1 because they fail differently — the round trip says the answer is right, these say the mechanism is right.

  **RT-83.6 asserts the ramp, not the mixture, and that wording is load-bearing.** An implementation returning `1.0` from `blendWeight` unconditionally would satisfy every round trip, because both tiles carry identical values there and any weighting reproduces them; it would satisfy RT-83.5, because a boundary pixel then holds its only tile's value; and it would satisfy a test asking merely for "a blend", because equal weights give the average of the two. What it destroys is the reason feathering exists. On a real upscale adjacent tiles genuinely differ, and a flat average across the overlap replaces a gradient with a visible band at every seam — trading a black border for banding, with a green suite. Comparing two positions within the overlap is what distinguishes a ramp from an average.
- **AC83.3** implies five conditions: cancellation stops each of the three loops that do per-unit work, it is reported as cancellation rather than as a failure, and an uncancelled run is unaffected. RT-83.7 to RT-83.9, RT-83.19, RT-83.22. The uncancelled case is what stops "process nothing" from passing the rest. The three loops are separate because each can be missed on its own: the tile loop is the obvious one, the stitch is the expensive one to leave running at roughly 36 bytes per output pixel all resident, and the face pass runs *after* the stitch — several seconds on a group photograph, and the phase the interface is showing when a user is most likely to press cancel.
- **AC83.4** implies three conditions: tile counts are values, the face count is a value, and no phase requires wording to identify. RT-83.10 to RT-83.12.
- **AC83.5** implies three conditions: a read failure reads plainly, a missing model reads plainly, and no description leaks a type name or code. RT-83.13 to RT-83.15. The third is the one that fails today. RT-83.15 samples; what generalises it is structural and stated below rather than tested.
- **AC83.6** implies two conditions: the wording of each phase is unchanged, and the counts within a phase appear where they did. RT-83.16, RT-83.17. Separate because a rendering that reads correctly but reorders "tile 3 of 12" is still a change to output a script may be reading.

### Test type justification

All twenty-three are regression tests — twenty-one under this issue's own criteria, and RT-83.20 and RT-83.21 under AC82.1. Every condition is machine-verifiable and each guards behaviour that must hold for the life of the project.

All but one run without Core ML. The round-trip and weighting tests drive `Tiler` directly, which is pure. The cancellation tests drive the three extracted loops with counting closures. The progress and error tests construct the values and read them. That matters: `RT-087` skips when the model is absent, and a test that skips is not a guard.

Round-trip fixtures are small synthetic images built in memory — a few hundred pixels square — so the data written stays bounded by construction, well inside the ceiling `Tiler.stitch` already implies at roughly 36 bytes per output pixel.

## Verification constraint

**The SSIM quality gate must not regress.** `RT064` compares output against PyTorch references and is slow enough that `make test` skips it; `make test-ssim` runs it. It is part of this issue's verification evidence, not optional.

A score falling below `0.90` is, and it would mean the boundary weighting has reached further than the boundary.

Recording the per-image scores before and after is part of the evidence, so the direction of movement is visible rather than only the pass.

## One limit on the evidence, stated rather than glossed

The issue asked for per-image SSIM scores before and after, so the direction of movement would be visible. `RT-064` emits a score only in its failure message, so a passing run leaves nothing to record, and obtaining the numbers would mean changing a test belonging to another issue. What can be said is that the gate holds at 0.90 for every image. That similarity should have *improved* — the fix replaces black boundary pixels with correct ones, and the reference has them correct — is reasoning from the change, not a measurement.

A gate that logged its scores would be worth having. Added to the backlog.
