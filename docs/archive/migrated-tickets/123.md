## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"toggling on and off 2x or 4x etc, should be instantaneous - it has already upscaled this image and should be rendering it from cache. instead it spends time upscaling every time"*

> *"toggling on and off the face model appears instantaneous - obviously rendering from cache."*

> *"even when i switch off face enhance, it fails to deliver a 2x or 4x upscale from cache, generating a new upscale each time."*

> *"I would love to have a toggle button for the upscaled image render on/off, but that is the whole point of the caching requirement, so that the cached upscale can be toggled QUICKLY"*

## This is a specification change, not a defect

Guide section 2.5 says the upscale *"re-runs when the working image changes ... or when the scale or model changes"*, and `PipelineCache` caches the **loaded pipeline**, not the produced renderings. So re-running on a scale change is what the design asks for, and the build is conforming.

The author's observation is that the design is wrong on this point: the upscale is deterministic --- guide 3.2 says so explicitly, and uses that determinism to justify discarding upscales at lock time --- so a rendering that has already been produced for a given asset, model, scale and face setting can be served rather than recomputed.

The face-enhancement toggle already behaves this way, which is the evidence that the machinery exists and the key is wrong rather than absent.

## Relationship to #106

**This subsumes #106** (choosing a scale after a completed run can serve the previous scale's cached rendering under the new scale's label). That ticket records the same code serving the *wrong* entry because `heldRendering` is consulted inside the `$scaleSelection` sink, where `@Published` has not yet published the new value, so the lookup is keyed by the scale being replaced.

The two are one problem seen from opposite sides: the key is computed at the wrong moment. #106 must be closed by this child rather than left open beside it.

#106 also records why its three-line fix was reverted: it changes run-versus-cache timing that RT-156, RT-158 and RT-90.52 encode. Those tests are expected to need superseding, with the reason recorded on their criteria. They must not be weakened.

## Acceptance criteria

To be drafted and audited. The system states this child must establish, in outline:

- A rendering already produced for a given working asset, model, scale and face setting is presented without re-running the pipeline.
- The rendering served is the one matching the requested settings, never the settings it replaced.
- Changing to a setting with no held rendering runs the pipeline as before.
- The number of renderings retained stays bounded.

## Debugging and fix procedure

1. **Reproduce the two halves separately.** Serve-nothing (a repeat of a previously rendered scale re-runs) and serve-wrong (#106's case). One key computed at the wrong moment should explain both; if it does not, there are two defects.
2. Compute the key from the **requested** settings, passed as a parameter, never read back off the published property inside its own sink. The comment at `UpscaleViewModel.swift:655-670` records this trap being met once already, three lines below the comment warning about the first instance.
3. Bound the retention deliberately and state the bound. Guide 3.2 already argues that retention should be proportional to the lock chain rather than to how many times the size was adjusted.
4. Run RT-156, RT-158 and RT-90.52 before and after. Where an expectation moves, record why on its criterion.

## Test plan

### The cause was already written down

`renderingKey(facesEnhanced:selection:)` has taken an optional selection all along, *"so the caller can supply the effective one, which a caller inside the `$scaleSelection` sink must"*. No caller did. The lookup read the published property, and `@Published` publishes in `willSet`, so inside the sink it still held the scale being **replaced**.

Choosing 8x looked up 4x. Where a 4x rendering was held it came back instantly — the previous scale's picture beneath a readout naming the new one.

**The same trap, three lines below the comment that warns about the first instance of it.** Guide 3.x's `@Published` rule, found again in the file that records it.

### Why this could be done now when #106 said it could not

#106's reason was specific and checkable: the fix *"moved three closed issues' GUI tests (RT-156, RT-158, RT-090.52) from passing to failing — not because they were wrong, but because they were written against the timings the defect produces."*

**All three pass.** The timings changed when **#131** stopped the application upscaling on launch: those tests no longer begin with a rendering already held, so the run-versus-cache boundary they were sensitive to has moved out from under them.

Verified by running them rather than assumed. That is the whole of why #106 can close: its blocker is gone, not routed around.
