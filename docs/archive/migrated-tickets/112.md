## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure). **Blocked on #117** (the GUI suite's upscale-complete signal), for the reason in "Why this waits" below.

## Problem statement

**Observed (author, UT round 3, 2026-08-25, alongside the UT-89.1 FAIL):**
*"when a FAL filter is applied, there is no curtain tool for comparison."*

**Expected:** a filter result can be compared against the base it descends
from — that comparison is the criterion AC94.3 exists to state, and UT-96.1
(the differently-shaped comparison) cannot even be attempted without the tool
appearing.

## Violated ACs

- **AC94.3** in [docs/ACs.md](../blob/master/docs/ACs.md): *"The curtain
  compares what is on the canvas against the base it descends from, so a
  filter result is compared against the picture it was made from rather than
  against its own upscale."* Its tests pin *what* the curtain compares; the
  author's report is that after a filter it is not offered at all.
- **AC90.6** in [docs/ACs.md](../blob/master/docs/ACs.md): *"The curtain
  compares whatever is displayed against the image it derives from, and is
  absent when there is no derivation."* Cited because the two directions are
  one criterion in practice. The defect is that "derivation" is implemented as
  "upscale", and a fix must keep the absence half true: with nothing derived at
  all, there is still no curtain.

## Root cause, traced 2026-08-26

The ticket's original first suspect was right.

`MainView.swift:492` gates the control on `if viewModel.result != nil`, and
`derivedImage` is `viewModel.result` (`MainView.swift:195-197`) — the **upscale**
output. The comment at `MainView.swift:500-505` states the reasoning outright:
*"Compare stays bound to `result`, because with nothing derived there is nothing
to compare against."*

That reasoning is false after a filter. A filter result **is** a derivation of
the base, which is what AC94.3 says the curtain exists to compare.

And the state the author hit is the one AC96.1 guarantees: raising an undersized
picture to the filterable minimum **turns the scale off**, so no upscale runs,
`viewModel.result` stays nil, and the control is never rendered.

## Why the existing tests did not catch it

RT-90.15 and RT-90.16 — including *"with a filter result present, the curtain
compares base against that result"*, marked passing — live in
`Tests/SuperscaleUXCoreTests/CanvasContentTests.swift`. They are package-level
over `CanvasContent`: they decide what the curtain *draws* and never reach the
toolbar condition that decides whether the control *exists*.

The criterion is proven one layer below the layer that fails. Guide section 7
has the sentence, and this delivery has now met it three times: *a package that
is complete and a feature that is delivered are not the same claim.*

## Why this waits on #117

Making Compare appear after a filter with no upscale invalidates the GUI suite's
completion signal. `waitForUpscaleComplete` is
`app.buttons["compareButton"].waitForExistence(timeout:)` at **45 call sites**.
The moment Compare means "there is something to compare" rather than "an upscale
finished", that helper returns true before any upscale has run, and 45 tests
begin asserting against a pre-upscale state while still reporting green.

#117 moves the signal onto a canvas state value first. Landing this ticket
before it would leave a window in which the suite reports green while asserting
nothing, and anything verified in that window would be unverified.

## Solution

The curtain belongs to *canvas content that descends from a base*, not to *a
completed upscale*. The gate moves off `viewModel.result` and onto the presence
of a derivation — which after AC94.3 means: something is displayed, and it is
not the base it descends from.

The absence half of AC90.6 is preserved explicitly rather than incidentally:
with only an imported picture and nothing derived, no curtain.

## Test plan

Every test names the scale state, because the scale state is the condition. With
a scale selected, an upscale runs, `viewModel.result` is non-nil, and Compare
appears **today** — so a test that applies a filter with the scale on passes
without any fix at all.

- RT-112.1: **with the scale off**, after a filter result reaches the canvas, the
  comparison affordance is present and enabled
- RT-112.2: **with the scale off**, entering comparison over a filter result
  shows the curtain, with two sides and a divider that can be moved
- RT-112.3: **with the scale on**, the affordance is present after a filter, so
  the existing behaviour is unchanged rather than traded away
- RT-112.4: with an imported picture, the scale off and no filter applied, no
  comparison affordance is offered, so AC90.6's absence half still holds
- RT-112.5: after a filter with the scale off, the canvas reports **a filter
  result** rather than an upscaled rendering, using the value #117 introduces

All five are GUI-level. **They must not be satisfiable at the `CanvasContent`
layer**, which is already green and is not where the defect is.

**Coverage boundary.** RT-112.2 asserts that the curtain is *there and usable*,
not which two images it holds. That identity is AC94.3's and is already pinned by
**RT-94.7**, which asserts against `baseFileURL`, the property the view reads —
a claim XCUITest cannot make, because it observes the accessibility tree and not
which file backs each side. This ticket is about the affordance being absent, not
about it comparing the wrong things.

**RT-112.5 is the vacuity guard for #117's migration**, expressed as a product
state rather than as a statement about a helper. If anything ever reports a
filter result as a finished upscale, it fails here — rather than 45 tests
quietly asserting nothing and reporting green.

UT-96.1 (the differently-shaped comparison) re-offers on master #79 once green,
together with the UT-89.1 re-offer from #111 — one author sitting covers both.
The stubbed 1024×1024 square against the 240×320 fixture also exercises AC96.3's
differing-shape drawing on the way.
