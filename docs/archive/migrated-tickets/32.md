## Original issue body

## Problem

When upscaling images that contain human faces, the face regions are replaced with black/brown squares in the output. The face detection and GFPGAN model are applied, but the enhanced face output is corrupted.

## Root cause

Three independent bugs in the GFPGAN CoreML model conversion:

### 1. Missing ×255 output scaling
The conversion script outputs float values in [0, 1] range but does not scale to [0, 255] pixel range before the CoreML ImageType output. Real-ESRGAN models wrap their output with \`OutputScaler\` that does \`out * 255.0\` — GFPGAN was missing this step. When CoreML converts the [0, 1] float tensor to a UInt8 pixel buffer (BGRA8), values are truncated to {0, 1} — producing an all-black image.

### 2. coremltools \`_cast\` handler bug
coremltools' TorchScript converter has a bug in its \`_cast\`/\`_int\` handler: it calls \`dtype(x.val)\` on numpy arrays, which fails with "only 0-dimensional arrays can be converted to Python scalars". This crashes the conversion at ~34% progress. Fix: monkey-patch the handler to call \`.item()\` first to extract the scalar.

### 3. fp16 precision destroys StyleGAN2 decoder output
coremltools defaults to \`FLOAT16\` compute precision. StyleGAN2's modulated convolution uses \`rsqrt(weight.pow(2).sum(...))\` for weight demodulation — this operation loses all spatial information in fp16, producing flat near-constant output (std=1.5 vs correct std=65.6). The model MUST be converted with \`compute_precision=ct.precision.FLOAT32\`.

Additionally, GFPGAN's \`ModulatedConv2d.forward()\` uses dynamic batch-dependent shapes in \`view()\` calls and grouped convolutions (\`groups=b\`). Since we always infer with batch=1, the forward method is monkey-patched to use static shapes and \`groups=1\` for clean TorchScript tracing.

### Verification
With all three fixes applied:
- **PyTorch direct output**: mean=80.8, std=60.7, range=[0, 255]
- **CoreML model output**: mean=80.8, std=65.6, range=[0, 255]
- Previous broken model: mean=80.7, std=1.5, range=[65, 109] (flat garbage)

## Solution

### 1. Root cause fix (convert_gfpgan.py)
Complete rewrite of the conversion script with:
- \`_patch_coremltools()\`: Monkey-patches the \`_cast\` handler for numpy array compatibility
- \`_patch_modulated_conv()\`: Patches \`ModulatedConv2d.forward\` for batch=1 static shapes
- \`compute_precision=ct.precision.FLOAT32\` in \`ct.convert()\`
- Output scaling to [0, 255] in the traceable wrapper

### 2. Swift safeguard (FaceEnhancer.swift)
After GFPGAN inference, validates the enhanced face has non-trivial brightness. If output is essentially black (mean pixel < 5), skips enhancement and preserves the original face. This protects users with older model installations.

### 3. Model reconversion
The GFPGAN model was successfully reconverted with all fixes and installed. Visual verification confirmed correct face enhancement on \`vance-wilson_4x.jpg\` (two faces enhanced correctly, no corruption).

## Root cause confirmed — 2026-03-20

**Verified with direct model inference:** `m.predict({'input': face_image})` returns an image where every RGB pixel is 0 (all black). The GFPGAN CoreML model outputs float values in [0, 1] range but the `ct.ImageType` output spec has no explicit scale, so CoreML truncates to UInt8 → all zeros.

**Comparison:**
- Real-ESRGAN conversion: wraps model in `OutputScaler` (`out * 255.0`) + `outputs=[ct.ImageType(name="output", scale=1.0)]`
- GFPGAN conversion: model outputs [0, 1] + `outputs=[ct.ImageType(name="output")]` (no scale) → **truncated to black**

Solution posted in issue body. Implementation starting now.

## Final fix — 2026-03-20

### Root cause update

The original analysis identified only the missing ×255 output scaling. Investigation revealed two additional bugs:

1. **coremltools `_cast` handler** crashes on numpy arrays with shape > 0 — monkey-patched to call `.item()` first
