## Original issue body

## Problem statement

**Observed:** at commit `061fda0` (pre-rewrite `9248d7d`) (the first fix for #104), the full GUI suite
fails 17 tests, including two that only launch the application
(`test_drop_target_visible_on_launch_RT107`,
`test_file_chooser_button_exists_RT110`). The application hangs at import.

**Expected:** the #104 fix changes only what happens to a scale chosen during a
run; nothing else.

A regression introduced by this delivery, in the fix for #104. Logged
retrospectively --- the corrective work began before this ticket existed,
contrary to the SDLC.

## Reproduction

1. Check out `061fda0` (pre-rewrite `9248d7d`)
2. `make test-gui` --- 17 failures; or launch the app and import any picture

## Violated AC

- **AC90.1** in [docs/ACs.md](../blob/master/docs/ACs.md): *"An imported image
  occupies the canvas from the moment it is loaded..."* --- representative; the
  17 failures span many criteria because the hang precedes all of them.

## Cause

`reupscaleIfNeeded`'s `!isProcessing` guard was load-bearing against
**re-entrancy**, not just busyness --- the two were conflated in one check.
`processImage` assigns published properties its own subscribers watch
(`adoptNativeScale` assigns `scaleSelection`; `reapplyDimensionCap` assigns the
dimension fields), and `@Published` republishes **even when the value is
unchanged**. With the guard gone, configuring a run re-entered `processImage`
through the `$scaleSelection` sink while it was still setting up.

## Solution outline (fix in working tree, verification pending)

`isConfiguringRun`, a private non-published flag set for the duration of
`processImage` and of `reupscaleForFaceToggle`'s restore block (every line of
that restore assigns a watched property). `reupscaleIfNeeded` refuses only when
the mutation was caused by run configuration itself. Deliberately not
`@Published`: publishing it would make it exactly the kind of state whose own
notification re-enters the code that set it.

Also in the working tree: the fold-in of the #106 fix is **reverted** --- it
changed run-versus-cache timing that three closed issues' tests encode, and it
belongs to #106, not here.

## Verification procedure --- run when the machine is free

The author is using the machine for UT validation; GUI runs seize the UI, so
they wait. In order:

1. `xcodebuild build-for-testing` (safe now --- no UI)
2. Targeted run: the three remaining failures (`RT156`, `RT158`, `RT090_52`)
   plus `RT101_1` and `RT101_3`. Expectation: all five pass, because the three
   were casualties of the folded-in #106 change, now reverted. If any still
   fails, stop and diagnose from the failure text --- do not guess
3. Full `make test-gui`. Baseline to beat: 101 executed, 0 failures
4. Full `make test` (package, safe anytime): baseline 533 executed, 6 skipped,
   0 failures

Spot-verified so far: 14 of the 17 pass individually against the flag fix,
including RT-100.10.

## Test plan

No new test IDs: the 17 existing GUI tests are the regression coverage, and
their breadth is exactly what caught this. The lesson for the guide is already
recorded (v3.23): inside a `@Published` sink, take the value; a control that
accepts a click must cause something or say it did not.
