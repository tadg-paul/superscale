## Original issue body

Child of delivery master #79 (slice 1). First of the functional slices, because it stops data loss that occurs today.

## Problem

The application has no model of how one image relates to another. It holds loose properties — an original, a result, some cached variants — and infers relationships from timing and from which view happens to be on screen. Three defects follow directly.

**Data loss.** `HistoryView` passes `session.preferredAssetURL` to the upscale handoff (`HistoryView.swift:181`). That accessor is `upscaledAssetURL ?? generatedAssetURL` (`GenerationSessionStore.swift:62-64`), so a session that has already been upscaled feeds its **upscaled** image back through the pipeline: a 4x of a 4x, with a second face-restoration pass over already-restored faces. The result is written to the same fixed `upscaled.<ext>` path (`GenerationSessionStore.swift:149-152`), destroying the original upscale.

`preferredAssetURL` is correct where it is used for display (`HistoryView.swift:81`, `:118`) — a viewer wants the finished image. It is wrong as the input to further processing. The accessor that is correct there, `upscaleSource`, is defined three lines below it and is never called.

**Data corruption.** The write-back observer fires on any change to `viewModel.resultData` while `pendingSessionID` is set (`MainView.swift:60-62`, `:128-140`). Sending a generated image to upscale and then dropping an unrelated file attributes that unrelated upscale to the cloud session, which then displays a stranger's photograph as the output of a prompt.

**Stale correlation.** `pendingSessionID` is cleared only on success or on error (`MainView.swift:64`, `:136`). Switching mode, dropping a new file, or abandoning the operation leaves it set.

**The plumbing to fix this already exists and is unused.** `GUIUpscaleSource` distinguishes `.selectedFile` from `.generatedFile`, and `GUIUpscaleResult` carries that provenance back out (`GUIUpscaleCoordinator.swift:8-18`, `:56-62`). `UpscaleViewModel` never reads `GUIUpscaleResult.source`. `GenerationCoordinator.upscaleSource` and `GenerationSessionRecord.upscaleSource` are both defined and never called. The lineage was designed, built, and then bypassed.

## Solution

Introduce an **asset graph** in `SuperscaleUXCore` that owns every image the application holds, the relationships between them, and the rules those relationships obey. Correctness stops depending on a developer remembering an ordering and becomes a property of the structure.

```swift
public enum AssetRole: String, Sendable {
    case source           // brought in by the user
    case raisedToMinimum  // raised only to the assumed minimum long edge
    case filtered         // output of a cloud filter
    case upscaled         // output of an upscale targeting the user's chosen size
}

public struct Asset: Identifiable, Equatable, Sendable {
    public let id: UUID
    public let role: AssetRole
    public let fileURL: URL
    public let pixelSize: CGSize
    public let parentID: UUID?
    public let provenance: Provenance?
}
```

`AssetGraph` holds the assets, the **base** pointer and the **candidate** pointer, and is the only place the rules live.

### Why two upscale roles

Both come from one upscale operation; the target decides which. `raisedToMinimum` targets the filter model's working resolution, so nothing is wasted by sending it and it is valid filter input. `upscaled` targets the size the user asked for, so sending it to a filter would discard everything the Neural Engine produced. The harm the rules prevent is *exceeding* model resolution, not upscaling as such.

### Upscales are derivations, not state

An upscale is deterministic: the same image, model and scale reproduce it in seconds. It is therefore never locked, never part of the base chain, and never needs preserving. That single fact is what lets lock discard upscales safely, and it is why saving a prior iteration can re-derive its upscale on demand.

### Reviving the provenance API

`GUIUpscaleSource` gains an asset identifier so the graph can attribute a result to the asset it came from. `UpscaleViewModel` reads `GUIUpscaleResult.source` rather than discarding it. Session attribution follows lineage instead of a `UUID` held in view state, which removes the timing dependency behind the corruption defect.

### Patterns and anti-patterns

- Swift, existing project structure. No new dependency, no new test architecture.
- The graph is a value type with pure transition functions, so the rules are testable without network access or Core ML.
- `CODING.md` prohibits error suppression: an invalid transition throws a typed error naming the rule it broke, rather than returning a bool or silently doing nothing.
- `SWIFT.md` prohibits force unwrapping and `try!`; pointer resolution returns optionals or throws.
- `CODING.md` requires evergreen naming: no `newBase`, no `improvedAsset`.
- Display keeps using `preferredAssetURL`. Only the processing input changes.

### What discarding may touch

Discarding is the one operation in this slice that removes a file, in a slice whose purpose is to stop files being removed. Its reach is therefore bounded explicitly rather than left to the implementation.

The graph removes a file only when all of the following hold: the asset's role is `upscaled`, the graph itself produced it, and it is no longer the current output of any working asset. Sources, imported images, filtered assets and every locked iteration are outside the operation entirely — not merely un-targeted, but unreachable by it. RT-81.31 holds the implementation to that.

This is what makes it safe: an upscale is a deterministic derivation, reproducible in seconds from the same image, model and scale. Nothing else in the graph is.

### Test location

`Tests/SuperscaleUXCoreTests/AssetGraphTests.swift`, XCTest, in the existing `SuperscaleUXCoreTests` target alongside `SessionStoreTests.swift` and `GUIUpscaleCoordinatorTests.swift`. No new target, no new dependency, no new test architecture. `make test` reaches it as part of the main package; nothing here belongs in the `OneOff` package.

### Condition enumeration

- **AC81.1** implies four conditions: filters do not read an upscaled asset, upscales do not read their own output, an attempted violation is reported rather than silent, and a stage requested with nothing to work on is reported too. RT-81.1 to RT-81.3, RT-81.25.
- **AC81.2** implies three conditions: a filter reads the base rather than the previous result, the new result becomes the candidate in place of the previous one, and results chain after a lock. RT-81.4, RT-81.30, RT-81.5. The middle condition is separate because reading the right input and storing the result in the right place fail independently: an implementation that reads the base correctly but leaves the candidate on the earlier output would have the user lock an image they had already moved past.
- **AC81.3** implies four conditions: filtering does not move the base, upscaling does not move it, a lock without a candidate does not move it, and a lock captures model resolution. RT-81.6 to RT-81.9.
- **AC81.4** implies three conditions: collisions across different working assets, collisions within one working asset upscaled repeatedly, and the session case that causes the data loss today. RT-81.10 to RT-81.12.
- **AC81.5** implies four conditions: descendants attach, non-descendants do not, an unrelated operation in between does not steal the association, and a lineage crossing two sessions attaches to the nearer. RT-81.13 to RT-81.15, RT-81.19. RT-81.14 places an unrelated session in the graph deliberately: without one, an implementation that attributes by recency rather than by lineage would pass every test in this row.
- **AC81.6** implies five conditions: order preserved, provenance carried, secrets absent, a missing file does not remove the entry, and a present file is reported available. RT-81.16 to RT-81.18, RT-81.20, RT-81.32. The last two are separate because they fail for different reasons: an implementation reporting everything unavailable is a different fault from one that drops absent entries from the chain, and the first would leave the workspace with nothing it could display or save.
- **AC81.7** implies six conditions: an output is identifiable as current, a later one supersedes it, changing the working asset clears it, superseded outputs are discarded, the current one is not discarded with them, and discarding reaches nothing else. RT-81.21 to RT-81.24, RT-81.26, RT-81.31. RT-81.24 and RT-81.26 are separate tests because they fail for different reasons: an implementation that discards everything is a different fault from one that discards nothing. RT-81.31 bounds the reach of discarding, which is otherwise unconstrained — an implementation that deleted a locked iteration's file would pass every other test in this row, and RT-81.20 would read the result as correct handling of an absent file rather than as the data loss this slice exists to stop.
- **AC81.8** implies three conditions: a reference the graph does not hold is refused, the session path resolves to the produced image, and display is unaffected. RT-81.27 to RT-81.29. A fourth property — that no stage entry point accepts a bare file location at all — is enforced by the signature at compile time and carries no test; see below.

### Why AC81.8 exists

The rules above govern the graph. The defects do not live in the graph — they live at the call sites that feed it.

`HistoryView.swift:181` hands `session.preferredAssetURL` to the upscale handoff, and that accessor prefers the upscaled asset. A correct graph with passing tests changes nothing while that line stands.

Deleting the accessor is the wrong fix. Seven of its eight uses in that file are correct: lines 81 and 118 display the image, 237 saves it, 249 reveals it, and 188, 193 and 198 test availability. A viewer wants the finished result. Only the one feeding further processing is wrong.

The fault is an untyped boundary. A `URL` meaning *the image to show* and a `URL` meaning *the image to process* are the same type, so one substitutes for the other silently. Typing the stage boundary to accept an asset reference makes `HistoryView.swift:181` stop compiling, and leaves the seven correct uses untouched.

That is the same discipline as slice 0: prevent by construction rather than rely on the next person noticing.

**The exclusion of bare file locations carries no test, deliberately.** It is a property of which functions exist, and a test cannot assert that an overload is absent: code calling a function that does not exist would not compile, so there would be nothing to run. Any attempt would end as a tautology or as source introspection, which `TESTING.md` forbids. The compiler is the instrument here, and a stronger one than a test, because it cannot be forgotten or skipped. Evidence is that the project compiles after the change while the seven correct uses of the display accessor are untouched, which is also what shows the change was surgical. What remains testable at runtime is that a reference is honoured only when the graph actually holds it, which is RT-81.27.

### Temporary state in tests

Several tests need files on disk: RT-81.10 and RT-81.11 concern path collision, RT-81.20 and RT-81.32 need a file to exist and then be removed, and RT-81.24, RT-81.26 and RT-81.31 concern discarding outputs.

Every such test allocates a unique per-run directory beneath the operating-system temporary directory, and removes it in teardown on success, on failure, and on handled interruption. Files are small placeholders rather than real images: the graph stores paths, sizes and metadata, so nothing under test needs actual pixels, and the data written stays bounded by construction.

Every file a discarding test can reach lives inside that per-run directory, so a fault in the reach of discarding shows up as a failed assertion rather than as a deletion somewhere else on the machine.

### Why AC81.7 exists, and how it bounds retention

AC81.4 requires every upscale to write to a path of its own rather than over an existing output, which is what closes the data-loss defect. Without a notion of *current*, that leaves the graph holding several upscaled assets with nothing identifying which corresponds to the working asset as it now stands — the view could not ask for the finished image, and neither could save.

It also leaves an unbounded write path in the model, which sits badly beside a defect about destroying files. Each output at the documented 4096-pixel cap is roughly 50 MB.

AC81.7 resolves both. One output is current per working asset; superseded ones are discarded once they are no longer current. Nothing is overwritten in place, so the data-loss defect stays closed, and the number of retained outputs stays proportional to the lock chain rather than to how many times the user adjusted a slider.

### How AC81.4 and AC81.7 divide the work

They govern different things, and the distinction matters because an earlier draft had them contradicting each other.

**AC81.4 is about collision.** The defect it closes is overwriting *in place*: the current code writes every upscale to a fixed `upscaled.<ext>` path, so the second destroys the first. The guarantee needed is that no upscale ever writes over another's output.

**AC81.7 is about lifecycle.** One output is current per working asset; superseded ones are released.

AC81.4 deliberately does not promise that every output survives, which would make bounded retention impossible. It promises only that nothing is destroyed by being written over — which is the actual fault.

Two consequences follow for the tests.

**RT-81.11 captures the first output's path before the second upscale runs.** The first is discarded once superseded, so a test that reads its path afterwards is asserting against something that no longer exists. The property under test is that the second upscale chose a different path, and that is observable at the moment it is chosen.

**A discarded path is not free for reuse.** Each upscale's path is derived from its own asset identity, so it is unique for the life of the graph. Reusing the path of a discarded output would satisfy AC81.4 as literally written — the path is unoccupied — while reintroducing the fixed-path pattern that caused the defect.

### Test type justification

All thirty-two are regression tests. The graph is a value type with pure transitions, so each exercises real behaviour through the type's own API with no network access, no Core ML, and no build-system invocation. All guard behaviour that must hold for the life of the project, which `TESTING.md` places in regression.

No user test is allocated: every condition is machine-verifiable, and `TESTING.md` reserves user tests for outcomes needing human judgement. The visible consequences of this slice are judged in the workspace slice.

## What was delivered

An `AssetGraph` in `SuperscaleUXCore` owns every image the application holds, the lineage between them, and the rules that lineage obeys. Correctness stopped being something a developer has to remember and became a property of the structure.

**The stage boundary is now typed.** `GUIUpscaleSource` no longer has a public initializer that accepts a location. A caller obtains one from the graph, from a generation session, or by declaring a file the user supplied directly. `HistoryView` was passing `session.preferredAssetURL` — the accessor that prefers the *upscaled* image — into the upscale handoff, so an already-upscaled session re-upscaled its own output over the top of the original. That line no longer compiles, and the seven correct uses of the same accessor for display, saving and revealing are untouched. The view now hands over the session and lets the model decide what may be processed.

**Attribution follows lineage rather than timing.** `MainView` held a `pendingSessionID`, and the write-back observer fired on any change to the result while it was set — so an unrelated file dropped in between was recorded as the output of a prompt. The result now carries the input it came from, and attribution reads that. `pendingSessionID` is gone entirely, which closes the stale-correlation defect by construction rather than by remembering to clear a variable.

**Upscales no longer collide.** Each is written to a location derived from its own identity, in the graph and in the session store, replacing the fixed `upscaled.<ext>` path where the second destroyed the first. One output is current per working asset; superseded ones are released, and releasing can reach nothing but an upscaled output the graph itself allocated.

The provenance API that was designed, built and then bypassed is now the path everything goes through.

## Findings worth recording

Three faults were found in work written for this issue, all by the audits:

1. **The fix reinstated the defect it closed.** `MainView.sendToUpscale` substituted the most recently recorded session whenever a source arrived without one — attribution by timing, in the one place the slice existed to remove it. Caught by `audit-code`, first pass, as a blocker. The remedy deleted the state rather than guarding it.

2. **A guard that silently did nothing.** The check bounding file removal to the graph's own directory compared file URLs. A file URL carries a directory flag, and a URL built for a directory that does not yet exist does not have it — so a graph whose output directory was named before being created found its own location unequal to itself and stopped releasing anything, with no error and no failing test.

3. **An overstated finding, corrected.** The second-pass report claimed a broader trigger for that fault than the evidence supported. `URL(fileURLWithPath:)` stats the path, so the URL comparison is correct whenever the directory already exists. Establishing the real trigger meant reverting the fix and watching which tests failed: RT-81.24 and RT-81.31, and only under the name-then-create ordering. The test fixture was changed to use that ordering, so the construction is now covered rather than merely commented.

The pre-code audits also caught two specification faults before any code existed: a test that specified something no test can assert — the absence of a function overload, which is a compile-time property — and a contradiction where one test required a superseded output to remain on disk while another required it to be discarded.
