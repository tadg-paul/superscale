## Original issue body

## Problem statement

**Observed (author, UT round of 2026-08-25):** applying any filter fails with
*"Error: the provider would not accept the image: invalid storage type."*
Reproduced across relaunch and after re-entering a FAL key that validates with
a green check. **This blocked three of the eight user tests** (UT-89.1,
UT-94.1, UT-96.1), and it means the cloud filter path — the headline feature of
the v2 MVP — has never completed once against the real provider through the GUI.

**Expected:** the reference uploads and the filter runs.

## The finding behind the finding

Every test of this path — RT-92.1 to RT-92.19 and RT-102.1 to RT-102.4, all
green — runs against a stubbed `FalHTTPTransport`. The stubs verify we send
what we *believe* the protocol is; nothing verifies the belief. A wire-format
error is therefore invisible to the entire suite by construction. That is not
a test gap to patch quietly; it is a missing test *class*, addressed in the
test plan below at the author's direction.

## Where the error comes from

- The message is `FalStorageError.initiateFailed(diagnostic:)` rendered by
  `FalStorageClient.swift:32` — so the initiate exchange itself was rejected,
  before any bytes moved.
- We send `POST {base}/storage/upload/initiate?storage_type=gcs`
  (`FalStorageClient.swift:150`), with file name and content type as JSON and
  the key in the Authorization header.
- "invalid storage type" names the one parameter we hard-code. **Hypothesis,
  unverified:** `gcs` is not an accepted value on the current API; fal's own
  tooling uploads to their CDN (the reference doc's row names the SDK's
  `upload_file`, which targets fal-cdn). `docs/FAL_REQUEST_REFERENCE.md`
  documents the no-cache rule for uploads but not the initiate exchange, so
  the value came from somewhere undocumented and nothing could contradict it.

## Violated AC

- **AC92.2** in [docs/ACs.md](../blob/master/docs/ACs.md): *"Uploading a
  reference obtains its destination from the provider before sending."* The
  provider declines to issue a destination, so nothing downstream can hold.
- AC94.1's flow is the user-visible casualty.

## Debugging and fix procedure

1. **Probe before changing code.** With the author's keys in `.env` (loaded
   via a shell wrapper, never committed, never echoed):
   `curl -s -X POST "https://rest.fal.ai/storage/upload/initiate?storage_type=gcs" -H "Authorization: Key $FAL_KEY" -H "Content-Type: application/json" -d '{"file_name":"probe.png","content_type":"image/png"}'`
   — confirm the live error matches the GUI's. Then repeat with candidate
   values (`fal-cdn-v3`, `fal-cdn`, omitted entirely) and record each response
   verbatim on this ticket. The accepted value and response shape decide the
   fix; do not guess it from SDK source alone.
2. Fix the value (or drop the parameter if the API defaults sensibly), and
   update `docs/FAL_REQUEST_REFERENCE.md` to document the initiate exchange it
   currently omits — endpoint, parameter, accepted value, response fields —
   with the probe transcript as its citation.
3. Confirm the stubbed tests still describe reality: whatever the probe shows
   the response to be, `RecordingTransport`'s canned responses must match it
   field for field, or the stubs are rehearsing a fiction again.
4. Full flow through the GUI once: import, filter, result on canvas. That is
   the author's UT-94.1 re-offer.

## Test plan — live OTs, per the author's authorization of 2026-08-25

New one-off tests in the one-off package (outside `make test`'s scope per
AC80.1, so the regression suite stays hermetic and free of secrets):

- **OT-107.1:** a live initiate against `rest.fal.ai` with the `.env` key
  returns an upload URL and a file URL — the wire format is proven, not
  believed
- **OT-107.2:** a live round trip — initiate, PUT a small PNG, GET the
  returned file URL — yields the bytes that were sent
- **OT-107.3:** the live error shape for a deliberately wrong storage type
  matches what the parser expects, so the diagnostic the user reads stays
  faithful

Keys load from `.env` in the shell wrapper; the OT skips with a clear message
when the variable is absent, and no credential appears in any test artefact,
log or fixture.
