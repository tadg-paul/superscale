## Original issue body

Child of delivery master #99. Closes findings 4, 5 and 6, recorded on #96, #89 and D-95.1 during the v2 MVP delivery.

Three separate findings share one issue because they share one cause: **a thing exists twice, or exists and is used nowhere, and only a person holding both halves in mind can tell.** Each was deferred from the child that found it because it fell outside that child's confirmed scope.

## Problem

### 1. Two functions lay out the curtain, with no rule for which

`CurtainGeometry.displayedFrame(imageSize:in:)` fits one picture into a container. `CurtainGeometry.pairedFrames(first:second:in:)` fits two, sharing a width. After #96, `ComparisonView` uses only the second, and `displayedFrame` has one caller left: RT-94.17's scroll-containment test.

They are not duplicates and neither is dead, but a reader arriving at the file has nothing telling them which to reach for, and the wrong choice reintroduces the defect #96 fixed: two differently-shaped pictures fitted independently, so one vertical divider falls at a different fraction of each.

### 2. A method with no production caller

`WorkspaceState.recordUpscale(pixelSize:fileExtension:)` allocates an upscale of what is displayed. **It has no production caller.** The application goes through `MainView.display(_:)`, which resolves an explicit reference and hands it to the view model.

#89 found and fixed a defect in it — until then it asked the graph for the *working* asset while the criterion is about the *displayed* one — and that defect was found by a test rather than by use, precisely because nothing in the application exercised the function.

A method with no production caller but a passing test is a method whose behaviour nobody has checked against the behaviour that ships.

**This was originally recorded as "two routes lead to an upscale", and that framing is wrong.** See DECISION D-103.1: `recordUpscale` **allocates a graph asset**, while `MainView.display(_:)` hands a source to `UpscaleViewModel.upscale`, which **renders a picture and records nothing** — the view model has no reference to the graph at all. They are not two paths to one outcome. One writes to the asset model; the other draws on screen.

Unifying them would mean recording every rendering as a graph asset, changing what the asset model contains and with it the lock chain, the file releases in `discardUpscales`, and the curtain's comparison guard — which #94 had to relax with the note that *"the view model performs its own upscales without recording them on the graph"*. That is a design change this delivery excludes.

### 3. Three types serve a feature the MVP removed

`GenerationCostPolicy`, `GenerationAccountState` and `GenerationAvailability` in `Sources/SuperscaleUXCore/GenerationCostPolicy.swift` are referenced by nothing but their own tests. `IMPLEMENTATION_GUIDE_v2.md` section 6 takes the cost-confirmation policy out of MVP scope along with the pricing and account clients, and #95 removed the control and the stored preference that fed `GenerationCostPolicy`.

`GenerationCostPolicy` is the subject of RT-76.5, a passing test for a closed issue's criterion. Deleting the type means marking that criterion superseded, which D-95.1 recorded as a decision rather than a tidy-up.

## Solution

**Finding 1: state the rule at the declarations, do not merge the functions.** Each documents when it is the right one and names the defect the wrong choice reintroduces. Merging them would give `pairedFrames` a degenerate single-picture mode and make the common case read worse to spare a reader one sentence.

**Finding 2: the distinction is documented at both declarations, and unifying them is left to a later delivery.** Recorded as DECISION D-103.1 with its evidence.

The original solution was to have `MainView` call `workspace.recordUpscale`. Checking the premise before implementing it showed the two are not alternatives: one allocates a graph asset, the other renders for display and touches the graph not at all.

**AC103.1 and its tests stand regardless.** They pin `recordUpscale`'s contract — that an allocation derives from the picture on the canvas — which #89 found broken and fixed, and which is worth holding whoever the caller turns out to be. The first test audit's finding, that five tests exercise a function the application does not call, is **accepted rather than closed**: closing it means the design change this delivery excludes. What mitigates it is that the reason now sits at the declaration, so the next reader meets an explanation rather than a puzzle.

The AC itself was also corrected. The first AC audit found it had written its own solution into it: *"allocated through one route"* is a fact about how the code is arranged, observable only by reading it, and unlike the other structural claims in this delivery it had an observable consequence available to state instead.

**Finding 3: `GenerationCostPolicy` is removed and AC76's cost-confirmation criterion marked superseded.** The MVP does not make that decision, `GenerationPreferences` no longer stores a threshold, and #95 removed the control. A type nothing consults is a thing a later reader has to prove is dead.

`GenerationAccountState` and `GenerationAvailability` are **retained**, because `GenerationCloudStatus.swift` still declares the pricing and account service protocols this delivery explicitly excludes from removal, and taking their state types while leaving their protocols would be a half-removal that reads worse than either whole.

### Condition enumeration

**AC103.1 implies five conditions**, and they are the five ways an allocation can still derive from the wrong picture. Three were in the first draft; the first AC audit added the last two.

- **The toggle shows the base.** The condition the losing route got wrong, and it was invisible until a test asked.
- **The candidate is displayed.** The ordinary case.
- **An upscaled asset is offered as input.** The graph's own rule, which must survive the change.
- **An upscaled asset is what is *displayed*.** With a scale selected the canvas shows a rendering, so "derive from what is on the canvas" read naively derives from the rendering — which is the very mistake this criterion exists to prevent, and a different condition from offering one explicitly.
- **A lock has moved the base.** After locking, the displayed picture is the new base. A route caching the previous one satisfies every condition above.

### The obligation on `audit-code`, revised

The first test audit required `audit-code` to confirm that `MainView` had adopted the single route, because nothing else would catch a half-done job: `display(_:)` compiles unchanged either way, so unlike #102 the compiler is no help.

**D-103.1 changed what there is to confirm.** The call site is not moving, so `audit-code`'s obligation is instead to verify that the distinction between allocating and rendering is documented at both declarations, in terms a reader can act on, and that no code change was made under this finding beyond those comments.

The underlying risk is unchanged and is now stated rather than solved: **five tests exercise a method the application does not call.** #100, one issue earlier in this delivery, is the same shape — six tests pinning `ImageLoader`, which was never broken, while the defect sat in a private view helper nothing exercised. There it was closable. Here it is not, without a design decision outside this scope.

**AC103.2 implies two conditions**, of which one is already covered.

- **A fresh preferences round trip carries no threshold.** RT-103.5.
- **A defaults dictionary left over from an older build stops carrying one.** Already covered by `test_theRetiredCostThresholdIsRemovedWhenPreferencesAreNextSaved` in `Tests/SuperscaleUXCoreTests/GenerationSettingsTests.swift`, written by #95 when it removed the preference key. Cited rather than duplicated: a second test asserting the same migration would be coverage theatre, and `TESTING.md` is explicit that high coverage with weak assertions is worthless.

**RT-103.5 constructs its store with a run-unique `UserDefaults(suiteName:)` and removes that suite in teardown.** `GenerationPreferencesStore.init(defaults:)` falls back to `.standard`, so a test taking the default would rewrite the author's own preferences on their own machine. #95's first test audit caught precisely this, in this same file.

The criterion originally also claimed "no type remains", and **no test can reach that.** A test cannot assert the absence of a type: if the type is deleted, any test naming it fails to compile; if it is not, no test notices. RT-103.4 was therefore not a weak test but not a test at all, and it is withdrawn with its identifier retired.

**The guarantee exists anyway and is stronger.** RT-76.5 names `GenerationCostPolicy` today, so deleting the type forces that test's deletion, and the suite compiles only if nothing else refers to it. `audit-code` confirms it — the same compile-time argument #102 records for its signature change and AC98.5 recorded for `private(set)`.

## Test type and location

Six regression tests. All are package tests in `Tests/SuperscaleUXCoreTests/`, machine-verifiable, guarding ongoing behaviour, invoking no build system, so all six are RT. RT-103.4's identifier is retired and not reused.

RT-76.5 in `Tests/SuperscaleUXCoreTests/CostPolicyTests.swift` is **removed with its subject**, and AC76's cost-confirmation criterion marked superseded in `docs/ACs.md` per `ISSUES.md` §"Immutability and supersession". The test's identifier is retired and not reused.

No user test. Nothing here changes what a user sees.
