## Finding: in this application's tree, only control-like elements carry a readable label or value

Two tickets have now run into the same wall from different directions, and together they say something more useful than either did alone.

| Attempt | Element | What was read back |
|---|---|---|
| #117 | The `canvas` ZStack with `accessibilityElement(children: .contain)` | value `""` |
| #117 | The outer `workspaceCanvas` container | value `""` |
| #117 | A `Color.clear` declared an element of its own | value `""` |
| #108 | The info panel's `Text` line carrying `accessibilityIdentifier("infoScale")` | label `""` |

Against which: `selectScale`'s own failure output printed real values off the scale **buttons** — *"2x enabled 'in effect'; 4x enabled 'inactive'"*. Buttons carry both label and value perfectly well.

**So the rule this codebase has been circling is narrower than it has been written.** Guide section 3.18 records that a container declaring `children: .contain` reports its label but not reliably its value, and 3.11 records that shapes never enter the tree at all. The evidence above extends both: a plain `Text`, and a shape declared an element, do not reliably carry text state either. What does is a control.

That matters well beyond these two tickets. Any criterion of the form "surface X reports state Y as a value" is only testable, and only reaches VoiceOver, if X is control-like. Both AC117.1 and RT-108.6 were written without that constraint being known, and both audits passed them.

**This is not diagnosed to a mechanism.** It is four measurements and a contrast, not an explanation, and the remedy that follows from it — attach state to a control, or give the element a control-like role — has not been tried. I have stopped at three remediation cycles per the stalled-work rule rather than continuing to guess.

**Consequences recorded rather than worked around:**

- **#117** is blocked on AC117.1, whose "as a value" clause may be unimplementable on the canvas as written. The options are on that ticket.
- **RT-108.6** on #108 cannot be verified as written. The identifier is signed off, so it stays with its reason rather than being deleted.
- **#111 and #112** remain behind #117.
- The finding itself is worth a guide entry in section 3.9's family, alongside the four accessibility mechanisms already recorded there. It is the fifth, and it is the first that constrains what a criterion can ask for.
