## The regression

**A generated session loses its link to its upscale once the Generate view has been rebuilt.**

`test_fixtureGenerationUpscalesAndAppearsInHistory` fails at `SuperscaleAppUITests.swift:1022`. The comment above the step that breaks says what it is for:

```swift
// Rebuilding Generate after a mode change must not lose the history linkage.
app.staticTexts["modeSettings"].click()
...
app.staticTexts["modeGenerate"].click()
sendToUpscale.click()
```

A user generates an image, switches to Settings and back, sends the result to Upscale, and the session never appears under "Upscaled" in History. The upscale is written, and it is attributed to nothing.

**Cause.** `GenerateView.lastSessionID` is `@State` on a view that SwiftUI destroys and rebuilds when the mode changes, so it resets to nil. What survived that rebuild was `MainView.latestGenerationSessionID`, fed by `GenerateView.onSessionRecorded` — both of which #81 deleted.

They were deleted on my own code audit's recommendation. Having removed the ambient-attribution fallback that was reading `latestGenerationSessionID`, the audit read the remaining state as dead and said so. It was not dead: it was the only thing holding the session identifier across a view lifetime, and the test proving that is in a target `make test` never runs.

**Violated:** `AC77.2 (legacy - see #77)` — *"Given a generated image is locally upscaled, the app associates the upscaled asset with the originating generation session."*

Cited as legacy rather than migrated: `docs/ACs.md` begins at the 2026-08-21 cutover, and close-time migration under this delivery covers a child's own criteria, not another issue's.

## The superseded test

// Re-enter custom mode and type width again

## Solution

### The session identifier travels with the output it describes

`GenerationCoordinator` is a `@StateObject` on `MainView`, so it survives a Generate rebuild. It already holds the generated output; it should hold the identifier of the session recorded for that output, and hand both out together:

```swift
public private(set) var recordedSessionID: UUID?

public func recordSession(_ id: UUID) { recordedSessionID = id }

public var upscaleSource: GUIUpscaleSource? {
    output.map { GUIUpscaleSource(origin: .generatedFile, url: $0.localURL, sessionID: recordedSessionID) }
}
```

**The identifier is cleared whenever the output changes**, not only when a new generation starts. Clearing at each entry point is the same shape as the fault being fixed — an identifier outliving the thing it describes, because somewhere forgot to clear it. Binding the clearing to the output makes "the identifier belongs to this output" true by construction: `phase` is the single place the output changes, so the identifier is cleared there and set only by `recordSession`.

**This is not the fallback #81 removed.** That fallback substituted *whichever session was recorded most recently* for an input that had none — attribution by timing, and wrong whenever the input came from somewhere else. This binds the identifier to the specific output it was recorded for: the coordinator's output and its session are one generation. An unrelated file dropped in between still carries no session, because it is not the coordinator's output.

`GenerateView` calls `coordinator.recordSession(record.id)` where it currently sets `lastSessionID`, and reads the identifier back from the coordinator rather than from its own state.

### RT-148 is rewritten against the toggle group

Keeping its identifier. What it exists to check — that a custom width entered after an image has loaded auto-populates the height from the aspect ratio — is unchanged and still worth checking. Only the way it re-enters custom mode changes: choosing `scaleCustom` when custom is already active now clears it, so the test either does not need the second click or must choose a preset first.

## Test plan

Regression tests added under `AC77.2`'s coverage, proving the violated criterion holds:

- ⏳ RT-86.1: the recorded identifier survives independently of any view, so it is still available after the view that recorded it is gone
- ⏳ RT-86.2: an upscale input built from a file carries no session identifier, whatever the coordinator has recorded
- ⏳ RT-86.3: a new generation clears the identifier of the session recorded for the previous one
- ⏳ RT-86.4: the coordinator's upscale input carries the identifier of the session recorded for its output
- ⏳ RT-86.5: the recorded identifier is cleared whenever the coordinator's output changes or is removed
- ⏳ RT-86.6: when recording a session fails, the coordinator's upscale input carries no session identifier

**The rebuild scenario is not re-created as a package test.** A package test cannot rebuild a SwiftUI view — that is a lifecycle event in the application target — and an unrelated imported file never reaches `GenerationCoordinator` at all, since it enters through `MainView.sendToUpscale`, which is also where a re-added fallback would live.

The scenario is held by `test_fixtureGenerationUpscalesAndAppearsInHistory` in `SuperscaleAppUITests`, which fails today and is the regression this issue fixes. Its transition from failing to passing is this issue's primary evidence, and it is why `make test-gui` becomes standing verification. Six green package tests would not demonstrate a fix they cannot exercise.

What the package tests hold is where the identifier lives and what it is bound to. RT-86.1 states the fix itself — the coordinator outlives the view, so the identifier does. RT-86.2 keeps the line against a re-added fallback at the level it can: an imported source carries nothing, whatever the coordinator has recorded. It is the same condition RT-81.14 holds at the graph level. RT-86.3 and RT-86.4 pin the binding to the output rather than to the coordinator's lifetime.

RT-86.5 exists because the binding is only as good as the clearing, and clearing at each entry point is how the original fault happened. The coordinator survives a Generate rebuild — which is the point — but it also survives a user reopening a previous session from History, so the identifier must follow the output rather than the coordinator's lifetime.

RT-86.6 pins the failure case. `GenerateView` records the session inside a `do/catch` and reports a failure through `localError` (`GenerateView.swift:468`); when that happens there is no identifier, the generated image is still on screen, and Send to Upscale still works. Attaching to nothing is correct — but it is observationally identical to the bug being fixed, and without this test a later change could "fix" the missing linkage by inventing one.

All six are regression tests in `Tests/SuperscaleUXCoreTests/GenerationCoordinatorTests.swift`, needing no network: the coordinator's session identifier is a value.

## The fix

The identifier moved to `GenerationCoordinator`, a `@StateObject` on the root view that outlives the rebuild, and is cleared in `phase`'s `didSet`.

Clearing there rather than at each entry point is deliberate: the fault was an identifier outliving what it described because a call site forgot, and a fix that reintroduced per-site clearing would be the same shape. Any change of phase changes the output, and a new output has no session recorded for it yet.

This binds the identifier to the coordinator's own output. An imported file is not that output and carries nothing, which RT-86.2 holds at the coordinator and RT-81.14 already holds at the graph.
