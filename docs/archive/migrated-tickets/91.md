## Original issue body

Child of delivery master #79. Reported from use.

## Problem

**A 2000-pixel-wide image upscaled 4× crashes the application.**

`Tiler.stitch` holds roughly 36 bytes per output pixel, all resident: a colour accumulator and a weight accumulator across the whole output, plus the output itself. At 8000 × 8000 that is about 2.3 GB before anything else in the process, and the application dies.

**The documented caps do not prevent it.** `IMPLEMENTATION_GUIDE_v2.md` warns above 4096 pixels on the long edge and refuses above 8192. A 2000-pixel image at 4× produces 8000, which sits between the two: permitted, and fatal.

The cap is expressed in the wrong unit. Memory scales with **area**, and a long-edge limit says nothing about it. 8192 × 8192 is 67 megapixels and 2.4 GB; 8192 × 1000 is 8 megapixels and 300 MB. One of those is fine and the other is not, and the current rule treats them identically.

## Violated criteria

**Corrected 2026-08-25. AC83.7 did not exist.** The first draft cited it as a legacy criterion on #83. `#83` carries AC83.1 to AC83.6 and no more, and `docs/ACs.md` holds no criterion mentioning the caps, 4096, 8192 or a long edge. The caps have only ever been prose in `IMPLEMENTATION_GUIDE_v2.md` 2.5 and 3.8 and a residual-risk note on #79: *"the stitching buffer allocates roughly 36 bytes per output pixel, all resident, which bounds supported output resolution."* The bound was acknowledged and never specified.

So this is a **backfill**, by the second path in `ISSUES.md` §"Bug-fix issues reference existing ACs": the underlying feature has a criterion set and the defect exposes a gap in it. **AC83.7 is added to `docs/ACs.md`** against the #83 family, which owns the kit constraint the cap exists to respect, with provenance recording that it was backfilled here. The same was done in this delivery for AC73.6, backfilled by #88.

> **AC83.7** — An upscale's output never exceeds the supported area, whatever asked for it: a scale is reduced to the largest that fits, a custom target is reduced proportionally, and the reduction is reported while the scale selection continues to show what was asked for. A picture that cannot fit at any scale is left as it is, with the reason given. The minimum long edge required for filtering is unaffected by that ceiling.

**Reworded at the first AC audit**, which found three faults in the first attempt. "Produces" is on the forbidden list. More seriously, the rule was written against the *scale*, and AC82.7's control offers a custom target as well as 2x, 4x and 8x: with a typed width and height there is no scale to reduce, so a user could type 10000 by 10000 and reach this same crash through a different door. And a picture already above the ceiling at 1x — 8000 by 8000 is 64 megapixels before anything is done to it — has no scale to fall back to at all. The rule now binds the **output**, whatever produced it.

The criterion is written here and migrated on closure. It is not a new AC table: this issue has none, and the row above joins #83's set.

## Solution

**Bound the output by pixel count rather than by long edge.** A ceiling of 32 megapixels is about 1.2 GB of accumulators, which leaves room for the process, the model and the window on the machines the application targets.

**Reduce the scale rather than refusing.** When the chosen scale would exceed the ceiling, the largest scale that fits is used and the user is told what happened and why. Refusing an upscale the user asked for, when a smaller one is available and useful, is a worse answer than delivering it — and a crash is worse than either.

This was offered as a recommendation rather than a decision, because "reduce silently", "reduce and say so", and "refuse with an explanation" are three different products.

**Ruled by the author, 2026-08-25** (master #79, ledger entry L32):

- **The ceiling becomes an area measurement**, as proposed. Reduce and tell.
- **The 1024-pixel minimum long edge stays an edge measurement and is unchanged**, because the AI model requires it. A floor expressed as an edge and a ceiling expressed as an area are not in conflict: they answer different questions. The floor asks whether a picture is big enough for the provider to work with; the ceiling asks whether the output fits in memory. Nothing about the second changes the first, and slice 7's work on the floor is untouched by this.

**Why 32 megapixels.** At roughly 36 bytes per output pixel the accumulators come to about 1.2 GB, which leaves the process, the Core ML model and the window their room on an 8 GB machine. The reported case, a 2000-pixel-wide picture at 4x, produces 64 megapixels and about 2.3 GB, which is what kills it. The figure is held in one named constant and is revisable, exactly as the minimum long edge is.

**What the user sees.** The largest scale that fits, and a message saying so, in the same unobtrusive register as the minimum-resolution message described in guide 2.5. Refusing an upscale when a smaller one is available and useful is a worse answer than delivering it, and a crash is worse than either.

## Regression tests

- ⏳ RT-91.1: an image whose output at the chosen scale would exceed the ceiling upscales at the largest scale that fits
- ⏳ RT-91.2: the decision reports the reduction as a value — what was asked for, what is used, and that it was reduced — and the scale selection still holds what was asked for
- ⏳ RT-91.3: an image whose output fits is upscaled at the chosen scale, unreduced
- ⏳ RT-91.4: the ceiling is expressed in output pixels, so a wide short image and a tall narrow one of the same area are treated alike
- ⏳ RT-91.5: the reported case, a 2000-pixel-wide image at 4×, yields a sizing that fits within the ceiling
- ⏳ RT-91.6: an image below the minimum long edge is still raised to it, however the ceiling is set, so the floor and the ceiling do not interfere
- ⏳ RT-91.7: an image whose output cannot fit at any scale is left unchanged, with the reason given rather than silently
- ⏳ RT-91.8: a custom target above the ceiling is reduced proportionally, preserving the requested aspect
- ⏳ RT-91.9: the ceiling binds the output actually produced, so a non-stretch custom target fitted to the source's aspect is judged on the fitted result rather than on what was typed

**A reduction does not rewrite the selection.** Raised by the second AC audit. **AC82.8** holds that
a scale selection persists until the user chooses a scale, and that importing an image, changing the
model and editing the custom dimensions all leave it alone. A reduction that moved the control from
8x to 4x would have the application change the user's choice on their behalf, which is exactly what
that criterion exists to prevent. So the control keeps showing what was asked for, the output is
what fits, and the message is what reconciles the two.

**Condition enumeration.** AC83.7 carries five conditions: the ceiling holds; a scale is reduced to
the largest that fits; a custom target is reduced proportionally; a picture that fits at no scale is
left alone with the reason given; and the minimum long edge is untouched by any of it. RT-91.1 and
RT-91.5 cover the first two, RT-91.8 and RT-91.9 the third, RT-91.7 the fourth, RT-91.6 the fifth,
with RT-91.2 on the reporting, RT-91.3 on the unreduced case and RT-91.4 on the unit.

- ⏳ RT-91.10: a coordinator asked to upscale a source above the ceiling requests an output within the ceiling from its processor

**One user test is allocated:**

> ⏳ UT-91.1: the message explaining a reduced upscale is clear and unobtrusive

Added by the second test audit, which overturned the first pass's conclusion that none was needed.
Every condition of the ceiling is machine-checkable, which is true and is not the whole question:
this produces a message the author reads on every large upscale, and its register is specified only
by analogy to the minimum-resolution message of guide 2.5. Both user tests that have failed in this
delivery failed on presentation rather than on function — the progress overlay's blur and the
curtain's divider — and both were things the author saw that no test did. It transfers to #79's
roll-up when this issue closes.

**Type justification.** All ten are regression tests. Nine exercise the sizing decision, which is a
function of input dimensions and a requested size. RT-91.5 is the reported case, and it runs against
that decision rather than by performing a 2.3 GB allocation, because a test that reproduces a crash
by crashing is not a test — so it is named for the sizing it asserts rather than for a completion it
does not observe.

**RT-91.10 is the wiring, and it exists because the arithmetic is not the risk.** Nine tests over a
function would all stay green against an upscale path that computed its own dimensions and never
called it, and the crash would remain. That is the same fault #90 is repairing in the curtain:
defensible arithmetic behind a caller feeding it the wrong numbers, unnoticed for five months. It
runs through `GUIUpscaleProcessing` with a stub processor, so it costs no Core ML and asserts what
the processor was *asked* for.

**The decision returns the reduction rather than announcing it.** What is used, what was asked for,
and whether it was reduced are values the package owns, so the regression pack can assert them; the
message the user reads is a rendering of those values. Without this the reporting would live on
`UpscaleViewModel`, in the app target, which `make test` does not build, and RT-91.2 would have no
reachable subject.

**Location.** `Tests/SuperscaleUXCoreTests/UpscaleCeilingTests.swift`. Not
`Tests/SuperscaleTests/`, which holds the kit's own tests and no sizing tests: the ceiling is
application policy about what a user may ask for, and `SuperscaleKit` is deliberately free of
application knowledge — its job is to allocate what it is told to.

The ceiling is **32 megapixels of output area**, one named constant, roughly 1.2 GB of accumulators at `Tiler.stitch`'s 36 bytes per output pixel. A preset is reduced to the largest that fits; a custom target is reduced proportionally so the requested shape survives; a picture that fits at no scale is refused in plain language rather than allocated and crashed on. The decision is returned as a value, so what the user is told is asserted in the regression pack rather than living in the app target where `make test` cannot see it.

**The scale selection is untouched by a reduction**, per AC82.8: it changes only when the user changes it. The control keeps showing what was asked for and the message reconciles it with what ran.

**The 1024-pixel minimum long edge is unaffected**, per the author's ruling of 2026-08-25. A floor expressed as an edge and a ceiling expressed as an area answer different questions: whether a picture is large enough for the provider to work with, and whether its output fits in memory.
