## Original issue body

Child of delivery master #79. Three reports from use, 2026-08-25, each diagnosed from source before this issue was written.

## Problem

**Applying a filter gives no feedback, then gives the wrong comparison, and scrolling the filter list moves the picture.**

The author, in order:

> *"i type in an api key, run a filter, hit apply, it seems to the user like nothing is happening. no progress spinner"*
>
> *"eventually something does come back, the curtain is there but the before/after image is the same"*
>
> *"when i scroll the filter categories the image scrolls with it - very odd"*

### The canvas only watches the upscale

`MainView.swift:101` draws the progress indicator when `viewModel.isProcessing`, which is the *local upscale* view model. A filter runs through `generationCoordinator`, whose phase is `.generating`. The application knows: `MainView.swift:415` colours the status dot from `generationCoordinator.phase == .generating`, and `:58` passes `isApplying` into the filter panel. The canvas is the one surface that never asks, and it is the surface the user is looking at while a paid call runs for tens of seconds.

### The curtain compares the filter result against its own upscale

`adoptFilterResult` at `MainView.swift:199` ends by calling `upscale(source, arrival: .filterResult)`. That reaches `processImage`, where the filter's output is a URL not seen before, so `isNewImage` is true and `originalImage` is replaced by **the filter's output**. `MainView.swift:122` then builds `ComparisonView(original: viewModel.originalImage, upscaled: derivedImage)`.

So after applying a filter the curtain compares the filtered picture against the upscale *of that same filtered picture*. The two sides differ in resolution and in nothing else, which is exactly "the before/after image is the same".

**AC90.6 already says what it should compare:** whatever is displayed against the image it derives from. The base is the user's own picture, held by the asset graph at `workspace.graph.base`; the candidate is the filter's output. That is the comparison worth having, because it answers the only question the user has after paying for a filter: did it do anything.

### The scroll monitor catches every scroll in the application

`ComparisonView.swift:294` installs `NSEvent.addLocalMonitorForEvents(matching: .scrollWheel)` and pans the image by the event's deltas. It never checks where the pointer is. Any scroll anywhere in the window reaches it, including over the filter category strip, which is itself a horizontal `ScrollView` at `FilterPanel.swift:115`.

### Condition enumeration

- **AC94.1** implies four conditions: each kind of work shows progress, the two in sequence do not leave a gap, and idle shows none. The third is the one a naive fix misses: a filter completing and its upscale starting are two separate operations, and the canvas going quiet between them reads as "finished" when it is not.
- **AC94.2** implies two: the kinds are distinguishable, and a provider call does not borrow the upscale's vocabulary. `UpscaleProgressReader` maps kit phases to text; a cloud call has no tiles and must not claim to.
- **AC94.3** implies four: the filtered case, the plain upscale case, the case where both have happened, and that the two sides are never one asset. The third is the reported defect and the fourth is what stops a fix that simply hides the curtain.
- **AC94.4** implies five: elsewhere does nothing, over the picture works, nothing at all when there is no comparison to pan, the belonging decision holds at any window size, and the pan is observable.

  **The last was raised by the test audit and is the reason the other four are testable at all.** `offset` is `@State` at `ComparisonView.swift:20` and nothing exposes it, so every one of RT-94.11 to RT-94.13 turns on whether the picture moved while nothing could tell. This is the fourth time in this delivery a criterion has pointed at state the accessibility tree cannot see — `refreshAccountButton` in #88, the curtain divider in #90, the active scale in #93 — and each time the test would have passed against the broken implementation.

### What this does to AC90.6

**AC94.3 supersedes AC90.6's comparison rule.** AC90.6, migrated by slice 9c, reads: *"The curtain
compares whatever is displayed against the image it derives from, and is absent when there is no
derivation."* After a filter and an upscale, the displayed picture is the upscaled filter result and
the image it *derives from* is the filter result — so AC90.6 specifies exactly the comparison
reported here as useless. The criterion is the defect, not merely the code that implements it.

The correction is one word of principle: the curtain compares against the **base the working image
descends from**, which is the asset graph's lineage, rather than against its immediate parent. AC90.6's
second clause, that the curtain is absent when there is no derivation, is unchanged and so are
RT-90.15, RT-90.16 and RT-90.17. **RT-90.24**, which asserts the curtain's behaviour while an earlier
locked iteration is being viewed, is re-read against the new rule by RT-94.16 rather than assumed to
carry over: an earlier iteration is itself a base, and what it compares against is a question the old
wording answered by accident.

Raised by `audit-acs` on this issue. Without it a correct implementation would fail a criterion
already in `docs/ACs.md`.

## Solution

**The canvas asks about all work, not one kind.** The indicator's condition becomes the disjunction of the local run and the provider call, and the message follows from whichever is under way. Both facts already reach `MainView`; neither reaches the canvas.

**The curtain reads the graph, not the view model.** `workspace.graph.base` is the picture the user brought in or last locked, and it survives a filter — that is what the asset graph is for, and slice 9b wired it. `MainView` currently reads `viewModel.originalImage`, which `processImage` overwrites with whatever it was last asked to upscale. The comparison takes the base from the graph and the working image from the display decision `CanvasContent` already makes.

**The scroll monitor learns where the pointer is**, or stops being a monitor. A local `NSEvent` monitor is a global interception dressed as a view behaviour: it fires for scrolls over the toolbar, the filter panel, the lock chain and the status bar. The narrow fix is to test the event's location against the comparison view's frame. The better one is to drop the monitor for SwiftUI's own gesture handling, which is scoped to the view by construction and cannot leak. This issue takes the narrow fix, because replacing the pan and zoom model is a change to `ComparisonView`'s interaction design and belongs with the aspect-ratio work rather than with a scroll bug.

## Test type and location

Eighteen regression tests.

**Whether a scroll belongs to the picture is a predicate**, taking the event's location and the
picture's displayed frame, and it lives in `SuperscaleUXCore` beside `CurtainGeometry`, which already
computes that frame. RT-94.17 tests it in the package, where a location is two numbers. Only RT-94.11
and RT-94.12 then need the window, to prove the view consults it.

**The comparison reports its pan as an accessibility value**, which is what makes RT-94.11 to
RT-94.13 assertable at all and is the same move #93 made for the scale readout. A pan expressed only
as a rendered offset reaches nobody: not VoiceOver, and not a test asking whether the picture moved.

**AC94.3's are package tests.** Which two images the curtain holds is a decision `CanvasContent` already owns, and RT-94.7 to RT-94.10 extend `CanvasContentTests` with a base, a candidate and a rendering of the candidate. No window, no provider, no Core ML.

**AC94.1 and AC94.2's are package tests over the progress state**, once the canvas's condition is a value rather than an expression buried in a `ViewBuilder`. The disjunction and the message selection move to a function beside `CanvasContent`, which is the same move made for the curtain's geometry and the toolbar's readout, and for the same reason: the arithmetic was never the risk.

**AC94.4's are GUI tests**, in `SuperscaleAppUITests`. Where a scroll lands and what it moves cannot be observed below the window, and the defect is precisely that an event reached a view it was not over.

**One user test:**

> ⏳ UT-94.1: applying a filter feels responsive from the moment Apply is pressed

Whether the feedback is timely and legible is judgement. This issue exists because a paid call ran for tens of seconds with nothing on screen, and the fix is only as good as it feels.
