## Original issue body

Child of delivery master #120 (bring the build onto the design of record).

## Problem statement

**Requested by the author, user-test round of 2026-08-27:**

> *"let's have all upscale buttons switched *OFF* on launch by default. The upscale operations take time, it should be a deliberate act by the user to switch them on/off"*

And, as the round's first observation:

> *"On launch, it appears like both 2x and 4x are pressed in"*

> *"Drop in image 1471x1661 res. The info bar at the top says 'scaled 2x, scale 4x requested'. it then has a spinner on top that appears to be trying to upscale it to 5884x res."*

> *"When i un-toggle both 2x and 4x, then re toggle 4x, it appears like 2x and 4x are pressed in, says the same info on top 'scale 2x in effect, 4x requested' then upscales to 5884x6644 again"*

## Two things here, and only one is the requested change

**The change.** Guide section 2.5 is explicit that the current behaviour is deliberate:

> *"In v1, dropping an image **upscales it immediately** at whatever scale is selected, and changing the scale or model re-runs it. That immediacy is the v1 experience and is kept."*

The author is now overriding that. The design's own argument for the off switch --- *"a filter-first user does not want that upscale at all"* --- applies equally to the default, and the round shows the cost being paid on the very first action of every session. Guide 2.5 must be amended, not worked around.

**The defect.** Two scale controls appearing pressed at once is separate and is not fixed by changing the default. It recurs after the author explicitly clears both and selects one, so it is not a launch-state artefact. The readout *"scale 2x in effect, 4x requested"* alongside two apparently-pressed buttons suggests the controls render from a different value than the readout does.

`audit-acs` must keep these apart. Changing the default hides the first observation without addressing the second, and a delivery that shipped only the change would have a user report the same thing again from a different starting point.

## Violated AC

- **AC82.8** in [docs/ACs.md](../blob/master/docs/ACs.md): the scale selection changes only when the user changes it. Two controls reading as selected when the user selected one is a candidate violation, though the fault may be in rendering rather than in the selection.
- **AC93.1**: the controls report the state. **UT-93.1** failed in this round and is re-offered on closure --- it is the criterion covering exactly the "which scale is in effect and which was asked for" question the author's readout observation raises.
- The launch default itself has no criterion. Expect a backfill onto the #82 family, and expect guide 2.5 to be amended with the reasoning recorded in its changelog.

## Interaction with the wider round

Overlaps **#125** (an oversized picture leaves one scale depressed and disabled). Both concern what the scale controls display versus what is selected. #125 owns the disabled-and-selected state on oversized pictures; this child owns the launch default and the two-controls-pressed rendering. The audits must write the split into both tickets so neither silently takes the other's half.

## Debugging and fix procedure

1. **Reproduce the two-pressed state after an explicit clear and reselect**, which is the author's second observation and rules out a launch artefact.
2. **Establish what each control renders from**, and whether it is the same value `ScaleReadout` uses. #100 (one pixel measurement) and #108 (the info panel's own scale arithmetic) both found a second private derivation of sizing truth; this has the same shape and the same remedy.
3. **Amend guide 2.5** for the default before implementing it, so the code follows the design rather than the design following the code.
4. **The off state already exists.** Guide 2.5 introduced it and the toggle-group clearing behaviour is built; this is a change to the initial value, not new machinery.
5. Confirm the degraded-state table in guide 2.8 still holds: local upscaling remains fully available with no key, and turning the default off must not read as unavailability.

## Test plan

- RT-131.1: on launch, no scale is selected
- RT-131.2: a picture brought in with no scale selected becomes the base without an upscale
- RT-131.3: selecting a scale after import runs the upscale
- RT-131.4: exactly one scale control reads as selected at any time
- RT-131.5: after clearing all scales and selecting one, only that one reads as selected
- RT-131.6: the scale readout and the control states derive from the same value
- UT-93.1 re-offered: upscale a picture large enough to be reduced and judge that the controls say which scale is in effect and which was asked for

### What this delivers, in plain language

A user launches the application and drops in a picture. Today it immediately spends several seconds upscaling something they may be about to filter and discard. After this issue, nothing upscales until they ask for it. Separately, the scale controls stop showing two scales as pressed when the user has selected one.

### The mechanism of the second half, established from code

`ScalePicker.tint(for:)`:

```swift
case .inEffect: return .accentColor
case .requestedNotInEffect: return .secondary
case .inactive: return nil
```

Both of the first two return a tint, and a tinted `.bordered` button reads as pressed. So when 8x is requested on a picture the area ceiling reduces to 4x, **4x is tinted as in-effect and 8x is tinted as requested** — and the author sees two pressed buttons beside a readout saying *"scale 2x in effect, 4x requested"*.

**This is deliberate design being read the wrong way, not a bug in the selection.** The state model is correct: AC82.8 requires the control to keep showing what was asked for, and the readout reconciles it. What fails is that "requested but running smaller" and "in effect" are rendered as the same visual category.

### F1 (blocker) — the ticket bundles a change and a defect, and the change hides the defect

Making the launch default `.off` removes the author's *first* observation (both pressed on launch) without touching the *cause*, which recurs the moment a ceiling reduction happens. The author reported it recurring after explicitly clearing and reselecting.

**Remediation.** Two criteria, two sets of tests, and the defect fixed on its own terms rather than made harder to reach.

### F2 (blocker) — the visual treatment for "requested but not in effect" is a product decision

The state must be distinguishable from "in effect" without reading as selected. That is a visual design choice with several defensible answers — an outline rather than a fill, a badge, a different weight — and `MAIN.md` §1 forbids me making it.

**Remediation.** **Ask the author.** Until then, implement only the half that is settled. Recorded here rather than guessed; the readout wording and the accessibility value already carry the state correctly, so nothing is untestable in the meantime.
