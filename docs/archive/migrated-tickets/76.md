## Original issue body

## Problem

Superscale UX v2 should make cloud-generation cost visible enough to avoid surprise spend. The app needs FAL pricing and account visibility modelled on `../pix`, with separate account/admin credentials and non-fatal handling when account data is unavailable.

### AC76.3 is superseded, not merely unimplemented

Recorded here rather than deleted, so the history stays legible.

Cost confirmation is out of scope for the v2 MVP. It was withdrawn in two steps by two different
issues, and neither on its own would have been enough:

- **#95** removed the Settings control that set the threshold, and the preference key behind it.
- **#103** removed `GenerationCostPolicy` and `GenerationCostDecision`, the types that consumed it,
  and renamed the file to match what it still holds. RT-76.5 exercised those types directly and went
  with them; RT-76.6 exercised the control and went with #95.

**AC103.2** in `docs/ACs.md` now states the criterion that replaced it: *no cost-confirmation
threshold is stored, and the policy that consumed it is absent from the application.* That is the
opposite guarantee to this one, deliberately, and it is the one the application currently meets.

A stored value nothing reads is a thing a later reader has to prove is dead, and a type with no
storage behind it still invites a caller. If pricing returns, this criterion is where its
requirements were last written down and is the right place to start from --- which is why it stays
here, struck through, rather than being deleted.
- AC76.4 covers non-fatal account/pricing failure and human wording review.

## Test Enumeration And Type Justification

`RT-76.1` through `RT-76.7` are regression tests because cost, account, and confirmation behaviour are persistent product-safety behaviours.

`UT-76.1` is a user test because warning clarity requires human judgement.

## Solution Design

### Scope

- Port FAL pricing and account behaviours from `../pix` into `FalGenerationKit` and `SuperscaleUXCore`.
- Use the generation key for pricing where required by FAL.
- Use the separate account/admin key for account balance, usage, and billing events.
- Use `0.05` as the initial cost confirmation threshold.
- Keep account failures non-fatal for generation.

### Patterns to follow

- Use fixture-backed HTTP tests for pricing and account endpoints.
- Cache pricing data for the session where appropriate.
- Keep cost policy in testable app logic, not ad hoc view conditionals.
- Redact secrets from diagnostics.

### Anti-patterns to avoid

- Do not use the generation key as a fallback account/admin key.
- Do not block valid generation solely because account visibility failed.
- Do not hard-code live prices into tests.
- Avoid CODING.md violations: silent network error suppression, hardcoded credentials, and implementation-detail tests.
- Avoid CODE/SWIFT.md violations: empty `catch`, `try!`, force unwraps, and UI state updates from background tasks.

### Test locations

- `Tests/FalGenerationKitTests/` for pricing and account HTTP fixtures.
- `Tests/SuperscaleUXCoreTests/` for cost policy and coordinator states.
- GUI/app test target for confirmation and warning states.

## Dependencies

- Depends on FAL core and settings/secrets.
- Can run after basic Generate mode exists; it does not block fixture-backed Generate UX.
