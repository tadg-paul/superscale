## Original issue body

Child of delivery master #120 (bring the build onto the design of record).

## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"There is no way to load a new image except by quitting the app and re-launching it"*

The author demonstrated this repeatedly through the round --- *"I restart the app, drop a large image of 3423x2698 onto the canvas"* --- and it is why several observations in the round each begin with a relaunch.

## This is a defect against a written specification

Guide section 2.2:

> *"Accepts PNG, JPEG, TIFF and HEIC via drag and drop, the open panel, or paste. One image at a time; this is not a batch tool."*

*"One image at a time"* bounds concurrency, not the number of images a session may contain. Nothing in the design says a session holds exactly one import for its lifetime, and guide 2.6 assumes otherwise by pointing at `File > Open Recent` as the way back to earlier work.

## Likely cause, stated as a hypothesis

`MainView` guards `adoptImportedImage` against re-adopting the same picture. That guard was widened by #111 (the hidden lock chain) to include what the view last asked to display, so that opening a locked iteration was not mistaken for an import:

    guard let url,
          url != generationCoordinator.output?.localURL,
          url != currentlyDisplayedFileURL,
          url != lastDisplayedURL

A guard written to exclude *internal* displays may be excluding *user* imports as well. That is a hypothesis from reading, not a diagnosis --- confirm it by reproduction before changing anything.

## Interaction with the wider round

This is downstream of **#121** (current-image state has two owners). Distinguishing "the user brought in a new picture" from "the application is showing a different picture" is exactly the question one owner of current state answers. Attempting it before #121 lands means widening the same guard a third time.

There is also a question the audits must settle rather than assume: **what happens to the existing lock chain when a new picture arrives.** Guide 3.2 makes the chain the lineage of the current base, and a new import starts a new chain with role `source`. Whether the previous chain is discarded, retained alongside, or the user is asked, is not specified. It affects whether unsaved work can be lost, so it is not a routine implementation choice.

## Violated AC

- The #82 or #87 family criteria covering import. `audit-acs` must locate the criterion that specifies bringing in a picture and determine whether it covers doing so more than once; if it does not, backfill rather than stretch.

## Debugging and fix procedure

1. **Reproduce all three import routes** --- drag and drop, the open panel, and paste --- with a picture already loaded. They may not all fail, and if only some do, the guard hypothesis is wrong or incomplete.
2. **Establish whether the picture is rejected or accepted-and-not-shown.** Those are different faults with different fixes, and the interface gives the user the same nothing in both cases.
3. **Do not simply remove the guard.** It exists because #111 found that viewing a locked iteration was being treated as an import, which broke the lock chain. Removing it reinstates that defect. The distinction wanted is by *origin*, not by URL.
4. **Settle the lock-chain question with the author** before implementing, if the audits cannot resolve it from the design. Silently discarding a chain of paid results would be worse than the defect.
5. Whatever the answer, an import must never leave the interface silent: guide 2.8's posture throughout is that the application reports what it has done.

## Test plan

- RT-130.1: a second picture brought in by drag and drop becomes the base
- RT-130.2: a second picture brought in through the open panel becomes the base
- RT-130.3: a second picture brought in by paste becomes the base
- RT-130.4: displaying a locked iteration is still not treated as an import
- RT-130.5: a filter result arriving from the provider is still not treated as an import
- RT-130.6: the behaviour decided for the existing lock chain is what occurs
- UT-130.1: work on one picture, bring in a second, and judge that the transition is clear and nothing is lost unexpectedly

### The cause, established from source, and it is not the guard

The ticket's hypothesis was that `adoptImportedImage`'s guard — widened by #111 — was excluding user imports along with internal displays. **It is not.** The guard compares against the coordinator's output, the workspace's displayed asset and the view's last display request; a genuinely new file matches none of them.

The real cause is simpler and worse: **there is no route in.**

- `fileChooser`, the open-panel button, lives on `DropTargetView`, which `canvasContent` renders **only when there is no image**. Once a picture is loaded it is gone.
- The `.commands` block has `Save As…` and an `Open Recent` submenu. **There is no plain Open command.**
- That leaves drag and drop from Finder onto the canvas, which is the one route that still works — and the only one XCUITest cannot drive.

This is already recorded, in the note under **AC89.8**: *"with a picture loaded the application offers no route to open another ... leaving only drag and drop from Finder, which XCUITest cannot drive. That guide section 2.2 promises the open panel as one of three import routes, and the application withdraws it once an image is loaded, is recorded as a separate product question on master #114."* This ticket is that question, answered.

### Criterion

Guide **2.2**: *"Accepts PNG, JPEG, TIFF and HEIC via drag and drop, the open panel, or paste."* Three routes, unconditionally. Two of them disappear once a picture is loaded.

**AC82.1** or its family covers import. `audit-acs` finds the criterion covers *bringing a picture in*, not *bringing a second one in*, so this is path 1: cite it and add regression tests. **No backfill** — "the open panel is available" is not a different system state from "the open panel is one of the import routes".

### F1 (finding) — the lock chain's fate on a new import is not a routine choice

Guide 3.2 makes the chain the lineage of the current base, and AC89.8 says an import starts a new chain and **releases the previous chain's files**. So bringing in a second picture discards a session's worth of paid filter results.

That is specified, so it is not a defect. But it becomes reachable for the first time here: today nobody can trigger it without restarting, which discards the work anyway.

**Recommendation: implement as specified, and record the exposure.** AC89.8 is deliberate and RT-89.26 stands over it. Adding a confirmation would be inventing an interaction the author did not ask for, and the author's own round asks separately for save-on-quit — which is the same concern and is explicitly out of this delivery's scope. Recorded so the connection is visible rather than lost.

### F2 (finding) — RT-130.1's drag-and-drop route cannot be driven

XCUITest cannot originate a Finder drag. RT-111.4 was retired for exactly this and the reason is on AC89.8.

**Recommendation.** RT-130.1 is **retired before sign-off**, identifier renumbered away rather than struck, which `ISSUES.md` §"AC and test ID allocation" permits while tests are draft. The route it covered is the one that already works, so nothing regresses uncovered. RT-130.2, the open panel, becomes the route under test — and it is the route being restored.

### F3 (finding) — the open panel is modal, so the test must handle it

An `NSOpenPanel` takes the screen. A test that opens one and cannot dismiss it hangs the suite for its full timeout and leaves a modal window for the next test.

**Recommendation.** Assert the panel **appears** and then dismiss it, rather than driving it to a selection. That the panel opens is the criterion; which file it returns is Cocoa's business. Recorded because the ambitious version of this test is the one that wedges the suite.

### Edge cases

| # | Case | Required state | Test |
|---|---|---|---|
| E1 | A picture is loaded | an Open command is available | RT-130.2 |
| E2 | Nothing loaded | the open panel is still reachable | RT-130.3 |

| E4 | A filter result arriving | still not treated as an import | RT-130.5 |

E3 and E4 are the regression guards. The guard they protect is #111's, and this ticket touches the same area.

### Two corrections to my own work, recorded

**RT-130.5 first asserted the chain's length was unchanged after applying a filter, and failed.** Applying to a picture below the filterable minimum raises it first, and a promoted raise advances the tip, so the chain legitimately gains an entry.
