## Original issue body

## Problem

Images smaller than 512×512 (the model's tile size) produce corrupted output. The output dimensions are correct, but content is stretched, offset, and partially lost.

**Example 1:** `icon.png` (384×344) → 1536×1376. Content appears over-scaled and cropped — a substantial portion of the original is missing.

**Example 2:** `icon2.png` (422×438, with transparency) → 1688×1752. The alpha channel resizes correctly, but the RGB content is offset from the alpha and cropped. A significant portion of the image is lost.

Both images produce a single tile (`Split into 1 tile`).

## Root cause

`CoreMLInference.upscale()` uses `VNCoreMLRequest` with `.scaleFill` (`CoreMLInference.swift:50`). When a tile is smaller than the model's expected input (512×512), Vision **stretches** the tile to fill 512×512, distorting its aspect ratio. The model then outputs at 4× the stretched input = 2048×2048.

The pipeline (`Pipeline.swift:82-91`) places this 2048×2048 output at the scaled origin (0,0) with size 2048×2048. When `Tiler.stitch()` writes it into the output buffer (1536×1376), pixels beyond the buffer bounds are clipped. The visible result is the top-left 1536×1376 portion of a stretched 2048×2048 image — content is distorted and truncated.

The alpha channel is unaffected because `Pipeline.upscaleAlpha()` uses bicubic interpolation (`CGContext.draw`) to resize directly to the correct target dimensions, bypassing CoreML entirely.

## Solution

**Pad tiles to model input size before inference; crop output back to expected dimensions after.**

### Changes

**`Pipeline.swift`** — in the tile processing loop (lines 76-92):

1. Before `inference.upscale(tile.image)`: if the tile is smaller than `tileSize` in either dimension, pad it to `tileSize × tileSize` using **reflection padding** (mirror pixels at edges — standard for Real-ESRGAN, avoids edge artefacts).
2. After `inference.upscale()`: crop the output from (0, 0) to `(originalTileW × scale, originalTileH × scale)`, discarding the upscaled padding region.
3. Use the cropped output as the upscaled tile for stitching.

```swift
// Before inference: pad undersized tiles
let paddedTile: CGImage
let needsPadding = tile.image.width < tileSize || tile.image.height < tileSize
if needsPadding {
    paddedTile = try padToSize(tile.image, width: tileSize, height: tileSize)
} else {
    paddedTile = tile.image
}

let upscaledImage = try inference.upscale(paddedTile)

// After inference: crop away upscaled padding
let croppedImage: CGImage
if needsPadding {
    let cropW = tile.image.width * scale
    let cropH = tile.image.height * scale
    let cropRect = CGRect(x: 0, y: 0, width: cropW, height: cropH)
    guard let cropped = upscaledImage.cropping(to: cropRect) else {
        throw ImageIOError.contextCreationFailed
    }
    croppedImage = cropped
} else {
    croppedImage = upscaledImage
}
```

**Add `padToSize()` helper** — creates a `tileSize × tileSize` canvas and draws the original image at origin (0, 0), with the remaining area filled by reflection padding. Reflection padding mirrors the image content at each edge, which is the standard approach for Real-ESRGAN and avoids boundary artefacts.

### Why this fixes both examples

- **icon.png (384×344):** Padded to 512×512 (reflected edges). Model output is 2048×2048 with correct content at (0,0)→(1536, 1376). Cropped to 1536×1376. No stretching.
- **icon2.png (422×438, alpha):** RGB padded and cropped correctly, now matches the alpha channel (which was already correctly resized). No offset.

### What does NOT change

- `CoreMLInference.swift` — `.scaleFill` is fine when the input is already the correct size.
- `Tiler.swift` — split and stitch logic unchanged.
- Multi-tile images — tiles at model input size are unaffected (padding is conditional).

## Implementation (commit 09e132e)

### Changes

| File | Change |
|------|--------|
| `Sources/Superscale/Pipeline.swift` | `padToSize()` rewritten: flips CGContext to top-left origin before drawing. Eliminates the `yOffset` calculation and coordinate confusion that caused vertically inverted output. |
| `docs/architecture.md` | Added note about sub-tile padding and the flipped CGContext approach. |

### Root cause

`CGBitmapContext` defaults to bottom-left origin. When `ctx.draw(cgImage, in:)` draws a CGImage (top-left origin) into a bottom-left context, the image is inverted in the bitmap. The previous code attempted to compensate with `yOffset = targetH - srcH`, which positioned the content correctly but left it vertically flipped. For full-canvas draws (`resizeImage()`), the flip is invisible because the image fills everything. For partial-canvas draws (`padToSize()`), the flipped content is cropped from the correct position but with inverted pixel rows — producing upside-down RGB relative to the separately-upscaled alpha channel.

The fix: `ctx.translateBy(x: 0, y: targetH); ctx.scaleBy(x: 1, y: -1)` flips the context to top-left origin before drawing. Content is written to the bitmap in the correct orientation, and the crop at `(0, 0)` extracts correctly-oriented content.

## Follow-up fix (commit ce21e87)

The CGContext-based `padToSize()` from commit 09e132e fixed icon3.png but broke icon.png. The context flip approach interacted incorrectly with partial reflection padding — when `reflectH < srcH`, the bottom strip was drawn at the wrong position, corrupting the content.

Replaced `padToSize()` entirely with pixel-buffer operations:
1. Render source CGImage to a byte array
2. Copy rows into a larger target buffer (content at top-left)
3. Reflect-pad right edge by mirroring columns
4. Reflect-pad bottom edge by mirroring rows
5. Create CGImage from the buffer

This eliminates all CGContext coordinate system confusion. Tested with all three icon images:
- icon.png (384×344, opaque) — correctly oriented ✅
- icon2.png (422×438, transparent RGBA) — correctly oriented, alpha aligned ✅
- icon3.png (224×207, transparent RGBA) — correctly oriented, alpha aligned ✅

RT-087, RT-088, RT-089 all passing. 6/6 pipeline tests green.
