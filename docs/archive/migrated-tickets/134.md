## Original issue body

Child of delivery master #133 (the 2026-08-29 user-test round).

## Problem statement

**Observed by the author, 2026-08-29:**

> *"I am unable to disable the curtain slider after applying a filter - previously logged this defect. I should be able to switch ON and OFF the filter. If i switch it off, i don't want to see it again until i toggle it back on no matter what i do in the app."*

## This is a repeat, and that is the first thing to explain

**#126 closed on 2026-08-28 having supposedly fixed exactly this.** It removed all four places the application wrote `showComparison`, made the setting default to on, and left the user's toggle as the only writer. **AC94.6** was backfilled for it and two tests were written specifically for the author's rule:

- **RT-126.3**: with the curtain switched off, no operation shows it
- **RT-126.4**: the setting survives a completed operation

Both pass. The author still cannot switch it off. **So the tests assert something true that is not what the author does**, and identifying that difference is this ticket's first job --- not re-reading the diff, which shows exactly one write to the setting and that one is the toggle itself:

```
SuperscaleApp/SuperscaleApp/MainView.swift:733:  viewModel.showComparison.toggle()
```

## Candidate differences between the tests and the author's session, to be settled by reproduction

1. **The fixture.** RT-126.3 and RT-126.4 use the suite's 240x320 picture, which is below the filterable minimum --- so applying a filter *raises* it, and the raise turns the scale off. The author's pictures are large, no raise happens, and a scale stays selected with an upscale produced. `derivedImage`, `canOfferComparison` and `comparisonBase` all take different branches in those two worlds.
2. **Which control the author means.** The report says both *"the curtain slider"* and *"switch ON and OFF the filter"*. There are two controls: **Compare**, which governs the curtain, and **Filter**, which flips the canvas between the filtered result and its base. If the Compare control is absent in the state the author reaches, there is nothing to switch off regardless of what the setting does.
3. **Whether the build under test carried the fix.** #126 landed at `2af6e01` on 2026-08-28. Worth eliminating, cheaply, before anything else.

## Violated AC

- **AC94.6** in [docs/ACs.md](../blob/master/docs/ACs.md): *"The comparison curtain is shown when the user has it switched on and there are two assets to compare, and at no other time. Nothing but the user changes that setting."*

The criterion is right. Its tests do not reach the author's path.

## Debugging and fix procedure

1. **Reproduce with a picture above the filterable minimum and a scale selected**, which is the ordinary case and the one the suite does not cover. Record whether the Compare control is present, what it says, and what the curtain does when it is pressed.
2. **Establish which control is missing or ineffective** before changing anything. The setting has one writer; if the curtain will not go, either the control is absent or the curtain is not reading the setting.
3. **Widen RT-126.3 and RT-126.4 to the case that failed**, rather than adding a third test beside them. Two passing tests over the wrong fixture is the defect in the verification, and leaving them narrow repeats it.
4. Do not disturb the four removals #126 made. The setting having one writer is what makes *"no matter what i do in the app"* achievable at all.

## Test plan

- RT-134.1: with a picture above the filterable minimum and a scale selected, the Compare control is present after a filter
- RT-134.2: pressing it switches the curtain off, and it stays off
- RT-134.3: with it off, applying another filter does not bring it back
- RT-134.4: with it off, changing the scale does not bring it back
- RT-134.5: with it off, selecting an earlier locked iteration does not bring it back
- UT-134.1: switch the curtain off, then work normally, and judge that it stays off

The AC audit flagged the label as its leading hypothesis before the run and predicted a criterion
would be needed if reproduction found it. It did.

A `Toggle` with a constant name and a pressed state, which is **the author's own rule** given about
the filter control in the previous round --- *"the user will understand 'Filter' and that the button
is a toggle"* and *"the change of wording on the toggle is confusing."* #129 applied it there and
left this one alternating. **AC94.7** states it generally, so the next renaming control is caught by
an existing rule rather than by a fourth report.

helper typed `.any` and re-run: 4 executed, 0 failures.
