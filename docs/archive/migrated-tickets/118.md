## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure). Found by that delivery's verification runs.

## Problem statement

Three GUI tests failed in an otherwise clean full run with the identical message, at identical coordinates:

```
Failed to synthesize event: Neither element nor any descendant has keyboard focus.
Event dispatch snapshot: TextView, {{1288.0, 722.5}, {316.0, 231.5}}, identifier: 'generationPromptField'
```

No assertion failed in any of them. The click on the prompt field lands, focus does not arrive, and `typeText` has nowhere to send its keystrokes.

**Re-run in isolation immediately afterwards, all three passed:** `Executed 3 tests, with 0 failures (0 unexpected) in 64.301 seconds`. The fault is intermittent.

## Evidence

| Run | Conditions | Result | Synthesis faults |
|---|---|---|---|
| 1 (2026-08-26T03:31Z) | exclusive machine | 101 executed, 6 failures — all the #115 directory defect | 0 |
| 2 (04:38Z) | **concurrent `gh`/`git`/`grep` by the agent** | killed, inconclusive | 25 |
| 3 (05:26Z) | exclusive machine | 103 executed, 3 failures | 3 |
| 3a (05:50Z) | the three tests alone | 3 executed, 0 failures | 0 |

Run 2 is not evidence about this defect — it is evidence that concurrent work makes the fault far more likely, which is already recorded in `IMPLEMENTATION_GUIDE_v2.md` section 7. Runs 1, 3 and 3a are the useful ones, and they establish that the fault occurs at a low rate even on an exclusive machine.

## Affected tests

All three reach the prompt field through the same two lines:

```swift
prompt.click()
prompt.typeText("UI fixture generation")
```

- `test_applyingAFilterProducesAResultOnTheCanvas`
- `test_aReshapedReturnIsMarkedInTheWindow_RT096_14`
- `test_assetsLandBeneathTheConfiguredRoot_RT116_4`

RT-115.5 uses the same helper and passed in the same run, which is what makes this a rate rather than a rule.

## Why it is worth fixing rather than tolerating

A suite that fails roughly three tests in a hundred for environmental reasons cannot distinguish itself from a suite with three real defects. Every run then costs a triage pass, and the triage has to be done by someone who knows which failures look environmental — which is knowledge held in a person rather than in the suite.

It also erodes the rule it sits next to. The handover already asks a reader to judge a run by `Executed N tests` and to treat a killed run as inconclusive; adding "and ignore focus timeouts" makes green a matter of interpretation.

## Diagnosis not yet done

This ticket records the observation and its evidence. The mechanism is not established, and the candidates below are candidates, not findings:

- the click is delivered before the view is ready to take focus, and nothing waits for focus to arrive;
- `TextEditor` in SwiftUI does not take first-responder status from a synthesized click as reliably as a `TextField` does;
- the keepalive's `caffeinate -u` declares user activity every 240 seconds, which may interact with event synthesis. Runs 1 and 3 both used it and differ in outcome, so it does not explain the variance on its own.

**Start with a diagnostic that isolates the mechanism**, not with a retry loop. A retry would make the symptom rarer and the cause permanent, and this suite has already recorded twice what it costs to make a test pass without knowing why.

## Acceptance criteria

To be drafted once the mechanism is isolated. A criterion written now would be a guess about what needs to be true, and the audits would be auditing the guess.

## Diagnosed: a managed software installer prompt was stealing focus

**Author's observation, 2026-08-26:** *"a managed software installer prompt was stealing focus, i killed it to let your tests continue"*.

That is the mechanism, and it accounts for every observation on this ticket:

- **The symptom.** `Neither element nor any descendant has keyboard focus` on `generationPromptField` is precisely what a modal prompt from another process produces. The click lands on the canvas, the prompt takes first responder, and `typeText` has nowhere to send its keystrokes.
- **The intermittency.** An installer prompt appears when it appears. That explains a fault rate that varied from 0 in run 1, to 25 in run 2, to 3 in run 3, to 0 in the isolation run 60 seconds later, with no change in the suite or the application between them.
- **The two killed runs.** Runs 2 and 4 ended with no `Executed` line. A managed installer active on the host is a plausible common cause, though this ticket does not claim it as established.

**All three of the hypotheses recorded above are wrong**, and they were wrong in the same way: each looked inside the application or the suite for the cause of something happening outside both. The candidates offered were the click racing view readiness, `TextEditor` not taking first responder from a synthesized click, and the keepalive's `caffeinate -u` interfering with synthesis. None of them is the answer.

The correction is worth more than the fix. The evidence available from inside the run, an intermittent focus failure on one element, is equally consistent with a suite defect and with another process taking the screen, and nothing in the log distinguishes them. That distinction was only available to a human looking at the machine.

## Consequence for this ticket

There is no defect here in the application or in the suite, so there is nothing to fix and no acceptance criteria to draft. What remains is worth recording rather than discarding:

- A GUI run on a host that may raise managed prompts is not evidence. `IMPLEMENTATION_GUIDE_v2.md` section 7 already requires the machine to itself and the display awake; it does not mention other processes taking focus, and this run showed that a suite can be invalidated without the display ever sleeping or locking.
- The recommendation is a documentation change to section 7 rather than a code change: before trusting a full run, confirm no managed installer, update prompt or other modal is pending, and treat a focus-synthesis failure as an environment signal rather than a defect until it reproduces on a quiet host.

Recommend closing as **environmental, no fix required**, with that documentation change made under this ticket. Held open pending that change rather than closed on the diagnosis alone.


### Comment by tigger-developer at 2026-08-26T09:34:13Z

## Closing: environmental, no application or suite defect

The mechanism is the author's observation, recorded above: a managed installer prompt taking focus. Confirmed further during this delivery, when a later run failed with `Failed to initialize for UI testing: Timed out while enabling automation mode` and a process check found JAMF Remote Assist running with an active capture component alongside Software Update. Managed processes were left alone; they are not this project's to kill.

There is nothing to fix in the application or the suite, so no acceptance criteria were drafted and none are needed.

**What was done instead is the documentation change**, in `1139659`, raising `IMPLEMENTATION_GUIDE_v2.md` to 3.26. Section 7's GUI-run rules covered the display sleeping or locking and said nothing about another application taking first responder. They now record:

- no other process may be able to take the screen, and the display never has to sleep for that to ruin a run;
- what it looks like when one does, in both the focus-failure and automation-timeout forms, and that neither names the cause;
- a check to run before starting on a managed host;
- that a focus-synthesis failure is an environment signal until it reproduces on a quiet host, because the distinguishing information is on the screen and not in the log.

That last line is the one worth having. Three hypotheses were recorded on this ticket, all looking inside the application or the suite for the cause of something happening outside both, and all wrong. The evidence available from inside a run cannot distinguish a suite defect from another process taking the screen.

Closed under delivery master #114. No ACs to migrate, no user tests to transfer.
