## Original issue body

Child of delivery master #114 (post-MVP verification and defect closure).

## Problem statement

**Observed (author, UT round of 2026-08-25 — failed UT-93.1, noted on passing
UT-91.1):** with a 3840×2160 picture and 8x requested, the info panel reads
*"Scale: 4× → 15360×8640"*. That output is 132 megapixels — over four times
the 32-megapixel ceiling — and cannot be what ran. In the same screenshot
(`ut91.1a.png`) no preset scale button reads active, and the custom dimension
fields have been populated with the same impossible 15360 × 8640. The status
bar's message, meanwhile, was judged good — so the application is telling the
user two different stories in two places.

**Expected:** every surface reports the decision the ceiling actually made.
For a 3840×2160 source, even 2x is 33.2 megapixels — over the ceiling — so no
preset fits at all, and every surface should agree with whatever the decision
engine concluded.

## Cause, anchored

`InfoPanel.swift:76`:

```swift
result.append("Scale: \(scale)× → \(w * scale)×\(h * scale)")
```

The panel multiplies input by scale itself. It never consults
`UpscaleCeiling.decide`, so it reports the request's arithmetic as though it
were the outcome. This is a **third private derivation of sizing truth** — the
exact pattern this week's work retired twice: two measurements of a picture
(#100), two routes to an upscale (#103, disproven), and now a view doing
arithmetic the decision engine owns. `ScaleReadout` exists precisely so
surfaces derive from the one pure function; the info panel predates that and
was never migrated.

**The `.custom` branch has the same defect.** `InfoPanel.swift:80-84` reports
`viewModel.customWidth` and `customHeight`, which are what was *typed* rather
than what the ceiling decided. `ScaleReadout` already distinguishes these as
`displayedDimensions` and `requestedDimensions`, which exist because they
differ. Fixing only the preset branch removes the third derivation and leaves a
fourth alive in the branch nobody looked at.

The populated custom fields are a second symptom needing their own diagnosis —
nothing should write request arithmetic into the user's input fields.

## Violated AC

- **AC93.1** in [docs/ACs.md](../blob/master/docs/ACs.md): *"...it is
  unambiguous which scale is in effect and which was asked for."* The panel
  names an output nothing will produce; the buttons name nothing at all.
- **AC83.7**: the reduction is reported *while the scale selection continues
  to show what was asked for* — the info panel contradicts the status bar's
  correct report.

**AC93.1 is violated in two places and this ticket closes one.** The criterion
covers *"the scale control **and the custom dimension fields**"*. The panel's
line is fixed here; whatever writes impossible dimensions into the fields is a
separate defect with its own ticket, per step 3.

## Debugging and fix procedure

1. **Move the line composition into `SuperscaleUXCore` first, then reproduce
   against it.** `InfoPanel` is in the application target, so no package test
   can reach the arithmetic as it stands, and the fail state is pure arithmetic
   that deserves a cheap test. A function taking the source size and the
   selection and returning the panel's lines makes RT-108.1 to RT-108.5
   package-level, and one GUI test then confirms the panel renders what the
   function returns rather than deriving anything of its own.

   This is the same correction `StorageRoots` made for storage locations and
   `ImageDimensions.pixelSize` made for measurement. It is what turns "one
   function owns sizing truth" from an intention into something a test can
   hold.
2. Rework **both** the preset and the custom scale lines to derive from
   `ScaleReadout` / `UpscaleCeiling.decide` — the same source the scale buttons
   use — rather than local arithmetic. Delete the local `w * scale` computation
   and the typed-dimension reporting entirely, from both branches, so a fourth
   derivation cannot grow back; guide 2.5's "one function" rule applies to
   sizing decisions as much as to measurements.
3. **Separately diagnose the custom fields.** Find what wrote 15360×8640 into
   them (suspect: whatever adopts dimensions on selection change). That is its
   own defect with its own ticket — do not fold an unrelated fix in here;
   log it when identified.
4. GUI regression: the author's UT-93.1 scenario — large picture, 8x chosen,
   then read buttons, panel and status bar and assert they agree.

**UT-93.1 is not re-offered from this ticket.** The author would be looking at
the same screen, where the custom fields still hold the impossible numbers this
ticket does not touch. The re-offer belongs to whichever ticket closes AC93.1's
second half, once both are done.

## Test plan

Package-level, over the line-composition function:

- RT-108.1: the scale line agrees with the ceiling's decision for a request the
  ceiling reduces
- RT-108.2: **the author's actual case, asserted literally.** Source 3840×2160
  with 8x requested produces the line the decision engine warrants, and the
  string `15360×8640` appears nowhere in the panel's output. Exact-string
  assertion is deliberate: rendered copy a user reads is itself the contract,
  and this defect is a wrong sentence rather than a wrong number in a struct.
  Asserting only "agrees with `UpscaleCeiling.decide`" would pass against an
  implementation that consults the engine and then formats its answer wrongly
- RT-108.3: it agrees for a request that fits unreduced, so the fix does not
  overcorrect
- RT-108.4: with custom dimensions typed that the ceiling reduces, the custom
  line reports the effective dimensions and the typed ones remain
  distinguishable — the same relationship AC93.1 requires of the fields
- RT-108.5: with the scale cleared, the panel reports upscaling as off and
  names no dimensions, so the branch that is correct today stays correct

GUI-level, over the wiring:

- RT-108.6: the info panel on screen shows the line the function returns, so the
  view is confirmed to render it rather than to derive anything itself
