## Original issue body

## Problem

We have CoreML `.mlpackage` files (from Phase 1) but no proof that they work in Swift on Apple Silicon. Before building the full CLI, we need to validate that CoreML inference produces acceptable output and runs at acceptable speed.

## Solution

Write a minimal Swift proof-of-concept that:

1. Loads a `.mlpackage` model via `MLModel`
2. Reads a small test image via `CGImage`
3. Runs inference on the image (or a single tile)
4. Writes the upscaled output
5. Measures wall-clock inference time

This can be a standalone Swift script or a minimal executable target. It does not need argument parsing, tiling, or error handling — just the minimal path to prove CoreML inference works.

### Quality validation

- Output image must have correct dimensions (input × scale factor)
- Visual inspection: sharp detail, no block artefacts, no colour shifts
- No PyTorch comparison needed — quality is assessed on its own terms

### Performance target

- 1024×1024 at 4× in under 30 seconds on M3 Air (from VISION.md success criteria)
- If tiling is needed for memory, that's acceptable at this stage

## Implementation

**Commit:** b61c630 — `feat: add CoreML inference proof of concept`

### What was done

1. **`Sources/Superscale/CoreMLInference.swift`** — Inference wrapper that:
   - Loads `.mlpackage` via `MLModel.compileModel(at:)` (compiles to temporary `.mlmodelc`)
   - Wraps Vision framework's `VNCoreMLRequest` for image-in/image-out prediction
   - Returns upscaled `CGImage` output
   - Defines `SuperscaleError` enum for pipeline error handling

2. **`Tests/SuperscaleTests/CoreMLTests.swift`** — RT-010 and RT-011 tests:
   - Both skip via `XCTSkipIf` when the model file isn't present
   - RT-010: Feeds a synthetic 64×64 gradient image, verifies output dimensions
   - RT-011: Benchmarks 1024×1024 inference against the 30-second target
   - Uses `@testable import Superscale` to access internal types

### Important note: model file dependency

Tests require `models/RealESRGAN_x4plus.mlpackage` which is produced by `make convert-models` (issue #3). Until the `.pth` checkpoints are downloaded and converted, tests will skip. To run them:

```bash
# Download checkpoint
mkdir -p checkpoints
# Download RealESRGAN_x4plus.pth from https://github.com/xinntao/Real-ESRGAN/releases

# Convert
make convert-models

# Run PoC tests
swift test --filter CoreMLTests
```

### Design note: fixed tile size

The conversion script produces models with a fixed 512×512 input shape. The Vision framework resizes any input to match. For the 4× model, output is always 2048×2048 regardless of input dimensions. Variable image sizes will be handled by the tiling engine (Phase 3b, issue #7).

### Comment by m13v at 2026-03-24T13:28:34Z

nice work on the CoreML inference numbers - 0.74s for 1024x1024 is impressive. we use CoreML via WhisperKit for on-device transcription in our macOS app and have some observations that might help with phase 3.

the fixed 512x512 input shape is going to be your biggest headache when you add tiling. Vision framework does resize automatically, but you lose sharpness on the tile boundaries if you don't add overlap. we found that 16-32px overlap between tiles, then blending the overlap region with a linear gradient, eliminates the seam artifacts.

also worth noting: MLModel.compileModel creates a temp .mlmodelc every time. for a CLI tool that runs repeatedly, caching the compiled model to a known path and checking if it exists first cuts startup time from ~4s to under 200ms on subsequent runs. MLModel(contentsOf:) on an already-compiled .mlmodelc is nearly instant.

for the visual quality check (AC4.3), SSIM comparison against a reference output from the PyTorch model would give you a quantitative baseline alongside the visual inspection.
