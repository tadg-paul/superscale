## Problem statement

**Observed by the author, user-test round of 2026-08-27:**

> *"adding a large image to the upscaler, get the following error: 'This image is 9 megapixels, and upscaling it would need more memory than is available. It is shown at its original size.' - that is a UT PASS ALMOST. The info text says 'scale 4x requested, too large to scale ...' which is good. However the 4x button looks depressed. Weirdly, when the application loses focus, the 4x button does not look depressed."*

> *"CORRECTION i just realized what it is. It looks depressed because it is in fact disabled, while 2x and 8x and custom are enabled. this explains why they look like normal buttons when app loses focus. So the real problem is this: ALL upscale buttons should be disabled for an image this large, not just 4x."*

> *"the problem is the 4x is *depressed and disabled* that is why it is visually such a problem in this context"*

> *"when i apply a filter, it tries to upscale it 4x, but the 4x should have been switched OFF before being disabled, and the 8x should have been disabled too."*

> *"when i drop a large image onto the canvas, i get the warning, but the 4x button is still depressed. It should be un-depressed, i.e. it should be OFF and it should be disabled, and all upscaling should be OFF and disabled for a large image."*

## Three separate faults in one interaction

1. **A control is simultaneously selected and disabled.** That state has no meaning: it reads as pressed, and the appearance changes when the window loses focus, which is how the author eventually diagnosed it.
2. **Only the requested scale is disabled.** 2x, 8x and custom remain live on a picture that cannot be upscaled at all.
3. **The selection is not cleared before the control is disabled**, so a subsequent filter still attempts the upscale the interface has just refused.

Fault three is the one with consequences beyond appearance: it produces the too-large error again on a later action, which the author hit from a second direction --- *"I click the 'show filtered/original' toggle, and immediately it tells me AGAIN the image is too large, because it is trying to upscale it again instead of just leaving the 4x toggle switched off like it should have."*

## Violated AC

- **AC82.8** in [docs/ACs.md](../blob/master/docs/ACs.md): the scale selection changes only when the user changes it. The area ceiling reducing a request must not rewrite the control.

There is tension to resolve rather than paper over: the author now asks for the selection to be **cleared** when a picture cannot be upscaled at all, which is a change to the selection by something other than the user. `audit-acs` must rule on whether AC82.8 is violated here, or whether it is being amended, and record which. The distinction is real: a *reduced* request must leave the control alone (AC82.8's case), while an *impossible* one may not.

The author's decision that **all** upscaling is disabled above the threshold is a specification change; guide 2.5 currently reduces to the largest scale that fits and leaves a picture that fits at no scale as it is.

## Debugging and fix procedure

1. **Reproduce and record which controls are enabled, which are selected, and what the information panel says**, for a picture that fits at no scale and for one that fits at some. They are different cases and the fix must keep them apart.
2. **Establish the disabled-and-selected state's source** before changing it. The hypothesis is that enablement is derived per-button from the ceiling while selection is held separately, so nothing clears one when the other changes.
3. **Decide the rule with the audits, not in the code**: whether a picture that fits at *some* scale keeps those scales live, or whether the author's "keep it simple" applies to every oversized picture. The author offered both readings; the ticket must not pick silently.
4. **Clear before disabling.** Whatever the rule, no control may be left selected and disabled.
5. **A filter must not attempt a refused upscale.** Once the selection is cleared this should follow, but assert it rather than assume it --- the author reached it by two different routes.
6. Guide 2.5's reduce-and-tell posture is unchanged for pictures that fit at some scale; only the fits-at-no-scale case is in question.

## Test plan

- RT-125.1: no scale control is ever both selected and disabled
- RT-125.2: for a picture that fits at no scale, every upscale control is disabled
- RT-125.3: for a picture that fits at no scale, no scale is selected after the warning
- RT-125.4: applying a filter to such a picture issues no upscale
- RT-125.5: toggling the comparison on such a picture issues no upscale and raises no second warning
- RT-125.6: a picture that fits at a reduced scale keeps its selection, per AC82.8
- RT-125.7: after a filter returns a picture within the limits, upscaling is available again
- UT-125.1: drop an oversized picture and judge that the controls say what is possible

### F1 (blocker) — the premise is wrong: no scale control is disabled, and the code anticipated this exact reading

The ticket, from the author's own correction: *"I just realized what it is. It looks depressed because it is in fact disabled, while 2x and 8x and custom are enabled."*

**It is not disabled.** `ScalePicker` carries no `.disabled` on any scale button — the only two in the file are on the custom width and height fields. And `ScaleReadout.isChoosable` returns `true` unconditionally, with this comment:

> *"Always. Marking a scale as not in effect is a statement, not a restriction: the natural way to render it is to dim the control, and dimmed reads as disabled — which would trap the user at the reduced scale until they imported a different picture."*

So the *"depressed and disabled"* appearance is `tint(for:)` returning `.secondary` for `requestedNotInEffect`. A `.secondary` tint on a `.bordered` button reads as **both** pressed and disabled, which is one visual doing duty for a state that is neither.

**Your observation is right and your inference is wrong**, and the difference matters: the fix is a visual treatment, not an enablement change.

### F2 (blocker) — this is the same defect as #131's second half, and they must not be fixed twice

**#131** records the same root: `tint(for:)` returns a colour for both `.inEffect` and `.requestedNotInEffect`, so whenever the ceiling reduces a request two buttons read as pressed. That ticket already carries three options and is awaiting the author's choice.

**Remediation.** #131 owns the tint. This ticket keeps the *behavioural* half only. Written into both so neither takes the other's.

### F3 (blocker) — *"all upscale buttons disabled for an image this large"* contradicts a documented decision that exists to prevent a trap

The comment above is not incidental: disabling the controls on an oversized picture means a user cannot change scale until they import a different picture. `ScaleReadout` was written to avoid precisely that.

**Remediation.** This is a **specification change**, and it reverses a deliberate one. It needs the author's ruling with the trade-off stated, not an implementation. Recorded rather than actioned.

### F4 (finding) — #131 has already changed the scenario underneath this ticket

Every observation here began *"adding a large image to the upscaler"* with a scale already in effect on launch. **Nothing is selected on launch as of #131**, so an oversized picture now arrives with no upscale attempted and no reduction to report. The sequence that produced the report cannot occur in the same way.

**Remediation.** The behavioural claims must be **re-reproduced against the current build** before any of them is treated as live. Two of the three may simply have gone.

### F5 (finding) — the one behavioural claim worth keeping

*"when i apply a filter, it tries to upscale it 4x"* after the too-large warning. If a scale that cannot run is still attempted at Apply, that is a real defect independent of appearance.

**Remediation.** Reproduce this specifically, with a scale deliberately selected on an oversized picture, and keep RT-125.4 for it.

### Where this leaves the ticket

- The appearance half moves to **#131**, where the decision already sits.
- The disable-everything half is a **specification change** awaiting the author.
- The behavioural half needs re-reproduction against a build that no longer upscales on launch.

**This child does not proceed to implementation on this audit**, and the reason is that two thirds of it turned out to be one visual decision already parked, and the remaining third may have been overtaken by #131. Recorded on master #120.
