## Original issue body

## Problem statement

**Observed (by code reading and one instrumented run; not yet by a dedicated
failing test):** with a rendering already held for the current scale, choosing a
*different* scale can serve that stale rendering instantly — no run starts, and
the canvas shows the previous scale's picture while the scale control names the
new one.

**Expected:** the picture on the canvas corresponds to the scale the control
says is in effect.

## Mechanism

`@Published` publishes in `willSet`. Inside the `$scaleSelection` sink,
`self.scaleSelection` still holds the value being **replaced**. The sink's own
guard was written with this in mind (its comment documents the trap), and
`reupscaleIfNeeded` correctly threads the *effective* selection through to
`processImage` — but the cached-rendering lookup inside `processImage`
(`heldRendering` → `renderingKey`) reads the **property**. So choosing 8x keys
the store by 4x, finds the rendering made earlier, marks it displayed and
returns before `start` is ever reached.

The second instance of the same trap three lines below the comment warning
about the first. Now recorded as a guide rule (v3.23).

## Reachability — when it bites and when it does not

- **Click a new scale while a run is in flight:** no rendering has published
  yet, the lookup misses, a real run starts with the correct request. Not
  reachable. (This is why #101's tests pass despite the defect.)
- **Click a new scale after the run completes, where the ceiling reduces the
  new choice back to the old one** (e.g. 8x → 4x on a large picture): the
  stale 4x rendering is arguably the right pixels, but the run is skipped, so
  the reduction notice, `resultSource` and run metadata are all stale. Degraded
  but subtle.
- **Click a new scale after the run completes, where the new scale fits**
  (e.g. 4x → 8x on a small picture): the 4x rendering is displayed while
  `ScaleReadout` — a pure function, correct about the request — says 8x is in
  effect. **This is the harmful case: wrong pixels under a right label.**

## Violated AC

- **AC93.1** in [docs/ACs.md](../blob/master/docs/ACs.md): the control shows
  what is actually in effect — but nothing is in effect; the displayed
  rendering belongs to the previous request. If review concludes AC93.1 does
  not strictly cover the canvas/control agreement, the correct move is a
  **backfill** on the #93 family per ISSUES.md §"Bug-fix issues reference
  existing ACs", second path — flagged for the author's ruling rather than
  decided unilaterally.

## Why this was not fixed inline (history that will save the fixer time)

The three-line fix — thread the effective selection into
`renderingKey`/`heldRendering` — **was applied and then deliberately reverted**
during #99's work. It is behaviourally correct but changes *when a real run
happens versus a cached rendering being served*, and three closed issues' GUI
tests encode the current timing: `RT156`, `RT158` (info panel content after a
scale change) and `RT090_52` (canvas undisturbed while work runs). All three
moved from passing to failing under the fix — not because the fix is wrong but
because they were written against the behaviour the defect produces. That is a
scoped change with its own verification burden, which is why it is this ticket
and not a rider on #101.

## Debugging and fix procedure

1. **Write the failing test first, at the harmful case.** GUI test: import a
   picture small enough that 8x fits (e.g. 800×640 → 8x is 32.8MP… too big;
   use 640×480 → 8x = 12.3MP, fits). Let the native 4x run complete
   (`waitForUpscaleComplete`). Click 8x via the existing `selectScale(8)`
   helper. Assert a new run occurs and the result changes: the info panel's
   `infoScale` should read `Scale: 8×` *and* the working image's reported size
   should be 8x the source — the second assertion is the one the defect fails.
   Confirm it fails against master before fixing anything.
2. **Apply the three-line fix**: `processImage` passes
   `selection ?? scaleSelection` to `heldRendering`; `renderingKey` already
   takes an optional selection parameter (left in place, with a 🚫 note at the
   call site pointing here — remove that note as part of the fix).
3. **Re-examine the three casualty tests individually, not as a batch.** For
   each, decide from its assertion whether it pinned *intended behaviour* (fix
   the code until it passes) or *the defect's timing* (rewrite the test's
   waits/assertions and record the supersession on its originating issue, as
   #82's toggle-group change did for RT148). Do not weaken any assertion to
   make it pass; that is the forbidden shortcut.
4. **Audit the store for the same trap once more**: every reader of
   `scaleSelection`, `customWidth`, `customHeight`, `definingDimension`
   reachable from any `@Published` sink takes the value as a parameter. The
   two known instances were three lines apart; assume a third until the sweep
   says otherwise.
5. Full `make test` and `make test-gui`, then `audit-code`, AC/test marks, and
   the usual closure evidence.

## Test plan

- RT-106.1: choosing a larger scale after a completed run produces that
  scale's output, not the held rendering (the step-1 test)
- RT-106.2: choosing a scale the ceiling reduces still runs and reports the
  reduction after a completed run (covers the subtle case: the notice must
  appear even though the pixels match)
