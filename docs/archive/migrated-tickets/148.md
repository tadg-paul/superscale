## Original issue body

## Problem statement

**Requested by the author:**

> *"Generate a new image from scratch with the FAL API: this should be a reasonably small tweak now. The UX is there already, simply allow the user to type in to the prompt and click 'Apply' on an emtpy canvas. This should invoke the fal model -> which for this v2 MVP is the same grok model without the '/edit' prefix"*

## He is right about the size of it, and here is the evidence

`FalRequestBuilder.swift:76` already chooses between the two endpoints:

```swift
let endpoint = isEdit ? handler.editEndpoint : handler.textEndpoint
```

and the handler already holds both (`FalRequestBuilder.swift:124-125`):

```swift
textEndpoint: FalGenerationRequest.defaultModelID,          // xai/grok-imagine-image
editEndpoint: "\(FalGenerationRequest.defaultModelID)/edit",
```

**So the text-to-image path exists, is reachable, and is exactly the model without `/edit`.** What is
missing is the *interface* allowing the request to be made with no reference image: `submitFilter`
begins by asking the graph for a filter input and returns immediately when there is none.

## What guide 2.2 says, and why this is a change to it

Guide 2.2 currently states:

> *"The MVP has no 'generate from a prompt' entry, because the filter corpus is built for transformation... Every MVP journey therefore starts from an image the user brings in."*

and records generation from a prompt as **the next version**. The author is bringing it into this
one. **Guide 2.2 must be amended before the code**, not after --- it is a scope statement, and
leaving it contradicting the build is how a specification stops being trusted.

It also predicted the shape correctly: *"When it arrives it becomes an additional way to create a
`source` asset, entering the same pipeline at the same point as an imported image, with filtering and
upscaling unchanged downstream."* That is the design; it does not need reinventing.

## Design consequences worth stating

- **The result is a `source`, not a `filtered`.** It has no parent, it starts a chain, and everything
  downstream --- filtering, upscaling, locking, comparison --- is unchanged. Anything else would make
  the first generation a special case forever.
- **No reference means no upload.** The three-step upload that #137 measured is skipped entirely, so
  a from-scratch generation is the *fastest* provider path in the application.
- **Apply must be reachable on an empty canvas**, which today it is not: the filter panel's Apply is
  gated on having a picture. That gate is the change.
- **The 108 filters are written to transform an input.** A user picking "Contact Sheet" with no
  picture will get something, and it may be odd. Worth a thought, not a blocker.

## Violated criteria

- Guide **2.2**'s scope statement. Being amended.
- **AC92.7**, that what goes to the provider is the base's own file, is about the edit path and is
  unchanged --- but must not be broken by a path that sends no file at all.
- Nothing covers generation without a source. Expect new criteria.

## Test plan

- RT-GEN.3: the request carries no reference field and no uploaded image

*Identifiers are placeholders until this issue has its number. **OT note:** no test here may reach

## Acceptance criteria

- **AC148.1** With an empty canvas and prompt text, Apply is available.
- **AC148.2** A generation with no picture behind it reaches the model without its `/edit` suffix and carries no reference image.
- **AC148.3** The returned picture becomes the base with role `source`, so filtering, upscaling, locking and comparison work on it unchanged.
- **AC148.4** With an empty canvas and no prompt text, Apply stays unavailable.
- **AC148.5** With a picture loaded, a filter still reaches the edit endpoint and still carries its reference, unchanged by this route existing.

### What this issue delivers, in plain language

A picture can be made from words alone. On an empty canvas, type a prompt, press Apply, and the
provider generates without being given anything to transform. What comes back is an ordinary
picture: it can be filtered, upscaled, locked and compared like any other.

### Evidence

- The author's reading was right and the code says so. `FalRequestBuilder.swift:51` ---
  `let isEdit = !acceptedReferences.isEmpty` --- and line 76 chooses `editEndpoint` or `textEndpoint`
  on it. `textEndpoint` is `FalGenerationRequest.defaultModelID`, the model **without** `/edit`.
- `FalRequestBuilder.swift:60` --- `if !isEdit || handler.editAcceptsSizing`. Grok's edit endpoint
  refuses a sizing parameter and its text endpoint accepts one, so sending no reference restores
  sizing as a side effect. Worth knowing rather than discovering.
- `WorkspaceModel.canApply` required `workingImage?.hasWorkingImage == true`. That was the only gate.
- Guide **2.2** said the MVP had no such entry. **Amended before the code**, as the ticket required.

### Edge cases

- **A filter chosen with no picture.** The corpus is written to transform an input, so a filter's
  text applied to nothing may produce something odd. Recorded in the guide as a property of the
  prompts rather than of the route. Not a criterion: "odd" is not assertable.
- **Prompt text but no key configured.** `canApply` still requires `isGenerationConfigured`, so Apply
  stays unavailable. Unchanged and covered by AC148.1's phrasing.
- **A returned picture below the filterable minimum.** It arrives as a `source`, so #96's raise
  applies to it exactly as to an imported picture. That is the point of AC148.3.
- **Generating twice in a row.** The second generation happens with a picture on the canvas, so it
  is an ordinary filter of the first. Correct, and follows from AC148.3 rather than needing its own
  rule.

### Quality self-audit

Five criteria, each a system state. **AC148.5 is the anti-regression clause** and the most important
of them: this ticket widens a gate that everything else in the filter path depends on, and the edit
route must be provably untouched.

Totals: **0 missing ACs, 0 edge-case gaps, 0 quality violations.**

### Findings

None. One implementation decision recorded rather than raised: `canGenerateFromNothing` is a
**separate** property rather than a relaxation of `canApply`. A great deal is gated on `canApply`,
and widening it would quietly change all of it; generating from nothing is a different act with a
different request, so it gets its own question.
