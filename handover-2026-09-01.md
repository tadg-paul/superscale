### What each one actually turned out to be

Worth reading before touching any of this code - several were not what the
report suggested.

- **#140** `MainView.clearPicture()` ended with `FilterSelection()`, whose
  initializer defaults `filters: []`, and the entire 108-filter corpus lives in
  that value. `FilterPanel` reads its rows from it and derives its category
  chips from the same place, so clearing a picture emptied the panel for the
  rest of the session. The intention was right and the partition was wrong: the
  *chosen* filter belongs to the picture, the *corpus* belongs to the
  application, and AC135.6's two-way split had no third place to put it.
- **#141** `visibleFilters` and-ed the chip and the query, so with Lighting
  chosen a search reached 4 filters of 108. The chip now clears **on focus**,
  not on the first keystroke. It is *cleared*, not ignored - making the search
  ignore a lit chip is one line and leaves a control that lies. Writing the test
  for that required making the chip's state addressable; it had been colour
  only.
- **#142** Four previous attempts changed the badge's position (#119), its width
  cap (#128), its opacity and its material, and left it a horizontal line with
  the spinner in front - the one thing asked for. It is now a `VStack`, one word
  per line, uppercased, `.title3.weight(.semibold)`, spinner last, rounded
  rectangle rather than a capsule. Words split explicitly rather than by
  wrapping, because wrapping needs a width and a width is what #128 removed.
- **#143** Reverses AC135.8. "Unsaved" is tracked in
  `viewModel.savedSourceURLs`, keyed on `inputURL` at the moment a save
  succeeds, because `inputURL` is the displayed source for *both* save routes -
  displaying a locked iteration sets it, which is the whole of #111.
- **#144** `FalRequestBuilder` needed nothing. Copy reads `displayedImage`, not
  `viewModel.result` - with the scale off there is no result, which is the
  mistake #112 fixed for the curtain. Paste writes a PNG into the configured
  generated root and enters through `handleDrop`, so it is an ordinary import.
- **#145** Nothing replaced `.newItem`, so AppKit's New Window survived and
  opened a second window onto the *same* `WorkspaceState` and
  `UpscaleViewModel`.
- **#146** Two causes one level apart: the row was a `LabeledContent`, which
  reflows its label above the content once the content's ideal width will not
  fit, and a `TextField`'s ideal width follows its text; and beneath that,
  `minWidth` alone left the field growing with the key and pushing the save,
  remove and status controls along the row. **#110 fixed one route into this and
  left the other open** - its note on `statusSlotWidth` records the same
  renegotiation.
- **#147** The shortcuts call `viewModel.choose(_:)`, the same method the
  buttons call, so they cannot drift. That matters: the scale controls are a
  toggle group and the obvious wrong implementation, `scaleSelection =
  .preset(2)`, sets but never clears.
- **#148** The author's size estimate was right.
  `FalRequestBuilder.swift:51` already had `let isEdit =
  !acceptedReferences.isEmpty`, and line 76 chose `editEndpoint` or
  `textEndpoint` on it. The only gate was `canApply` requiring a working image.
  The returned picture arrives as a **`source`** via `importImage`, not as a
  candidate - `recordFilter` needs a base to hang from and an empty canvas has
  none, so it would have been refused.

**AC135.8 is superseded and kept in place marked as such.** It said a clear
asks for no confirmation. It was written after the author had already asked
once for the opposite, so the specification recorded his request as wrong.
#143 reverses it. Do not delete the superseded entry - the record of the
mistake is the point.

## Traps - read before you spend a day on one

### 1. Kill a GUI run and you orphan an application instance

**This cost most of a delivery window.** Five full or partial `make test-gui`
runs were started; several were stopped with `TaskStop`. Each stop left the
launched `Superscale.app` behind. They accumulated to roughly a hundred, and
the suite then failed with:

```
Application 'com.tadgpaul.superscale' does not have a process ID
```

Failures spread into tests the round never touched and the count climbed run
over run - 3 -> 1 -> 35 - which reads exactly like a machine degrading. It was
not. After `pkill`, the same tree ran **223 / 0**.

- **Check with `pgrep -f "Superscale.app/Contents/MacOS"`.**
  `ps -Aco pid,comm | grep Superscale` returns nothing even when a hundred are
  running, because `comm` truncates. That false negative was reported as
  evidence twice.
- **Never run two GUI suites at once.** The second reports
  *"not foreground and does not allow background interaction"*.
- If you stop a run, clean up before starting another.

Four hypotheses were pursued and all four were wrong before the real cause was
found: chip-strip overflow, saved window geometry, an identifier on the
`ScrollView` absorbing hit tests, and `.accessibilityValue` synthesizing a new
element. Each looked plausible, each got a code change, none held. The
abandoned work is in `git stash` as `wip-chip-diagnosis` and can be dropped.

### 2. A GUI run is judged by its `Executed N tests` line and nothing else

A run reported here as "15 failures" had not finished; it completed at **35**.
Counting `Test Case ... failed` lines in a live log is not a result. This rule
is written into #139's own baselines section and was still broken.

### 3. SwiftUI accessibility containers absorb their children

Met three times now:

- The curtain absorbed its divider (#90, D-2)
- The progress badge absorbs its words (#142) - three attempts to make them
  individually addressable all failed; the badge stays `.combine`d and its
  arrangement is asserted through the badge's own height
- An identifier added to the category `ScrollView` made every chip inside it
  unhittable

If a child element cannot be found or clicked, look at what container was
recently identified or declared.

### 4. `CommandGroup(replacing: .pasteboard)` removes the standard Edit menu

It takes Cut, Copy, Paste and Select All away from **every text field in the
application**, including the open panel's "Go to folder" field the suite types
into. Two tests failed with `loadTestImage` timing out at 133 seconds, which
reads as a harness fault. Use `after:`.

### 5. Tests that cannot enter the failing state

**RT-87.37** asserted *"search reaches across categories, so nothing is behind
a chip"* - correctly - and ran from a state with no chip active. The author
reported the defect three times while it stayed green. Widened by #141 to start
from a chipped state.

The same shape appeared in #135's clear tests: they asserted everything the
clear must **do** and nothing it must **not touch**, which is how #140 shipped.

**Eighteen assertions** in the GUI suite used `dropTarget` as proof that the
canvas had cleared. `DropTargetView` is also rendered behind a loaded picture at
`opacity(0.01)` so it can still receive drops, so that identifier is present
either way and every one of those assertions was true before the clear as well
as after. They now wait on the absence of `clearImageButton`, which renders only
when a picture is loaded.

## Where things live

- **`AppCommands`** (in `SuperscaleApp.swift`, not its own file - the target is
  not a synchronized folder). Carries File-menu commands to `MainView`, which
  owns `WorkspaceState` and therefore owns the decision about unsaved work.
  Counters, not booleans, so the same command can be issued twice.
- **`MainView.requestClear()` / `performClear()`** - the split between deciding
  and doing. All three clear routes go through `requestClear`.
- **`viewModel.savedSourceURLs`** - what has been written to disk this session,
  keyed on `inputURL` because that is the displayed source for both save routes.
- **`WorkspaceModel.canGenerateFromNothing` / `generateRequest()`** - the
  prompt-only path. `FalRequestBuilder` already chose the text endpoint when no
  reference was attached; the only gate was `canApply` requiring a working
  image.
- **Test helpers worth knowing:** `waitUntilCanvasIsEmpty()`,
  `clearWarningAlert` (through `app.dialogs`/`app.sheets` - identifiers inside
  a SwiftUI `.alert` do not survive into the `NSAlert`), `compareControl`
  (typed `.any`, because a `Toggle` with `.toggleStyle(.button)` is not an
  `app.buttons`).

### 6. Repeats are comprehension failures, not coding ones

Four items this round were repeats: #142 at its **fifth** raising, #141 at its
**third**, #143 and #144 at their **second**. In every case something had been
delivered and did not answer what was asked.

The pattern in #142 is the clearest: *"still too small"* appeared in the report
every time and was read as *the shading is too wide for the text*, which is what
#128 fixed and is not what was written. Each child this round therefore began by
restating the request in the author's own words and checking the restatement
against it before any code. Do the same.

### 7. Two mistakes of mine that reached the branch

- **#134's `Toggle` was committed without running its own GUI tests.**
  `.toggleStyle(.button)` does not resolve through `app.buttons`, so twenty-two
  call sites stopped finding the control. Repaired via one `compareControl`
  helper typed `.any`.
- **#140 is a regression I shipped in #135 the day before**, reported by the
  author within a day. #135's tests asserted everything the clear must *do* and
  nothing it must *not touch*.
